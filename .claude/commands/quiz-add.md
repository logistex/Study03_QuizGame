`questions.js`에 새 문항을 넣는다. 받은 인수는 `$ARGUMENTS`다.

**이 명령어는 새 요구를 만드는 것이 아니라 규격이 이미 정해 둔 절차를 밟는 것이다.**
`spec/PRD.md` 8절이 문제은행 확대를 예정하면서 거쳐야 할 것을 적어 두었다.

> 문제 추가는 3.6절의 작성 규칙과 4.2절의 데이터 검사를 통과해야 한다.
> 더해 `answer`가 실제 정답을 가리키는지, 해설이 그 정답의 근거를 설명하는지
> 클로드가 판정하고 사람이 채택 여부를 결정한다.

## 1. 인수를 읽는다

`$ARGUMENTS`를 공백으로 나누어 낱말마다 성격을 가린다. **순서를 보지 않는다.**

| 낱말이 | 무엇으로 읽나 |
|---|---|
| 네 카테고리 이름이거나 그 일부 | 카테고리 |
| "전체", "모두" | 네 카테고리 전부 |
| 초급, 중급, 고급 또는 `easy`, `medium`, `hard` | 난이도 |
| 숫자만으로 되어 있음 | 문항 수 |

카테고리 이름과 `id` 약어는 `spec/PRD.md` 3.6절에 있다.

- 규격에 없는 낱말이라도 **뜻이 닿으면 옮겨 읽는다.** "상급"은 고급, "하급"은 초급이다
- 같은 성격이 두 번 나오면 넣지 말고 되묻는다
- 생략된 것은 이렇게 채운다

| 생략된 것 | 무엇으로 채우나 |
|---|---|
| 카테고리 | 분포가 기준에서 가장 먼 카테고리. `/quiz-stats`가 세는 기준을 그대로 쓴다 |
| 난이도 | 그 카테고리에서 기준보다 모자란 난이도 |
| 문항 수 | 한 문항 |

카테고리를 "전체"로 읽었으면 문항 수는 **카테고리마다의 개수**다. `전체 10`은 마흔 문항이다.

**파일에 넣기 전에 무엇을 무엇으로 읽었는지 밝히고 확인을 받는다.**
잘못 읽은 것은 넣은 뒤에 되돌리는 것보다 넣기 전에 잡는 편이 싸다.

## 2. 문항을 쓴다

지켜야 할 것은 규격에 있다. 여기에 옮겨 적지 않는다. **베껴 두면 규격을 고칠 때 어긋난다.**

| 무엇 | 어디 |
|---|---|
| 필드 형식, `id` 짓는 법, 카테고리 약어 | `spec/PRD.md` 3.6절 |
| 작성 규칙 여덟 가지 | `spec/PRD.md` 3.6절, `spec/IMPL-PLAN.md` "문제 데이터 작성 규칙" |
| 검사 함수가 보는 것 | `spec/PRD.md` 4.2절, `spec/IMPL-PLAN.md` "검사 항목과 콘솔 출력 형식" |
| 1단계 검토 여덟 항목 | `spec/IMPL-PLAN.md` "육안 검토 절차 (1.8)" |
| 분포 기준을 문항 수에서 계산하는 법 | `.claude/commands/quiz-stats.md` |

**해설에 넣는 연도, 수치, 인명은 외부 출처 둘 이상으로 대조한다.** 기억으로 적지 않는다.
계획서 1.8절 7번이 정한 것이고, 자료가 갈리면 주류 학설을 따르되 판단 근거를 주석으로 남긴다.
이미 대조가 끝난 사실은 `history/32`, `history/33`, `history/38`에 있다.

`id`는 그 카테고리의 마지막 번호 다음을 쓴다. 번호를 비워 두지 않는다.

## 3. 넣은 뒤 확인한다

**데이터 검사 함수만 돌린다.** 부르는 줄은 `spec/IMPL-PLAN.md` "저장소 밖에서 검사 함수를
부를 때"에 있다. 그 줄을 그대로 쓰고 저장소 뿌리에서 실행한다.

```bash
node -e "
const fs = require('fs'), vm = require('vm');
const ctx = vm.createContext({ console, document: { addEventListener() {} } });
vm.runInContext(fs.readFileSync('questions.js','utf8'), ctx);
vm.runInContext(fs.readFileSync('script.js','utf8'), ctx);
const errors = vm.runInContext('validateData()', ctx);
console.log(errors.length ? errors.join('\n') : '위반 0건');
"
```

위반이 나오면 **넣은 문항을 되돌리고** 무엇이 걸렸는지 보고한다.

## 4. 커밋하고 원격에 올린다

**커밋이 곧 백업이다.** 넣은 것을 되돌리는 일이 `git revert` 한 줄이 되고,
무엇을 왜 넣었는지가 메시지에 남는다. 실습에서 git을 안 쓰면 되돌릴 방법이 없다.

- **3절의 검사가 위반 0건일 때만 한다.** 걸렸으면 되돌리고 커밋하지 않는다
- **`questions.js`만 담는다.** 다른 파일이 함께 바뀌어 있으면 그 파일은 남겨 둔다
- 커밋한 뒤 **곧바로 원격에 올린다.** 올려야 이 컴퓨터 밖에 남고, 검증을 맡는 세션에
  넘길 "대상 커밋"이 깃허브 주소로 가리킬 수 있는 자리가 된다
- 검증 전에 올리는 것이 맞다. 잘못 들어간 것은 되돌리는 커밋을 하나 더 쌓아 고친다

```bash
git commit questions.js -F - <<'EOF'
<카테고리>에 <n>문항을 더한다

<난이도와 정답 인덱스를 어떻게 배분했는지 한 줄>

<id와 주제를 나열한 줄>

해설의 사실은 출처 둘씩 대조했다. <대조하지 못한 것이 있으면 여기에 적는다>

검사 함수 위반 0건이다. 검증은 다른 세션 몫이라 여기서 돌리지 않는다.

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
EOF
git push origin main
```

메시지에 **넣은 문항의 `id`와 해설의 출처**를 적는다. 둘이 빠지면 나중에 이 커밋만 보고
무엇을 왜 넣었는지 알 수 없다.

## 5. 보고

- 넣은 문항을 `id`, 문제, 정답, 난이도 순으로 적는다
- 해설에 넣은 사실마다 **어느 출처 둘로 대조했는지** 적는다. 대조하지 못한 것은 "미확인"으로 적는다
- **넣기 전과 넣은 뒤의 분포를 함께 보인다.** 문항 수, 난이도 배분, 정답 인덱스 분포다
- 검사 함수 출력을 그대로 옮긴다. "걸린 것이 없다"를 범위 없이 쓰지 않는다
- **커밋 해시와 원격에 올린 사실을 적는다.** 검증을 맡는 세션에 넘길 "대상 커밋"이 이것이다
- 끝에 이어서 실행할 명령을 적는다. **데스크톱 앱에서는 한 줄에 하나씩 친다**

```
/quiz-validate <카테고리>
/quiz-stats <카테고리>
```

- 다음 한 줄을 함께 적는다 — **문항을 쓴 쪽이 판정하면 쓸 때 한 판단을 되풀이한다.
  규격이 정한 닫는 조건은 다른 세션이 한 번 더 돌아야 채워진다**(계획서 1.8절)

## 6. 하지 않는 것

- **문항 작성 기준을 새로 만들지 않는다.** 규격에 이미 있다
- **기준을 이 파일에 베껴 적지 않는다.** 규격을 가리키기만 한다
- **`/quiz-validate`와 `/quiz-stats`를 여기서 부르지 않는다.**
  안에서 부르면 검증까지 마친 것처럼 보이고, 판정을 문항 작성자가 한 사실이 가려진다
- **강제로 푸시하지 않고 기록을 지우지 않는다.** 잘못 들어간 것은 되돌리는 커밋을
  하나 더 쌓아 고친다. 이 저장소는 틀린 판단도 정정을 달아 남기는 곳이다

## 7. 규격에 반영할 것

문항을 넣다가 규격과 코드가 어긋난 것을 발견하면 여기에 모아 적는다.
`id`가 없는 지적이라 문항 결과와 섞으면 몇 건인지 셀 수 없다.
