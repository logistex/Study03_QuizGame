## 0. 먼저 — 갈리지 않은 것

다투지 않아도 되는 것을 먼저 치운다. 아래는 세 프롬프트가 이미 같다.

- 검사 로직을 다시 짜지 않고 `validateData()`를 쓴다
- 만든 뒤 실제로 돌려 본다
- 문제 파일을 고치지 않는다
- 걸린 것이 없으면 "고칠 것 없음"이라고 적는다
- 걸린 것은 `id`, 어긋나는 것, 권고 문구 순으로 적는다
- 외부 출처 두 곳 이상 대조, 기억으로 판정 금지, 확인 못 하면 "미확인"
- 근거 절 번호를 항목마다 단다

**판정 기준 셋도 세 판이 모두 통과했다.** `r2-run.md` 기준이다.

| | A (`r1-impl5`) | B (`r1-review6`) | C (`r1-impl7`) |
|---|---|---|---|
| 1. 글자 그대로 따라 했을 때 숫자가 나오는가 | 위반 0건 | 위반 0건 | 위반 0건 |
| 2. 새 기준을 만들지 않는가 | 통과 | 통과 | 통과 |
| 3. 절 번호를 정확히 가리키는가 | 통과 | 통과 | 통과 |

**세 판이 지리에서 낸 지적도 `ge_01` 한 건으로 같다.** 즉 셋 다 쓸 수 있는 물건을 만들어 냈다. 아래 갈림은 그 위에서 무엇을 더 얻고 무엇을 잃느냐다.

## 갈린 지점 1 — 절 번호를 짚어 줄 것인가, 찾게 할 것인가

| | 방식 |
|---|---|
| A | **안 짚는다.** "절 번호는 내가 짚어 주지 않을 테니 네가 문서에서 찾아라" |
| B | **짚는다.** `2.1절`, `3.6절`, `4.2절`, `IMPL-PLAN 1.8절`을 지정 |
| C | **반만 짚는다.** 3.6절만 짚고 "위 세 규칙"이 무엇인지 본문에서 확인하게 함 |

### 쟁점이 되는 자료

A가 실측을 냈다(`r1-impl5.md` 2절).

| 판본 | 프롬프트 | 사람이 볼 항목 수 |
|---|---|---|
| v2 | 기준을 조목조목 적은 20줄 | 4 |
| v3 | 문서를 가리키기만 한 12줄 | 8 |

주장은 **"절 번호를 짚어 주는 것은 친절이 아니라 상한선"** 이다. 실제로 v2에서 `해설이 근거를 대는가`가 사라졌고, 그 항목은 `history/08-stage1-review.md`가 1단계에서 쓰던 넷 중 하나였다.

이번 실행이 낸 항목 수는 이렇다(`r2-run.md`).

- A 6행 + 규격 미구현 4행
- B 3 + 2행
- C 4행

### 답할 것

1. 절 번호를 짚어 주면 결과가 좁아진다는 A의 주장을, 이번 실행 결과가 뒷받침하는가 뒤집는가
2. 좁아지는 것이 손해인가. 좁고 정확한 것과 넓고 헐거운 것 중 어느 쪽을 택하는가
3. 짚어 주는 쪽을 택한다면, v2에서 항목이 사라진 일을 무엇으로 막는가

## 갈린 지점 2 — 실행 방법을 프롬프트가 알려 줄 것인가

| | 방식 |
|---|---|
| A | **안 알려 준다.** "돌아간 것만 적어줘. 안 돌아가면 돌아갈 때까지 고쳐" |
| B | **안 알려 준다.** "네가 직접 찾아서 확인해. 성공한 방법만 적어" |
| C | **힌트를 준다.** "브라우저용이라 `document`에서 `ReferenceError`가 나. 떼어서 돌리든 흉내 내서 돌리든 방법은 네가 정해" |

세 판이 고른 방법과 그 성질이 갈렸다.

| | 쓴 방법 | 성질 |
|---|---|---|
| A | `vm.createContext` + `document` 스텁 | 파일이 바뀌어도 버틴다 |

### 답할 것

2. 힌트 없이도 A와 B가 같은 방법에 도달했다는 사실을 어떻게 읽는가
3. 힌트를 넣는다면 `script.js`가 바뀔 때 프롬프트가 낡는 문제를 어떻게 하는가

## 갈린 지점 3 — 규격 밖 표시를 어떻게 할 것인가

`r2-facts-review6.md` 3절이 확인한 것이다. **A와 C가 규격 안의 항목을 규격 밖이라고 표시하게 했다.**

| 판 | 생성된 명령어의 표기 | 사실 |
|---|---|---|
| A | `## 4. 사실 확인 (규격 밖)` | `spec/IMPL-PLAN.md` 1.8절 7번에 있다 |
| C | `## 3. 사실 확인 (규격에 없다)` | 같다 |
| B | 표기 없음 | 오표기는 없다 |

한편 B는 표시를 시키지 않아 **규격 안과 밖이 구분되지 않는다.** A와 C가 그 구분을 노린 것 자체는 갈림이 아니다.

### 답할 것

1. 규격 안과 밖을 표시하는 장치를 남길 것인가
2. 남긴다면 프롬프트가 목록을 미리 적어 주는 방식(A, C)이 옳은가, 명령어가 규격을 읽고 스스로 판정하게 하는 방식이 옳은가
3. B는 표시가 없어 구분이 사라진다. 이것을 어떻게 메우는가

## 갈린 지점 4 — "해설이 근거를 대는가"를 넣을 것인가

근거 시비는 끝났다. 두 곳에 있다.

- `spec/PRD.md` 3.6절 필드 표 — `explanation`의 정의
- `spec/IMPL-PLAN.md` 1.8절 육안 검토 2번 — "`explanation`이 그 정답의 근거를 설명하는가"

이번 실행에서 A와 B는 넣었고 **C는 넣지 않았다.** C는 근거 부재를 이유로 뺐으나 그 이유가 사실과 달랐고, `r1-impl7.md`에 정정 문단을 붙여 이미 거두었다(커밋 `7bb0e25`).

### 답할 것

1. 넣는 것에 셋 다 동의하는가. 반대가 있으면 근거 부재가 아닌 다른 이유를 대야 한다
2. 이 항목이 프롬프트의 어느 문장 때문에 살아남았는지, 셋의 문장을 대조해 어느 표현을 최종안에 쓸 것인가

## 갈린 지점 6 — 기존 검증 기록을 먼저 보게 할 것인가

**B만 넣었다.** 이번 실행에서 결과가 갈린 유일한 자리다.

| | 사실 확인 결과 |
|---|---|
| A | 미확인 |
| B | **기존 기록으로 확인됨.** `history/32-…`와 `history/33-…`을 찾아, 33번 5절에 지리 문항별 출처가 두 곳씩 있음을 확인 |
| C | 미확인 |

- 규격에는 없다. `r2-facts-review6.md` 정정 1이 이 한 줄에 대한 지적은 유효하다고 적었다
- 40문항 외부 출처 대조는 검색 40여 회가 든다. 이미 끝난 것을 다시 하면 그 품이 버려진다
- 반대로, 기존 기록을 믿게 하면 **낡은 기록을 그대로 물려받을 위험**이 생긴다

### 답할 것

1. 규격에 없는 것을 프롬프트가 넣어도 되는가. 된다면 규격 밖 표시를 함께 붙일 것인가
2. 기존 기록을 믿는 범위를 어디까지 둘 것인가. 언제 다시 대조하는가
3. A와 C가 "미확인"으로 남긴 것은 규칙대로 정직한 것이다. 미확인을 줄이는 것이 목표인가, 정직하게 남기는 것이 목표인가

## 갈린 지점 7 — 규격이 덮지 못하는 곳을 찾게 할 것인가

**A만 넣었다.** "그 함수가 덮지 못하는 규격 항목이 있는지 확인해서 사람이 볼 목록에 넣어줘."

이 한 줄이 실제로 하나를 찾았다.

- PRD 3.6절 필드 표는 `question` 60자, 선택지 20자를 못박는다
- `validateData()`에는 **길이 검사가 없다**
- 지금은 위반 0건이나 PRD 8절이 문제은행 확대를 예정하고 있다

A판 실행은 규격 미구현 4행을 따로 냈고, B와 C는 이 자리를 내지 않았다.

### 답할 것

1. 명령어가 규격과 코드의 어긋남까지 찾는 것이 이 명령어의 몫인가, 넘치는 일인가
2. 몫이라면 최종안에 어느 문장으로 넣을 것인가
3. 찾아낸 어긋남을 어디에 적을 것인가. 검증 보고 안인가, 별도 문서인가
