## 2. 왜 이렇게 썼는가

### 2.1 "돌려 보고 성공한 방법만 적어"가 이 프롬프트의 핵심이다

지금 저장소에 있는 명령어는 "Node로 그 함수를 그대로 돌려 결과를 받는다"고 적고 있다. 돌아가지 않는다.

```
$ node script.js
ReferenceError: document is not defined   (script.js:759)
```

`script.js`에 `module.exports`도 `export`도 없고, 마지막 줄이 `document.addEventListener('DOMContentLoaded', init);`이라 파일을 읽는 순간 터진다. `questions.js`를 먼저 읽혀도 같다.

**프롬프트가 "돌려라"라고만 하면 이 결과가 다시 나온다.** 쓰는 쪽이 실행해 보지 않고 그럴듯한 문장을 적기 때문이다. 그래서 세 겹으로 막았다.

1. 만들기 전에 직접 돌려서 되는 방법을 찾게 한다
2. 성공한 방법을 복사해 쓸 수 있는 형태로 본문에 넣게 한다
3. 다 만든 뒤 명령어를 실제로 실행해 보게 한다

**되는 방법을 프롬프트가 알려 주지는 않았다.** 알려 주면 `script.js`가 바뀌는 순간 프롬프트가 낡는다. 이 프로젝트의 검토 규범도 같다 — 어디가 왜 걸리는지만 알려 주고 고칠 방법은 저쪽이 정한다.

### 2.2 규칙의 개수를 프롬프트가 못박지 않았다

"3.6절 끝에 적어 둔 규칙들"이라고만 하고 **몇 개인지는 쓰지 않았다.** 지금 명령어가 "위 세 규칙"이라 적고 표에는 네 행을 두고 있는데, 네 번째는 2.1절 규칙이다. 인용은 맞지만 "세 규칙"에는 들지 않는다.

프롬프트에 "세 규칙"이라고 박으면 규격이 바뀔 때 프롬프트가 먼저 틀린다. **개수는 규격이 정하고 프롬프트는 규격을 가리키기만 한다.**

3.6절 밖의 규칙을 넣는 것 자체는 막지 않았다. 대신 **넣는 이유와 절 번호를 밝히게** 했다. 넣고 빼는 기준이 하나면 된다.

### 2.3 자동 검사와 사람 판단을 따로 적게 했다

섞여 있으면 읽는 사람이 "이건 기계가 걸렀나 사람이 걸렀나"를 매번 판단하게 된다. 기계가 거른 것은 재현되고 사람이 거른 것은 재현되지 않는다. 성질이 다르므로 자리를 나눈다.

### 2.4 기존 검증 기록을 먼저 보게 했다

40문항 외부 출처 대조는 검색 40여 회가 든다. 이미 끝난 문항을 다시 대조하면 그 품이 통째로 버려진다. **어느 문서를 보라고는 적지 않았다.** 저장소가 자라면 그 목록이 낡기 때문이고, 규격을 가리키는 방식과 같은 이유다.

### 2.5 마지막 줄이 판정을 가능하게 한다

"다 만든 뒤 실제로 한 번 실행해 보고 결과를 보여 줘."

이 줄이 없으면 프롬프트를 돌린 결과가 **파일 하나**뿐이라 좋고 나쁨을 읽어서 판단해야 한다. 이 줄이 있으면 결과가 **파일과 실행 출력 둘**이 되어 규칙 4절의 판정 항목 1번(지시가 실제로 실행되는가)을 그 자리에서 확인할 수 있다.

## 3. 이 프롬프트가 일부러 담지 않은 것

- **명령어 본문의 문장을 지정하지 않았다.** 프롬프트가 결과물을 받아쓰게 하면 프롬프트를 겨루는 의미가 없다
- **되는 실행 방법을 알려 주지 않았다.** 2.1절 참조
- **표에 들어갈 행을 나열하지 않았다.** 규격을 읽고 정하게 했다
- **출처로 쓸 기관을 지정하지 않았다.** "두 곳 이상"과 "기억 금지"까지만 정했다
