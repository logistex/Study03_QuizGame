## 2. 설계 원칙 — 짚어 주지 말고 가리킨다

**기준을 프롬프트에 적으면 적은 만큼만 나온다. 문서를 가리키면 문서만큼 나온다.**

오늘 이 세션에서 같은 명령어를 세 번 만들었고, 그 결과가 이 원칙의 근거다.

| 판본 | 만든 방법 | 사람이 볼 항목 수 |
|---|---|---|
| v1 | 프롬프트 없이 세션이 직접 작성 | 5 |
| v2 | 기준을 조목조목 적은 20줄 프롬프트 | **4** |
| v3 | 문서를 가리키기만 한 12줄 프롬프트 | **8** |

- v1과 v3는 `archive/commands/`에 있다. v2는 `.claude/commands/quiz-validate.md`의 `f16f43f` 시점 판본이다
- **긴 프롬프트가 가장 좁은 결과를 냈다.** 줄 수와 결과의 넓이가 반대로 갔다

### v2가 좁아진 지점

v2를 만든 프롬프트에 이 줄이 있었다.

```
자동으로 안 잡히는 것은 spec/PRD.md 3.6절 끝에 "자동 검사로 판정할 수 없다"고
적어 둔 규칙들이야. 그걸 표로 만들어서 문항마다 확인하게 해줘.
```

PRD 3.6절 끝은 **"위 세 규칙은 자동 검사로 판정할 수 없다"**이다. 셋으로 못박은 문장이다.

- 모델은 지시받은 지점을 정확히 읽고 셋만 가져왔다
- v1에 있던 `해설이 근거를 대는가`가 빠졌다. 이 규칙은 3.6절 **필드 표**에 있고("`explanation` 해설. 한두 문장으로 정답의 근거를 설명한다") "위 세 규칙"에는 안 든다
- 그런데 이 항목은 `history/08-stage1-review.md`에서 1단계 검토 때 실제로 확인한 네 항목 중 하나였다. **살아 있던 검사가 프롬프트의 좁힘 때문에 사라졌다**

절 번호를 짚어 주는 것은 친절이 아니라 상한선이다. 그래서 제출 프롬프트는 절 번호를 대지 않고 **"네가 문서에서 찾아라"**로 뒤집었다.

## 3. 판정 기준 세 항목에 대한 대응

### 기준 1 — 지시가 실제로 실행되는가

프롬프트에 이 두 줄을 넣었다.

```
돌리는 명령줄을 실제로 실행해 보고, 돌아간 것만 적어줘. 안 돌아가면 돌아갈 때까지 고쳐.
```

**"Node로 돌려라"라고만 쓰면 돌아가지 않는 절차가 나온다.** 규칙 문서 4절 1번의 지적이 그것이고, v1과 v2가 모두 그 상태다.

다만 한 가지를 나란히 적어 둔다. **실행 자체가 불가능한 것은 아니다.** v3가 낸 방법을 이 세션에서 직접 돌려 확인했다.

```bash
node -e "
const fs = require('fs'), vm = require('vm');
const ctx = vm.createContext({ console, document: { addEventListener() {} } });
vm.runInContext(fs.readFileSync('questions.js','utf8'), ctx);
vm.runInContext(fs.readFileSync('script.js','utf8'), ctx);
const errors = vm.runInContext('validateData()', ctx);
console.log(errors.length ? errors.join('\n') : '위반 0건');
"
```

출력은 `위반 0건`이었다.

- `vm.createContext`로 격리하고 `document` 스텁을 주면 마지막 줄의 `addEventListener` 등록이 통과한다
- `export`가 없어도 `runInContext`로 같은 컨텍스트에서 함수를 부를 수 있다
- 즉 **막힌 것은 실행 가능성이 아니라 방법을 확인하지 않고 적은 절차다.** 프롬프트가 "돌려 보고 적어라"를 요구하면 이 문제는 생기지 않는다

### 기준 2 — 새 검증 기준을 만들지 않는가

두 장치를 넣었다.

- **기준을 적지 않고 문서를 읽게 한다.** 프롬프트에 판정 항목을 하나도 적지 않았다. 적으면 그것이 새 기준이 된다
- **규격에 없는 것은 표시하게 한다.** `규격에 없는 것을 넣었으면 "규격 밖"이라고 표시해줘`. 규격과 명령어가 섞이면 다음 사람이 어느 쪽이 기준인지 판단해야 한다

마지막 세 항목(외부 출처, 배치 분할, 파일 수정 금지)은 **어느 규격에도 없다.** 그래서 프롬프트가 말해 줘야 하고, `규격에 없는 것 세 가지만 더해줘`로 개수까지 못박아 그 이상 새 기준이 붙는 것을 막았다.

### 기준 3 — 규격의 절 번호를 정확히 가리키는가

- 프롬프트가 절 번호를 대지 않으므로 **명령어가 스스로 찾아 달아야 한다.** 그래서 `항목마다 근거 절을 함께 적고`를 요구했다
- 절 번호가 틀리면 명령어 안에서 바로 드러난다. 짚어 주면 그 번호를 그대로 베끼므로 틀려도 안 드러난다

여기에 한 줄을 더 넣었다.

```
그 함수가 덮지 못하는 규격 항목이 있는지 확인해서 사람이 볼 목록에 넣어줘.
```

**이것이 규격과 코드가 어긋난 자리를 찾아낸다.** v3가 실제로 하나 찾았고, 이 세션에서 확인했다.

- PRD 3.6절 필드 표는 `question` 60자, 각 선택지 20자를 못박는다
- `script.js`의 `validateData()`에는 **길이 검사가 없다.** `options.length !== 4`(개수)와 문제 수 검사뿐이다
- 지금은 위반 0건이라 드러난 결함은 없다. 다만 PRD 8절이 문제은행 확대를 예정하고 있어 문제를 늘리면 조용히 어긋난다
- v1도 v2도 이 대목을 못 봤다. v3는 우연히 찾았고, **제출 프롬프트는 그것을 우연이 아니라 지시로 만든다**

## 4. 규격에 없는 세 항목을 고른 근거

### 외부 출처 두 곳 이상

`history/08-stage1-review.md`가 40문항을 **원본 지식으로 재대조**해 "사실 오류 0건"으로 닫았다. 오늘 외부 출처를 대고 다시 보니 해설 오류 1건(`sc_05`)과 재는 기준 누락 2건(`ge_01`, `ge_04`)이 나왔다. 근거는 `history/32-question-source-verification-report.md` 3절이다.

- **기억끼리의 대조와 출처와의 대조가 갈린다.** 두 모델이 같은 오해를 공유하면 그대로 통과한다

### 문항 4개씩 나눠 병렬, 결과 파일 우선 저장

`history/32-question-source-verification-report.md` 4절에 두 번의 시도가 기록되어 있다.

| | 첫 시도 | 두 번째 |
|---|---|---|
| 나눈 단위 | 4갈래, 갈래당 10문항 | 10갈래, 갈래당 4문항 |
| 중간 저장 | 없음 | 결과 파일을 먼저 씀 |
| 결과 | 40분 넘게 돌다 끊김, **부분 결과도 회수 못 함** | 갈래마다 78~164초, 전체 3분 |

- 갈래 안이 직렬이면 갈래 하나의 소요가 전체 소요다
- 서브에이전트는 실패해도 조용하다. 파일이 없으면 남는 것이 없다

### 문제 파일 수정 금지, "고칠 것 없음"도 결과

- 고칠지는 사람이 정한다. 이 프로젝트에서 규격 동결 해제, 하단 안내, 사파리 중단을 모두 사람이 정했다
- **고칠 것이 없다는 것도 점검 결과다.** 통과를 통과라고 안 적고 개선 제안으로 채우면 다음 사람이 무엇이 실제 지적인지 가려내야 한다

## 5. 확인한 것과 확인하지 못한 것

### 확인한 것

- 위 `node -e` 명령을 이 세션에서 실행해 `위반 0건`을 받았다
- `validateData()`에 길이 검사가 없다는 것을 `sed`로 함수 본문을 훑고, 별도 스크립트로 40문항의 글자 수를 세어 확인했다. 현재 길이 위반은 0건이다
- v1, v2, v3 세 판본을 `diff`로 대조했다. v2에서 빠진 행이 `해설이 근거를 대는가` 하나임을 확인했다
- v3가 인용한 `history/12-question-guidelines.md`의 절 번호(2, 3, 4, 5절)가 실제 절 구성과 맞는지 확인했다. 맞다

### 확인하지 못한 것

- **제출 프롬프트를 아직 돌려 보지 않았다.** 이 프롬프트가 실제로 어떤 명령어를 만들어 내는지는 2라운드에서 260811-7이 돌려야 알 수 있다. 위 근거는 v1, v2, v3에서 얻은 것이지 제출본에서 얻은 것이 아니다
- **`/quiz-validate`를 실행해 본 적이 없다.** 이 세션은 주 작업 폴더가 저장소 밖이라 슬래시 명령어를 부를 수 없다
- `spec/IMPL-PLAN.md`를 프롬프트에서 읽게 했으나, 그 문서에 검증 기준이 얼마나 들어 있는지 이 세션이 따로 훑지 않았다. 넣은 이유는 규칙 문서 4절 2번이 기준의 소재로 지목했기 때문이다
