## 0. 총평

**PRD 요구사항 누락은 없다.** 3.0절 공통 규칙부터 4.3절 접근성까지 항목 단위로 대조했고, 계획이 다루지 않은 요구사항을 찾지 못했다. 요소 id 계약과 화면 문구 모음을 앞머리에 확정해 둔 것은 특히 좋은 판단이다. 단계마다 문구를 새로 짓다 생기는 표기 흔들림을 구조적으로 막는다.

문제는 요구사항 쪽이 아니라 **검증 절차와 함수 명세** 쪽에 있다.

- 필수 수정 3건 — 이대로 두면 명세가 불완전하거나, 검증이 결함을 잡지 못하면서 잡았다고 착각하게 만든다
- 보완 권고 9건 — 실행에 지장은 없으나 재작업이나 헛수고를 부른다

가장 중요한 것은 **필수 수정 2번**이다. R3 체크리스트의 두 항목이 서로 모순되고, 그중 하나는 통과해도 R3가 검증되지 않는다.

### PRD 해석이 정확한 지점

- **`saveResult`의 인덱스에 `+1`을 붙여 표시** — PRD는 "순위표 N위 진입"이라고만 적었고 인덱스가 0부터라는 사실은 3.4절에 있다. 계획이 `${N + 1}위`로 정확히 옮겼다.
- **선택지 섞기 시점** — PRD는 "문제를 처음 그릴 때 한 번"이라 했는데, 계획은 판 시작 시점에 10문제를 한꺼번에 `prepareQuestion`에 통과시킨다. "그 문제를 푸는 동안 바뀌지 않는다"는 요구를 더 확실히 만족하므로 어긋난 해석이 아니다.
- **V0을 검사에 통합** — PRD는 로드 실패(4.2-1)와 데이터 검사(4.2-2)를 별개 항목으로 두지만, 화면 문구가 같으므로 하나로 합친 것이 타당하다.
- **`beforeunload` 해제 두 곳** — PRD 수정본이 반영되어 있다. `showDataError()`에 해제 호출을 넣지 않는다는 문장까지 명시했다.

## 2. 필수 수정 3건

### 1. `state.answered`를 `true`로 만드는 곳이 없다

`state` 표(54~62줄)에 `answered` 필드를 정의했고, `handleAnswer` 1번(429줄)이 이 값을 읽어 중복 채점을 막는다. 그런데 **계획 어디에도 이 값을 대입하는 단계가 없다.** `renderQuestion`의 책임 서술(370줄)에도 `false`로 되돌린다는 말이 없다.

명세대로 구현하면 가드는 항상 `false`를 읽어 아무 일도 하지 않는다. 실제 재선택 방어는 3.4절 3번의 `disabled`가 하므로 증상이 드러나지 않고, 3단계 체크리스트의 "답을 고른 뒤 다른 선택지를 눌러도 점수가 변하지 않는다"도 그대로 통과한다. **죽은 가드가 검증까지 통과한 채 남는다.**

**수정**: 두 곳을 명세에 넣는다.

- `handleAnswer` 1번과 2번 사이에 `state.answered = true`
- `renderQuestion`의 책임에 `state.answered = false`로 초기화

또는 `answered` 필드를 상태 표에서 빼고 `disabled` 하나로 방어한다고 명시한다. 어느 쪽이든 읽기만 하고 쓰지 않는 지금 상태는 안 된다.

### 2. R3 체크리스트의 두 항목이 서로 모순된다

4단계 체크리스트 626줄과 627줄이 정면으로 어긋난다.

- 626줄: "**이 항목은 실행으로 판정되지 않는다.** 맨 앞 삽입 + 안정 정렬 아래에서는 이름·점수 검색과 참조 검색이 같은 값을 내므로 화면에 차이가 나타나지 않는다."
- 627줄: "동명동점 상황 … **두 줄이 모두 강조되면** 이름과 점수로 줄을 찾고 있는 것이다."

**626줄이 맞다.** 이름과 점수로 찾는 구현은 `findIndex`가 될 텐데, 맨 앞 삽입 + 안정 정렬이면 새 기록이 언제나 동점 그룹의 최상위에 온다. 따라서 `findIndex`도 `indexOf`와 같은 인덱스를 돌려준다. 새 기록이 잘려 나가면서 같은 이름·같은 점수의 기존 기록만 남는 상황도 만들 수 없다. 같은 이유로 새 기록이 항상 위이기 때문이다.

627줄이 가정한 "두 줄이 모두 강조되는" 상황은 인덱스 하나를 반환하는 계약에서는 발생하지 않는다. **통과해도 R3를 검증한 것이 아닌데 검증했다고 기록에 남는다.** 잡지 못하는 검증은 없는 검증보다 나쁘다.

**수정**: 627줄에서 R3 표시를 뗀다. 항목 자체는 살릴 값어치가 있으나 목적이 다르다.

> - [ ] **(PRD 3.4절 — 기록을 합치지 않음)** 같은 이름으로 같은 점수를 두 번 낸다. 순위표에 두 줄이 각각 남고, 두 번째 판의 결과 화면에서 강조된 줄이 하나뿐이며 두 줄 중 위쪽이다

R3의 검증 수단은 626줄의 코드 확인 하나뿐이라는 점을 명시하고, 해당 항목에 "실행 검증 없음 — 코드 확인 필수"를 눈에 띄게 남긴다.

### 3. git 저장소를 만드는 시점이 계획에 없다

5단계 체크리스트 마지막(706줄)이 `git status`와 `git diff`로 임시 변경의 원상 복구를 확인하라고 한다. 그런데 계획에서 git이 처음 등장하는 곳은 **6단계 1번(722줄)의 "커밋하고 GitHub 저장소에 올린다"** 이다. 5단계 시점에 저장소가 없으면 그 체크리스트를 수행할 수 없다.

게다가 `git diff`는 5단계보다 **1단계에서 더 필요하다.** 1.5절의 검사 함수 검증 절차가 `kh_01`을 여덟 번 망가뜨렸다 되돌리는 방식이고, 1단계 체크리스트가 "임시 변경이 전부 원상 복구되었다"를 요구한다. 40문제를 눈으로 대조하는 것보다 `git diff`가 확실하다.

**수정**: 1단계 하위 작업 1.1 앞에 `git init`을 넣고, 1.5와 5.3의 원상 복구 확인 수단으로 `git diff`를 명시한다. GitHub Pages 배포가 전제이므로 어차피 저장소는 필요하다.

## 3. 보완 권고 9건

### 1. `renderResult`가 순위표 데이터를 어디서 얻는지 정의되지 않았다

`saveRanking`은 인덱스만 돌려주고 저장한 목록은 돌려주지 않는다. 그런데 `renderResult`는 "순위표를 그리되 인덱스 N인 줄을 강조한다"(586줄)를 해야 한다. 목록을 얻으려면 `readRankings()`를 다시 불러야 하는데 계획에 그 말이 없다.

같은 탭에서 연속 호출이므로 결과는 맞지만, "계획을 받아 구현하는 사람이 PRD를 다시 해석할 일이 없어야 한다"는 이 문서의 기준에서는 빈틈이다. `renderResult`가 `readRankings()`를 부른다고 적거나, `saveRanking`이 `{ index, list }`를 반환하도록 계약을 바꾼다. 후자가 읽기 횟수도 줄고 인덱스와 목록의 대응도 보장한다.

### 2. R2 검증의 앞부분이 무효다

480줄의 검증이 두 부분으로 되어 있다.

- 앞: "정답 텍스트를 적어 둔 뒤 그 텍스트가 적힌 버튼을 누른다. `정답입니다.`가 떠야 한다"
- 뒤: "원본 데이터와 대조한다. `QUESTIONS…find(…)`의 `options[answer]`가 방금 적어 둔 텍스트와 같아야 한다"

**앞부분은 `answer`가 틀려도 반드시 통과한다.** 틀린 `answer`가 가리키는 텍스트의 버튼을 누르면 당연히 정답 판정이 난다. 계획 자신도 같은 줄 뒤쪽에서 이 사실을 적고 있어, 한 항목 안에서 무효한 절차와 유효한 절차가 섞여 있다. 앞부분은 빼고 뒤부터 시작하는 편이 명확하다.

더해 뒷부분은 `state.quiz[0]` 한 문제만 본다. 열 문제를 한 번에 대조하는 편이 확실하고 손도 덜 간다.

```javascript
state.quiz.every(q => {
  const orig = Object.values(QUESTIONS).flat().find(o => o.id === q.id);
  return q.options[q.answer] === orig.options[orig.answer];
})
```

이 값이 `true`여야 한다. `false`면 어느 문제인지도 `filter`로 바로 찾을 수 있다.

### 3. 순위표 검증에 11판을 손으로 풀게 되어 있다

4단계 완료 기준만 세어도 1번 1판, 3번 1판, 4번 1판, 6번 6판이고, 체크리스트의 동명동점 항목이 2판을 더 요구한다. **모두 11판, 110문제를 클릭으로 풀어야 한다.** 5단계와 6단계에도 판을 도는 항목이 더 있다.

순위표의 정렬, 자르기, 강조는 실제 플레이 없이도 검증된다. 콘솔에서 저장 함수를 직접 부르면 된다.

```javascript
saveRanking('korean_history', { name: '테스터A', score: 9, total: 10, date: formatDate() })
```

**수정 제안**: 4단계 완료 기준 6번(6판 쌓기)과 체크리스트의 보관 수 항목에 "콘솔에서 `saveRanking`을 직접 호출해 기록을 쌓아도 된다"를 덧붙인다. 다만 완료 기준 1번(끝까지 한 판)은 `finishGame`의 전체 경로를 지나므로 실제 플레이로 남긴다. 확인이 끝나면 "기록 지우기"로 테스트 데이터를 비운다는 문장도 함께 넣는다.

### 4. `showScreen`과 `renderQuestion`의 호출 순서가 명시되지 않았다

`showScreen`은 제목으로 초점을 옮기고(297줄), `renderQuestion`은 문제 텍스트로 옮긴다(370줄). 퀴즈 화면 진입 시 최종 초점이 문제 텍스트여야 하므로(PRD 4.3절), **`showScreen` → `renderQuestion` 순서여야 한다.** 순서를 뒤집으면 초점이 제목에 남는다.

`startGame`의 책임 서술(369줄)은 "문제를 뽑아 첫 문제를 그린 뒤 이탈 경고를 켠다"로, `showScreen`을 언제 부르는지 나오지 않는다. 5단계 체크리스트에 결과 확인 항목은 있으나 순서 자체를 계획에 적어 두는 편이 안전하다.

### 5. `pickCategoryQuiz`가 `category` 객체를 어떻게 얻는지 없다

`prepareQuestion(q, category)`는 `categoryName`을 붙이기 위해 카테고리 객체를 받는다. `pickCategoryQuiz(categoryId)`는 id만 가지고 있으므로 `CATEGORIES.find(c => c.id === categoryId)`가 필요하다. 자명하지만 계획의 다른 부분이 이 수준까지 확정해 둔 것에 비해 빠져 있다.

### 6. 3단계에서 색을 정하고 5단계에서 대비를 확인한다

난이도 배지 3종과 정답 초록, 오답 빨강의 스타일은 3단계에서 만들고(358줄), 대비 4.5:1 확인은 5단계에서 한다(671줄). PRD 6절의 단계 구분을 따른 것이므로 잘못은 아니다.

다만 5단계에서 대비 미달이 나오면 색을 다시 고르고 강조 스타일을 손보는 재작업이 생긴다. 3단계 스타일 항목에 "색을 정할 때 흰 배경 대비 4.5:1을 미리 확인한다. 특히 주황 계열"을 한 줄 넣으면 재작업이 줄어든다. 5단계 검증은 그대로 둔다.

### 7. 2단계에 순위표 열기와 닫기 핸들러가 함수 목록에 없다

2단계 완료 기준 5번이 "순위표 보기 → 닫기 → 이름 유지"를 요구하는데, 함수 목록(296~301줄)에 `btn-open-ranking`과 `btn-close-ranking`의 핸들러가 없다. `showScreen` 호출뿐이라 별도 함수가 아니어서 빠진 것으로 보이나, 이벤트를 거는 작업이 어느 단계에 속하는지는 적어 두는 편이 낫다.

### 8. 첫 줄의 기준 문서명이 다르다

5줄이 "`PRD.md`(최종본)"으로 시작한다. 이 폴더 기준으로는 `PRD-v3.md`다. 계획 작성 세션의 폴더에서는 `PRD.md`가 맞았겠지만, 두 문서를 나란히 두는 지금은 어느 것을 가리키는지 헷갈린다. 파일명을 `PRD-v3.md`로 고치거나 "구현 계획 세션에서는 `PRD.md`로 두었다"는 주석을 단다.

### 9. GitHub Pages 캐시로 재배포 반영이 늦을 수 있다

6단계 완료 기준 1번이 "Network 탭에 404가 하나도 없다"를 요구한다. 첫 배포에서 경로 오류가 나 파일을 고치고 다시 올리면, GitHub Pages의 CDN 캐시 때문에 반영이 몇 분 늦을 수 있다. 고쳤는데도 404가 계속 나오면 캐시를 의심하라는 한 줄이 있으면 헤매지 않는다. 강제 새로고침이나 몇 분 대기로 확인한다.

## 4. 잘 만들어진 부분

지적만 남기면 균형이 맞지 않으므로 함께 적는다.

- **요소 id 계약과 화면 문구 모음을 앞머리에 확정한 것** — 단계마다 id와 문구를 새로 정하다 생기는 흔들림을 구조적으로 막는다. PRD에는 없던 층이다.
- **1.5절 검사 함수 검증 절차** — "40문제가 통과한 것이 데이터가 맞다는 뜻인지 검사가 아무것도 안 한다는 뜻인지 구별할 수 없다"는 문제 인식이 정확하다. 검사기를 검사하는 단계를 넣은 것은 이 계획에서 가장 좋은 판단이다.
- **R1 검증에 `state.quiz.map(q => q.categoryName)`을 쓴 것** — 최종 셔플 누락은 화면으로 판정할 수 없는데, 콘솔 한 줄로 블록 뭉침을 즉시 드러낸다. 다섯 판 반복은 3+3+2+2 배분의 무작위성까지 함께 확인하므로 과하지 않다.
- **R4 검증에 `formatDate`가 인자를 받게 만든 것** — 시스템 시계를 건드리지 않고 새벽 시각을 검증할 수 있다. 검증을 위해 인터페이스를 설계한 사례이고, 그 이유까지 547줄에 적어 두었다.
- **`grep` 기반 검증 항목들** — `aria-live`, `toISOString`, `Math.random`, 절대 경로는 모두 "있으면 안 되는 것"이라 실행 검증이 어렵다. `grep` 결과가 비어 있음을 기준으로 삼은 것이 적절하다.
- **부록 "이 계획이 다루지 않는 것"** — PRD 7절 제외 항목과 4.1절 알려진 제약을 한곳에 모아 "손대지 않는다"고 못박았다. 구현 중 눈에 띄는 것을 고치려다 범위가 번지는 것을 막는다.
