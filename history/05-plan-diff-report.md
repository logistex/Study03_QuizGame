## 1. 죽은 코드가 사라졌다

- 상태 객체에서 `answered` 필드 삭제
  - 최초본은 필드를 정의하고 `handleAnswer`가 읽었으나 **대입하는 곳이 없었다**
  - 가드가 늘 `false`를 읽어 무효였고, 실제 방어는 `disabled`가 하고 있었다
  - 증상이 없어 체크리스트까지 통과하는 종류였다
- `handleAnswer` 단계가 9개에서 8개로 줄었다 — 1번 가드 제거
- 제거로 끝내지 않고 **왜 필요 없는지를 상태 객체 절에 남겼다**
  - 비활성 버튼은 자식 요소를 눌러도 클릭 이벤트가 발생하지 않음
  - `handleAnswer`가 동기 함수라 연타의 두 번째 클릭은 비활성 적용 뒤에 도착
- **성립 전제를 함께 못박았다** — 선택지가 진짜 `<button>`일 때만 유효. `<div>` + `aria-disabled`면 클릭이 그대로 발생

## 2. 검증이 실제로 결함을 잡게 됐다

가장 큰 변화다. 통과해도 아무것도 보증하지 못하던 항목 둘이 고쳐졌다.

**R2 (`answer` 갱신)**

- 최초본: "정답 텍스트가 적힌 버튼을 눌러 `정답입니다.` 확인" → **`answer`가 틀려도 반드시 통과한다.** 강조와 피드백이 같은 잘못된 값을 보기 때문
- 반영본: 콘솔 한 줄로 열 문제를 원본과 일괄 대조

```javascript
state.quiz.every(q => {
  const orig = Object.values(QUESTIONS).flat().find(o => o.id === q.id);
  return q.options[q.answer] === orig.options[orig.answer];
})
```

- `false`일 때 `every`를 `filter`로 바꿔 어느 문제인지 찾는 방법까지 적었다
- 검사 범위도 1문제에서 10문제로 넓어졌다

**R3 (인덱스를 객체 참조로 찾기)**

- 최초본: 두 항목이 서로 모순 — 한쪽은 "실행으로 판정되지 않는다", 다른 쪽은 실행으로 판정하라
- 반영본: 세 항목으로 분리하고 각각 무엇을 잡는지 라벨을 달았다

| 항목 | 잡는 결함 | 판정 수단 |
|---|---|---|
| `(R3)` | 이름 대조로 인덱스를 찾는 구현 | **코드 확인만** |
| `(PRD 3.4절)` | 같은 이름 기록을 합치거나 갱신하는 구현 | 실행 |
| `(렌더링 계약)` | `highlightIndex`를 무시하고 강조하는 구현 | 실행 |

- R3 항목 제목에 **"실행 검증 없음, 코드 확인 필수"** 를 넣어 착각을 막았다
- "아래 두 항목은 R3 검증이 아니다"를 명시해 세 항목이 붙어 있어도 서로 오인되지 않는다
- 실패했을 때 원인이 셋 중 어디인지 체크리스트에서 바로 읽힌다

## 3. 검증 부담이 줄었다

- 4단계 순위표 검증이 **11판 110문제 수동 풀이**를 요구했다
- 정렬, 자르기, 미진입 판정은 저장 함수만 지나가므로 콘솔 호출로 대체 가능해졌다

```javascript
saveRanking('korean_history', { name: '테스터A', score: 9, total: 10, date: formatDate() })
```

- **줄이면 안 되는 것을 함께 판단했다** — 완료 기준 1번은 실제 플레이로 남겼다. `finishGame`의 전체 경로(이탈 경고 해제 → 키 결정 → 저장 → 렌더링 → 화면 전환)를 지나는 것이 그것뿐이기 때문
- 테스트 데이터를 "기록 지우기"로 비운다는 뒤처리까지 적었다

## 4. 명세의 구멍이 메워졌다

구현자가 판단해야 했던 자리가 확정됐다.

| 위치 | 최초본 | 반영본 |
|---|---|---|
| `startGame` | "문제를 뽑아 첫 문제를 그린 뒤" | `state` 초기화 → 문제 뽑기 → `showScreen` → `renderQuestion` → 이탈 경고 순서 명시 |
| `pickCategoryQuiz` | `category` 객체를 얻는 방법 없음 | `CATEGORIES.find(c => c.id === categoryId)` 명시 |
| `renderResult` | 순위표 목록의 출처 없음 | `readRankings()`를 다시 불러 얻는다고 명시 |
| 2단계 | 순위표 열기, 닫기 핸들러의 소속 불명 | 이벤트 바인딩이 2단계 몫임을 명시 |

- `startGame` 순서는 특히 중요하다. 뒤집으면 초점이 제목에 남아 PRD 4.3절 요구가 깨진다

## 5. 판단 근거가 문서에 남았다

나중에 같은 고민을 반복하지 않도록 "왜 이렇게 하지 않았는가"를 적었다.

- **`renderResult`** — `saveRanking`이 `{ index, list }`를 돌려주면 읽기 한 번을 아낄 수 있지만, PRD 3.4절이 반환값을 세 가지로 못박았으므로 계약을 바꾸지 않는다
  - 구현 편의로 PRD를 조용히 바꾸는 것을 막는 기록이다
- **`disabled` 단독 방어** — 성립 근거 셋과 전제(`<button>`)를 함께 적었다
- 체크리스트에도 반영 — "재선택 방어를 여기에만 맡기므로 `<div>`나 `aria-disabled`로 대신하면 안 된다"

## 6. 재작업과 삽질을 미리 막았다

- **색 대비** — 검증은 5단계지만 색을 정하는 것은 3단계다. 3단계에 "흰 배경 대비 4.5:1 사전 확인, 특히 `diff-hard` 주황"을 넣어, 5단계에서 미달이 나 색과 강조 스타일을 다시 손보는 경로를 없앴다
- **Pages 캐시** — 경로를 고쳤는데도 404가 이어지면 CDN 캐시를 먼저 의심하라고 적었다. "코드를 더 고치기 전에 이것부터 배제한다"
- **복구 확인** — 1단계 검사 함수 검증은 데이터를 여덟 번 망가뜨렸다 되돌린다. 눈 대조 대신 `git diff questions.js`가 비어야 한다는 기준으로 바꿨다

## 7. 체크리스트가 촘촘해졌다

- 선택지 요소 검증 항목 신설 — `<button>`인지, 답을 고르면 넷 다 `disabled`인지 개발자 도구로 확인
- 재선택 방어 항목 보강 — "`✓`가 붙은 정답 버튼의 **글자 부분을 정확히** 눌러도" 점수가 변하지 않는지
  - 방어가 `disabled` 하나뿐이 되면서 자식 요소 클릭까지 확인 대상이 됐다
