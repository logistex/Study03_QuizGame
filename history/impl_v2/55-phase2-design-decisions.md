### 1.1 Supabase를 고른 근거

**판단 기준은 무료 티어와 가입 절차, 학생이 따라 할 수 있는가다.** 52번이 정해 둔 기준이고, 5장에서 구현까지 하기로 하면서 결정적인 기준이 되었다.

| 후보 | 카드 | 걸리는 점 |
|---|---|---|
| **Supabase** | **불필요** | — |
| Firebase | **필요** | Cloud Functions 배포에 Blaze 요금제가 필요하고, 무료 한도 안에서 써도 카드를 등록해야 한다 |
| Cloudflare D1 | 불필요 | 인증을 직접 만들어야 한다 |

**Firebase는 카드에서 탈락했다.** 수강생 서른 명에게 카드를 요구하면 실습이 성립하지 않는다.

Supabase가 더 나은 점 둘이 있다. **깃허브 계정으로 가입한다** — 학생이 이미 갖고 있는 것이라 새 계정이 안 늘어난다. 그리고 **인증과 DB와 권한이 한 곳에 있다.**

무료 플랜 한도는 요금 페이지에서 확인했다. DB 500MB, **조직당** 활성 프로젝트 2개, 월간 활성 사용자 5만, 1주일 비활성이면 일시정지다.

- **조직당이라는 것을 화면으로 확인했다.** 사용자 계정에 무료 조직 셋이 있고 각각 프로젝트 하나씩이다. 처음에 계정 전체 한도로 잘못 말했다가 바로잡았다
- **수업 규모로는 용량이 넉넉하다.** 실제로 걸리는 것은 일시정지 하나이고, 수업 전에 깨우는 절차를 노트에 넣어야 한다

2026년 8월 1일 약관 변경은 **데이터 처리 부속서를 약관 본문에 포함한 것**이고 요금이나 한도와 무관하다. 정책 변경 목록에 2026년 무료 플랜을 조인 항목은 없다.

### 1.2 Vercel을 고른 근거

**DB 때문만이 아니라 서버에서 코드를 돌려야 하기 때문에 옮긴다.** GitHub Pages는 파일을 보내 줄 뿐 계산하지 않는다.

- 카드가 필요 없고 깃허브 계정으로 가입한다
- **프레임워크를 안 들여도 된다.** 지금 파일 넷을 그대로 올리고 `api/` 폴더에 함수 파일 하나를 두면 서버 채점이 된다. 1차의 단순함이 유지된다
- Hobby 한도는 프로젝트 200개, 하루 배포 100회, 함수 호출 월 100만이다. 비상업 용도만 허용하나 수업용은 걸리지 않는다

**한 가지가 걸린다.** 문서에 "Hobby 팀의 프로젝트는 깃 조직이 소유한 저장소에 연결할 수 없다"고 되어 있다. **학생은 개인 계정에 저장소를 두어야 한다.** 배포 직전에 발견하면 수업 시간이 날아가므로 첫 개발 단계에서 확인한다.

채점을 Supabase의 Postgres 함수에 둘 수도 있으나 SQL이라 신입생에게 새 문법이다. **Vercel 함수는 브라우저에서 쓰던 자바스크립트를 그대로 쓴다.**

### 1.3 5장의 경계

**5장이 5.3.9까지 전부를 안고 간다.** 5장의 주제가 "체계적인 개발과 관리"이고, 이 실습이 보여 준 것은 PRD를 쓰고 검토받고 계획을 세우고 다시 검토받고 구현하고 또 검토받는 왕복이다. **그 왕복이 한 장 안에서 닫혀야 주제가 선다.**

교재는 5장을 정적 앱으로 마치고 6장에서 API로 가므로, 우리 5.3은 교재 6장 자리를 당겨 오는 셈이다.

## 2. 채점을 서버로 옮긴다

**52번에 없던 결정이고, 논의 중에 새로 나왔다.**

### 2.1 지금 어디서 도는가

전부 학생의 브라우저 안이다. `index.html`이 `questions.js`를 불러오는 순간 **60문항의 정답과 해설이 학생의 컴퓨터로 내려온다.** 판정은 `script.js`의 한 줄이다.

```javascript
const isCorrect = choiceIndex === question.answer;
```

- **정답이 이미 학생 손에 있다.** 콘솔에 `QUESTIONS.geography[0].answer` 한 줄이면 나온다
- **선택지를 섞어도 소용없다.** 섞는 것도 브라우저가 하고 `answer`를 새 자리로 다시 계산해 둔다
- **점수를 믿을 수 없다.** `localStorage`를 고치면 100점이 된다

1차에서는 문제가 아니었다. **혼자 풀어 보는 앱이고 순위도 자기 브라우저에만 남았으니 속여 봐야 자기를 속이는 것**이었다. 선생님 기능에 성적 관리가 들어오는 순간 달라진다.

### 2.2 무엇을 바꾸는가

- **문항을 서버 함수가 읽어 `answer`를 빼고 내려보낸다**
- **채점도 같은 함수가 한다.** 브라우저는 고른 번호만 보낸다
- **응시 기록은 서버 함수만 쓴다.** 학생 쪽에 쓰기 정책을 두지 않는다
- **문항 생성도 서버 함수가 한다.** 선생님이 화면에서 요청하면 서버가 Anthropic API를 호출한다. API 키는 본교 웹 사이트에서 발급받을 수 있어 학생도 같은 구성을 실습할 수 있다

### 2.3 키를 자리마다 하나씩 둔다

| 코드 | 키 | 어디 두나 |
|---|---|---|
| 브라우저 | `anon` | 소스에 그대로 적어도 된다 |
| 서버 함수 | `service_role` | Vercel 환경 변수. 저장소에 넣지 않는다 |

**두 키를 바꿔 쓰면 각각 이렇게 된다.** 서버 함수에 `anon`을 쓰면 채점이 안 되고, 브라우저에 `service_role`을 쓰면 **학생이 그 키로 DB 전체를 마음대로 읽고 쓸 수 있다.** 뒤엣것이 이 설계에서 가장 위험한 실수다.

**`service_role`은 RLS를 건너뛰므로 권한 검사도 함께 건너뛴다.** 함수가 로그인 토큰으로 누구인지 직접 확인해야 하고, 이 단계를 빠뜨리면 아무나 남의 이름으로 점수를 넣을 수 있다.

## 3. RLS로 되는 것과 안 되는 것

Supabase 문서를 받아 확인했다.

**`anon` 키는 브라우저에 두라고 만든 키다.** 문서가 웹 페이지, 앱, 소스 코드에 노출해도 안전하다고 못박고 있다. 안전한 까닭이 RLS다. 키 자체는 권한을 주지 않고 테이블마다 켜 둔 정책이 무엇을 볼 수 있는지 정한다.

**RLS를 안 켠 테이블은 `anon` 키로 전부 읽힌다.** 문서가 모든 테이블에 켜라고 적은 자리다.

**RLS는 행을 거르지 열을 가리지 않는다.** 모든 질의에 `WHERE`를 덧붙이는 방식이라, 문항 행을 읽게 허용하면 그 행의 `answer` 열도 함께 간다. 열을 가리는 길은 셋인데 **서버 경유를 골랐다.** 채점 때문에 만들 함수가 이미 있어 새 개념이 안 늘고, "정답은 서버에만 있다"는 한 문장으로 설명이 끝난다.

**점수 값 자체는 RLS가 못 지킨다.** 정책은 학생이 **어느 행을** 쓸 수 있는지는 정하지만 **무슨 값을** 쓰는지는 못 정한다. 자기 `user_id`로 100점을 넣는 것은 정책상 정당한 쓰기다.

## 4. DB가 해결하지 않는 것

**전제를 미래형으로 적어야 한다.** 아직 만들지 않았으므로 "해결된 것"이 아니라 "해결될 것"이다.

| 1차의 한계 | 2차에서 해결될 것인가 |
|---|---|
| 기록이 그 브라우저에만 남는다 | **성립한다.** 저장 위치가 서버로 옮겨진다 |
| 학생끼리 순위를 견줄 수 없다 | **성립한다** |
| 이름만으로 사용자를 못 가른다 | **성립한다.** 인증이 붙는다 |
| 개발 단계별 배포본의 기록이 섞인다 | **성립하지 않는다. 자리를 옮긴다** |

넷째가 중요하다. **원인이 `localStorage`가 아니라 한 호스트에 개발 단계별 배포본을 폴더로 나란히 올린 배포 방식이다.** 2차 앱을 주소 하나로만 배포하면 DB 없이도 이 혼선은 안 생긴다. "이래서 DB가 필요하다"의 근거로 세우면 반박당한다.

2차도 개발 단계마다 배포본을 남기면 **그 배포본들이 이번에는 같은 DB를 함께 쓴다.** 오리진을 공유하던 것이 DB 인스턴스를 공유하는 것으로 바뀔 뿐이고, **이번에는 더 위험하다.** `localStorage`는 각자의 브라우저 안이라 남에게 영향이 없었는데 DB는 한 곳이라 다른 학생의 기록까지 건드린다.

**1차 배포본 여섯은 그대로 둔다.** `gh-pages`를 열어 확인했다 — 최신본 하나와 `stage1-final`, `stage2`, `stage3-final`, `stage4-final`, `stage5-final` 다섯이다. 개발 단계별로 눌러 보는 실습이 이 노트의 값이고, 혼선은 5.3.9에서 대조할 때 산 예가 된다.

## 5. 그 밖에 정한 것

|---|---|
| 반 단위 | 두지 않는다. 수업용이라 수강생 전체를 하나로 본다. 역할은 선생님과 학생 둘 |
| 선생님 기능 | 문항 관리와 성적 관리, 대시보드 |
| 선생님의 작업 수단 | **앱 화면(UI)뿐이다.** 클로드 코드 같은 개발 도구를 쓰지 않는다 |
| 문항 생성 | **선생님이 직접 출제하거나 등록하지 않는다.** 화면에서 요청하면 서버 함수가 Anthropic API를 호출해 생성하고, 규격 검증을 거친 것을 선생님이 확인해 채택한다 |
| 문항 저장 위치 | **DB.** 선생님이 화면에서 늘리려면 파일 방식으로는 성립하지 않는다 |

| PRD | 나누지 않는다. 2차 착수 시점 판본을 `archive/`에 뜨고 `spec/PRD.md`를 고친다 |

**낱말도 정했다.**

- **개발 단계** 또는 **6단계 개발 절차**. 맨 "단계"로 줄여 쓰지 않는다
- **승계**는 2차가 가져가는 것, **존치**는 1차가 남는 것. 주체가 바뀌느냐로 가른다
- **노트에 굵은 글꼴을 쓰지 않는다**

## 6. 새로 생긴 결정 항목

**문항을 DB에 두기로 정해졌다.** 아래는 그 결정이 무엇을 끌고 오는지다.

- **명령어 넷(`quiz-add`, `quiz-validate`, `quiz-stats`, `quiz-daily`)을 다 고쳐야 한다.** 전부 `questions.js`라는 파일을 고치고 읽는 전제로 만들어졌다
- **데이터 검사 함수를 부르는 시점이 바뀐다.** 페이지 로드 시점이 아니라 문항을 넣는 시점에 서버에서 부른다
- 검사 항목 자체는 바뀌지 않는다

**2차 개발 단계를 몇 개로 나눌지도 안 정해졌다.** 나눠 볼 만한 자리는 인증, 데이터 이전, 서버 채점, 선생님 화면이다.
