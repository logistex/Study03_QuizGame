## 1. 확인받은 목록과 그 뒤에 온 지적

목록은 대화에서 확인받았고, 사용자가 다섯을 더했다. 다섯 모두 반영했다.

| # | 지적 | 어떻게 반영했나 |
|---|---|---|
| 1 | 요청 테이블과 5단계 완료 기준이 부딪힌다 | 결정 5에 "채택 전 문항이 DB에 안 들어간다"의 경계 절을 만들고 표로 갈랐다. 5단계 완료 기준, 거절 확인, 체크리스트를 **문항 테이블**로 못박고 체크리스트에 요청 테이블을 함께 세는 줄을 더했다 |
| 2 | 깃허브 아이디를 키로 쓰면 행 수준 보안과 연결이 한 겹 필요하다 | 사용자 테이블에 **인증 식별자 열**을 함께 두기로 정했다. 두 열을 잇는 것은 첫 로그인이고, 2단계 작업 목록과 체크리스트에 그 자리를 넣었다 |
| 3 | DB 둘이 무료 한도에 정확히 맞는다 | 결정 6에 "둘이 한도의 전부다" 절을 만들고, 셋째를 만들 수 없다는 것과 **개발용도 관리 대상**이라는 것을 적었다 |
| 4 | 상태 확인 요청은 호출이 하나 느는 설계다 | 결정 4에 저장 시도 결과로 판정하는 안과 견준 표와 근거를 넣었다. PRD 3.5절이 명시한 "한 판도 안 친 사용자"가 값의 근거다 |
| 5 | 가운뎃점을 쉼표로 | 계획서 본문에는 가운뎃점이 없다. 대화에 쓴 "문항 생성·관리"가 그것이었고 계획서는 "문항을 생성하고 판정하고, 채택, 수정, 삭제를 수행한다"로 적혀 있다 |

## 2. 어느 절에 무엇을 담았나

| 절 | 무엇 |
|---|---|

| 계획서가 정한 것 | 결정 1~10 |

## 3. 65번 9절의 아홉을 어떻게 정했나

| 65번 9절 | 정한 것 | 근거 |
|---|---|---|
| DB 조회 방법 | **`fetch`. 라이브러리를 쓰지 않는다** | PRD 4절 CDN 금지, PRD 4절 빌드 없음, PRD 1.4절 파일 구성 넷 |
| 서버 함수 분할과 이름 | **넷** — `api/questions.js`, `api/submit.js`, `api/authoring.js`, `api/users.js` | PRD 1.4절 책임 셋 + PRD 3.8절 역할 바꾸기. 파일 경계가 단계 경계와 맞는다 |
| 순위 저장, 조회 계약 | **응시 기록에서 상위 N을 뽑는다.** 순위표 테이블을 두지 않고 기록을 지우지 않는다 | PRD 3.10절 응시 기록 하나, 65번 7절 대시보드가 그 기록을 쓴다 |
| 하단 문구와 실패 상태 | 문구 열하나 확정. 쓰기 가능 여부는 `api/submit.js`의 GET | PRD 3.5절 세 상태, PRD 3.5절이 짚은 "한 판도 안 친 사용자" |
| 생성 요청 묶기 | **요청 테이블** | PRD 3.9절 7번(채택한 것만 넣는다), 65번 5절 이력 |
| 개발용과 수업용 저장 | **DB 둘.** 프리뷰는 개발용, 프로덕션은 수업용 | PRD 4.1절 6번, 65번 8절 배포가 이미 둘로 갈려 있다, PRD 4.4절 환경 변수 |
| 검사 항목의 시점 | **넷으로 가름** — 넣거나 고치는 시점, DB 유일 제약, 지우는 시점, 판을 시작하는 시점 | PRD 4.2절 머리말이 "넣는 시점에 판정할 수 없다"고 짚은 자리 |
| 고친 문항과 과거 기록 | **판본을 남기지 않고 고치되 알린다** | PRD 3.9절(점수는 그대로), PRD 3.10절에 판본 열이 없다 |
| 사용자 테이블의 아이디 | **깃허브 아이디를 키로, 인증 식별자를 열로 함께** | 65번 3절(첫 선생님을 DB에 직접 넣는다), 행 수준 보안이 인증 정보로 행을 거른다 |

**넷째는 처음에 셋으로 갈랐다가 넷이 되었다.** `id`, `question` 중복을 넣는 시점과 DB 제약 둘로 세지 않으면 검사와 삽입 사이가 비어 있다.

## 4. 65번에 없으나 PRD에서 따라 나온 결정 하나

**결정 10 — 응시 세션을 둔다.**

- PRD 1.4절이 "브라우저는 고른 선택지 번호를 서버에 보내고"라고 정했다
- PRD 2.1절이 선택지 순서를 섞으라고 정했다
- **둘을 같이 지키려면 서버가 그 번호가 무엇을 가리키는지 알아야 한다**

그래서 선택지 섞기를 서버로 옮기고, 판마다 세션 행을 만들어 문항 `id`와 섞은 순서를 담기로 했다. 즉시 피드백(PRD 3.2절)이 서버 채점과 함께 서려면 채점이 문항마다 한 번씩 돌아야 하는 것도 여기서 나온다.

**따라 나오는 것이 하나 더 있다.** 문항별 응답이 세션 행에 남으므로 65번 7절의 "많이 틀린 문항"이 그 자리에서 나온다.

## 5. 검색에 무엇을 썼나

다음 사람이 같은 검색을 돌릴 수 있게 그대로 적는다. **고치기 전에 돌렸다.**

```bash
# PRD가 계획서를 가리키는 자리 — 열둘
grep -c "IMPL-PLAN-2" spec/PRD.md
grep -n "IMPL-PLAN-2" spec/PRD.md

# 저장소 전체에서 계획서를 가리키는 자리
grep -rn "IMPL-PLAN-2" --include="*.md" .

# 명령어 넷이 규격의 절과 이름을 인용하는 자리
grep -rn "절\|questions.js\|IMPL-PLAN" .claude/commands/*.md

# 한 겹 더 따라간 것 — 계획서 1.8절을 가리키는 자리
grep -rn "계획서 1\.8절\|1\.8절" spec/PRD.md .claude/commands/*.md
grep -rn "저장소 밖에서 검사 함수" spec/ .claude/commands/

# 표기 규칙
grep -n "·" spec/IMPL-PLAN-2.md
```

**한 겹 더 따라간 것이 둘을 잡았다**([62번](62-prd-phase2-review-round2.md) 7.2절).

- **"계획서 1.8절"이 PRD 세 줄과 명령어 넷에 있다.** 2차 계획서에 소수점 절 번호를 만들지 않기로 한 것이 여기서 나왔다
- **`spec/IMPL-PLAN.md`의 "저장소 밖에서 검사 함수를 부를 때"를 명령어 셋이 가리킨다.** 3단계가 `questions.js`를 지우면 그 항목이 쓸모없어진다. 3단계 작업 목록에 넣었다

**식별자 검색에 걸리지 않는 것도 있었다.** 데이터 검사가 브라우저에서 서버로 옮겨 가는 것은 이름이 아니라 **주체와 시점**이 바뀌는 것이라 `validateData` 검색으로는 나오지 않는다. PRD 1.5절과 4.2절을 읽어 잡았다.

## 7. 묻는 것 — 비워 둔 자리 하나

**2단계의 인증 클라이언트.** 계획서 2단계에 "열린 자리"로 표시하고, 그 자리가 정해지기 전에는 2단계를 시작할 수 없다고 적었다.

- 결정 1은 **DB 조회**를 `fetch`로 정했다. 근거가 PRD 4절과 1.4절에 있다
- **로그인을 시작하고 토큰을 받아 보관하는 경로**는 65번에도 PRD에도 없다. 추측해 적지 않았다

사용자가 후보 둘을 주었고 계획서에 그대로 적어 두었다.

| 후보 | 무엇 |
|---|---|
| 라이브러리 없이 | 인증 경로로 보내고 돌아온 주소에서 토큰을 직접 꺼내 쓴다 |
| 예외를 하나 둔다 | 결정 1에 인증 클라이언트만 예외로 둔다 |

정해지면 채울 것 — 로그인 버튼이 무엇을 부르는가, 토큰을 어디에 두는가, 서버 함수에 어떻게 실어 보내는가, 로그아웃이 무엇을 지우는가.

**노트 5.3.1의 한계 목록을 저장소에서 볼 수 없다.** 65번 2절이 마지막 검증으로 지정한 자리다. 계획서에 항목을 옮겨 적지 않고 "노트가 정본이고 대조할 때 그것을 연다"로 두었다.

## 8. PRD에 고칠 것으로 보이는 것 — 고치지 않았다

**근거 문서를 고치면서 그 근거로 계획서를 쓰면 나중에 대조할 때 어긋난 자리가 보이지 않는다.** 그래서 셋 다 그대로 두었다.

### 8.1 PRD 1.4절의 `api/` 책임이 셋인데 넷이다

> `api/` … 책임 셋을 맡는다 — 문항을 정답 열 없이 전달하는 것, 채점하고 응시 기록을 저장하는 것, 문항을 생성해 검증하는 것

**PRD 3.8절 권한 표의 마지막 줄이 "역할 바꾸기 | 서버 함수만"이다.** 넷째 책임인데 1.4절에 없다. 계획서는 넷으로 나눴다(결정 2).

### 8.2 PRD 3.10절 응시 기록에 문항별 응답 자리가 없다

> 응시 기록 | 응시자, 카테고리, 점수, 총 문제 수, 응시 때

- **65번 7절이 대시보드 항목으로 "많이 틀린 문항"을 정했다.** 무엇을 틀렸는지를 담지 않으면 나오지 않는다
- PRD 3.9절도 "이미 응시 기록이 쌓인 문항을 고치면 **무엇을 틀렸는지가 바뀐다**"고 적어, 그 정보가 기록에 있다는 것을 전제하고 있다
- 계획서는 응시 세션 행에 문항별 응답을 담아 이 자리를 메웠다(결정 10). **PRD 3.10절의 데이터 모델을 넘어선 것이다**

### 8.3 PRD 3.4절이 1차 계약을 담은 채 남아 있다

[63번](63-round2-adoption.md) 4절이 이미 남긴 것이다. **이제 계약이 정해졌으므로**(결정 3) 3.4절의 "저장 구조"와 "저장 함수의 계약" 두 목이 계획서를 가리키는 한 줄로 바뀔 수 있다.

- 1차의 `quizGameRankings` 저장 구조와 읽기, 삽입, 정렬, 자르기, 쓰기 순서가 그대로 남아 있다
- 결정 3은 **자르지 않는다.** 두 서술이 같은 자리에서 반대다

### 8.4 65번에서는 고칠 것을 찾지 못했다

9절의 아홉이 모두 계획서에서 닫혔고, 1절과 2절의 단계와 검증도 PRD 6절과 어긋나지 않았다.

## 9. 계획서가 규격 밖으로 넘어간 자리 — 넷

**8절과 별개로, 계획서가 PRD에 없는 것을 정한 자리를 모아 둔다.** 나중에 PRD에 올릴지 판단하는 자리다.

| 무엇 | 어디 | 까닭 |
|---|---|---|
| 응시 세션 테이블 | 결정 10 | PRD 1.4절과 2.1절을 같이 지키려면 필요하다 |
| 생성 요청 테이블 | 결정 5 | PRD 3.9절과 3.10절이 "계획서가 정한다"로 넘긴 자리다. **넘긴 자리이므로 규격 밖이 아니다** |
| 사용자 테이블의 인증 식별자 열 | 함수 계약 | 행 수준 보안이 깃허브 아이디로는 행을 거를 수 없다 |
| 공개 키를 서버 함수가 내려 준다 | 결정 6 | 소스에 적으면 프리뷰가 수업용 DB를 본다. PRD 4.4절은 "적어도 된다"이지 "적어야 한다"가 아니다 |

넷 가운데 둘째만 규격이 넘긴 자리이고, 나머지 셋은 계획서가 새로 만든 것이다.

## 10. 남은 일

1. **인증 클라이언트를 정한다.** 2단계 착수 조건이다(7절)
2. **다른 세션의 검토를 받는다.** PRD가 두 라운드를 돈 것과 같은 자리다
3. **8절의 셋을 PRD에 반영할지 정한다.** 규격 동결의 예외인 "코드와 규격이 어긋난 것"이 아니라 **규격 안에서 어긋난 것**이라 판단이 필요하다
4. README의 문서 목록에 `spec/IMPL-PLAN-2.md`를 더한다. 지금은 1차 계획서만 실려 있다
