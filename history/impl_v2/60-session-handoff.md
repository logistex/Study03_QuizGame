## 2. 이 세션이 한 일

### 2.1 문항을 60개로 채웠다

지리와 예술과 문화에 다섯씩 넣었다([53번](../53-ge-ac-additions.md)). `/quiz-add`에 커밋과 푸시를 붙여, 문항을 넣으면 그 자리에서 원격까지 올라간다.

**대조하다 문항을 두 번 바꿨다.** 둘 다 시점에 기대는 서술이었다.

- 경상북도 면적 — 군위군 편입으로 수치가 갈려 문항을 통째로 뺐다
- 사그라다 파밀리아 — 2026년 6월 완공 선언으로 "미완성"이 사실이 아니게 되었다

### 2.2 2차 설계를 정했다

[55번](55-phase2-design-decisions.md)에 있다. 52번이 남긴 결정 셋을 닫고 새 결정 셋이 더 나왔다.

| 무엇 | 결정 |
|---|---|
| 인증과 저장 | Supabase |
| 배포 | Vercel |
| 5장의 경계 | 5.3.9까지 전부. 구현과 검증을 6장으로 넘기지 않는다 |
| 채점 | **서버 함수가 한다.** 문항도 서버를 거쳐 정답을 빼고 전달한다 |
| 문항 저장 | **DB.** 선생님이 화면에서 늘리려면 파일 방식으로는 성립하지 않는다 |
| 선생님의 작업 수단 | **앱 화면뿐이다.** 직접 출제하거나 등록하지 않고 요청과 채택만 한다 |
| 2차 소스 코드 | `main` 브랜치. 1차 소스는 태그로 보존된다 |

**프롬프트를 먼저 설계해 두고 실행했다.** [`archive/prompts/prd-phase2-prompt.md`](../../archive/prompts/prd-phase2-prompt.md)에 있다.

**이 왕복에서 가장 값진 것 둘을 적어 둔다.**

- **근거 문서를 규격과 같은 커밋에서 고치면 안 된다.** 55번을 PRD 개정과 함께 고쳐, 두 문서를 대조해도 어긋난 자리가 안 보이게 되었다. `git show`로 개정 전 판을 꺼내야 보였다
- **적어야 할 것은 어긋난 자리의 목록이 아니라 찾는 방법이다.** 목록을 적으면 다음 개정에서는 다른 목록이 나온다

둘 다 프롬프트에 넣었다.

### 2.4 문체 규격을 세웠다

`~/.claude/STYLE.md`가 정본이고 전역 `CLAUDE.md` 7절이 가리킨다.

- 볼드를 쓰지 않는다. 강조가 꼭 필요하면 밑줄을 절제해 쓴다
- 서술형 종결(`~한다`)을 원칙적으로 쓰지 않는다. 예외는 사용자가 직접 적용한다
- **대화창 답변도 음슴체로 쓴다**

**문서가 자기 규칙을 어기던 자리 넷을 함께 고쳤다.** 특히 7절이 "규칙보다 이 예시를 우선"이라 못박고 있어, 예시에 볼드가 남으면 금지가 무효가 되는 자리였다.

### 2.5 그 밖에

- `history/impl_v2/` 신설. **1차 문서는 옮기지 않는다** — 옮기면 링크 160곳이 걸리고 그 절반 이상이 과거 기록이다
- `gh-pages` 재생성 명령이 `main` 대신 `stage6-final`을 꺼내게 고쳤다. 그대로 두면 2차 코드가 1차 배포 자리에 올라가 깨진다
- `CLAUDE.md` 태그 표를 실제 태그 열둘에 맞추고 커밋 열을 더했다
- `archive/CLAUDE-v7.md`부터 `v9.md`까지 셋을 떴다

### 3.2 `spec/IMPL-PLAN-2.md`를 쓴다

**아직 없는데 PRD가 아홉 자리에서 가리킨다.** 계획서가 정해야 할 것이 그만큼 쌓여 있다.

- 서버 함수를 몇 개로 나누고 이름을 무엇으로 할지
- 문항 생성 요청을 어떻게 기록할지 — 만든 때만으로는 한 요청이 만든 여러 문항을 못 가른다
- Supabase 클라이언트를 도입할지
- 3.4절 저장 함수 계약과 4.2절 에러 처리를 서버 기준으로 다시 정의
- 3.5절 안내 문구 — "이 브라우저에만 저장되며"가 사실과 반대가 된다

**PRD를 고칠 때 쓴 프롬프트 방식을 그대로 쓸 수 있다.** 다만 계획서는 새로 쓰는 것이라 "개정 범위" 대신 "무엇을 담을지"를 지정하게 된다.

### 3.3 PRD 8.3절의 결정 넷

계획서를 쓰기 전에 앞의 둘이 정해져야 한다.

- **2차 개발 단계를 몇 개로 나눌 것인가** — 인증, 데이터 이전, 서버 채점, 선생님 화면이 후보
- **화면이 몇 개가 되는가** — 선생님 화면을 몇 개로 나눌지가 없다
- 대시보드를 어디까지 만들 것인가
- 문제은행 확대를 어디서 멈출 것인가

### 3.4 순서를 지켜야 하는 것 셋

**2차 소스를 `main`에 올리기 전에 정해 두어야 한다.** 위험은 브랜치가 아니라 "무엇을 먼저 하느냐"에 있다.

1. DB에 문항 테이블을 만들고 60문항을 넣는다
2. 명령어 넷과 데이터 검사 함수를 DB 기준으로 고친다
3. 그다음에 `questions.js`를 지운다

순서가 어긋나면 그 사이에 문항 관리가 통째로 멈춘다. 계획서의 완료 기준에 넣는다.

### 3.5 노트 작업

- **5.3 링크 전수 조사** — 5장 노트가 완성된 뒤에 한다. 기본값은 시점 고정이고, 최신을 가리켜야 할 것만 골라낸다. 1차 앱의 소스를 가리킬 때는 `blob/phase2-start/`를 앵커로 쓴다
- 5.3.6.4와 5.3.6.5의 관계를 한 줄로 잇는 것 — 스스로 찾은 넷과 검토가 더 찾은 다섯이 반복처럼 읽힌다
- 5.3.6.4의 "물어본 것"이 누구에게인지 — 사람에게 물은 것이다
- 노트 5.2.7 두 절은 반영되었다

## 5. 주의할 것

- **자칭은 "저"로 쓴다.** 사용자를 신 교수라고 부른다
- **대화창 답변은 음슴체다.** `~/.claude/STYLE.md`를 따른다
- **보고는 중요한 건으로 제한한다.** 중간 단계와 도구 이름을 알리지 않는다
- **검색 요약을 원문 대신 쓰지 않는다.** 원문을 받아 확인한다
- **규격을 고치면 그것을 가리키는 자리를 전부 찾는다.** `spec/PRD.md`만 보지 말고 `spec/IMPL-PLAN.md`의 검증 절차와 체크리스트까지 본다. 절 번호가 바뀌면 그 번호를 가리키는 자리가 끊긴다
- **판정은 문항을 쓴 세션이 하지 않는다.** 두 라운드를 서로 다른 세션이 돈다
