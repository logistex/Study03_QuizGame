# 71번 3장의 안 넷 검토와 용어 통일

- 앞 문서: [71번 세션 인계](71-session-handoff.md)
- 이 문서가 다루는 것: 71번 3장의 안 넷을 신 교수와 검토한 결과, 그 과정에서 드러난 규격 결함 셋, 용어 통일, 노트 구조 변경
- 커밋 `fc0175b`, `2727395`, `8b87f85`

## 1. 대조표를 먼저 확인함

71번 3장이 노트 5.3.7.4와 5.3.7.5가 계획서 및 5.3.9와 겹치는 실태를 표로 냈음. 세 자리를 열어 대조한 결과 여섯 행 가운데 다섯이 맞고 한 행이 부분 불일치였음.

- 「데이터 검사 시점 변경」 행이 노트 5.3.7.5를 빈칸으로 두었으나, 그 목 마지막 줄이 「1차와 2차에서 데이터 검사가 도는 자리가 다른 것도 함께 적음」으로 언급하고 있었음

71번이 적은 근거 둘도 사실과 달랐음.

| 71번의 기술 | 실제 |
|---|---|
| c)의 산출물 링크가 `c5fa894`에 고정돼 있고 그 뒤 세 차례 더 수정함 | 계획서 파일 자체는 `14b989e` 한 번만 바뀜. 세 차례는 커밋 수임 |
| 5.3.7.5는 5.3.9와 거의 전부 겹침 | 여덟 항목 가운데 넷만 겹침. 단계마다 셋, 마지막에 둘, 체크리스트를 몰 수 없음, 문항 판정 제외는 5.3.9에 없음 |

**결론이 같더라도 근거를 고침.** 링크가 낡은 것은 맞으나 이유가 달랐고, 안 3은 전제가 틀려 다시 보아야 했음.

## 2. 안 1을 채택하고 그 과정에서 규격 결함 셋을 발견함

안 1은 계획서 「검증 셋」 절에 다섯 단계의 거절을 모은 표를 넣는 것임. 표가 노트에만 있으면 계획서를 고칠 때 따라오지 않기 때문임.

옮기려고 대조하는 과정에서 셋이 드러났음.

### 2.1 4단계 완료 기준이 둘인데 노트 표는 셋이었음

계획서 4단계 「거절한다」 줄이 직접 저장과 점수 위조 둘이었고, 노트 표에는 「남의 기록 직접 조회」가 더 있었음. 그 거절은 계획서의 검증 표와 체크리스트에는 있었으나 완료 기준에서만 빠져 있었음.

**PRD 3.8절이 순위표를 서버 함수로 돌린 이유가 그 거절이므로 누락으로 판정하고 완료 기준을 셋으로 맞춤.**

### 2.2 「거절」이 세 가지를 뭉뚱그리고 있었음

신 교수가 「정책 없는 테이블을 공개 키로 조회하려는 요청을 서버가 거절한다는 뜻인가」를 물어 드러났음. 실제로는 셋임.

| 무엇이 막나 | 어떻게 나타나나 |
|---|---|
| 행 수준 보안이 조회를 거른다 | 오류가 아니라 빈 결과가 옴. 0행이 정상 동작임 |
| 행 수준 보안이 쓰기를 막는다 | 오류로 거절됨 |
| 서버 함수가 요청자를 검사한다 | 거절 응답이 옴 |

PRD 3.8절이 「거르고」와 「검사한다」로 갈라 둔 것을 계획서가 한 낱말로 합쳐 놓았음. 계획서 「검증 수단」 절에 정의를 넣고 셋을 묶어 부른다는 것을 밝혔음.

**1단계의 비밀 키 항목은 셋의 어디에도 안 듦.** 서버가 막는 것이 아니라 저장소를 검색해 확인하는 것임. 완료 기준에는 두되 모은 표에서 빼고, 뺀 이유를 두 자리에 남겼음.

### 2.3 키 이름이 폐기 예정이었음

「비밀 키가 무엇인지 몰랐다, 이것이 나의 무지인가」라는 물음에서 시작했음. 무지가 아니라 문서 결함이었음.

- 계획서 전체에 `service_role`과 `anon`이 한 번도 안 나옴. 계획서만 읽으면 「비밀 키」를 원래 이름과 이을 수 없음
- 원어와 나란히 놓이는 자리가 PRD 4.4절 표의 한 칸뿐이었음

확인해 보니 Supabase가 이름을 바꾸어 두 벌이 공존하고 있었음. API Keys 탭의 publishable key와 secret key가 현행이고, Legacy API Keys 탭의 `anon`과 `service_role`은 2026년 말 폐기 예정임. **학생이 화면에서 만나는 이름과 규격을 맞추기 위해 현행 이름으로 옮김.**

## 3. 용어 병기 규칙을 정함

신 교수의 판단은 「문서를 처음부터 정독하지 않으므로 첫 회가 아니라 나오는 곳마다 병기한다」임.

| 어디 | 꼴 |
|---|---|
| 산문 | 공개 키(`publishable key`), 비밀 키(`secret key`), 행 수준 보안(RLS, row level security) |
| 표 칸과 체크리스트 | 공개 키, 비밀 키, 행 수준 보안(RLS) |

PRD 7줄과 계획서 18줄에 적용했음. 표를 줄인 꼴로 둔 것은 PRD 3.8절 권한 표의 한 칸이 스물넉 자 늘면 칸이 세 배가 되기 때문임.

## 4. 「개발」과 「구현」을 구현으로 통일함

한 대상을 두 낱말로 부르고 있었음. PRD 6장 제목과 계획서 제목은 구현인데 본문의 단계 이름은 개발이었고, 단계 표기에 차수를 붙이면서 계획서가 개발 47곳이 됐음.

세어 본 결과 구현 계열이 77곳, 개발 계열이 114곳이었음. 작업량은 개발 쪽이 적었으나 **신 교수의 판단으로 구현을 택했음.** 구현이 코드 작성에만 국한되지 않고 DB와 배포와 검증까지 덮는다고 보았음. 노트 A와 B가 이미 전부 구현이라 그쪽과도 맞음.

- 저장소 넷에서 69줄, 노트 C에서 57곳을 고침
- 노트 A와 B는 손댈 것이 없었음. 개발 계열 표현이 0곳이었음
- 개발용 DB, 개발자 도구, 개발 서버, 개발 환경은 그대로 둠. 단계를 가리키는 말이 아님
- 노트의 코드 블록 여섯은 안 고침. 그때 보낸 프롬프트와 그때의 PRD 요약을 그대로 인용한 자리임

## 5. 노트 구조를 바꿈

안 2와 안 3은 「초안 두 토글을 어떻게 처분할지」였으나, 신 교수가 **「노트 작성을 계속하다가 초안에서 쓸 것이 있으면 가져다 쓴다」**로 방향을 바꿈. 처분 문제가 재료 문제가 되어 지금 결정할 것이 없어졌음.

바뀐 것은 이러함.

| 무엇 | 어떻게 |
|---|---|
| 5.3.7.4 신설 | 「확정된 구현 계획서」. 최종본 링크와 수정 이력 여섯을 담고 각 이력에 diff 링크를 검 |
| 5.3.7.3 c)의 산출물 링크 | `c5fa894`에서 `01c13ce`로. 작성 직후 검토 전 시점임 |
| 초안 두 토글 | 번호를 떼고 「(초안, 재료)」로 표시. 구분선 아래에 그대로 둠 |
| 5.3.8 | 「신규 앱의 단계별 구현」. 기본 개념 넷을 5.3.8.1에 a)~d)로 묶고, 5.3.8.2부터 구현 1~5단계가 이어짐 |

**노션 편집에서 사고가 한 번 났음.** 새 토글에 닫는 태그를 안 넣어 뒤쪽 전체가 한 단 안으로 들어갔고, 5.3.8과 5.3.9가 5.3.7의 자식이 되고 5.4가 5.3의 자식이 됐음. 되읽어서 발견했고 세 번에 나눠 복구했음. 글자가 사라진 자리는 없음.

**깃허브 앵커 링크를 200으로 확인한 것이 근거가 안 됐음.** 깃허브는 앵커가 없어도 200을 주므로, 실제로는 커밋을 원격에 안 올려 링크가 어긋난 것을 신 교수가 눌러 보고 발견했음. **앵커는 렌더된 HTML의 `id`를 봐야 판정됨.**

## 6. 추가 검토를 생략하기로 함

71번 4장이 열어 둔 항목임. 오늘 계획서가 다섯 차례 더 바뀌었으므로 다른 세션의 재검토를 열 수도 있었음.

**열지 않기로 함.** 이 앱은 수업 실습용이고 정해진 수업 시간 안에 구현까지 마쳐야 함. 검토 라운드를 한 번 더 돌리면 그만큼 실습 시간이 줄어듦. 오늘의 수정이 새 설계를 넣은 것이 아니라 이미 정해진 것의 낱말과 누락을 맞춘 것이라는 점도 함께 고려했음.

**대신 생략했다는 사실을 여기 남김.** 규격 결함이 구현 중에 드러나면 이 결정이 원인 후보임.
