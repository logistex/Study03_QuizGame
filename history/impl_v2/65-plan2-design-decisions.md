# 65번 — 2차 개발계획서를 쓰기 전에 정한 것

- 이 문서는 `spec/IMPL-PLAN-2.md`를 쓰는 프롬프트의 근거 문서다. PRD 개정에서 [55번](55-phase2-design-decisions.md)이 맡던 자리다
- **여기 적힌 것만 근거로 쓴다.** 대화에서 오간 기억은 근거가 아니다
- 규격이 아니다. PRD와 어긋나면 [`spec/PRD.md`](../../spec/PRD.md)가 맞다
- 대상 판본 — 커밋 `034099d`의 PRD([64번](64-prd-phase2-summary.md)에 요약)

## 1. 개발 단계는 다섯이다

| 단계 | 무엇 | 끝나면 화면에서 |
|---|---|---|
| 1 | 준비와 배포 골격 — Supabase, Vercel 연결, 빈 테이블과 정책, **첫 선생님 한 줄 넣기**, 지금 앱 그대로 배포 | 1차와 같은 앱이 Vercel 주소에서 돈다 |
| 2 | 인증 — 로그인, 역할 판정, 이름 입력 제거 | 로그인해야 게임이 시작된다 |
| 3 | 문항 이전 — 60문항 적재, 문항 서버 함수, 브라우저 로드 변경, 명령어 넷 수정, `questions.js` 삭제 | 문제가 서버에서 오고 정답이 브라우저에 없다 |
| 4 | 서버 채점과 순위 — 채점 함수, 응시 기록 저장, 순위표 서버 조회 | 점수가 서버에서 나오고 수강생 순위가 함께 보인다 |
| 5 | 선생님 화면 셋 — 문항 관리, 성적 관리, 설정 | 선생님이 화면에서 문항을 늘리고 성적을 보며 역할을 바꾼다 |

**고른 까닭 셋.**

- 매 단계 끝에 배포해 화면으로 확인할 것이 있다. 계층으로 자르면 중간 단계에서 볼 것이 없다
- 1단계가 배포 골격이라 조직 저장소 제약이나 요금제 문제를 첫 단계에서 만난다. PRD 4.1절 5번이 "배포 직전에 발견하면 되돌릴 시간이 없다"고 적은 자리다
- 순서 셋(DB 적재 → 명령어 넷 수정 → `questions.js` 삭제)이 3단계 안에 함께 들어가 그 사이에 문항 관리가 멈추지 않는다

**인증이 문항 이전보다 앞이다.** 문항을 먼저 옮기면 서버 채점까지 갈 수 있으나 누가 응시했는지 기록할 자리가 없어 되돌아온다.

## 2. 검증은 단계마다 셋, 마지막에 둘

단계마다 셋을 밟는다.

1. 완료 기준 대조
2. 배포 후 스모크 테스트 — 로컬에서 됐다는 것은 증거가 되지 못한다
3. **그 단계에서 새로 생긴 거절 확인** — 서버가 막아야 할 것을 실제로 막는가

셋째가 2차에서 붙는 것이다. 1차는 수동 체크리스트를 5단계에 몰았으나 2차는 그럴 수 없다. 권한 경계가 단계마다 새로 생기고, 막히는지는 화면이 정상으로 보이는 것과 무관하다.

| 단계 | 그 단계에서 확인할 거절 |
|---|---|
| 1 | 정책 없는 테이블이 잠기는가. 비밀 키가 저장소가 아니라 배포 설정에서 읽히는가 |
| 2 | 로그인 없이 시작이 막히는가. 역할이 다른 계정에서 화면이 갈리는가 |
| 3 | 문항 응답에 정답 열이 없는가. 규격에 어긋나는 문항이 넣는 시점에 거절되는가 |
| 4 | 브라우저에서 응시 기록을 직접 저장하면 거절되는가. 점수를 고쳐 보내도 서버 판정이 이기는가 |
| 5 | 학생 계정으로 문항 생성이나 역할 변경을 요청하면 거절되는가. 채택 전 문항이 DB에 안 들어가는가. 마지막 선생님을 내리는 요청이 거절되는가 |

마지막에 둘을 더 한다.

- PRD 4.1절과 노트 5.3.1의 한계를 하나씩 짚어 해소 여부를 대조한다
- 화면 전부를 지나는 전체 스모크

**문항 판정은 여기 들어가지 않는다.** 문항이 늘 때마다 도는 것이라 개발 단계와 주기가 다르다.

## 3. 인증과 역할

- **로그인은 깃허브 계정 하나로 한다.** 비밀번호를 우리가 다루지 않으므로 가입 화면이 필요 없다
- 이 수업의 학생은 저장소를 만들고 배포처에도 깃허브로 가입하므로 계정을 이미 갖는다. 구글은 동의 화면 설정이 붙어 실습이 무거워진다
- **역할은 사용자 테이블의 역할 열로 가른다.** 로그인한 사람의 깃허브 아이디로 그 줄을 찾는다
- **첫 선생님은 DB에 직접 넣는다.** 앱 안에서 만들 수 없다. 권한을 줄 사람이 아직 없기 때문이다
- **그다음부터는 선생님이 설정 화면에서 더하고 바꾸고 지운다.** 배포 설정을 열거나 다시 배포할 일이 없다
- **역할을 바꾸는 것은 서버 함수만 한다.** 브라우저가 역할 열을 쓸 수 있으면 학생이 자기를 선생님으로 바꾼다
- **마지막 선생님은 지우거나 강등할 수 없다.** 선생님이 0명이 되면 설정 화면에 들어갈 사람이 없어진다
- **이메일로 가르지 않는다.** 깃허브는 이메일을 비공개로 둘 수 있어 값이 비거나 `noreply` 주소가 온다. 아이디는 저장소 주소에 이미 들어 있어 수업에서 알기도 쉽다

**환경 변수에 목록을 두는 안을 물렸다.** 값을 바꾸려면 배포 설정 화면을 열고 다시 배포해야 하는데, 선생님이 앱 화면에서만 작업한다는 원칙과 어긋나고 배포를 줄이기로 한 것과도 부딪친다.

**브라우저가 보낸 역할을 믿지 않는다.** 선생님 전용 링크나 가입 시 체크박스는 통제가 되지 않는다. 링크는 숨겨지지 않고 체크는 브라우저가 보내는 값이다. PRD 3.8절이 점수 값을 두고 정한 것과 같은 자리다.

**학생이 자기 앱을 만들 때는 자기 아이디를 첫 선생님으로 넣는다.** 그러면 선생님 화면까지 확인할 수 있다.

## 4. 화면은 여덟이다

| 누가 | 화면 |
|---|---|
| 모두 | 로그인 |
| 학생 | 시작, 퀴즈 진행, 결과, 순위표 |
| 선생님 | 문항 관리, 성적 관리, 설정 |

**설정 화면은 사용자 목록과 역할 바꾸기를 담는다.** 처음에는 두지 않기로 했으나, 역할을 DB에 두고 앱에서 관리하기로 하면서 필요해졌다.

## 5. 선생님 문항 관리 화면

**명령어 넷을 화면에서 부른다.** 규격이 이미 명령어 안에 있으므로 화면은 인수를 받는 자리만 만든다.

| 자리 | 무엇 |
|---|---|
| 목록과 분포 | `quiz-stats` |
| 생성 요청 | `quiz-add`. **용례를 보여 주고 자연어로 받는다** |
| 판정 | `quiz-validate` |
| 하루치 | `quiz-daily`. 버튼 하나, 값은 아래에 미리 정한다 |
| 고치기 | 문항, 선택지, 해설 모두 |
| 지우기 | 문항 삭제 |
| 이력 | 생성 요청 단위로 되돌아보기 |

**고친 문항은 생성된 문항과 같은 관문을 지난다.** 수정 → 데이터 검사 → 판정 → 선생님 채택. 고치면서 규격을 깰 수 있기 때문이다.

**이미 응시 기록이 쌓인 문항을 고치면 과거 기록의 뜻이 달라진다.** 점수는 그대로이나 무엇을 틀렸는지가 바뀌어 대시보드의 "많이 틀린 문항"이 흔들린다. 이 관계를 어떻게 둘지는 계획서에서 정한다.

**자연어를 그대로 받으므로 역할 검사가 실질적인 방벽이다.** 임의 문자열이 API 프롬프트로 들어간다. 5단계 거절 확인에 학생 계정 호출이 막히는지가 들어간다.

### `quiz-daily` 버튼의 고정값

버튼은 인수를 받지 않으므로 값을 미리 정한다. **화면에 이 값을 안내한다.**

| 값 | 무엇 |
|---|---|
| 대상 카테고리 | 문항이 가장 적은 카테고리 하나 |
| 넣을 개수 | 5 |
| 난이도 | 그 카테고리에서 모자란 쪽을 채운다 |
| 정답 인덱스 | 치우친 값을 피한다 |
| 동률이면 | 카테고리 `id` 순으로 앞선 것 |

버튼 한 번이 도는 것은 셋이다 — 다섯 문항 생성, 판정, 분포 표시.

**카테고리당 문항 수 상한은 30이다.** 상한에 닿으면 버튼이 멈추고 알린다. PRD 8.3절이 미정으로 둔 "문제은행 확대를 어디서 멈출 것인가"가 이 값으로 닫힌다.

## 6. 판정 라운드를 앱에서 어떻게 두나

PRD와 계획서는 판정을 **서로 다른 세션 둘이 각각 한 번씩** 돌라고 정했다. 앱 안에는 세션이 없으므로 그대로 옮길 수 없다. 노트 5.3.9.2가 미정으로 둔 자리다.

규칙의 핵심은 둘이었다.

| 무엇 | 앱에서 |
|---|---|
| 쓴 쪽이 판정하지 않는다 | **지킬 수 있다.** 생성 호출과 판정 호출을 나누고 판정에 생성 맥락을 주지 않는다 |
| 재현되지 않으니 두 번 돈다 | **형식만 남는다.** 같은 모델을 같은 프롬프트로 두 번 부르는 것은 서로 다른 세션이 아니다 |

**그래서 이렇게 정한다.**

- 앱 안에서는 판정을 한 번 돌리되 생성 맥락을 끊는다
- 두 번째 라운드는 사람이 맡는다. 선생님이 판정 결과를 보고 채택하는 자리가 그것이다
- 문제은행을 크게 늘릴 때는 지금처럼 세션 둘이 도는 경로를 남긴다

**이것은 규격을 한 칸 무르는 결정이다.** 계획서에 그 사실을 적는다.

## 7. 대시보드

- 차트를 넣는다. **다만 라이브러리를 쓰지 않는다.** PRD 4절이 웹 폰트와 CDN을 쓰지 않기로 했고, 막대는 요소 너비로 추세는 인라인 SVG로 그릴 수 있다
- 항목은 카테고리별 정답률, 점수 추세, 많이 틀린 문항
- 성적 관리 화면에서 학생 하나를 짚어 들어가는 자리를 둔다

## 8. 단계별 배포본을 어떻게 남기나

**1차의 방식을 그대로 쓸 수 없다.** `gh-pages`에 폴더를 만들어 여섯 주소를 영구히 남겼으나 Vercel에는 그에 해당하는 자리가 없다.

무료 요금제의 보존은 30일이고 Hobby는 이 값을 늘릴 수 없다. 예외로 최근 배포 10개, 상태가 Ready인 최근 프로덕션 20개, 별칭이 붙은 배포 등이 남는다. 곧 **배포 횟수에 따라 앞 단계가 밀려날 수 있고, 그 갈림이 학기 중 배포 횟수에 달려 있다.**

**배포 횟수를 줄여 예외 안에 들어가게 한다.** 두 가지를 함께 쓴다.

| 무엇 | 어떻게 |
|---|---|
| 단계 작업을 브랜치에서 한다 | `main` 병합은 단계를 마칠 때 한 번만 한다. 프로덕션 배포가 단계마다 하나씩 다섯이 된다. 중간 작업은 프리뷰로 생기고, 프리뷰는 보존 예외가 따로 스물이라 프로덕션 다섯을 밀어내지 않는다 |
| 소스가 안 바뀐 커밋은 배포하지 않는다 | 이 저장소는 소스와 문서가 같은 `main`에 있어 문서만 고쳐도 배포가 생긴다. 빌드 건너뛰기 설정으로 거른다 |

**둘을 같이 써야 한다.** 브랜치만 쓰면 문서 커밋이 배포를 만들고, 건너뛰기만 쓰면 단계 안의 소스 커밋마다 배포가 쌓인다.

**건너뛰기는 배포처 설정에 조건 한 줄을 넣는 일이다.** 코드가 아니라 설정이며, 종료 코드가 0이면 건너뛰고 1이면 배포한다.

```bash
git diff --quiet HEAD^ HEAD -- index.html style.css script.js api/ vercel.json
```

- 소스 넷과 `api/`가 안 바뀌면 배포하지 않는다. 나머지는 문서다
- **조건을 반대로 두면 아무것도 배포되지 않는다.** 1단계 완료 기준에 "문서만 고친 커밋은 배포가 안 생기고 소스를 고친 커밋은 생긴다"를 넣는다
- 프로덕션 배포는 단계마다 하나씩 다섯이 된다. 브랜치에 올릴 때 생기는 프리뷰는 따로 세므로 다섯을 밀어내지 않는다

- 단계마다 그 시점 배포 주소를 README에 적는다
- 오래 남겨야 하는 것은 태그다. 소스는 태그로 보존되고 사라지지 않는다
- 별칭을 붙여 보존하는 길이 있으나 도메인이 필요해 수업에는 무겁다

확인한 자리 — <https://vercel.com/docs/deployment-retention>, <https://vercel.com/docs/functions/limitations>

**함수 실행 시간은 걱정할 자리가 아니다.** Hobby 최대 300초다. 문항 다섯 생성과 판정을 한 요청에 담아도 여유가 있다.

## 9. 계획서가 정할 것

여기서 정하지 않는다. PRD가 `spec/IMPL-PLAN-2.md`를 가리키는 자리들이다.

- 브라우저가 DB를 조회하는 방법 — 클라이언트 라이브러리인가 `fetch`인가
- 서버 함수를 몇 개 파일로 나누고 이름을 무엇으로 할지
- 순위 저장과 조회 함수의 계약
- 순위표 하단 안내 문구와 저장 실패의 상태 구분
- 한 생성 요청이 만든 문항을 묶는 방법 — 요청 테이블인가 요청 식별자인가
- 개발용 저장과 수업용 저장을 어떻게 나눌지
- 데이터 검사 항목을 각각 어느 시점에 둘지
- 고친 문항과 과거 응시 기록의 관계
- 사용자 테이블의 "아이디"가 무엇인가 — 깃허브 아이디인지 인증 서비스가 주는 식별자인지. 로그인한 사람을 그 줄과 맞추는 열이다

## 10. 연습 응시

**시작 화면에 모드를 둔다.** 연습으로 고르면 서버가 채점은 하되 응시 기록을 저장하지 않는다.

- 별도 링크로 가르지 않는다. 주소는 숨겨지지 않고, 숨길 까닭도 없다
- 학생도 쓴다. 시연 기록이 순위표에 남지 않게 하는 것이 첫 목적이나 연습 자체의 가치가 크다
- **기록 삭제 기능을 두지 않는다.** 연습 모드가 대부분을 덜어 낸다. 실수로 정식 응시한 것은 남으나 빈도가 낮다

## 11. 아직 열려 있는 것

- **없다.** 남은 것은 계획서가 정할 자리(9절)다
