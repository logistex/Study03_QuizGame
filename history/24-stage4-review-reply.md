## 1. 재현해 확인한 것

한 판도 하지 않은 상태에서 `Storage.prototype.setItem`만 예외를 던지게 만들고 "순위표 보기"를 열었다.

| 확인 | 고치기 전 |
|---|---|
| `readRankings()`가 `null`인가 | **아니다.** 정상 객체를 돌려준다 |
| 표가 감춰지는가 | 감춰지지 않는다. 다섯 표를 그린다 |
| "기록 지우기"가 감춰지는가 | 감춰지지 않는다 |
| 저장 불가 안내가 보이는가 | **보이지 않는다** |

지적 그대로다. 게다가 다섯 표에 모두 `아직 기록이 없습니다.`가 떠서, 저장이 아예 안 되는 상태가 "아직 안 해서 비어 있다"로 보인다.

**요청서 3.2절에 "`getItem`은 살아 있어서 `readRankings()`가 `null`이 되는 경로는 확인하지 못했다"고 적어 놓고도, 그 문장이 결함을 가리키고 있다는 것을 못 봤다.** 확인하지 못한 것을 적는 것과 그것이 무엇을 가리는지 보는 것은 다른 일이었다.

## 3. 항목별

### 3.1 조치 1 — 쓰기 가능 여부를 따로 판정한다. 단 "기록 지우기"는 감추지 않는다

읽기와 쓰기를 따로 본다. 순위 기록을 건드리지 않도록 별도 키로 시험하고 곧바로 지운다.

```javascript
function canWriteRankings() {
  try {
    localStorage.setItem(PROBE_KEY, '1');
    localStorage.removeItem(PROBE_KEY);
    return true;
  } catch (error) {
    return false;
  }
}
```

`renderRankingScreen`의 분기가 셋이 되었다.

| 상태 | 표 | 기록 지우기 | 안내 |
|---|---|---|---|
| 정상 | 보임 | 보임 | 감춤 |
| 읽기는 됨, **쓰기만 막힘** | **보임** | **보임** | **보임** |
| 읽기까지 막힘 | 감춤 | 감춤 | 보임 |

**가운데 줄에서 "기록 지우기"를 감추지 않은 것이 처방과 다른 부분이다.**

- 쓰기가 막히는 흔한 원인 하나가 **용량 초과**인데, 그때 "기록 지우기"는 눌러도 소용없는 버튼이 아니라 **그 상황을 푸는 유일한 수단**이다. `removeItem`은 공간을 비우는 방향이라 `setItem`이 막힌 상태에서도 대개 동작한다
- 원래 감춤의 근거는 "지울 것이 없는 상태에서 버튼만 남으면 눌러도 아무 일이 없어 고장으로 보인다"였다. 그 근거는 **읽기까지 막혀 기록 자체가 없는 경우**에 성립한다. 읽기가 되는 경우에는 지울 기록이 실제로 있다
- 표를 감추지 않은 이유도 같다. 기존 기록은 진짜 데이터이므로 보여 주는 것이 맞다

요구하신 두 조건은 그대로 만족한다.

- 한 판도 안 한 사용자가 순위표를 열면 안내가 보인다
- 저장이 되는 정상 상태에서는 안내가 보이지 않는다

### 3.2 조치 3 — 1번이 아니라 4번을 고쳤다

완료 기준 1번을 "기록이 쌓인 상태"로 바꾸면 **빈 순위표에서의 경로가 사라진다.** 첫 판은 첫 판대로 `순위표 1위 진입`과 인덱스 0 강조를 지난다.

그래서 원래 두 번째 판을 다루던 4번을 고쳤다.

> 4. **기록이 쌓인 상태에서 낮은 점수로 한 판을 끝까지 푼다** → 강조된 줄이 정확히 하나이며 그 줄이다. 콘솔로 대신하지 않는다. 1번은 빈 순위표라 강조가 언제나 인덱스 0이고, **인덱스 0이 아닌 강조를 지나는 경로는 이 항목뿐이다.**

두 항목이 각각 다른 경로를 덮게 되었다.

### 3.3 조치 4 — 규칙으로 세웠다

계획서 4단계에 넣었다.

> **콘솔 대체를 허용하는 자리에는 그 대체가 건너뛰는 경로를 함께 적는다.**
> 무엇을 콘솔로 대신할 수 있는지만 적으면, 대신하는 순간 무엇이 확인되지 않는지가 남지 않는다. 그 빈틈은 나중에 우연히 발견되거나 발견되지 않는다.

이번 자리에서 건너뛴 것이 `finishGame`의 뒷부분(`renderResult`와 화면 전환)이라는 것도 함께 적었다.

### 3.4 조치 5 — 근거가 뒤집혔다는 지적을 받는다

> 계약은 코드를 위해 있는 것이지 그 반대가 아니다

맞는 말이다. 계약을 지키려고 입력란을 게임 상태의 통로로 쓴 것이 거꾸로였다.

```javascript
function startGame(mode, categoryId, playerName) {
  const name = playerName === undefined ? readPlayerName() : playerName;
```

- 기존 호출부 둘은 그대로다
- **입력란을 비운 채 "다시 도전"을 눌러도 직전 판의 이름으로 시작하는 것을 확인했다.** 고치기 전에는 입력란 값에 끌려갔다

### 3.5 조치 6 — `th.scope = 'col'`

붙였다. 네 열 모두 `scope="col"`이 들어가는 것을 확인했다.

## 4. 확인

고친 뒤 세 상태를 각각 확인했다.

```
정상          안내 감춤, 표 보임, 지우기 보임
쓰기만 막힘    안내 보임, 표 보임, 지우기 보임
읽기도 막힘    안내 보임, 표 감춤, 지우기 감춤
```

- 시험용 키(`quizGameStorageProbe`)가 저장소에 남지 않는 것도 확인했다
- 이름 미입력 방어, 전 범위 도전, 한 판 완주, 다시 도전까지 다시 밟아 회귀가 없는 것을 보았다

체크리스트에도 두 줄을 더했다. **`setItem`만 막아서는 감춤 분기가 한 번도 실행되지 않는다**는 사실을 항목 안에 적어 두었다.

## 5. 8절의 스크린리더 대목

검토 측이 정정을 보내 왔고 그대로 받는다.

- 스크린리더 확인은 **이미 통과**로 끝나 19번 3.2절에 기록되어 있다. 판정과 해설이 둘 다 읽혔다
- 따라서 5단계를 기다릴 이유가 없고, PRD 3.2절과 4.3절을 열 일도 없다. 20번의 (나) 판단은 발동하지 않는다
- 2, 3단계 조치 5(`aria-label` 부여)는 "읽힌다" 경로로 확정되어 이미 반영되어 있다(`17b169a`)

**덧붙인 지적 하나가 열려 있다.** 확인 환경이 VoiceOver와 Chrome 하나뿐이고, macOS에서 VoiceOver와 가장 흔히 짝지어 쓰이는 **Safari가 확인되지 않았다.** PRD 4절이 Safari를 지원 브라우저로 명시하고 있고, 판정 표가 "스크린리더마다 갈리면 안 읽힌다"를 담고 있으므로 짚어야 하는 것이 맞다.

- 같은 기기에서 브라우저만 바꾸면 되므로 비용이 거의 없다
- **확인 중이다.** 결과가 나오는 대로 따로 알린다
- 안 읽히면 `role="status"` 경로로 가야 하고, 그때는 규격 동결 판단이 다시 살아난다
- NVDA는 Windows가 필요해 별개 문제라는 판단에도 동의한다

## 6. 되묻는 것 하나 — 하단 고정 안내

23번 2절이 이 문장을 지목했다.

> 기록은 이 브라우저에만 저장되며, 브라우저 정책에 따라 사라질 수 있습니다.

- 다만 **계획서 4.5절이 "마크업에 고정으로 두고 늘 보인다"고 적고 있어** 이 문서를 쓰는 시점에는 손대지 않았다
- **저장 불가일 때 이 문장을 감추는 편이 나은가.** 그렇다면 계획서 4.5절 한 줄을 함께 고쳐야 한다
