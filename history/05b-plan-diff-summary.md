# 구현 계획서 개선점

## 개요

- 대조: 최초본(2026-08-12 22:27, 778줄) ↔ 반영본(`ff95ac5`, 805줄)
- 방법: 두 판본 전문 diff. 추가 48줄, 삭제 20줄
- 변경은 전부 합의 12건으로 추적된다. 합의 밖 수정이나 문구 손질이 섞이지 않았다

## 죽은 코드가 사라졌다

- 상태 객체에서 `answered` 필드를 삭제했다. 최초본은 필드를 정의하고 `handleAnswer`가 읽었으나 대입하는 곳이 없었다
- 가드가 늘 `false`를 읽어 무효였고 실제 방어는 `disabled`가 하고 있었다. 증상이 없어 체크리스트까지 통과하는 종류였다
- `handleAnswer` 단계가 9개에서 8개로 줄었다
- 제거로 끝내지 않고 왜 필요 없는지와 성립 전제를 함께 남겼다. 선택지가 진짜 `<button>`일 때만 성립하며 `<div>`에 `aria-disabled`만 걸면 클릭이 그대로 발생한다

## 검증이 실제로 결함을 잡게 됐다

가장 큰 변화다. 통과해도 아무것도 보증하지 못하던 항목 둘이 고쳐졌다.

R2 — `answer` 갱신

- 최초본은 "정답 텍스트가 적힌 버튼을 눌러 정답 판정을 확인"이었다. `answer`가 틀려도 반드시 통과한다. 강조와 피드백이 같은 잘못된 값을 보기 때문이다
- 반영본은 콘솔 한 줄로 열 문제를 원본과 일괄 대조한다. 실패했을 때 어느 문제인지 찾는 방법까지 적었다
- 검사 범위도 1문제에서 10문제로 넓어졌다

R3 — 인덱스를 객체 참조로 찾기

- 최초본은 두 항목이 서로 모순이었다. 한쪽은 실행으로 판정되지 않는다고 하고 다른 쪽은 실행으로 판정하라고 했다
- 반영본은 세 항목으로 나누고 각각 무엇을 잡는지 라벨을 달았다

| 항목 | 잡는 결함 | 판정 수단 |
|---|---|---|
| R3 | 이름 대조로 인덱스를 찾는 구현 | 코드 확인만 |
| PRD 3.4절 | 같은 이름 기록을 합치거나 갱신하는 구현 | 실행 |
| 렌더링 계약 | `highlightIndex`를 무시하고 강조하는 구현 | 실행 |

- 제목에 "실행 검증 없음, 코드 확인 필수"를 넣어 착각을 막았고, 실패 원인이 셋 중 어디인지 체크리스트에서 바로 읽힌다

## 검증 부담이 줄었다

- 4단계 순위표 검증이 11판 110문제 수동 풀이를 요구했다. 정렬, 자르기, 미진입 판정은 저장 함수만 지나가므로 콘솔 호출로 대체할 수 있게 됐다
- 줄이면 안 되는 것을 함께 판단했다. 완료 기준 1번은 실제 플레이로 남겼다. `finishGame`의 전체 경로를 지나는 것이 그것뿐이기 때문이다

## 명세의 구멍이 메워졌다

구현자가 스스로 판단해야 했던 네 자리가 확정됐다.

- `startGame` — `state` 초기화 → 문제 뽑기 → `showScreen` → `renderQuestion` → 이탈 경고 순서. 뒤집으면 초점이 제목에 남아 PRD 4.3절 요구가 깨진다
- `pickCategoryQuiz` — `category` 객체를 `CATEGORIES.find`로 얻는다
- `renderResult` — 순위표 목록은 `readRankings()`를 다시 불러 얻는다
- 2단계 — 순위표 열기, 닫기 핸들러의 이벤트 바인딩이 2단계 몫임을 명시했다

## 판단 근거와 예방이 문서에 남았다

- `renderResult`에 "저장 함수가 `{ index, list }`를 돌려주면 읽기를 아낄 수 있지만 PRD 3.4절 계약을 바꾸지 않는다"를 적었다. 구현 편의로 PRD를 조용히 바꾸는 것을 막는 기록이다
- 색 대비는 검증이 5단계지만 색을 정하는 것은 3단계다. 3단계에 사전 확인을 넣어 재작업 경로를 없앴다
- 경로를 고쳤는데도 404가 이어지면 Pages의 CDN 캐시를 먼저 배제하라고 적었다
- 1단계 원상 복구 확인을 눈 대조에서 `git diff`가 비어야 한다는 기준으로 바꿨다
- 방어가 `disabled` 하나로 줄면서 그 전제를 체크리스트로 승격했다. 요소가 `<button>`인지, 정답 버튼의 글자 부분을 정확히 눌러도 점수가 변하지 않는지
