## 2. 정정 — 스크린리더 낭독에 대한 내 1차 권고가 과했다

요청서의 첫 번째 항목이 정확히 내 오판을 겨눈다. 먼저 적는다.

### 무엇을 잘못 적었나

1차 검토 의견서(필수 수정 7)에서 이렇게 썼다.

> 초점을 옮기면 스크린리더가 그 내용을 읽으므로 `aria-live` 없이 전달된다

**이 단언이 지나쳤다.** 현재 `#feedback`은 `role`도 접근 가능한 이름도 없는 `<div tabindex="-1">`이고, 자식으로 `<p>` 둘을 갖는다. 이 형태에 초점을 옮겼을 때

- 스크린리더가 요소의 접근 가능한 이름을 읽는데, 이 요소에는 이름이 없다
- 자식 문단 둘을 이어서 읽는지는 **구현마다 다르다.** 읽는 것도 있고 건너뛰는 것도 있다
- 즉 낭독이 보장되지 않는다

구현 측이 "초점만 옮겨 놓고 낭독이 안 되면 채점 결과가 전달되지 않는다"고 우려한 것이 맞다.

### 검토하지 않은 선택지

당시 `aria-live`를 물린 근거는 "라이브 영역과 초점 이동을 같은 타이밍에 쓰는 것은 알려진 안티패턴"이었다. 그 지적 자체는 맞다. 그러나 거기서 **초점 이동을 없애고 라이브 영역 하나만 두는 쪽**을 충분히 검토하지 않고 반대쪽을 골랐다.

| 조합 | 성격 |
|---|---|
| 라이브 영역 둘 + 초점 이동 | v2의 상태. 안티패턴이 맞다 |
| 라이브 영역 없음 + 초점 이동 | 지금 상태. 낭독이 보장되지 않는다 |
| **라이브 영역 하나 + 초점 이동 없음** | 검토하지 않았다. 이런 경우의 표준에 가깝다 |

### 확인과 대응

나는 스크린리더를 실행할 수 없다. 요청대로 VoiceOver나 NVDA로 확인이 필요하다. 확인할 것은 셋이다.

- 답을 고른 뒤 판정과 해설이 **둘 다** 읽히는가
- 화면을 전환할 때 제목이 읽히는가
- 새 문제를 그릴 때 문제 텍스트가 읽히는가

결과에 따라 대응이 갈린다.

**읽힌다면** 지금 구조를 그대로 두되, 접근 가능한 이름을 붙여 두기를 권한다. 이름이 없는 초점 대상은 구현이 바뀌면 조용히 낭독을 잃는다.

```html
<div class="feedback" id="feedback" tabindex="-1" aria-label="채점 결과" hidden></div>
```

**읽히지 않는다면** PRD 3.2절과 4.3절을 되돌려야 한다. `#feedback`에 `role="status"` 하나를 주고 초점 이동을 없애는 형태다. 스크롤은 그대로 두어 "다음 문제" 버튼이 화면에 들어오게 한다.

- 이 경우 계획서 3단계 체크리스트의 "답을 고르면 초점이 `#feedback`에 있다"와 R5(`aria-live` 부재 확인)도 함께 바뀐다
- **PRD를 되돌리는 판단이 필요해진 것은 내 오판에서 비롯됐다.** 규격 변경 자체를 주저할 이유로 삼지 말기 바란다

## 3. 새로 찾은 것

### 3.1 퀴즈 화면 진입 시 초점이 두 번 이동한다 — 명세 위반

```
startGame → showScreen('screen-quiz')  →  #quiz-title 에 초점
          → renderQuestion()           →  #question-text 에 초점
```

PRD 4.3절은 이렇게 적혀 있다.

> 화면을 전환하면 제목으로, 문제를 새로 그리면 문제 텍스트로, 답을 고르면 피드백 영역으로 초점을 옮긴다. **퀴즈 진행 화면에 들어갈 때는 두 규칙이 겹치므로 제목을 건너뛰고 첫 문제 텍스트로 옮긴다.**

- 구현은 제목을 **거쳐서** 간다. 건너뛰지 않는다
- 최종 상태는 `#question-text`라 화면과 콘솔로는 판정되지 않는다. `document.activeElement` 확인도 통과한다
- 스크린리더는 "퀴즈 진행"을 읽기 시작했다가 끊기고 문제를 읽는다. 2절과 같은 성격의 문제다
- 다른 세 화면은 초점이 한 번만 이동한다. 퀴즈 화면만 겹친다

고치는 방법은 `showScreen`에 초점 대상을 넘길 수 있게 하는 것이다.

```javascript
function showScreen(screenId, focusTarget) {
  document.querySelectorAll('.screen').forEach(function (section) {
    section.hidden = section.id !== screenId;
  });
  (focusTarget || document.querySelector('#' + screenId + ' .title')).focus();
}
```

`startGame`은 화면을 드러낸 뒤 `renderQuestion()`이 초점을 잡게 하고, `showScreen`에는 초점을 옮기지 말라고 알리는 형태가 더 단순할 수도 있다. 어느 쪽이든 **제목에 초점이 한 번 갔다 오는 경로만 없애면 된다.**

### 3.2 포트를 바꾸면 `localStorage`가 분리된다 — 4단계에 들어가기 전에

판단 요청 4번에 대한 답인데, 개발 편의 문제로 끝나지 않는다.

- `localhost:8000`과 `localhost:8765`는 **오리진이 다르다.** `localStorage`가 완전히 별개다
- 3단계까지는 저장을 쓰지 않아 무해했다
- **4단계는 순위 저장이 핵심이다.** 포트를 바꾼 뒤 순위표를 열면 앞서 쌓은 기록이 보이지 않는다. "저장이 안 된다"로 오진하기 쉽다
- 완료 기준 5번("새로고침하고 순위표 보기 → 앞서 만든 기록이 그대로 있다")이 포트를 바꾸는 순간 거짓으로 실패한다

**포트를 고정하고 캐시는 다른 방법으로 무력화하기를 권한다.**

- 개발자 도구 Network 탭의 "Disable cache". 도구가 열려 있는 동안만 적용된다
- 또는 하드 리로드(`Cmd+Shift+R`, `Ctrl+Shift+R`)
- PRD 4.1절이 적은 `8000`으로 고정하면 문서와도 맞는다

## 4. 확인하지 못한 넷에 대한 의견

### 1. 스크린리더 낭독 — 2절을 볼 것

### 2. 키보드 활성화 — 코드상 이상 없음

- 선택지는 `<button type="button">`이고 커스텀 키 핸들러가 없다. `Enter`와 `Space`는 브라우저가 클릭을 합성하므로 `click` 리스너가 그대로 걸린다
- 자동화 도구가 합성하지 못한 것은 도구의 한계이지 코드 문제가 아니다
- **함께 확인할 것**: 답을 고르면 선택지 넷이 `disabled`가 되어 탭 순서에서 빠진다. 이때 초점은 `#feedback`에 있으므로 `Tab` 한 번에 `#btn-next`에 닿아야 한다. 설계 의도가 그것이므로 함께 보면 좋다

### 3. 이탈 경고 확인창 — 코드 형태는 표준

```javascript
function handleBeforeUnload(event) {
  event.preventDefault();
  event.returnValue = '';
}
```

- 지금 브라우저가 요구하는 형태다
- `beforeunload`는 페이지와 한 번이라도 상호작용해야 동작하는데(sticky activation), 판을 시작하려면 버튼을 눌러야 하므로 충족된다
- 등록과 해제 지점이 각각 한 곳, 두 곳인 것도 확인했다. 남은 것은 실제로 뜨는지 보는 일뿐이다

### 4. 모바일 스크롤 — 코드상 이상 없음

- `next.scrollIntoView({ block: 'end' })`로 버튼을 아래쪽에 맞춘다
- `goNext`의 `screen-quiz.scrollIntoView({ block: 'start' })`로 위로 되돌린다
- `renderQuestion`의 `focus()`가 이미 스크롤을 일으켜 두 번 스크롤되지만 최종 위치는 상단이라 무해하다
- 실기기 확인만 남았다

## 5. R1 검증 방법 — 불안이 옳았다

"최대 연속 길이로 우연히 3이 나온 판과 최종 섞기가 빠진 판을 가를 수 있는가"를 물었다. 20만 판을 모의해 세 지표를 비교했다.

| 지표 | 최종 셔플 없음 | 최종 셔플 있음 |
|---|---|---|
| 최대 연속 | 항상 3 | 3이 나올 확률 **12.6%** |
| 인접 동일쌍 | 항상 6 | 6이 나올 확률 **0.1%** |
| 블록 수 | 항상 4 | 4가 나올 확률 **0.1%** |

- **최대 연속은 한 판으로 판별할 수 없다.** 셔플이 있어도 12.6% 확률로 3이 나온다. 실제로 다섯 판 중 둘에서 3이 나왔는데, 그 자체로는 아무것도 말해 주지 않는다
- 다섯 판을 반복한 것이 이를 메웠다. 셔플이 있는데 다섯 판 모두 최대 연속이 3일 확률은 약 3만분의 1이다. **결론은 신뢰할 수 있다**
- 다만 **블록 수를 쓰면 한 판으로 1000분의 1**이다. 셔플이 빠지면 값이 정확히 4로 고정되므로 "4면 의심"이라는 판정선도 명확하다

```javascript
// 블록 수 — 셔플이 빠지면 정확히 4가 나온다
state.quiz.map(q => q.categoryName).filter((c, i, a) => i === 0 || c !== a[i - 1]).length
```

R2와 R5의 확인 방법에는 빈틈이 없다. R2를 원본과 대조한 것, 같은 문제를 스무 번 준비해 열네 가지 배열이 나온 것을 함께 본 것이 특히 좋다.

## 6. 판단 요청 4건

| # | 판단 | 근거 |
|---|---|---|
| 1 | `outline: none` — **맞다** | `tabindex="-1"`은 `Tab`으로 도달할 수 없어 WCAG 2.4.7의 대상이 아니다. 제목에 초점 테두리가 그려지면 시각 사용자가 오히려 혼란스럽다. `#feedback`도 `Tab` 한 번에 `#btn-next`로 빠져나가므로 초점 위치를 잃는 시간이 짧고 예측 가능하다 |
| 2 | `opacity: 1` — **맞다** | 답한 뒤에도 선택지를 읽어야 하므로 흐리게 하면 안 된다. `disabled` 속성은 스크린리더에 그대로 전달되므로 보조기술에는 영향이 없다. `cursor: default`로 마우스 사용자에게 신호를 준 것도 적절하다. 답하지 않은 두 오답이 답 전과 같아 보이지만, 정답 강조와 "다음 문제" 버튼 등장으로 상태 변화가 충분히 드러난다 |
| 3 | 색 대비 사전 측정 — **맞다. 단 범위 조건이 붙는다** | 아래 |
| 4 | 포트 — **3.2절을 볼 것** | 개발 편의가 아니라 4단계 검증을 깨뜨리는 문제다 |

### 3번의 범위 조건

- 3단계에서 잰 색(난이도 배지 3종, 정답 초록, 오답 빨강)은 **다시 잴 필요가 없다.** 값이 바뀌지 않았는지만 확인하면 된다
- 다만 **4단계에서 순위표 강조 줄 색이 새로 생긴다.** 그건 3단계에서 잰 적이 없으므로 5단계에서 재야 한다
- 5단계 체크리스트를 지우지 말고, "이미 잰 것은 변경 여부만, 새로 생긴 것은 새로 잰다"로 읽으면 된다
