# 40문항 외부 출처 검증 보고

- 대상: `questions.js` 40문항
- 방법: 서브에이전트 10팀, 4문항씩 분담. 문항마다 서로 다른 도메인의 외부 출처 2곳 이상 대조
- 작성: 구현 세션
- 원자료: `doc/verify/batch-01.md` ~ `batch-10.md` (저장소에는 올리지 않는다)

## 0. 이 검증의 범위 — 먼저 밝힌다

**이것은 `/quiz-validate`를 돌린 결과가 아니다.** 그 명령어가 정한 절차 가운데 3절만 수행했다.

| `quiz-validate` 절차 | 이번에 했나 |
|---|---|
| 1절 자동 검사 — Node로 `validateData()` 실행 | 아니오 |
| 2절 정답이 하나로만 읽히는가 | 예 |
| 2절 최상급 표현에 재는 기준이 있는가 | **계통적으로는 아니오** |
| 2절 시점과 범위가 한정되어 있는가 | **계통적으로는 아니오** |
| 2절 선택지 위치를 지칭하지 않는가 | 아니오 |
| 2절 해설이 근거를 대는가 | 아니오 |
| 2절 12번 문서의 교차 검증 관점 | 아니오 |
| 3절 외부 출처 2곳 이상 사실 확인 | 예 |
| 4절 파일을 직접 고치지 않는다 | 예 |

각 팀에 준 지시는 셋이다. 정답이 맞는가, 해설의 사실이 맞는가, 다른 보기도 답이 되는가.

**그래서 아래 3.2절과 3.3절의 지적은 계통적 점검의 결과가 아니다.** 해당 배치에만 확인할 지점을 힌트로 넣었기 때문에 걸린 것이다. 같은 종류의 결함이 힌트를 주지 않은 문항에도 있을 수 있고, 이번 검증은 그것을 보지 못한다. `/quiz-validate`를 온전히 돌리는 일은 따로 남는다.

## 1. 총평

- **정답이 틀린 문항은 0건이다.** 40문항 모두 `options[answer]`가 실제 정답이고, 다른 보기가 답이 되는 경우도 없다
- **해설이 틀린 것 1건**을 찾았다. `sc_05`다
- **재는 기준이 빠져 규격에 어긋나는 것 2건**을 찾았다. `ge_01`, `ge_04`다
- 단서를 더하는 편이 나은 것 3건, 손댈 필요 없는 통용 표현 3건이 함께 나왔다

8번 문서에서 검토 측이 기억으로 40문항을 대조해 "사실 오류 0건"으로 닫았다. **외부 출처를 대니 사실 오류 1건과 규격 위반 2건이 나왔다.** 기억끼리의 대조와 출처와의 대조가 갈리는 지점이 여기다.

## 2. 근거 주석은 값을 했다

`// 근거:` 주석을 달아 둔 다섯 문항은 **전부 주석에 적은 판단대로 확인됐다.**

| id | 주석이 적어 둔 판단 | 확인 결과 |
|---|---|---|
| `kh_07` | 문항이 "지은 사람"을 물으므로 저술 완성(1610) 기준 | 1596년 착수, 1610년 완성, 1613년 간행. 주석대로 맞다 |
| `kh_09` | 문항이 "반포한 왕"을 물으므로 시행(1485, 성종) 기준 | 세조가 1467년 완성했으나 이듬해 사망해 반포하지 못했고, 1485년 성종 때 을사대전이 반포, 시행됐다 |
| `sc_10` | 프랭클린 기여 평가는 정착했으나 발표자로는 왓슨과 크릭이 표준 서술 | 최신 서술이 갈리는 것까지 확인됐고, 보기 구성상 문제는 없다 |
| `ge_02` | 2020년 중국, 네팔 공동 재측량치 | 2020-12-08 공동 발표 8,848.86m |
| `ac_10` | 문항이 "작곡한"을 물으므로 작곡(1876) 기준 | 1875년 여름 착수, 1876년 4월 총보 완성, 초연은 1877년 3월 4일 |

주석이 무엇을 근거로 삼았는지 드러내 두었기 때문에, 검증하는 쪽이 **어디를 검산해야 하는지 바로 알 수 있었다.** 주석이 근거의 정확성을 보증한 것이 아니라 검산 지점을 표시한 것인데, 그것이 이번에 실제로 작동했다.

## 3. 지적 9건

### 3.1 해설이 틀린 것 — 1건, 고쳐야 한다

**`sc_05`** 소리가 가장 빠르게 전달되는 물질의 상태

- 지금: "소리는 입자가 촘촘히 붙어 있을수록 빠르게 전달되므로 고체에서 가장 빠르다."
- 실제: 음속은 `v = √(탄성률/밀도)`로 정해진다. 밀도만 커지면 오히려 느려진다. 납은 강철보다 밀도가 크지만 음속은 느리다
- **결론("고체가 가장 빠르다")은 맞고 이유가 틀렸다.** 40문항 중 유일한 사실 오류다
- 권고 문구: "소리는 입자끼리 단단히 이어져 있을수록 빠르게 전달되므로 고체에서 가장 빠르다."

같은 문항에 하나 더 있다.

- 문두가 "물질의 상태"를 묻는데 보기에 **진공**이 있다. 진공은 상태가 아니라 매질의 부재다
- 오답 판별에는 지장이 없다. 문항 구성의 문제다

### 3.2 재는 기준이 빠진 것 — 2건, PRD 3.6절 위반이다

3.6절이 "최상급 표현에는 재는 기준을 함께 적는다"고 못박았다. 두 문항이 이 규칙에 걸린다.

**`ge_01`** 우리나라에서 가장 큰 섬

| 기준 | 값 | 출처 |
|---|---|---|
| 제주 본섬 | 1,833.2㎢ | 위키백과 |
| 제주특별자치도 (부속 도서 포함) | 1,850.23㎢ | 한국민족문화대백과사전 |

- 해설의 "약 1,833제곱킬로미터"는 본섬 기준으로 맞다. 그러나 어느 기준인지 적혀 있지 않다
- 권고: "제주도는 본섬 면적이 약 1,833제곱킬로미터로 우리나라에서 가장 큰 섬이다."
- 국토지리정보원, 통계청의 1차 자료로는 확인하지 못했다

**`ge_04`** 남한에서 가장 긴 강

| 지표 | 값 | 출처 |
|---|---|---|
| 하천연장 (국가하천 구간) | 약 400.7km | 환경부 |

- 권고: "낙동강은 유로연장이 약 510킬로미터로 남한의 강 가운데 가장 길다."

## 4. 진행 방식에 대하여 — 두 번 돌렸다

### 4.1 첫 시도는 실패했다

카테고리별 4팀으로 나눴다. **40분 넘게 돌고 결과 없이 끊겼다.** 프로세스가 종료될 때 함께 멈춘 것으로 보이며, 부분 결과도 회수하지 못했다.

- 나눈 단위가 4개뿐이라 한 팀이 10문항을 차례로 처리했다. 팀 하나가 20회 넘게 검색을 직렬로 돌았다
- 출처 규칙을 무겁게 준 것이 팀당 작업량을 키웠다
- **중간 결과를 어디에도 쓰지 않았다.** 이것이 가장 큰 잘못이다

### 4.2 두 번째 시도

셋을 바꿨다.

| 바꾼 것 | 첫 시도 | 두 번째 |
|---|---|---|
| 나눈 단위 | 4팀, 팀당 10문항 | 10팀, 팀당 4문항 |
| 팀당 지시 | 무거움 (출처 우선순위 상세, 항목별 판정) | 가벼움 (문항당 검색 1~2회로 끝내라) |
| 중간 저장 | 없음 | **각 팀이 결과 파일을 먼저 쓰고 그다음 응답** |

결과는 10팀 모두 78 ~ 164초, 전체 3분 남짓이다.

### 4.3 그래서 31번 문서의 문장에 단서를 붙인다

31번 4.4절에 "판단이 아니라 확인인 일에서는 병렬이 이긴다"고 적었다. **맞지만 조건이 있다.**

- **나눈 단위 수가 충분해야 한다.** 병렬도가 4배여도 팀 안이 직렬이면 팀 하나의 소요가 전체 소요다
- **단위당 작업량이 같아야 한다.** 지시를 무겁게 주면 병렬로 얻은 이득을 작업량 증가가 먹는다
- **중간 결과가 남아야 한다.** 서브에이전트는 실패해도 조용하다는 것을 17번에 적어 두었는데, 이번에는 거기에 더해 **부분 결과조차 회수되지 않았다.** 사람이 중계하는 방식이었다면 검토 측이 33번을 파일로 올린 것처럼 남았을 것이다

## 5. 남는 것

- **`/quiz-validate`를 온전히 돌리는 일.** 0절에 적었듯 이번에는 3절만 했다. 1절과 2절에서 더 나올 수 있다
- **명령어 정의에 실행 방식을 반영하는 일.** 지금 `quiz-validate.md`는 한 세션이 차례로 보는 절차로 읽힌다. 배치로 나눠 병렬로 돌리고 결과를 파일로 먼저 쓰라는 대목이 없다. 다만 이 문서를 쓰는 시점에 명령어를 고치면 비교가 깨지므로, 비교가 끝난 뒤에 고친다
- **`questions.js`를 고칠지 정하는 일.** 3.1절과 3.2절의 3건이 대상이다. 1차 구현은 6단계로 닫혔고 태그도 찍혔다. 본편만 고치고 단계 스냅샷 태그는 건드리지 않는 것을 권한다
- **검토 측 33번과의 대조.** 이 문서를 확정한 뒤에 연다. 34번에서 정리한다
