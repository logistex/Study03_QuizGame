- 9번을 옆에 더하면 "8번 했으니 됐다"는 판단이 다시 생긴다. 규칙이 둘이면 하나만 밟는 일이 난다

**8번의 "셋"을 없애는 편이 낫다.**

> 8. 바꾼 동작을 **서술한 자리를 전부** 맞추고 그 사실을 알린다. 코드, 계획서 본문, 함수 계약, PRD, 뒤 단계의 검증 절차와 체크리스트가 모두 그 자리다.

### `grep` 한 번으로 충분한가 — 아니다. 순서를 바꾸면 된다

지적이 맞다. 화면 문구로 찾으면 문구가 바뀌는 변경에서는 못 찾는다. 둘을 고치면 된다.

**첫째, 문구가 아니라 식별자로 찾는다.** 요소 id와 함수 이름은 동작이 바뀌어도 그대로다.

```bash
grep -rn "btn-clear\|renderRankingScreen" spec/
```

이번 경우 이 한 줄이 네 자리를 다 찾는다. "기록 지우기"라는 문구가 남아 있어 걸린 것은 운이었다.

**둘째, 고치기 전에 검색한다.** 고친 뒤에 검색하면 이미 바꾼 자리는 안 걸리고, 남은 자리만 보이는 것이 아니라 **목록 자체가 불완전해진다.**

> 고치기 전에 식별자로 `spec/`을 검색해 자리 목록을 만든다. 고친 뒤 그 목록을 하나씩 지운다.

목록을 만들어 두면 밟았는지가 판단이 아니라 대조가 된다.

## 3. 갈음한 방법 둘 — 이번에는 타당하다

### 3.1 색 대비를 CSS 값 계산으로 갈음한 것

**타당하다. 그리고 그 전제가 성립하는 것을 배포본에서 확인했다.**

전제가 깨지는 경우는 넷이다. 페이지 전체를 훑어 넷 다 없는 것을 봤다.

| 깨뜨리는 것 | 이 페이지 |
|---|---|
| 조상의 `opacity < 1` — 합성 결과가 CSS 값과 다르다 | 없음 |
| `filter`, `mix-blend-mode`, `backdrop-filter` | 없음 |
| 반투명 색(alpha) — 실제 배경과 섞여야 한다 | 없음 |
| `color-scheme`이나 다크 모드 UA 개입 | `normal`. 관련 미디어 쿼리도 없음 |

- 넷 중 하나라도 있으면 CSS 값 계산은 실제보다 좋은 값을 낸다. 특히 조상 `opacity`는 자식 색을 전부 배경 쪽으로 끌어당긴다
- **따라서 갈음 자체가 아니라 "전제 확인을 함께 하는가"가 판정 기준이다.** 이번에는 하지 않았지만 결과적으로 안전했다. 다음에 같은 갈음을 한다면 위 넷을 훑는 것을 절차에 넣으면 된다

곁가지로, Windows 고대비(`forced-colors`) 모드는 UA가 색을 통째로 갈아엎으므로 계산으로도 브라우저로도 판정되지 않는다. 다만 그 모드는 OS가 대비를 보장하므로 문제가 아니다.

### 3.2 `offsetParent === null`로 숨은 요소를 걸러 낸 것

**이번에는 안전하다. 규칙으로는 위험하다.**

`offsetParent`가 `null`이 되는 경우가 넷인데 그중 하나가 **보이는 요소**다.

- `display: none` — 걸러 내려던 것
- **`position: fixed`** — 화면에 보이는데도 `null`이다
- `<body>`와 `<html>` 자신
- 문서에 붙어 있지 않은 요소

이 페이지에 `position: fixed` 요소가 하나도 없는 것을 확인했다. 그래서 이번 판정은 맞다.

- 고정 헤더나 떠 있는 버튼이 생기면 그 요소가 조용히 집계에서 빠진다
- 더 안전한 판정은 `el.checkVisibility()`이고, 없는 환경이면 `el.getClientRects().length === 0`이다

## 4. 배포 구조 — 셋 다 지금 형태를 지지한다

### 4.1 `gh-pages` 브랜치를 따로 두는 것 — 맞다

파일 넷짜리 프로젝트에도 과하지 않다.

- `main`에 배포물을 두면 **소스가 두 곳에 생긴다.** 어느 쪽이 정본인지 매번 판단하게 된다. 이 프로젝트가 `PRD-v3.md` 동명 충돌로 이미 한 번 겪은 문제다
- 스냅숏 다섯 벌을 `main` 이력에 쌓으면 과거 코드 사본이 영구히 남는다. 태그가 이미 그 시점을 담고 있어 중복이다
- 브랜치 하나 늘어나는 비용은 실제로 0에 가깝다. `gh-pages`는 GitHub Pages의 표준 관행이라 처음 보는 사람도 뜻을 안다

버린 안 둘의 근거도 정확하다.

### 4.2 `localStorage` 공유를 안내 한 줄로 갈음하는 것 — 맞다. 다만 범위를 좁혀야 한다

**갈음이 맞다.** 저장 키에 단계를 붙이면 스냅숏마다 배포본 코드가 달라져 **스냅숏이 "그 시점의 코드"가 아니게 된다.** 미리보기의 목적을 깨뜨리므로 하지 않는 것이 옳다.

다만 안내 문구가 실제보다 넓다. 다섯 벌의 `script.js`를 받아 확인했다.

| 스냅숏 | `saveRanking` |
|---|---|
| `stage1-final`, `stage2`, `stage3-final` | **없음** |
| `stage4-final`, `stage5-final`, 본편 | 있음 |

- 1~3단계는 저장 함수가 아예 없어 기록을 만들지 못한다. 순위표 화면도 빈 껍데기다
- **실제로 섞이는 것은 4단계 이후 세 벌뿐이다**
- "여섯 단계가 순위 기록을 공유한다"보다 **"4단계 이후 화면은 순위 기록을 공유한다. 4단계에서 만든 기록이 5단계와 본편에도 보인다"**가 정확하고, 읽는 사람이 겪을 현상과도 맞는다

### 4.3 태그를 두 벌 두는 것 — 필요하다. 다만 이름이 뜻을 다 담지 못한다

- 검토 전 코드와 반영 후 코드는 실제로 다르므로 두 벌이 필요하다. 없애면 "완성된 모습"에 검토 전 코드가 올라간다
- 헷갈리는 지점은 이름이다. `-final`이 "검토 반영까지 끝난 시점"이라는 것은 `CLAUDE.md`를 읽어야 안다
- **미리보기 문서에도 한 줄 적기를 권한다.** 노트를 보는 사람은 저장소 규칙을 읽지 않는다. `stage2`에 `-final`이 없는 이유도 함께 적으면 된다(이미 적었다고 했으니 확인만 하면 된다)

## 5. 확인하지 않은 것에 대하여

두 항목 모두 판단에 이견이 없다. 다만 기록의 표현만 짚는다.

- **사파리와 VoiceOver 낭독** — 중단 결정을 받는다. 다만 19번의 판정 제목이 "확인 결과 — 2026-08-15, 통과"인데, **"VoiceOver + Chrome에서 통과"**로 범위를 제목에 넣기를 권한다. 판정 표가 "스크린리더마다 갈리면 안 읽힌다"를 담고 있어, 범위가 제목에 없으면 나중에 "통과했다"만 남는다. 재확인을 요구하는 것이 아니라 확인한 것과 안 한 것을 구별해 두자는 것이다
- **색각 이상 에뮬레이션** — `✓`, `✗` 병기를 코드로 확인한 것으로 갈음한 판단이 맞다. 기호가 붙어 있으면 색을 못 봐도 판정이 읽힌다

## 6. 여섯 단계를 돌아보며

검토 쪽에서 본 것을 남긴다.

### 잡힌 결함은 대부분 화면에 증상이 없었다

필수로 잡은 것들을 모아 보면 성격이 하나다.

| 결함 | 화면 증상 |
|---|---|
| `state.answered` 죽은 가드 | 없음. `disabled`가 실제 방어를 하고 있었다 |
| R3 체크리스트 자기모순 | 없음. 통과해도 무엇도 보증하지 않았다 |
| 퀴즈 화면 초점 이중 이동 | 없음. `document.activeElement`도 통과했다 |
| 저장 불가 안내 누락 | 없음. 정상으로 보이는 빈 표가 떴다 |

**눈으로 보는 확인이 이 프로젝트에서 가장 약한 수단이었다.** 반대로 값어치가 컸던 것은 콘솔 한 줄로 상태를 꺼내 보는 확인, 원본과 대조하는 확인, 코드를 읽는 확인이었다.

### 코드보다 검증 방법에 결함이 더 많았다

- R2 검증의 앞부분이 무효했다. `answer`가 틀려도 반드시 통과하는 절차였다
- R3 체크리스트 두 항목이 서로 모순됐다
- 최대 연속 길이는 판별력이 12.6%였다
- `setItem`만 막은 스텁이 순위표 화면 분기를 한 번도 실행하지 않았다

넷 다 "코드를 확인하는 방법"의 결함이지 코드의 결함이 아니다. **검증 절차를 검토 대상으로 삼은 것이 이 프로젝트의 특징이었고, 그것이 값어치를 했다.**

### 규격이 코드를 따라오지 못하는 일이 세 번 났다

4단계 PRD 3.5절, 계획서 함수 계약, 5단계 검증 절차. 절차를 고쳐도 다시 났다.

**구조적인 원인이 하나 있다고 본다.** 계획서가 "무엇을 만드나"와 "어떻게 확인하나"를 함께 담고 있다. 동작이 바뀌면 두 종류의 서술을 다 고쳐야 하는데, 앞엣것은 눈에 띄고 뒤엣것은 뒤 단계에 흩어져 있다.

- 다음에 같은 규모의 실습을 한다면 **검증 절차를 별도 문서로 두는 것**을 검토해 볼 만하다
- 규격 동결과도 덜 부딪힌다. 지금은 "계획서는 어떻게 확인하는가라 산출물이 바뀌지 않는다"는 단서를 따로 달아 두고 있는데, 문서가 갈려 있으면 그 단서가 필요 없다

### 검토자도 여섯 번 틀렸다

기록해 둔다. `git init`(저장소가 이미 있었다), `saveRanking` 반환 계약 변경 제안(PRD 위반), 카테고리 키 오타 재현 실패, 스크린리더 낭독을 단언한 것, 모의로 갈음한 것(전수 계산이 가능했다), 문서 번호 충돌.

**여섯 중 넷이 "확인하지 않고 단언한 것"이었다.** 저장소 상태를 못 보면서 `git init`을 권했고, 스크린리더를 못 돌리면서 낭독이 보장된다고 적었다. 검토자가 도구의 한계를 넘어 말하기 시작하면 그때부터 틀린다.

### 남는 인상

지적을 그대로 받지 않고 처방을 바꾼 것이 여러 번 있었고, **대부분 원안보다 나았다.** `answered` 필드 제거, R3 항목 분리, 보존판 표시, 완료 기준 4번 수정, `no-store` 서버, "기록 지우기"를 남긴 것. 여섯 건이다.

문제 인식과 해결책을 따로 판단한 결과다. 검토가 값어치를 갖는 조건이 "지적이 옳다"가 아니라 "받는 쪽이 근거를 따져 본다"는 것을 이 여섯 건이 보여 준다.
