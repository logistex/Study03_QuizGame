## 2. 점검 전에 발견한 것 — 5단계 검증 절차가 옛 서술이었다

계획서 5.3절과 체크리스트에 4단계 변경 이전 서술이 남아 있었다.

```
5.3절:      순위표 화면은 표와 "기록 지우기"를 모두 감춘다
체크리스트:  localStorage 불가 상태의 순위표 화면에서
            "기록 지우기" 버튼이 감춰져 있다
```

현재 동작은 **쓰기만 막히면 표와 버튼이 보이고**, 읽기까지 막혀야 감춰진다. 옛 절차를 그대로 밟았으면 **정상인 것을 결함으로 판정했을 자리다.**

- 26번이 "규격이 코드를 따라오지 못했다"고 지적했을 때 PRD 3.5절과 계획서 함수 계약을 고쳤는데, **그 동작을 참조하는 뒤 단계의 검증 절차는 훑지 않았다**
- 구현 측 잘못이다. 26번이 패턴까지 짚어 줬는데 좁게 적용했다
- `CLAUDE.md`에 절차 9번을 더했다 — **바꾼 동작의 이름으로 `spec/` 전체를 `grep`한다.** 만들자마자 적용해 보니 남은 옛 서술은 없었다

### 3.2 접근성

- **R5** — `grep -nE 'aria-live|role="status"|role="alert"' index.html script.js`가 잡는 것은 `index.html`의 주석 한 줄뿐이다. 코드에는 없다. 그 주석은 "여기에 `aria-live`를 주지 않는다"고 적어 둔 것이라 남겨 둔다
- **조작 요소** — 시작 화면과 퀴즈 화면의 요소가 전부 진짜 `<button>`이나 `<input>`이다. 탭 순서에서 빠진 버튼이 없다
- **색 외 단서** — 정답에 `✓`, 오답에 `✗`가 붙는다
- **키보드 조작** — 사람이 확인했다. 초점 테두리가 모든 버튼에서 보이고 `Enter`와 `Space` 둘 다로 눌린다. 자동화가 키 이벤트의 기본 동작을 일으키지 못해 2단계부터 사람에게 맡겨 온 항목이다

## 4. 사람이 확인하다 나온 것

키보드 확인을 부탁하면서 스크린리더 이야기가 함께 나왔다. 둘 다 코드를 고치지 않고 정리했다.

### 4.1 선택지가 몇 개인지 알 수 없다 — PRD 8절로

문제 텍스트를 읽고 나면 아무 안내 없이 조용해져서, `Tab`을 눌러 보아야 선택지가 몇 개인지 안다.

- 결함은 아니다. 스크린리더는 초점이 있는 것만 읽는다
- 다만 처음 쓰는 사람은 문제를 들은 뒤 무엇을 해야 할지 모른다
- **8절로 보냈다.** 4.3절에 없는 새 요구라 "새 기능을 넣지 않는다"와 부딪히고, R5와 인접해 접근성 속성을 덧붙이면 낭독 흐름을 다시 확인해야 하는데 그 수단을 더 쓰지 않기로 했다

### 4.2 답을 고르면 "다음 문제"로 초점이 가야 하지 않나 — 규격대로 둔다

**2차 PRD 검토에서 정확히 그 구조가 문제로 지적되어 지금 형태가 됐다.**

> 답 선택 후 "다음 문제" 버튼으로 초점을 옮기면 스크린리더가 정답 낭독을 끊는다

버튼으로 바로 보내면 채점 결과가 전달되지 않는다. 대신 `Tab` 한 번에 닿도록 선택지를 비활성해 탭 순서에서 빼고 버튼을 피드백 바로 뒤에 두었다. **눈으로 보는 사용자의 `Tab` 한 번이 의도된 비용이다.**
