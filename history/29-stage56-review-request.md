## 0. 이번 요청의 성격

앞 단계들과 다르다. **5단계는 코드를 한 줄도 고치지 않았고, 6단계는 올리고 확인한 것이 전부다.** 새로 짠 코드가 없으므로 코드 검토의 값어치가 작다. 그래서 봐 주셨으면 하는 것을 셋으로 좁힌다.

1. **판단 요청 — 단계별 스냅숏 배포 구조.** 계획서 범위 밖이라 혼자 정했다. 3절
2. **5단계에서 또 나온 규격 누락.** 같은 패턴이 반복된 것이라 절차가 충분한지 봐 달라. 2절
3. 점검 결과 자체의 타당성. 1절과 4절

## 1. 5단계 — 무엇을 어떻게 확인했나

계획서 5단계는 점검 항목이고 산출물이 없다. 확인 방법을 함께 적는다.

| 항목 | 방법 | 결과 |
|---|---|---|
| R5 | `grep -nE 'aria-live\|role="status"\|role="alert"'` | 코드에 없음. 잡히는 것은 주석 한 줄 |
| 반응형 375px | 폭을 바꾸고 다섯 화면에서 `scrollWidth`와 `clientWidth` 대조 | 모두 375로 같음. 가로 스크롤 없음 |
| 선택지 높이 | `getBoundingClientRect().height` | 50px (기준 44px) |
| 선택지 잘림 | `scrollWidth`, `scrollHeight`를 `client*`와 대조 | 잘림 없음 |
| 색 대비 | CSS에서 색을 뽑아 WCAG 상대 휘도로 계산 | 아홉 조합 모두 4.5:1 초과 |
| 조작 요소 | 화면별로 `button`, `input`, `[tabindex]`를 세어 종류 확인 | 전부 진짜 `<button>`이나 `<input>` |
| 에러 1, 2 | `questions-x.js`로 바꾸기, `kh_01`의 `answer`를 9로 | 안내 문구, 카드 0개, 눌러도 시작 안 됨 |
| 에러 3 | `setItem`만, 그리고 `getItem`까지 던지게 함 | 두 갈래 각각 확인 |
| 키보드 | **사람이 확인** | 초점 테두리 보임, `Enter`와 `Space` 둘 다 눌림 |

색 대비는 값을 적어 둔다. 계획서가 특별히 확인하라고 한 주황 배지가 가장 빠듯하다.

```
초급 7.02  중급 6.74  고급(주황) 5.84  정답 9.02  오답 7.97
강조 줄 14.96  강조 줄 왼쪽 선 6.87  본문 16.76  보조 글자 9.14
```

**임시 변경은 전부 되돌렸고 `git status`로 확인했다.**

### 봐 주셨으면 하는 것

- 색 대비를 **CSS 값에서 계산한 것**으로 갈음했다. 계획서는 "개발자 도구에서 색을 집어 대비값을 확인한다"이다. 계산은 정확하지만 **화면에 실제로 그려진 색이 CSS 값과 같다는 전제**가 깔린다. 이 전제가 깨지는 경우가 있는가
- 조작 요소를 `document.querySelectorAll`로 세어 "전부 `<button>`"을 확인했다. 숨은 요소(`offsetParent === null`)를 제외했는데, 이 걸러 내기가 놓치는 것이 있는가

## 2. 5단계에서 또 나온 규격 누락 — 절차가 충분한가

**점검을 시작하기 전에 계획서 5단계 검증 절차가 4단계 변경 이전 서술로 남아 있는 것을 발견했다.**

```
5.3절:      순위표 화면은 표와 "기록 지우기"를 모두 감춘다
체크리스트:  localStorage 불가 상태의 순위표 화면에서
            "기록 지우기" 버튼이 감춰져 있다
```

그대로 밟았으면 **정상인 것을 결함으로 판정했을 자리다.**

- 26번이 "규격이 코드를 따라오지 못했다"고 지적했을 때 PRD 3.5절과 계획서 함수 계약을 고쳤는데, **그 동작을 참조하는 뒤 단계의 검증 절차는 훑지 않았다**
- 26번이 패턴까지 짚어 줬는데 좁게 적용한 것이라 구현 측 잘못이다

`CLAUDE.md`에 절차를 하나 더했다.

> 9. **바꾼 동작을 참조하는 뒤 단계의 검증 절차까지 훑는다.** 찾는 방법은 단순하다 — 바꾼 화면이나 함수의 이름으로 `spec/` 전체를 `grep`한다

만들자마자 적용해 보니 남은 옛 서술은 없었다.

### 봐 주셨으면 하는 것

- **`grep` 한 번으로 충분한가.** 이번에는 "기록 지우기"라는 화면 문구가 그대로 남아 있어 걸렸다. 문구가 바뀌는 변경이었다면 같은 방법으로 못 찾는다
- 8번(셋을 맞춘다)과 9번(뒤 단계까지 훑는다)을 나눠 둔 것이 맞는가, 아니면 8번을 넓게 고쳐 쓰는 편이 나은가

## 3. 판단 요청 — 단계별 스냅숏 배포 구조

**계획서 6단계는 "정적 파일 넷을 그대로 올린다"만 적고 있다.** 단계별 스냅숏은 노트의 미리보기(5.1.6.0)를 위해 더한 것이라 범위 밖이다. 혼자 정했으므로 판단을 받고 싶다.

```
gh-pages/
├── index.html, style.css, script.js, questions.js   최신본
├── .nojekyll
├── stage1-final/   stage2/   stage3-final/   stage4-final/   stage5-final/
```

정한 것 넷과 근거다.

| 정한 것 | 근거 | 버린 안 |
|---|---|---|
| `gh-pages` 브랜치를 따로 둔다 | `main`은 소스와 문서만 담는다 | `main`의 `docs/` — 소스가 두 곳에 생긴다. `main`에 스냅숏 커밋 — 과거 코드 사본이 이력에 쌓이고, 태그가 이미 그 시점을 담고 있어 중복이다 |
| 스냅숏에 파일 넷만 넣는다 | 문서까지 넣으면 같은 문서가 여섯 벌 생긴다 | — |
| 올리는 시점은 `-final` 태그 | 5.1.6.0의 제목이 "완성된 모습"이다. 검토 반영 전 코드를 보여 주면 뜻이 어긋난다 | 원래 `stageN` 태그 — 검토 전 코드다 |
| `localStorage` 공유는 안내 한 줄로 갈음 | 저장 키에 단계를 붙이면 배포본 코드를 고치는 일이다(26번 6절) | 키에 단계 접미사 |

**2단계만 `-final`이 없다.** 2단계 검토를 3단계와 묶어 받아 단독 최종본이 존재하지 않는다. 노트에도 그 이유를 적었다.

### 봐 주셨으면 하는 것

- **배포물 브랜치를 따로 두는 것이 이 규모에 맞는가.** 파일 넷짜리 프로젝트에 브랜치를 하나 더 두는 것이 과한가
- **여섯 벌이 같은 오리진을 쓰는 것을 안내 한 줄로 갈음해도 되는가.** 3단계를 보다 4단계로 가면 앞서 쌓은 기록이 그대로 보인다
- 태그를 두 벌(`stageN`, `stageN-final`) 두는 것이 헷갈리지 않는가. 노트의 산출물 표는 `stageN`을, 미리보기 링크는 `-final`을 쓴다

## 4. 6단계 — 배포 후 확인

**로컬 확인을 완료 기준으로 삼지 않았다.** 아래는 전부 배포 URL에서 한 것이다.

| 확인 | 결과 |
|---|---|
| 여섯 주소 응답 | 모두 200 |
| 자원 파일 셋 | 모두 200 |
| Network 404 | 없음 |
| 콘솔 에러 | 없음 |
| 두 모드 한 바퀴 | 결과 화면 도달, 순위 저장 확인 |
| 사람 확인 | 완료 기준 전부 통과. 새로고침 뒤 기록 유지, 사파리 한 바퀴, **두 탭 동시 저장** |

- 올리기 전에 절대 경로 참조가 없는 것을 `grep`으로 확인했다. 하위 폴더에서도 자원이 뜨는 근거다(R6)
- 두 탭 동시 저장은 5단계까지 콘솔로만 확인했던 항목이라 여기서 닫혔다
- 사파리는 `file://`이 아니라 배포 URL이므로 `localStorage`가 정상 동작한다

## 5. 확인하지 않은 것

- **사파리와 VoiceOver 낭독.** 사람이 확인을 여기서 그만두기로 했다(25번 2절). 크롬에서는 통과했고, 무엇을 안 본 채 닫는지 기록해 두었다
- 색각 이상 에뮬레이션. `✓`, `✗` 병기를 코드로 확인한 것으로 갈음했다
