## 1. 명령어와 스킬의 동작 — 확인한 것

35번이 남긴 표를 채웠다. 노트 5.2.2에 반영했다.

| 확인 항목 | 결과 |
|---|---|
| 첫 인수 번호 | `$0`. 교재의 `$1`은 틀림 |
| 범위 밖 자리표시자 | 빈 값이 되지 않고 `$2`가 글자 그대로 들어옴. 최신 문서에도 없는 내용 |
| `&&` 체이닝 | **안 됨.** 뒤가 앞 명령어의 인수 문자열이 됨 |
| 스킬과 명령어의 쓰임 | 같음. 인수 치환도 같고 클로드가 스스로 부를 수 있는 것도 같음 |
| 스킬만 다른 것 | 폴더 하나에 `SKILL.md`, 앞머리에 `name`, 본문 앞에 `Base directory` 한 줄 |

### 체이닝이 안 되는 모양

`/quiz-stats && /quiz-validate 지리`를 치면 명령어에 도착하는 인수가 이렇다.

```
ARGUMENTS: && /quiz-validate 지리
```

- 뒤가 둘째 명령어로 갈라지지 않고 첫째 명령어의 인수가 된다
- `/quiz-stats`는 인수를 안 쓰므로 버려지고 한 번만 돈다
- **인수를 쓰는 명령어에서는 더 나쁘다.** `/quiz-validate 지리 && /quiz-stats`는 대상 범위가 `지리 && /quiz-stats`가 되고 오류가 안 뜬다

### 반영 시점 — 셋이 갈린다

| 무엇 | 언제 붙나 | 어떻게 확인했나 |
|---|---|---|
| `.claude/commands/*.md` | 만든 즉시 | 세션 중 만든 `reload-check`가 대화창에서 인식됨 |
| `.claude/skills/<이름>/SKILL.md` | 폴더가 이미 있으면 즉시, 폴더가 그때 처음 생기면 앱 재실행 뒤 | 조건을 달리해 스킬 셋을 만들어 확인 (`skill-check`, `view-history`, `folder-check`) |
| `CLAUDE.md` (프로젝트, 글로벌) | **새 세션** | `/context`의 `Memory Files` 토큰 수 — 같은 세션 6.1k 그대로, 새 세션 6.4k |

**앱을 재시작하고 같은 세션을 이어 열었을 때는 아직 확인하지 못했다.** 확인하려면 이어 연 세션에서 `/context`를 돌려 프로젝트 `CLAUDE.md`가 6.1k인지 6.4k인지 보면 된다.

## 2. 세 세션 합의 — 요약

`consensus/` 폴더에 전 과정이 있다. 여기서는 결론만 적는다.

- 대상은 `quiz-validate` **생성 프롬프트**였다. 명령어 파일이 아니다
- 세 세션이 각자 낸 프롬프트 가운데 **그대로 채택된 것은 없다**
- 관통하는 한 문장 — **프롬프트가 대신 정해 준 것은 검증되지 않는다**

이 세션이 맡은 것은 실행과 최종 결정이었다. 세 프롬프트를 각각 돌려 `consensus/r2-run.md`에 원문으로 올렸고, `consensus/r3-agreement.md` 6절에 확정 문단을 붙였다.

일곱 지점 중 이 세션의 안이 그대로 살아남은 것은 없다. 두 지점은 자기 안이 나쁜 결과를 냈다.

- **실행 방법 힌트** — 힌트를 준 판만 `script.js` 1~112행을 떼는 방법을 골랐다. 행 번호에 의존한다. 힌트 없는 두 판은 `vm` + `document` 스텁에 닿았고 파일이 바뀌어도 버틴다
- **"규격에 없는 것 세 가지"** — 이렇게 단정한 두 프롬프트가 만든 명령어 **둘 다** 외부 출처 대조를 규격 밖으로 표시했다. 실제로는 `spec/IMPL-PLAN.md` 1.8절 7번에 있다

## 3. 프롬프트를 다섯 가지로 돌려 견줬다

같은 일을 시키는 프롬프트를 길이와 방식만 달리해 돌리고, 나온 명령어와 실행 결과를 대조했다.

| | 교재 4항목 | 최소 3줄 | spec 둘 | spec 둘 + 12번 | 신본 |
|---|---|---|---|---|---|
| 자동 검사 | **없음** | 있으나 **안 돌아감** | 위반 0건 | 위반 0건 | 위반 0건 |
| 사람이 보는 항목 | 4 | 3 | 8 + 3 | 8 + 3 | 8 |
| 문항 간 중복 | 없음 | 없음 | 있음 | 있음 | 있음 |
| 교차 검증 | 있음 | **없음** | 있음 | 있음 | 있음 |
| 근거 절 번호 | 없음 | 3.6절 하나 | 행마다 | 행마다 | 행마다 |
| 기존 검증 기록 조회 | 없음 | 없음 | 없음 | 없음 | 있음 |
| 지리 10문항에서 잡은 것 | `ge_01` | `ge_01` | `ge_01` | `ge_01` | `ge_01` |

### 읽을 것

- **최소 프롬프트는 돌아가지 않는 절차를 냈다.** "Node로 그 함수를 돌려 결과를 받는다"만 적혀 돌리는 줄이 없다. 글자 그대로 따라 하면 `ReferenceError: document is not defined`가 난다
- **교재의 네 항목은 검증 명령어가 아니라 작성 지침이다.** 첫 줄이 "모든 문제 작성 시 확인 사항"이다. 자동 검사가 없는 것은 결함이 아니라 다른 물건이라는 뜻이다
- **교재의 네 항목은 이미 규격에 흡수되어 있다.** 12번 문서 3절이 현행 체계와 대조했고 그 결과가 PRD 3.6절과 계획서 1.8절에 들어갔다. 그래서 `spec/` 둘만 읽게 한 판과 12번까지 읽게 한 판의 **검사 항목이 하나도 갈리지 않았다**
- **다섯 판이 지리에서 낸 지적은 모두 `ge_01` 하나로 같다.** 갈리는 것은 잡은 개수가 아니라 **못 잡는 종류**다. `questions.js` 사본에서 `ge_03`의 선택지를 넷에서 셋으로 줄여 보니, 자동 검사가 있는 판만 `ge_03: options 길이가 3`을 잡았다

## 4. 프롬프트에서 무엇을 걷어낼 수 있나 — 절제 실험

줄을 하나씩 빼고 다시 돌려 결과가 같은지 봤다.

| 뺀 줄 | 결과 | 판정 |
|---|---|---|
| `검사 로직을 다시 짜지 마` | 여전히 `validateData()`를 씀 | **걷어내도 됨** |
| `카테고리는 영문 id와 한글 이름을 둘 다` | 그대로 나옴 | **걷어내도 됨** |
| `걸린 게 없으면 "고칠 것 없음"` | 보고 절에서 사라짐 | **남긴다** |
| 생성 일시, `argument-hint` 따옴표, 만든 뒤 실행 확인 | `CLAUDE.md`로 옮기니 그대로 살아남음 | **옮긴다** |

- 프롬프트는 52줄에서 43줄로 줄었다. **17%다.** "절반으로 줄 것"이라던 앞선 예측은 과했다
- 남은 것 대부분이 이 명령어에만 해당하는 것과 이 저장소의 사실이라 걷어낼 자리가 별로 없었다

### 걷어내는 기준

| | 어떻게 하나 |
|---|---|
| 모델이 **몰라서** 못 하는 것 | 남긴다. 저장소 사실이라 성능과 무관하다 |
| 모델이 **알면서도 안 하는 것** | 남긴다. "돌려 보고 적어라"가 그것이다 |
| 모델이 **알아서 하는 것** | 걷어낸다 |

**이 실험의 한계.** 확정본을 아는 세션이 걷어낸 판을 만들었다. 결과가 확정본 쪽으로 끌렸을 수 있다. 문맥이 깨끗한 쪽에서 돌려야 제대로 된 절제가 된다.

## 5. 규격의 미흡 넷과 그 보완

합의를 마친 뒤 규격을 다시 훑어 넷을 찾았다. 커밋 `46ffe3b`, `2b61a38`.

| # | 무엇이 미흡했나 | 어떻게 고쳤나 |
|---|---|---|
| 1 | `question` 60자, 선택지 20자 규칙에 **확인하는 자리가 없었다.** 4.2절 검사 항목에도 1.8절 육안 검토에도 없다 | 검사 함수에 V10, V11로 넣고 PRD 4.2절 표와 계획서 검사 항목, 1.5절 검증 표를 함께 맞췄다 |
| 2 | **3.6절(작성 규칙)과 4.2절(검사 항목)을 잇는 것이 없었다.** 1번의 원인이다 | PRD 3.6절에 "규칙마다 무엇이 확인하는가" 표를 더했다. 칸이 비면 그 규칙이 어디서도 확인되지 않는다는 뜻이다 |
| 3 | **"규격"의 범위가 못박혀 있지 않았다.** PRD만 규격으로 읽어 사고가 났다 | `CLAUDE.md`에 규격은 `spec/` 둘을 말한다고 적었다 |
| 4 | **검사 함수를 명령줄에서 부르는 경로가 규격에 없었다.** 부르는 쪽마다 다른 방법을 새로 만들었다 | 계획서에 "저장소 밖에서 검사 함수를 부를 때"를 두고 확인된 줄을 넣었다 |

여기에 3.6절 끝의 **"위 세 규칙"이라는 표현을 거뒀다.** 자동으로 못 잡는 규칙이 그 셋 말고도 있는데 그 문장을 인용하면 셋에서 멈춘다. 오늘 그렇게 멈춘 판이 실제로 나왔다.

### 규격을 고치니 프롬프트가 줄었다

규격 보완 뒤에 프롬프트를 다시 짜서 돌렸다.

| | 합의 확정본 | 규격 보완 뒤 |
|---|---|---|
| 프롬프트 | 43줄 | **28줄** |
| 사람이 보는 항목 | 6 | **8** |
| 문항 간 중복 | 없음 | **있음** |

**프롬프트가 줄었는데 결과가 넓어졌다.** 확인 수단 표가 "무엇을 봐야 하는가"를, 계획서의 실행 경로가 "어떻게 돌리는가"를 규격이 가져갔기 때문이다.

**다만 신본이 더 나은 프롬프트라서 이긴 것이 아니다.** 같은 신본을 규격 보완 전에 돌렸으면 확정본보다 못했다. 그래서 `consensus/r3-agreement.md`는 고치지 않는다. 그 시점 규격에서는 확정본이 맞았다.
