# PRD-v2 검토 및 권고안

검토 대상: `PRD-v2.md` (2026-08-10 20:42 KST 작성)
갱신: 2026-08-11 23:11 KST — 1차 검토 후 결정 사항 반영, 재검토 결과 추가

## 0. 총평

문서 자체의 완성도는 높다. 셔플 알고리즘 선택 근거(2.1절), 저장 함수가 삽입 인덱스를 돌려주는 설계(3.4절), 안정 정렬 의존 명시, 제외 항목마다 이유를 붙인 7절은 구현자가 조용히 틀릴 만한 지점을 미리 막아 둔 좋은 서술이다.

문제는 대부분 두 가지 전제가 흔들린 데서 파생된다.

1. 실행 방식이 `file://`가 아니라 GitHub Pages(`https://`)다.
2. 한 판의 문제 수가 10문제로 고정된다.

이 둘을 반영한 뒤 남는 결함이 **필수 수정 8건**, **개선 권고 11건**이다. 그리고 이 19건을 모두 반영해도 **해결되지 않는 문제 5건**이 있어 4절에 따로 적는다.

## 1. 확정된 결정과 그 파급

### 1.1 결정 A — 한 판은 항상 10문제, 1차 구현부터 적용

**확정 내용**

- 카테고리별 도전, 전 범위 도전 모두 매 판 10문제를 출제한다.
- 만점은 두 모드 모두 10점이다.
- 순위표는 카테고리 4개와 전 범위 1개, 모두 5개를 독립으로 유지한다.
- 문제은행 확대는 2차 구현으로 예정한다.

**왜 1차부터인가**: 1차를 40문제 만점으로 내면 2차 전환 시 통합 순위표에 40점 만점 기록과 10점 만점 기록이 섞인다. 점수 내림차순으로만 정렬하므로 40문제 중 12점이 10문제 중 10점(만점)보다 위에 온다. 3.4절이 세운 원칙이 순위표 내부에서 깨진다. 처음부터 10점으로 고정하면 전환 비용이 0이 된다.

**바뀌는 절**

| 절 | 현행 | 수정 |
|---|---|---|
| 2 게임 규칙 | 카테고리별 10문제(10점), 전체 40문제(40점) | 두 모드 모두 10문제, 만점 10점 |
| 3.1 | "전체 도전 (40문제)" 버튼 | "전 범위 도전 (10문제)". 숫자는 출제 수 상수에서 조립 |
| 3.1 | 카드에 `QUESTIONS[id].length` 표시 | 출제 수를 표시. 보유 수는 2차에서 출제 수와 달라진다 |
| 3.3 | "같은 모드를 새로 섞어" | "같은 모드로 문제를 새로 뽑아" |
| 3.4 | 통합 순위표 만점 40점 | 만점 10점. 분리 근거를 출제 범위 차이로 다시 씀 |
| 7 | "문제은행 확대" 제외 항목 | 삭제하고 8절(2차 계획)로 이관 |

**순위표 분리 근거 교체**: 두 모드의 만점이 같아지면서 기존 근거("만점이 달라 비교가 성립하지 않는다")가 사라진다. 새 근거 — 전 범위 도전은 네 분야가 섞여 나오므로 한 분야를 깊게 아는 사람과 두루 아는 사람의 성적이 다르게 나온다. 같은 10점이어도 의미가 다르다.

### 1.2 결정 A-2 — 전 범위 도전의 카테고리 배분

**확정 내용**: 무작위로 고른 2개 카테고리에서 3문제씩, 나머지 2개 카테고리에서 2문제씩 뽑는다(3+3+2+2 = 10).

**이 결정이 단순 무작위보다 나은 이유**: 1차 권고에서는 단순 무작위를 제안했으나, 순위표를 두는 이상 이쪽이 옳다. 40문제에서 단순 무작위로 10개를 뽑으면 한국사가 5문제 나오는 판이 생긴다. 그런 판은 사실상 카테고리 도전에 가까운데, 결과는 전 범위 순위표라는 **같은 표에서 겨루게 된다.** 3+3+2+2는 판마다 어느 카테고리가 3문제인지만 달라지고 구성의 형태는 고정되므로, 판 간 난이도 편차가 줄고 순위 비교가 성립한다.

**구현 시 명시해야 할 두 가지**

1. **합친 뒤 반드시 다시 섞는다.** 카테고리별로 뽑아 이어 붙이면 한국사 3문제가 연달아 나오고 그다음 과학 3문제가 나온다. 카테고리 순서대로 출제되는 셈이라 "섞어서 푼다"는 규칙이 무너진다. 뽑기와 최종 순서 섞기는 별개 단계다.
2. **이 배분은 카테고리 4개, 출제 10문제라는 전제에 묶여 있다.** 카테고리를 5개로 늘리거나 출제 수를 바꾸면 3+3+2+2가 성립하지 않는다. PRD에 전제를 함께 적지 않으면 나중에 카테고리를 추가할 때 조용히 깨진다.

```javascript
const counts = [3, 3, 2, 2];
const order = shuffle(CATEGORIES);
const picked = order.flatMap((cat, i) => shuffle(QUESTIONS[cat.id]).slice(0, counts[i]));
const quiz = shuffle(picked);   // 이 줄을 빠뜨리면 카테고리 순서대로 나온다
```

**데이터 검사와의 관계**: 이 배분은 카테고리당 최소 3문제를 요구하는데, 필수 수정 3의 "10문제 이상" 검사가 이를 포함하므로 별도 검사는 필요 없다.

### 1.3 결정 B — GitHub Pages 배포

**Safari의 `localStorage` 차단 문제는 해소된다.** 그 제약은 `file://` 오리진 고유의 것이고 GitHub Pages는 `https://` 오리진이므로 순위표가 정상 동작한다.

**무효가 되는 근거 두 곳** (결론은 유지, 근거만 교체)

- **1.5절 전체** — "`file://`이라 `fetch`가 차단된다"는 https에서 성립하지 않는다. 그렇다고 `questions.js`를 바꿀 필요는 없다. `fetch`로 옮기면 초기화가 비동기가 되고 4.1-1의 로드 실패 처리가 복잡해진다. 새 근거 — 빌드 도구가 필요 없고, 로드 순서가 `<script>` 태그 순서로 보장되며, 로컬에서 파일을 직접 열어 확인할 때도 그대로 동작한다.
- **3.4절 마지막 문단** — "`file://`는 다른 로컬 페이지와 저장소를 공유한다"도 성립하지 않는다. 다만 **키 이름 유지라는 결론은 그대로이고 근거는 오히려 강해진다.** GitHub Pages 프로젝트 페이지는 `https://<사용자>.github.io/<저장소>/`에 놓이지만 오리진은 `https://<사용자>.github.io` 하나다. 같은 계정에 올린 모든 프로젝트 페이지가 `localStorage`를 공유하므로, 실습 프로젝트를 여러 개 올리면 실제로 충돌한다.

**새로 생기는 제약 세 가지**

1. **Safari ITP 7일 규칙** — 사이트에 7일간 상호작용이 없으면 `localStorage`를 포함한 스크립트 작성 저장소를 삭제한다. `https`에서도 적용되며 코드로 막을 수 없다. 4.1-4(데이터 손상)와 다른 상황이다. 데이터가 통째로 사라져 정상적인 빈 순위표로 보이므로 사용자는 오작동으로 오해한다.
2. **파일명 대소문자** — GitHub Pages는 구분하고 macOS 로컬은 구분하지 않는다. 로컬에서 되던 참조가 배포 후 404가 난다.
3. **절대 경로 금지** — 프로젝트 페이지는 하위 경로에 놓이므로 `/style.css`는 `https://<사용자>.github.io/style.css`를 가리켜 깨진다.

뒤 두 가지는 **로컬에서 절대 재현되지 않고 배포해야만 드러난다.** 6절 구현 단계에 "배포 후 확인"을 별도 단계로 두어야 한다.

**로컬 개발 시 Safari 제약은 남는다**: 배포 전에 `index.html`을 Safari로 직접 열면 순위표만 동작하지 않는다. 로컬 확인은 Chrome이나 Edge로 하고 Safari는 배포 후에 확인한다. 굳이 로컬에서 Safari로 순위표까지 보려면 로컬 서버를 띄운다.

```bash
python3 -m http.server 8000
```

**안정 정렬 의존(3.4절)**: 배포하면 방문자 브라우저를 통제할 수 없지만, `Array.prototype.sort`의 안정 정렬은 ES2019 이후 모든 주요 브라우저가 보장하므로 그대로 의존해도 된다. 근거 문장만 "대상 브라우저가 최신 Chrome, Edge, Safari이므로" 대신 "ES2019 이후 모든 주요 브라우저가 보장하므로"로 고친다.

## 2. 필수 수정 8건

현행 문서만으로 구현하면 버그나 미정의 동작으로 이어지는 항목이다.

### 1. `beforeunload` 해제 시점이 없다 (3.2절)

"진행 중에 새로고침하거나 페이지를 닫으려 하면 확인창을 띄운다"만 있고 **언제 이 경고를 거두는지가 없다.** 해제하지 않으면 게임을 정상적으로 끝낸 뒤에도 창을 닫을 때마다 경고가 뜬다. 정상 종료에까지 경고가 붙으면 사용자는 경고를 무시하는 법을 배우고, 정작 진행 중 실수를 막는 효과가 사라진다.

**수정**: 세 시점에 핸들러를 해제한다 — 마지막 문제를 마치고 결과 화면으로 넘어갈 때, "그만두기"를 확인했을 때, 데이터 검사 실패로 게임을 시작하지 못했을 때.

**다만 이 수정으로 문제가 다 풀리지는 않는다. 4절 1번, 2번을 함께 볼 것.**

### 2. 저장 실패와 순위 진입 메시지가 충돌한다 (3.3절 + 4.1-3)

4.1-3은 실패 시 "순위 저장만 건너뛴다"고 하고 3.3절은 저장 함수 반환값으로 진입 여부를 표시한다. **저장을 건너뛰었을 때 무엇을 돌려주는지가 정의되지 않았다.** `null`을 돌려주면 만점자에게도 "순위표에 들지 못했습니다."가 뜬다.

**수정**: 반환을 세 상태로 구분한다.

| 반환 | 의미 | 결과 화면 |
|---|---|---|
| 정수 | 진입, 해당 인덱스 | "순위표 N위 진입" + 줄 강조 |
| `null` | 저장은 됐으나 순위권 밖 | "순위표에 들지 못했습니다." |
| `'unavailable'` | 저장 자체가 불가 | 진입 여부는 표시하지 않고 안내 문구만 |

세 번째 경우 순위표 영역도 보여 줄 것이 없으므로 함께 감춘다. **순위표 화면(3.5절)의 "기록 지우기" 버튼도 같이 감춘다.** 지울 것이 없는 상태에서 버튼만 남으면 눌러도 아무 일이 없어 고장으로 보인다.

### 3. 데이터 검사 항목이 부족하다 (4.1-2)

현행은 문제 수, `options.length === 4`, `0 <= answer <= 3` 세 가지다. 통과하고도 조용히 잘못 동작하는 경우가 남는다.

| 추가할 검사 | 빠뜨릴 때 증상 |
|---|---|
| **문제 수가 10 이상인가** | 결정 A로 새로 필요. 9문제뿐이면 10문제를 뽑지 못한다 |
| `difficulty`가 세 값 중 하나인가 | 오타면 배지 CSS 클래스가 없어 스타일만 빠진 채 표시된다 |
| `answer`가 정수인가 | `'0'`(문자열)이나 `1.5`면 강조와 채점이 어긋난다 |
| `options` 안에 같은 텍스트가 없는가 | 정답 강조가 두 곳에 걸리고 "정답은 ○○입니다"가 어느 쪽인지 못 가리킨다 |
| `question`, `explanation`이 비어 있지 않은가 | 빈 화면이 나오고 원인을 찾기 어렵다 |
| `id`가 중복되지 않는가 | 2차에서 문제를 추가하다 겹치면 추적이 어려워진다 |
| `question` 텍스트가 중복되지 않는가 | 2차 확대 시 같은 문제를 다른 id로 두 번 쓰게 된다 |
| `CATEGORIES`의 id가 `QUESTIONS`에 모두 있는가 | 카드는 그려지는데 시작하면 빈 배열에서 문제를 뽑는다 |

**문제 수 검사는 "10개인가"가 아니라 "10 이상인가"로 쓴다.** 전자로 쓰면 2차에서 문제를 늘리는 순간 검사 자체가 걸림돌이 된다.

**실패 지점을 특정해야 한다.** 현행은 "어긋나면 시작을 막는다"뿐이라 40문제 중 어느 것이 틀렸는지 알 수 없다. 사용자 화면에는 일반 메시지를 띄우되, **콘솔에 문제 id와 위반 항목을 출력**한다(`kh_07: options 길이가 3`). 이 검사의 주 사용자는 플레이어가 아니라 데이터를 쓰는 사람이다.

**이 수정으로도 잡히지 않는 오류가 있다. 4절 3번을 볼 것.**

### 4. 검사 시점이 모호하다 (4.1-2)

"시작할 때"가 페이지 로드 시점인지 시작 버튼을 누른 시점인지 불분명하다. 4.1-1은 명확히 로드 시점이다.

**수정**: 두 검사를 로드 시점에 함께 수행하고 실패 시 같은 방식으로 처리한다. 시작 화면을 정상 표시했다가 버튼을 누른 뒤에야 막으면 원인을 알기 어렵다.

### 5. 검사 로직이 5단계에 배치되어 있다 (6절)

이 검사는 **1단계(문제 데이터 작성)에서 가장 필요한 도구다.** 40문제를 손으로 쓰면서 `answer` 인덱스나 선택지 개수를 틀리기 쉬운데, 검사가 5단계에 있으면 그때까지 발견하지 못한다. 2차에서 문제를 추가할 때도 이 검사가 관문 역할을 한다.

**수정**: 검사 함수를 1단계로 옮기고 1단계 완료 기준을 "검사를 통과한다"로 바꾼다. 완료 기준이 눈으로 확인하는 것에서 실행해서 확인하는 것으로 바뀐다.

### 6. 카테고리 카드의 키보드 접근성이 명시되지 않았다 (3.1절 + 4.2절)

4.2절은 선택지 버튼만 다룬다. "카드"라는 표현 때문에 `<div>`에 클릭 핸들러를 붙이는 구현이 나오기 쉽고, 그러면 **키보드만 쓰는 사용자는 게임을 시작할 수 없다.** 선택지 접근성을 그만큼 챙긴 문서에서 첫 화면이 막히는 것은 아깝다.

**수정**: 3.1절에 "카테고리 카드는 `<button>`으로 만들고 카드 모양은 CSS로 낸다"를 명시하고, 4.2절에 "조작 가능한 모든 요소는 키보드로 도달하고 실행할 수 있다"를 추가한다.

### 7. `aria-live` 이중 지정과 초점 이동이 서로 부딪힌다 (3.2절 + 4.2절)

두 문제가 겹쳐 있다.

- 4.2절은 "피드백 문구와 해설 영역에 `aria-live`를 준다"고 한다. 라이브 영역이 둘이면 알림이 두 번 발생하고, 갱신 순서와 낭독 순서가 일치한다는 보장이 없다.
- 3.2절은 답을 고른 뒤 "다음 문제" 버튼에 초점을 준다. **초점이 이동하면 스크린리더는 읽던 것을 끊고 새 요소를 읽는다.** 즉 정답 여부와 해설이 낭독되다 말고 "다음 문제 버튼"으로 넘어간다. 4.2절이 든 이유("정답 여부가 소리로 전달되지 않으면 다음 문제로 넘어갈 판단을 할 수 없다") 자체가 무력해진다.

라이브 영역과 초점 이동을 같은 타이밍에 쓰는 것은 알려진 안티패턴이다.

**수정**: `aria-live`를 쓰지 않고 **초점 이동 하나로 통일한다.**

- 피드백과 해설을 한 컨테이너에 담고 그 컨테이너에 `tabindex="-1"`을 준다.
- 답을 고르면 그 컨테이너로 초점을 옮긴다. 초점이 이동하면 스크린리더가 그 내용을 읽으므로 `aria-live` 없이 전달된다.
- "다음 문제" 버튼은 컨테이너 **바로 뒤**에 두어 Tab 한 번으로 닿게 한다.
- 시각적 스크롤은 기존대로 버튼이 화면에 들어오도록 한다.

이러면 낭독이 끊기지 않고, 낭독 순서가 "정답 여부 → 해설"로 보장되며, 3.2절의 원래 의도(버튼이 화면 밖으로 밀리지 않게)도 유지된다.

### 8. 이름 12자 초과 처리가 정의되지 않았다 (3.1절)

"앞뒤 공백을 잘라 낸 뒤 길이를 재며, 최대 12자까지 받는다"는 **초과 시 거부인지 절단인지를 정하지 않았다.** 그리고 `maxlength="12"`로 구현하면 자르기 전 기준으로 세므로 규칙과 어긋난다. 공백 3개 + 이름 10자를 입력하면 자르기 전에 잘려 나간다.

**수정**: 절단하지 않고 거부한다. 조용히 자르면 순위표에 본인이 입력한 적 없는 이름이 남는다. `maxlength`는 두지 않거나 넉넉히 두고, 시작 시점에 자른 결과가 12자를 넘으면 "이름은 12자까지 입력할 수 있습니다."를 빈 이름 안내와 같은 자리에 표시하고 시작을 막는다.

## 3. 개선 권고 11건

버그로 이어지지는 않지만 문서의 빈틈이거나 품질을 올리는 항목이다. 전부 반영한다.

1. **화면 전환 구현 방식 (3절 전반)** — 네 화면을 어떻게 감추는지 정의되지 않았다. `visibility: hidden`이나 투명도로 감추면 감춘 화면이 스크린리더에 읽히고 탭 순서에도 남는다. `hidden` 속성이나 `display: none`을 명시한다.
2. **화면 전환 시 초점 이동 (4.2절)** — 화면이 바뀌어도 초점이 사라진 버튼 자리에 남으면 스크린리더 사용자는 전환을 인지하지 못한다. 각 화면 제목에 `tabindex="-1"`을 주고 전환 직후 초점을 옮긴다.
3. **색 대비 기준 (4.2절)** — 난이도 배지 세 가지와 정답 초록, 오답 빨강의 대비 기준이 없다. "본문과 배경의 대비를 4.5:1 이상으로 한다(WCAG AA)"를 넣는다. 주황 계열 배지가 특히 흰 배경에서 대비가 안 나온다.
4. **`textContent` 규칙 승격 (3.3절)** — 3.5절에만 있는데 결과 화면도 이름을 표시한다. 3절 앞머리에 "플레이어가 입력한 값은 어느 화면에서든 `textContent`로 넣는다"를 일반 규칙으로 올린다.
5. **순위표 손상 시 복구 범위 (4.1-4)** — "빈 순위표로 초기화"가 다섯 개 전부인지 문제가 있는 것만인지 불분명하다. 순위표 단위로 검사해 깨진 것만 비운다. 하나가 깨졌다고 나머지 네 개를 날릴 이유가 없다.
6. **저장 직전에 다시 읽는다 (3.4절)** — 두 탭에서 각각 플레이하면 나중에 저장하는 쪽이 앞선 저장을 덮어쓴다. 저장 함수가 "읽기 → 삽입 → 정렬 → 자르기 → 쓰기" 순서를 지키고 **읽기를 쓰기 직전에** 하면 대부분 해결된다. 화면 진입 시점에 읽어 둔 값을 재사용하지 않는다.
7. **날짜에 `toISOString()`을 쓰지 않는다 (3.4절)** — "로컬 시간대 기준"이라 잘 적혀 있으나, 가장 흔한 구현인 `new Date().toISOString().slice(0, 10)`은 UTC라 **한국 시간 오전 9시 이전에는 전날 날짜가 찍힌다.** 2.1절이 `sort(() => Math.random() - 0.5)`를 짚어 금지한 것과 같은 성격의 함정이므로 같은 방식으로 경고를 넣는다.
8. **셔플 시점 (2.1절)** — "선택지 순서도 문제를 보여 줄 때마다 섞는다"는 재렌더링마다 섞는다는 뜻으로 읽힌다. "문제를 처음 그릴 때 한 번 섞고, 그 문제를 푸는 동안은 바꾸지 않는다"로 고친다.
9. **점수 표기의 모호함 (3.2절)** — 진행 상황 `3 / 10 문제`와 점수 `2 / 10`이 나란히 있으면 어느 쪽이 점수인지 즉시 읽히지 않는다. `점수 2 / 10`처럼 라벨을 붙인다.
10. **에러 메시지 해제 시점 (3.1절)** — "이름을 입력해 주세요."가 언제 사라지는지 없다. 입력란에 글자가 들어오면 지운다.
11. **3.2절 문단 정리** — "화면 상단에 다음을 표시한다" 목록 뒤에 "본문에는 ... 상단에는 '그만두기' 버튼을 둔다"가 다시 나와 상단 서술이 두 번 갈린다. 상단 요소를 한곳에 모은다.

## 4. 위 19건을 모두 반영해도 남는 문제

수정 항목을 반영해도 해결되지 않는 것들이다. 대부분 문서화로만 대응할 수 있다.

### 1. Safari는 `beforeunload`가 아예 동작하지 않는다 — 근거 사슬이 끊긴다

**필수 수정 1(해제 시점 명시)로는 풀리지 않는 별개 문제다.** iOS Safari는 `beforeunload`를 발생시키지 않고, 데스크톱 Safari도 지원이 제한적이다. Apple이 bfcache 정책상 의도적으로 막은 것이라 우회 방법이 없다. 대체로 거론되는 `pagehide`는 정리 작업용이라 **확인창을 띄울 수 없다.**

결과적으로 3.2절의 이탈 보호는 **Safari 사용자에게 존재하지 않는다.** 지원 브라우저에 Safari가 있고 모바일을 명시적으로 지원하는 제품이므로 무시할 수 없는 공백이다.

더 중요한 것은 **7절의 논리가 무너진다**는 점이다. 7절은 "진행 중 새로고침 시 이어 하기"를 제외하면서 근거로 "실수로 날리는 것은 확인창으로 막는다(3.2절)"를 들었다. Safari에는 그 확인창이 없으므로 제외 근거가 성립하지 않는다.

**권고: 제약을 인정하고 문서화한다.** 근거는 결정 A가 이미 심각도를 낮췄다는 것이다 — 한 판이 40문제였을 때는 이탈 손실이 컸지만 10문제면 다시 하면 된다. 이어 하기를 구현하면 진행 상태 저장 구조가 생겨 7절이 피하려던 복잡도가 그대로 돌아온다.

7절 해당 항목을 이렇게 고친다.

> - **진행 중 새로고침 시 이어 하기** — 진행 상황을 저장해야 하므로 저장 구조가 커진다. Chrome과 Edge에서는 확인창으로 실수를 막지만(3.2절), Safari는 `beforeunload`를 지원하지 않아 확인창 없이 진행 상황이 사라진다. 한 판이 10문제로 짧아 손실이 크지 않다고 보고 이대로 둔다.

### 2. `beforeunload` 확인창의 문구를 정할 수 없다

3.2절이 "확인창을 띄운다"고만 해서 구현자가 커스텀 문구를 쓰려 시도할 수 있다. 모든 최신 브라우저는 커스텀 메시지를 무시하고 자체 기본 문구를 띄운다. 문구를 정하는 작업은 헛수고이므로 "브라우저 기본 문구가 표시되며 내용을 지정할 수 없다"를 3.2절에 적어 둔다.

### 3. 데이터 검사로 잡을 수 없는 오류가 남는다

필수 수정 3으로 형식 오류는 대부분 잡히지만, **내용이 틀린 것은 기계가 판별할 수 없다.**

- `answer`가 0~3 안에 있지만 **실제 정답이 아닌 선택지를 가리키는 경우.** 검사도 통과하고 화면도 정상이며 채점만 조용히 틀린다. 2.1절이 경고한 "갱신을 빠뜨려도 화면은 정상으로 보인다"와 같은 종류의 실패다.
- `explanation`이 채워져 있으나 **정답과 무관하거나 틀린 내용인 경우.**
- 문제 텍스트가 **선택지 위치를 지칭하는 경우**("위의 두 번째 보기는"). 2.1절 규칙이지만 자동 검사는 오탐이 많다("두 번째로 큰 행성은?"은 정상 문제다).

**권고**: 1단계 완료 기준에 육안 검토를 명시한다. "모든 문제에 대해 `answer`가 가리키는 선택지가 실제 정답인지, 해설이 그 정답의 근거를 설명하는지 사람이 확인한다." 검사 함수가 있다고 해서 이 단계를 건너뛰면 안 된다는 점을 문서가 말해 주어야 한다.

### 4. Safari ITP 7일 저장 삭제

`https` 오리진에서도 적용되며 코드로 막을 방법이 없다. 서버를 두지 않는 이상 대응 불가다. 순위표 화면에 "기록은 이 브라우저에만 저장되며, 브라우저 정책에 따라 사라질 수 있습니다."를 표시해 오작동으로 오해하지 않게 한다.

### 5. 브라우저 뒤로 가기가 게임을 끊는다

네 화면을 한 페이지에서 전환하므로 히스토리 항목이 하나뿐이다. 퀴즈 진행 중 뒤로 가기를 누르면 시작 화면으로 돌아가는 것이 아니라 **사이트를 벗어난다.** 모바일에서 뒤로 가기는 매우 흔한 제스처이고, Safari에서는 확인창도 뜨지 않는다(위 1번).

`history.pushState`로 화면마다 히스토리 항목을 넣으면 해결되지만 화면 전환 전반을 다시 설계해야 한다. **이번 범위에서는 제외하고 7절에 제외 항목으로 명시할 것을 권한다.** 알려진 동작으로 적어 두는 것과 빠뜨리는 것은 다르다.

## 6. 대체 문구 초안

### 2절 게임 규칙 (해당 항목만)

> - 카테고리는 한국사, 과학, 지리, 예술과 문화 네 가지다.
> - 플레이 모드는 두 가지이며, 어느 쪽이든 한 판은 10문제다.
>   - **카테고리별 도전**: 고른 카테고리의 문제 중 10문제를 무작위로 뽑아 푼다.
>   - **전 범위 도전**: 무작위로 고른 두 카테고리에서 3문제씩, 나머지 두 카테고리에서 2문제씩 뽑아 모두 10문제를 푼다. 어느 카테고리가 3문제인지는 판마다 달라진다.
> - 만점은 두 모드 모두 10점이다.
> - 문제 선정과 순서 섞기는 판을 시작할 때마다 새로 한다. 선택지 순서는 문제를 처음 그릴 때 한 번 섞고, 그 문제를 푸는 동안은 바꾸지 않는다.

### 2.1절에 추가

> 문제를 뽑을 때도 같은 `shuffle`을 쓴다.
>
> ```javascript
> const counts = [3, 3, 2, 2];
> const order = shuffle(CATEGORIES);
> const picked = order.flatMap((cat, i) => shuffle(QUESTIONS[cat.id]).slice(0, counts[i]));
> const quiz = shuffle(picked);
> ```
>
> 마지막 줄을 빠뜨리면 한국사 세 문제가 연달아 나오고 그다음 과학 문제가 나오는 식으로 카테고리 순서대로 출제된다. 뽑기와 최종 순서 섞기는 별개 단계다.
>
> 이 배분은 카테고리가 네 개이고 한 판이 10문제라는 전제에 묶여 있다. 둘 중 하나를 바꾸면 `counts`를 다시 정해야 한다.
>
> 출제 수는 `QUIZ_LENGTH = 10` 상수로 두고 화면에 문제 수를 적을 때도 이 상수에서 조립한다. 라벨에 숫자를 직접 쓰면 출제 수를 바꿀 때 문구만 남아 사실과 어긋난다.

### 3.4절 순위표 표와 분리 근거

> | 순위표 | 대상 | 보관 수 | 만점 |
> |---|---|---|---|
> | 카테고리별 | 카테고리별 도전 결과 | 카테고리마다 상위 5개 | 10점 |
> | 전 범위 | 전 범위 도전 결과 | 상위 10개 | 10점 |
>
> 만점은 같지만 출제 범위가 다르므로 표를 나눈다. 전 범위 도전은 네 분야가 섞여 나오므로 한 분야를 깊게 아는 사람과 두루 아는 사람의 성적이 다르게 나온다. 같은 10점이어도 의미가 다르다.

### 3.4절 마지막 문단

> GitHub Pages 프로젝트 페이지는 `https://<사용자>.github.io/<저장소>/` 경로에 놓이지만 오리진은 `https://<사용자>.github.io` 하나다. 같은 계정에 올린 다른 프로젝트 페이지와 `localStorage`를 공유하므로, 다른 프로젝트가 키를 덮어쓰지 않도록 `quizGameRankings`라는 이름을 그대로 유지한다.

### 4절 비기능 요구사항

> | 항목 | 내용 |
> |---|---|
> | 배포 | GitHub Pages. 빌드 과정 없이 정적 파일 네 개를 그대로 올린다 |
> | 실행 | 브라우저에서 배포 URL로 접속한다. 로컬 확인은 `index.html`을 직접 열어도 된다 |
> | 경로 | 자원 참조는 모두 상대 경로로 쓴다. 프로젝트 페이지는 하위 경로에 놓이므로 `/style.css` 같은 절대 경로는 깨진다 |
> | 파일명 | 모두 소문자로 쓰고 참조와 정확히 일치시킨다. macOS는 대소문자를 구분하지 않지만 GitHub Pages는 구분하므로, 로컬에서 되던 참조가 배포 후 404가 날 수 있다 |
> | 외부 의존성 | 없다. 웹 폰트, CDN, 라이브러리를 쓰지 않는다 |
> | 반응형 | 모바일 세로 화면과 데스크톱을 모두 지원한다 |
> | 브라우저 | 최신 Chrome, Edge, Safari를 기준으로 한다 |
>
> ### 4.0 알려진 제약
>
> 다음은 코드로 해결할 수 없어 알려진 동작으로 둔다.
>
> - 순위 기록은 브라우저의 `localStorage`에만 남는다. 다른 브라우저나 다른 기기에서는 보이지 않고, 사용자가 브라우저 저장 데이터를 지우면 함께 지워진다.
> - **Safari는 사이트에 7일간 상호작용이 없으면 스크립트가 저장한 데이터를 삭제한다.** 일주일 넘게 방문하지 않은 Safari 사용자는 순위표가 빈 상태로 만나게 된다.
> - **Safari는 `beforeunload`를 지원하지 않는다.** 진행 중 새로고침이나 페이지 이탈을 막는 확인창(3.2절)이 Safari, 특히 iOS Safari에서는 뜨지 않는다.
>
> 순위표 화면에 "기록은 이 브라우저에만 저장되며, 브라우저 정책에 따라 사라질 수 있습니다."를 표시한다.

### 6절 구현 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1 | 데이터 검사 함수와 `questions.js` 작성 | 네 카테고리에 10문제씩 채우고 4.1-2의 모든 검사를 통과한다. 더해 모든 문제의 `answer`가 실제 정답을 가리키는지, 해설이 그 근거를 설명하는지 사람이 확인한다 |
| 2 | `index.html` 골격과 시작 화면 | 이름 입력, 카테고리 카드, 전 범위 도전 버튼이 보이고 화면 전환이 동작한다. 카드와 버튼을 키보드로 실행할 수 있다 |
| 3 | 문제 선정, 퀴즈 진행, 즉시 피드백 | 매 판 10문제가 새로 뽑히고 전 범위 도전에서 3+3+2+2 배분과 최종 섞기가 확인되며, 정답, 오답 강조와 해설이 표시되고 점수가 누적된다 |
| 4 | 결과 화면과 순위 기록, 순위표 화면 | 최종 점수가 나오고 `localStorage`에 순위가 저장되며, 다섯 개 순위표를 확인할 수 있고 다시 열어도 기록이 남아 있다 |
| 5 | 반응형 마무리와 에러 처리 | 모바일 폭에서 레이아웃이 깨지지 않고, 4.1의 네 상황과 4.2의 접근성 항목이 처리된다 |
| 6 | 배포와 배포 후 확인 | GitHub Pages에 올린 뒤 배포 URL에서 네 화면과 순위 저장이 동작한다. Safari로도 확인한다 |

기존 1단계 주석("문제를 10개만 쓰고 6단계에서 늘린다")은 8절 참조로 바꾼다.

**6단계를 새로 넣은 이유**: 파일명 대소문자와 상대 경로 문제는 로컬에서 절대 재현되지 않고 배포해야만 드러난다. 로컬 확인을 완료 기준으로 삼으면 이 두 가지를 놓친 채 완료가 된다.

## 7. 결정이 필요한 남은 항목

어느 쪽이든 타당해서 임의로 정하지 않았다. 답이 없으면 괄호 안 기본값으로 쓴다.

1. **"처음으로"를 눌렀을 때 이름을 남기는가** — 3.3절에 서술이 없고, 7절은 "'처음으로'를 누를 때까지 바뀌지 않는다"고 하여 초기화를 암시하는데 본문에 근거가 없다. 둘 중 하나는 고쳐야 한다. (기본값: **남긴다.** 순위표 화면에서 돌아올 때 남기기로 한 것과 같은 이유이며 지울 까닭이 없다. 7절 문구를 "브라우저를 닫았다 다시 열면 사라진다"로 정정한다.)
2. **전 범위 도전의 이름** — 40문제가 아니므로 "전체 도전 (40문제)"는 쓸 수 없다. (기본값: **"전 범위 도전"**. "전체"는 문제 수를 연상시키는데 실제로는 범위를 뜻하므로 오해를 줄인다.)
3. **카테고리 카드에 보유 문제 수를 함께 보여 주는가** — 1차에서는 보유 10, 출제 10으로 같지만 2차에서 갈린다. (기본값: **출제 수만 표시한다.** 플레이어에게 필요한 정보는 몇 문제를 푸는지다.)
4. **브라우저 뒤로 가기 처리** — 4절 5번. (기본값: **제외하고 7절에 명시한다.**)
