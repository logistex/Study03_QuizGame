## 3. 항목별 계획

### 3.1 초점 경로 (조치 2, 필수)

`showScreen`에 초점 이동 여부를 넘기는 인자를 더한다. 기본값은 지금 동작이라 나머지 네 호출부는 그대로 둔다.

```javascript
function showScreen(screenId, moveFocus) {
  document.querySelectorAll('.screen').forEach(function (section) {
    section.hidden = section.id !== screenId;
  });
  if (moveFocus !== false) {
    document.querySelector('#' + screenId + ' .title').focus();
  }
}
```

```javascript
// startGame
showScreen('screen-quiz', false);
renderQuestion();
```

검토가 제시한 `focusTarget`을 넘기는 형태를 택하지 않은 이유를 적는다.

- 초점을 어디로 옮길지 아는 책임은 `renderQuestion`에 있다. `startGame`이 `#question-text`를 알게 되면 같은 지식이 두 곳에 생긴다
- 4단계에서 결과 화면과 순위표를 그릴 때도 "화면을 드러내는 일"과 "무엇에 초점을 줄지"가 갈라져 있는 편이 낫다

계획서 두 줄을 함께 고친다.

- 358행 `showScreen` 계약 — 초점 이동을 생략할 수 있다는 것을 적는다. 이미 구현이 끝난 2단계 함수이므로 남은 단계의 함수 계약은 건드리지 않는다
- 563행 체크리스트 — 최종 상태가 아니라 **경로**를 보게 바꾼다

```javascript
// 판을 시작하기 전에 콘솔에 넣는다
const seen = [];
document.addEventListener('focusin', function (e) { seen.push(e.target.id); });
// 판을 시작한 뒤 seen을 본다
// 통과: ['question-text']   지금: ['quiz-title', 'question-text']
```

이 절차라야 재현이 된다. 검토가 "이번 검토가 아니면 4단계로 넘어갔을 항목"이라고 한 것이 맞고, 원인은 확인 방법이 최종 상태만 물은 데 있다.

### 3.2 스크린리더 낭독 (조치 1, 필수, 사람 확인)

나는 스크린리더를 실행할 수 없다. 확인은 사람이 한다. 순서를 적어 둔다.

1. VoiceOver(`Cmd+F5`) 또는 NVDA를 켠다
2. 이름을 넣고 아무 카테고리나 눌러 판을 시작한다 → **문제 텍스트가 읽히는가**
3. 아무 선택지나 고른다 → **판정과 해설이 둘 다 읽히는가**
4. "그만두기"를 눌러 시작 화면으로 돌아간다 → **화면 제목이 읽히는가**

3번이 핵심이다. 판정만 읽히고 해설이 끊기는 것도 "안 읽힌다"로 본다.

| 결과 | 대응 |
|---|---|
| 셋 다 읽힌다 | 구조를 그대로 두고 `#feedback`에 `aria-label="채점 결과"`만 붙인다 (조치 5) |
| 3번이 안 읽힌다 | `#feedback`에 `role="status"`를 주고 초점 이동을 없앤다. PRD 3.2절과 4.3절, 계획서 505행과 562행이 함께 바뀐다 |

두 번째 경로는 규격을 여는 일이라 4절에서 따로 다룬다.

### 3.3 포트와 캐시 (조치 3, 권고, 방법을 바꾼다)

권고는 "포트를 `8000`으로 고정하고 캐시는 Disable cache나 하드 리로드로 무력화"였다. **포트 고정은 받고 캐시 처리 방법은 바꾼다.**

받지 않는 이유는 둘이다.

- Disable cache는 개발자 도구가 열려 있는 동안만 걸린다. **미리보기 도구가 여는 창에는 적용되지 않는다**
- 하드 리로드와 새 탭은 이미 매 단계 해 봤고 풀리지 않았다(17번 문서 5절). 포트를 바꾸는 것만 통했다

원인을 이번에 확인했다. 서버가 `Cache-Control`을 아예 보내지 않고 `Last-Modified`만 보낸다. 그래서 브라우저가 스스로 정한 기간 동안 재검증 없이 캐시를 쓴다. 원인이 서버 쪽이므로 서버에서 막는다.

```python
# .claude/serve.py
import http.server

class NoCacheHandler(http.server.SimpleHTTPRequestHandler):
    def end_headers(self):
        self.send_header('Cache-Control', 'no-store')
        super().end_headers()

http.server.test(HandlerClass=NoCacheHandler, port=8000, bind='127.0.0.1')
```

- 이 형태로 응답에 `Cache-Control: no-store`가 붙는 것을 `curl -I`로 확인했다
- `.claude/launch.json`이 이 스크립트를 8000으로 띄우게 바꾼다
- `.claude/`는 `.gitignore` 대상이라 **배포 산출물이 아니다.** PRD 4.1절이 적은 `8000`과도 맞는다
- 이렇게 하면 4단계 완료 기준 5번("새로고침하고 순위표 보기")이 포트에 묶이지 않는다

### 3.4 R1 지표 (조치 4, 권고)

검토 측 수치를 그대로 두지 않고 20만 판을 다시 돌렸다. 값이 같다.

| 지표 | 최종 셔플 없음 | 최종 셔플 있음 (20만 판) |
|---|---|---|
| 최대 연속 | 항상 3 | 3 이상이 12.627% |
| 블록 수 | 항상 4 | 4가 0.092% |

- 셔플이 빠지면 카테고리별로 뽑아 이어 붙인 그대로라 블록 수가 **정확히 4**가 된다. 판정선이 값 하나로 떨어진다
- 계획서 544행의 확인 방법을 블록 수로 바꾼다. 눈으로 "뭉쳐 보이는가"를 묻던 것도 함께 없앤다

```javascript
// 전 범위 도전을 시작한 뒤 콘솔에 넣는다
state.quiz.map(q => q.categoryName).filter((c, i, a) => i === 0 || c !== a[i - 1]).length
// 통과: 5 이상   4면 최종 섞기 누락을 의심한다
```

- 판 다섯 번 반복은 그대로 둔다. 한 판으로도 판별되지만 배분 확인(3+3+2+2)을 겸하기 때문이다

## 4. 규격 동결과의 관계 — 판단을 요청한다

규칙은 이렇다. **2단계부터 6단계까지 PRD를 고치지 않고, 규격 변경은 8절(2차 구현)로 보낸다. 예외는 코드와 규격이 어긋난 것을 발견했을 때뿐이다.**

- **3.1은 예외에 해당한다.** 코드가 PRD 4.3절을 어겼으니 코드를 고친다. PRD는 건드리지 않는다
- **3.2의 "안 읽힌다" 경로는 예외가 아니다.** 코드는 규격대로 짜였고, 규격이 근거로 삼은 문장("초점을 옮기면 낭독은 보장된다", PRD 170행)이 사실과 다른 경우다

그래서 갈래가 둘이다.

| 갈래 | 결과 |
|---|---|
| (가) 8절로 보낸다 | 3단계는 그대로 둔다. 채점 결과가 전달되지 않는 상태로 5단계, 6단계를 지나 배포된다 |
| (나) 동결을 연다 | PRD 3.2절과 4.3절을 지금 고친다. 규격을 고치지 않는다는 원칙이 한 번 깨진다 |

- **(나)를 권한다.** 접근성 결함을 알고도 배포까지 끌고 가는 쪽이 나쁘다. 고치는 범위도 `#feedback` 한 곳으로 좁다
- 다만 **동결을 여는 것은 사람의 결정이다.** 3.2의 확인 결과가 "안 읽힌다"로 나오면 그때 묻는다
- 검토 측이 "규격 변경을 주저할 이유로 삼지 말라"고 적은 것은 받는다. 주저해서가 아니라 원칙을 세운 사람이 정할 일이라 올린다

## 5. 하지 않을 것

- 검토가 "코드상 이상 없음"으로 닫은 셋 — 키보드 활성화, 이탈 경고 확인창, 모바일 스크롤 — 은 코드를 건드리지 않는다. 사람이 볼 항목으로만 남긴다
- 3단계에서 잰 색 대비 다섯 조합은 다시 재지 않는다. 5단계에서 값이 바뀌었는지만 본다
- 4단계에서 생기는 순위표 강조 줄 색은 5단계 체크리스트에 새로 넣는다. 지금 넣지 않는다
