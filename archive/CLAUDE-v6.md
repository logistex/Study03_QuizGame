# 이 저장소에서 일하는 방법

『바이브 코딩』 5장 실습이다. **PRD를 쓰고, 새 세션에서 검토받아 고치고, 계획을 세우고, 다시 검토받고, 구현하고, 또 검토받는 과정 자체가 결과물이다.** 그래서 오간 문서를 지우지 않고 `history/`에 번호순으로 남긴다. 틀린 판단도 정정 문단을 달아 남긴다.

## 무엇을 먼저 읽나

| 무엇이 궁금한가 | 어디를 보나 |
|---|---|
| 무엇을 만드는가 | `spec/PRD.md` |
| 어떻게 만들고 확인하는가 | `spec/IMPL-PLAN.md` |
| 지금까지 오간 것 | `history/01`~, 번호순이 시간순 |
| 지금 열려 있는 것 | `history/25-open-items.md` |

## 단계마다 하는 일

1. 챕터 표시를 남긴다. **일이 실제로 시작될 때** 찍는다. 미리 찍으면 엉뚱한 작업이 그 아래 들어간다
2. 계획서의 해당 단계 절을 읽고 그대로 구현한다
3. 완료 기준과 체크리스트를 하나씩 밟는다
4. 커밋하고 태그를 붙인다 — `git tag stage4 && git push origin --tags`
5. 작업 보고서를 `history/`에 쓴다
6. 노트용 요약을 만들어 노션에 넣는다
7. README의 단계 표와 문서 목록을 갱신한다

검토 지적을 반영할 때는 하나가 더 붙는다.

8. **바꾼 동작을 서술한 자리를 전부 맞추고 그 사실을 알린다.** 코드, 계획서 본문, 함수 계약, PRD, **뒤 단계의 검증 절차와 체크리스트**가 모두 그 자리다. 회신을 쓴 뒤에 결정이 더 나오면 회신 문서에 덧붙임을 남긴다

**"셋"으로 세지 않는다.** 처음에는 "코드, 계획서, PRD 셋을 맞춘다"로 적었는데, 그 "셋"이 범위를 세 파일로 좁혔다. 세 파일은 맞췄는데 5단계 검증 절차를 빠뜨렸고, 그대로 밟았으면 정상인 것을 결함으로 판정했을 뻔했다. 규칙을 둘로 나눠 두면 "앞엣것 했으니 됐다"는 판단이 다시 생긴다.

**찾는 방법은 둘을 지킨다.**

- **문구가 아니라 식별자로 찾는다.** 요소 id와 함수 이름은 동작이 바뀌어도 그대로다. 화면 문구로 찾으면 문구가 바뀌는 변경에서 놓친다
- **고치기 전에 검색해 목록을 만든다.** 고친 뒤에 검색하면 이미 바꾼 자리가 안 걸려 목록 자체가 불완전해진다

```bash
grep -rn "btn-clear\|renderRankingScreen" spec/   # 고치기 전에, 식별자로
```

목록을 만들어 두면 다 밟았는지가 판단이 아니라 대조가 된다.

## 검토 지적을 받으면

**먼저 재현해 사실을 확인한 뒤 고친다.** 1단계에서 이 방식으로 검토 측 오류 두 건을 잡았고, 4단계에서는 지적이 사실임을 재현으로 확인한 뒤 고쳤다.

- 지적을 그대로 받지 않고 **처방을 바꾸는 것은 된다.** 다만 왜 바꿨는지를 회신에 적는다
- 근거가 틀렸다는 지적을 받으면 결론이 같더라도 **근거를 고친다.** 틀린 전제가 남으면 나중에 그 전제로 다른 결정을 내릴 때 틀린다

## 규격이란 무엇인가

**`spec/` 폴더의 두 문서를 함께 말한다.** PRD만 뒤지고 "규격에 없다"고 하지 않는다.

- `spec/PRD.md` — 무엇을 만드는가. 정본이다
- `spec/IMPL-PLAN.md` — 어떻게 만들고 확인하는가. 육안 검토 절차가 여기 있다

`history/`의 검토 문서는 규격이 아니다. 관점의 출처일 뿐이고, 채택된 권고는 `spec/`으로 옮겨져 있다.

이 구분을 안 지켜 사고가 났다. 서로 못 보고 만든 두 판이 같은 자리에서 틀렸다 — 출처 둘 이상 대조를 "규격 밖"으로 표시했는데 `spec/IMPL-PLAN.md` 1.8절 7번에 있다.

**문서나 규격의 낱말을 그대로 옮길 때는 그 분류가 지금도 맞는지 확인한다.** 확인하지 않았으면 "확인하지 않았다"를 함께 적는다.

낱말은 쓰인 시점의 도구를 담고 있다. 그대로 옮기면 그 시점에 갇힌다.

- 계획서가 "육안 검토"라고 적은 것을 "사람이 보는 항목"으로 옮겼는데, 그 여덟을 지금은 클로드가 판정한다. 검사 함수가 못 잡는다는 뜻이지 모델이 못 한다는 뜻이 아니었다
- "규격이 정한 실행 경로는 브라우저"라고 옮기고 명령줄 경로가 없는 것을 규격 밖이라 했는데, **없다는 것 자체가 규격의 공백**이었다

## 규격 동결

**2단계부터 6단계까지 PRD를 고치지 않는다.** 규격 변경이 필요하면 PRD 8절(2차 구현 예정)로 보낸다.

예외는 하나다. **코드와 규격이 어긋난 것을 발견했을 때.** 새 요구를 넣는 것이 아니라 이미 구현된 것을 적는 일이라 설계를 흔들지 않는다.

계획서도 같은 기준이다. 남은 단계의 함수 계약과 요소 id 계약은 건드리지 않는다. 다만 **이미 끝난 단계의 검증 절차를 고치는 것은 된다.** 계획서는 "어떻게 확인하는가"라 산출물이 바뀌지 않기 때문이다.

## 검증

- 검증 수단은 셋이다 — 데이터 검사 함수, 클로드의 판정, 그리고 브라우저에서 직접 확인하는 수동 체크리스트. 테스트 프레임워크를 도입하지 않는다
- **클로드가 판정하고 사람이 채택 여부를 결정한다.** 문항 규칙 여덟 가지가 이 자리다(`spec/PRD.md` 3.6절, `spec/IMPL-PLAN.md` 1.8절). 검사 함수와 달리 재현되지 않으므로 **서로 다른 세션 둘이 각각 한 번씩** 돌고 라운드마다 기록을 남긴다
- **콘솔 대체를 허용하는 자리에는 그 대체가 건너뛰는 경로를 함께 적는다.** 무엇을 대신할 수 있는지만 적으면, 대신하는 순간 무엇이 확인되지 않는지가 남지 않는다
- **화면에 증상이 없는 결함이 이 프로젝트의 주된 위험이다.** 최종 상태만 보는 확인은 경로에서 생기는 결함을 놓친다. 초점 이동은 `focusin` 기록으로, 순위 인덱스는 코드 확인으로 판정한다

### 도구의 한계

- **브라우저 자동화가 키 이벤트의 기본 동작을 일으키지 못한다.** `keydown:Enter`는 도착하는데 클릭이 합성되지 않는다. 초점 이동까지만 자동으로 확인하고 **누르는 것은 사람에게 맡긴다**
- `confirm` 확인창도 자동으로 띄울 수 없다. 핸들러가 붙어 있는지를 세어 판정한다
- **스크린리더는 사람만 확인할 수 있다.** 소리를 잡을 수 없다

## 개발 환경

`.claude/`에 `serve.py`와 `launch.json`이 있다. **둘 다 gitignore 대상이라 새 세션에는 없다.** 없으면 아래를 다시 만든다.

```python
# .claude/serve.py
import http.server


class NoCacheHandler(http.server.SimpleHTTPRequestHandler):
    def end_headers(self):
        self.send_header('Cache-Control', 'no-store')
        super().end_headers()


if __name__ == '__main__':
    http.server.test(HandlerClass=NoCacheHandler, port=8010, bind='127.0.0.1')
```

**브라우저가 `script.js`를 캐시해 새 코드가 실행되지 않는 일이 3단계까지 매번 생겼다.** 원인은 `python3 -m http.server`가 `Cache-Control`을 보내지 않고 `Last-Modified`만 보내는 것이다. 강제 새로고침과 새 탭으로는 안 풀렸고 포트를 바꾸는 것만 통했는데, 새 오리진에 캐시 항목이 없어서였다.

- **포트를 바꿔 가며 개발하지 않는다.** 오리진이 달라져 `localStorage`가 분리되고, 4단계부터는 순위 기록이 사라진 것처럼 보인다
- 포트는 **8010**이다. PRD 4.1절은 8000으로 적었으나 다른 작업이 그 포트를 쓰고 있어 비켜 두었다. 중요한 것은 값이 아니라 고정이다
- 로컬에서 `file://`로 열면 사파리는 `localStorage` 접근에서 오류를 낸다. 로컬 확인은 크롬이나 엣지로 한다(PRD 4.1절)

## 배포

`gh-pages` 브랜치가 배포물이다. `main`은 소스와 문서만 담는다.

```
gh-pages/
├── index.html, style.css, script.js, questions.js   최신본
├── .nojekyll
├── stage1-final/   각 단계의 검토 반영까지 끝난 시점, 파일 넷만
├── stage2/         2단계만 -final이 없다
├── stage3-final/
├── stage4-final/
└── stage5-final/
```

태그가 바뀌면 그 폴더만 다시 만든다. `git archive`가 태그 시점의 파일을 그대로 꺼내므로 워크트리를 만들 필요가 없다.

```bash
git worktree add --detach /tmp/ghp && cd /tmp/ghp && git checkout gh-pages
git archive main index.html style.css script.js questions.js | tar -x
for t in stage1-final stage2 stage3-final stage4-final stage5-final; do
  mkdir -p "$t" && git archive "$t" index.html style.css script.js questions.js | tar -x -C "$t"
done
```

- **문서는 복사하지 않는다.** `spec/`, `history/`, `archive/`까지 넣으면 같은 문서가 여섯 벌 생긴다
- **여섯 주소가 같은 오리진이라 `localStorage`를 공유한다.** 3단계를 보다 4단계로 가면 앞서 쌓인 기록이 그대로 보인다. 저장 키에 단계를 붙이는 것은 배포본 코드를 고치는 일이라 하지 않고, 노트에 한 줄 적는 것으로 갈음한다

## 2차 구현

1차 구현(1~6단계)은 배포로 닫혔다. 2차 구현은 문서를 폴더로 나눈다.

```
spec/            PRD.md — 정본 하나. 2차에서도 이것을 고친다
phase2/spec/     IMPL-PLAN-2.md — 2차 구현 계획
phase2/history/  2차에서 오간 문서. 번호는 1차에서 이어 붙인다
phase2/archive/  2차의 개정 전 판본
.claude/commands/  커스텀 명령어. 수정 이력이 남도록 저장소에 둔다
```

- **PRD는 나누지 않는다.** 정본이 둘이 되면 어느 쪽이 맞는지 매번 판단하게 된다. 2차 착수 시점의 PRD를 `archive/`에 보존하고 `spec/PRD.md`를 고친다
- **계획서는 나눈다.** 1차 계획서가 900줄에 가깝고, 2차는 단계와 검증이 다르다
- **문서 번호는 이어 붙인다.** 폴더가 갈려도 "17번 문서"가 하나를 가리켜야 한다

## `CLAUDE.md`를 고칠 때

**고치기 전 판을 `archive/CLAUDE-vN.md`로 남긴다.** 첫머리에 어느 시점인지와 현재 문서가 어디인지를 적는다. 노션 노트가 그 판본을 링크로 참조한다.

| 판본 | 시점 |
|---|---|
| `CLAUDE-v1.md` | 최초본. 규칙을 인계 문서에서 옮겨 온 시점 |
| `CLAUDE-v2.md` | 1차 구현을 마치고 5, 6단계 검토까지 반영한 시점 |
| `CLAUDE-v3.md` | 세 세션 합의로 명령어 생성 프롬프트를 정하기 직전 시점 |
| `CLAUDE-v4.md` | 확인 수단을 "클로드가 판정"으로 바꾸기 직전 시점 |
| `CLAUDE-v5.md` | 판정 두 번을 서로 다른 세션이 하도록 조이기 직전 시점 |

## 저장소 구조와 태그

```
spec/      PRD.md, IMPL-PLAN.md — 현행 규격
history/   오간 문서, 번호순이 시간순
consensus/ 세 세션이 함께 결론을 내는 문서, 라운드순. 규칙은 consensus/00-rules.md
archive/   개정 전 판본 (PRD-v1~v3, README-v1~v3)
doc/       교재 집필용 내부 문서 (gitignore)
```

태그는 **그 단계 작업이 끝난 시점**을 가리킨다. 노트의 산출물 표가 이 태그로 소스를 링크한다.

| 태그 | 뜻 |
|---|---|
| `stage1`~`stage4` | 그 단계 구현을 마친 시점. 검토 반영은 아직이다 |
| `stage1-final`, `stage3-final`, `stage4-final` | 검토 반영까지 끝난 시점 |

**2단계에는 `-final`이 없다.** 2단계 검토를 3단계와 묶어 받아 단독 최종본이 존재하지 않는다. 노트의 단계별 실행 링크는 `-final`이 있으면 그것을, 없으면 원래 태그를 쓴다.

## 커스텀 명령어와 스킬을 만들 때

**만들 때마다 프롬프트에 다시 적지 않아도 되도록 여기 둔다.**

- **앞머리는 YAML이다.** `argument-hint` 값이 대괄호로 시작하면 따옴표로 묶는다. 안 묶으면 목록으로 읽혀 깨지고, 클로드 코드는 그대로 실행하므로 깃허브 화면에서만 드러난다
- **만들면 그 자리에서 한 번 돌려 확인한다.** 만들어 놓고 끝내지 않는다. 돌려 보지 않은 절차는 그럴듯한 문장으로 남는다
- 새 파일 첫머리의 생성 일시는 아래 문서 작성 규칙을 따른다

**여기 두지 않는 것이 있다.** "대상 파일을 고치지 말라"는 명령어마다 다르다. `quiz-validate`는 고치면 안 되고 `quiz-add`는 고치는 것이 일이다. 명령어의 성격에서 나오는 것은 그 명령어의 프롬프트에 적는다.

## 문서 작성

- 요약문은 **개조식**으로 쓴다. 마침표를 붙이지 않고 굵게 표기도 쓰지 않는다. 20~30줄로 짧게
- 설명이 필요한 낱말을 쓰지 않는다. "탐침", "산문" 같은 표현으로 두 번 지적받았다
- 가운뎃점 대신 쉼표를 쓴다
- 새로 만드는 파일 첫머리에 `<!-- 생성: YYYY-MM-DD HH:MM KST -->`를 넣는다. 시각은 `TZ=Asia/Seoul date`로 확인한다
- **번호를 붙일 때는 마지막 번호를 확인하고 다음 번호를 쓴다.** 경로가 비었는지만 보고 번호가 비었는지를 안 봐서 17번이 겹친 적이 있다

편집 규칙이 있다. 사고를 내고 얻은 것이다.

1. **넣기 전에 그 자리 원문을 탭까지 그대로 확인한다.** 노션 본문은 탭으로 들여쓰고 공백이 아니다
2. **붙일 자리의 앞뒤를 포함한 유일한 문자열**을 `old_str`로 잡는다
3. **넣은 뒤 이웃 블록이 그대로인지 확인한다.** 이것을 빠뜨려 블록 하나를 잃은 적이 있다
4. 한글을 유니코드 코드값으로 적다 오타를 여러 번 냈다. **넣은 뒤 반드시 되읽는다**
5. 페이지가 커지면 편집이 통째로 막힌다(`rich_text_element_count` 한도). 한 줄 수정도 거부되므로 페이지를 줄여야 한다

토글은 `<details>` / `<summary>`이고 자식을 탭으로 들여쓴다. 계층은 `5.1.6.N`이 탭 2개, `a)`가 3개, 그 아래가 4개, 항목이 5개다.
