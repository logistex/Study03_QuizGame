# 상식 퀴즈 게임 PRD

## 1. 개요

### 1.1 목적

4지선다 객관식 상식 퀴즈 게임을 만든다. 플레이어는 이름을 입력하고 카테고리를 골라 문제를 풀며, 답을 고르는 즉시 정답 여부와 해설을 확인한다. 한 판이 끝나면 최종 점수를 확인하고, 기록이 상위권에 들면 순위표에 이름이 남는다.

### 1.2 대상 사용자

- 로그인이나 회원 가입 없이 링크로 바로 접속해 즐기려는 개인 사용자
- 모바일과 데스크톱 어느 쪽에서든 브라우저만으로 즐기려는 사용자

### 1.3 기술 스택

| 항목 | 선택 |
|---|---|
| 언어 | Vanilla JavaScript (ES6+) |
| 마크업, 스타일 | HTML5, CSS3 |
| 인증 | Supabase Auth. 로그인은 깃허브 계정으로만 한다 |
| 데이터 저장 | Supabase (PostgreSQL) |
| 문제 데이터 | DB 테이블 (1차의 `questions.js`를 대신한다) |
| 서버 코드 | Vercel Functions (`api/` 폴더의 자바스크립트 파일) |
| 문항 생성 | Anthropic API (서버 함수에서만 호출한다) |
| 외부 라이브러리 | 브라우저가 DB를 직접 조회하는 것은 3.8절이 정했다. 그것을 클라이언트 라이브러리로 할지 `fetch`로 할지는 `spec/IMPL-PLAN-2.md`에서 정한다 |
| 배포 | Vercel |
| 실행 방식 | 배포 URL로 접속. `index.html`을 직접 열면 서버 함수가 없어 동작하지 않는다 |

**프레임워크를 도입하지 않는다.** 1차와 같이 HTML, CSS, 자바스크립트 파일만으로 구성하고 서버가 필요한 자리에만 `api/` 폴더의 함수 파일을 둔다. 1차의 단순함을 유지하는 것이 학습 목적에 맞는다.

**GitHub Pages에서 Vercel로 옮기는 까닭은 DB 때문만이 아니다.** 정적 호스팅은 파일을 전달할 뿐 요청마다 코드를 실행하지 않으므로, 채점을 서버에서 하려면 코드를 실행할 자리가 있는 곳으로 옮겨야 한다.

### 1.4 파일 구성

| 파일 | 역할 |
|---|---|
| `index.html` | 화면들의 마크업을 모두 담는다 |
| `style.css` | 전체 스타일과 반응형 레이아웃 |
| `script.js` | 게임 상태 관리, 화면 전환, 서버 함수 호출, 화면 렌더링 |
| `api/` | 서버 함수를 둔다. 책임 넷을 맡는다 — 문항을 정답 열 없이 전달하는 것, 채점하고 응시 기록을 저장하며 순위표를 돌려주는 것, 문항을 생성해 검증하는 것, 역할을 바꾸는 것 |

**넷째 책임은 3.8절이 정한 것이다.** 역할을 바꾸는 것은 서버 함수만 한다.

**파일을 몇 개로 나눌지와 그 이름은 `spec/IMPL-PLAN-2.md`에서 정한다.** 여기서 이름을 정해 두면 계획서가 그것에 묶인다.

**`questions.js`가 사라진다.** 문항이 DB로 옮겨 가므로 브라우저에 문제 데이터를 통째로 내려보내지 않는다. 1차의 파일은 태그 안에 그대로 남는다.

**채점 로직이 `script.js`에서 빠진다.** 브라우저는 고른 선택지 번호를 서버에 보내고, 맞는지는 서버 함수가 판정한다.

`index.html` 머리에서 `style.css`를 연결하고, 하단에서 `script.js`를 읽는다. **문제 데이터를 읽는 `<script>` 태그가 없다.** 문항은 서버 함수를 통해 받는다.

```html
<link rel="stylesheet" href="style.css">
...
<script src="script.js"></script>
```

1차에서는 `questions.js`를 `script.js`보다 먼저 읽어 로드 순서를 태그 순서로 보장했다. 2차에서는 문항이 요청으로 도착하므로 그 보장이 필요 없어진다.

**자원 참조는 모두 상대 경로로 쓴다.** 1차에서는 GitHub Pages 프로젝트 페이지가 `https://<사용자>.github.io/<저장소>/` 하위 경로에 놓이는 것이 까닭이었다. 2차 배포처는 도메인 루트에 놓이므로 그 까닭은 사라지나, 배포처를 다시 옮기거나 하위 경로에 두게 될 때를 대비해 지시는 그대로 둔다.

### 1.5 문제 데이터를 파일이 아닌 DB에 두는 이유

1차에서는 `questions.js`를 `<script>` 태그로 읽었다. 빌드 도구 없이 로드 순서를 보장할 수 있고, 초기화가 동기적으로 끝나 데이터 검사를 페이지 로드 시점에 한 번에 마칠 수 있었기 때문이다.

2차에서 DB로 옮기는 까닭은 둘이다.

- **정답을 브라우저에 내려보내지 않기 위해서다.** 파일로 두면 문제와 정답과 해설이 통째로 학생의 컴퓨터에 도착한다.
- **선생님이 화면에서 문항을 늘릴 수 있게 하기 위해서다.** 파일을 고치려면 개발 도구를 다루어야 한다.

문제 데이터 검사(4.2절)는 페이지 로드 시점이 아니라 **문항을 넣는 시점에 서버에서** 한다. 검사 항목 자체는 바뀌지 않는다.

## 2. 게임 규칙

- 4지선다 객관식이다.
- 카테고리는 한국사, 과학, 지리, 예술과 문화 네 가지다.
- 플레이 모드는 두 가지이며, **어느 쪽이든 한 판은 10문제다.**
  - **카테고리별 도전**: 고른 카테고리의 문제 중 10문제를 무작위로 뽑아 푼다.
  - **전 범위 도전**: 무작위로 고른 두 카테고리에서 3문제씩, 나머지 두 카테고리에서 2문제씩 뽑아 모두 10문제를 푼다. 어느 카테고리가 3문제인지는 판마다 달라진다.
- 만점은 두 모드 모두 10점이다.
- 문제 선정과 순서 섞기는 판을 시작할 때마다 새로 한다. 선택지 순서는 문제를 처음 그릴 때 한 번 섞고, 그 문제를 푸는 동안은 바꾸지 않는다.
- 정답은 1점, 오답은 0점이다. 난이도는 배점에 영향을 주지 않는다.
- 답을 고르면 즉시 정답 여부와 해설을 보여 주고, 그 문제는 다시 고를 수 없다.
- 한 판이 끝나면 최종 점수와 정답률을 보여 주고, 상위권 기록이면 순위표에 남긴다.

### 2.1 문제 선정과 셔플

문제 선정, 문제 순서 섞기, 선택지 순서 섞기에 모두 Fisher-Yates 알고리즘을 쓴다.

```javascript
function shuffle(arr) {
  const a = arr.slice();
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}
```

`sort(() => Math.random() - 0.5)`는 쓰지 않는다. 비교 결과가 호출할 때마다 달라져 순서가 고르게 섞이지 않고, 정답이 특정 자리에 더 자주 남는다. 섞이기는 하므로 화면으로는 이상을 알아챌 수 없다.

**출제 수는 `QUIZ_LENGTH = 10` 상수로 둔다.** 화면에 문제 수를 적을 때도 이 상수에서 조립한다. 라벨에 숫자를 직접 쓰면 출제 수를 바꿀 때 문구만 남아 사실과 어긋난다.

카테고리별 도전은 해당 카테고리에서 바로 뽑는다.

```javascript
const quiz = shuffle(QUESTIONS[categoryId]).slice(0, QUIZ_LENGTH);
```

전 범위 도전은 카테고리마다 정해진 수만큼 뽑은 뒤 **합친 결과를 다시 섞는다.**

```javascript
const counts = [3, 3, 2, 2];
const order = shuffle(CATEGORIES);
const picked = order.flatMap((cat, i) => shuffle(QUESTIONS[cat.id]).slice(0, counts[i]));
const quiz = shuffle(picked);   // 이 줄을 빠뜨리면 카테고리 순서대로 나온다
```

마지막 줄을 빠뜨리면 한국사 세 문제가 연달아 나오고 그다음 과학 문제가 나오는 식으로 카테고리 순서대로 출제된다. 뽑기와 최종 순서 섞기는 별개 단계다.

**이 배분은 카테고리가 네 개이고 한 판이 10문제라는 전제에 묶여 있다.** 둘 중 하나를 바꾸면 `counts`를 다시 정해야 한다.

카테고리를 균등하게 배분하는 이유는 순위표 때문이다. 40문제에서 단순 무작위로 10개를 뽑으면 한국사가 5문제 나오는 판이 생기는데, 그런 판은 사실상 카테고리 도전에 가까우면서도 전 범위 순위표라는 같은 표에서 겨루게 된다. 배분을 고정하면 판 간 난이도 편차가 줄어 순위 비교가 성립한다.

선택지를 섞으면 규칙 둘이 따라온다.

- 선택지를 섞은 뒤에는 `answer`를 정답 텍스트의 새 인덱스로 갱신한다. 갱신을 빠뜨려도 화면은 정상으로 보이므로 채점만 조용히 틀린다.
- 문제 텍스트와 해설은 선택지의 위치를 지칭하지 않는다. "위의 두 번째 보기는"과 같은 표현은 섞는 순간 사실과 어긋난다. 이 규칙은 문제 데이터를 쓰는 1단계에서 지켜야 한다.

## 3. 기능 요구사항

### 3.0 모든 화면에 적용되는 규칙

- **화면 전환은 `hidden` 속성이나 `display: none`으로 한다.** `visibility: hidden`이나 투명도로 감추면 감춘 화면의 내용이 스크린리더에 읽히고 탭 순서에도 남는다.
- **화면을 전환한 직후 그 화면의 제목으로 초점을 옮긴다.** 제목에 `tabindex="-1"`을 준다. 초점이 사라진 버튼 자리에 남으면 스크린리더 사용자는 화면이 바뀐 사실을 알 수 없다.
- **플레이어가 입력한 값은 어느 화면에서든 `textContent`로 넣는다.** 입력값이 마크업으로 해석되지 않게 한다.
- **조작 가능한 요소는 모두 `<button>`이나 표준 폼 요소로 만든다.** 카드처럼 보이는 것도 마찬가지이며 모양은 CSS로 낸다. `<div>`에 클릭 핸들러를 붙이면 키보드 사용자가 조작할 수 없다.

### 3.1 시작 화면

- 게임 제목을 표시한다.
- **로그인한 사용자만 게임을 시작할 수 있다**(3.7절). 로그인하지 않았으면 시작을 막고 로그인으로 안내한다. 로그인 화면은 하나다.
- 로그인한 사용자의 이름을 표시한다. **순위표에 남는 이름도 이것이며 화면에서 따로 입력받지 않는다**(3.10절).
- 카테고리 카드 네 개를 표시한다. 각 카드에는 카테고리 이름과 **출제 수(10문제)** 를 적는다. 숫자는 `QUIZ_LENGTH`에서 조립하며 마크업에 직접 쓰지 않는다. 보유 문제 수는 표시하지 않는다. 플레이어에게 필요한 정보는 몇 문제를 푸는지다.
- "전 범위 도전 (10문제)" 버튼을 별도로 둔다.
- "순위표 보기" 버튼을 두어 저장된 기록을 확인할 수 있게 한다.
- **연습 모드를 고를 수 있다.** 연습으로 응시하면 채점과 해설은 그대로 받되 기록이 남지 않는다(3.4절).
  - 시연이나 시험 삼아 친 판이 순위표에 남는 것을 막는 것이 첫 목적이나, 학생이 연습하는 데도 쓴다.
  - **별도 주소로 가르지 않는다.** 주소는 숨겨지지 않고, 숨길 까닭도 없다.
- 카드나 전 범위 도전 버튼을 누르면 해당 모드로 퀴즈를 시작한다.

### 3.2 퀴즈 진행 화면

화면 상단에 다음을 표시한다.

- 진행 상황 (예: `3 / 10 문제`)
- 현재 점수 (예: `점수 2 / 10`). "점수" 라벨을 붙인다. 진행 상황과 표기가 같은 꼴이라 라벨이 없으면 어느 쪽이 점수인지 즉시 읽히지 않는다.
- 현재 문제의 카테고리 이름과 난이도 배지
- "그만두기" 버튼

난이도 배지는 CSS 클래스로 색을 구분한다.

| 난이도 | 클래스 | 색 계열 | 화면 라벨 |
|---|---|---|---|
| `easy` | `diff-easy` | 초록 | 초급 |
| `medium` | `diff-medium` | 파랑 | 중급 |
| `hard` | `diff-hard` | 주황 | 고급 |

본문에는 문제 텍스트와 선택지 버튼 네 개를 둔다. 그 아래에 피드백 영역과 "다음 문제" 버튼을 이 순서로 둔다.

문제를 새로 그릴 때는 **문제 텍스트로 초점을 옮긴다.** 스크린리더가 새 문제를 읽게 하기 위해서다.

선택지를 누른 뒤의 동작은 다음과 같다.

- 네 버튼을 모두 비활성화해 재선택을 막는다.
- 정답 버튼을 초록색으로 강조하고 ✓를 함께 표시한다.
- 오답을 골랐다면 고른 버튼을 빨간색으로 강조하고 ✗를 함께 표시한다. 색만으로 구분하지 않는다.
- 피드백 영역에 정답 여부와 해설을 함께 채운다. 정답이면 "정답입니다.", 오답이면 "오답입니다. 정답은 ○○입니다."로 적으며, ○○ 자리에는 정답 선택지의 텍스트를 넣는다. 그 아래에 해당 문제의 해설을 붙인다.
- **피드백 영역으로 초점을 옮긴다.** 영역에 `tabindex="-1"`을 준다.
- "다음 문제" 버튼을 노출한다. 마지막 문제에서는 "결과 보기"로 표시한다.
- 버튼이 화면에 들어오도록 스크롤한다. 해설이 펼쳐지면 모바일에서 버튼이 화면 밖으로 밀리는데, 눌러야 넘어가는 구조라 그대로 두면 게임이 멈춘 것처럼 보인다.

**피드백 영역에 `aria-live`를 주지 않는다.** 초점을 옮기면 스크린리더가 그 내용을 읽으므로 낭독은 보장되고, 라이브 영역과 초점 이동을 함께 쓰면 낭독이 도중에 끊긴다. 정답 여부와 해설을 한 영역에 담고 초점 이동 하나로 전달하며, "다음 문제" 버튼을 영역 바로 뒤에 두어 Tab 한 번으로 닿게 한다.

"다음 문제"를 누른 뒤의 동작은 다음과 같다.

- 버튼을 즉시 숨기고 다음 문제를 그린 뒤 다시 노출한다. 연타로 문제를 건너뛰는 것을 막는다.
- 스크롤을 문제 영역 상단으로 되돌린다. 앞 문제에서 내려간 위치 그대로 두면 다음 문제가 중간부터 보인다.

자동으로 다음 문제로 넘어가지 않는다. 해설을 읽을 시간이 필요하므로, 플레이어가 버튼을 눌러야 넘어간다.

"그만두기"를 누르면 확인창을 띄우고, 확인하면 기록을 남기지 않은 채 시작 화면으로 돌아간다. 잘못 고른 카테고리로 들어갔을 때 판을 끝낼 때까지 나갈 수 없는 상태를 막기 위한 것이다.

#### 이탈 경고

진행 중에 새로고침하거나 페이지를 닫으려 하면 `beforeunload`로 확인창을 띄운다. 이어 하기는 범위 밖이므로(7장), 실수로 진행 상황을 날리는 것만 막는다.

- **핸들러는 판을 시작할 때 등록하고, 다음 두 시점에 해제한다.** 마지막 문제를 마치고 결과 화면으로 넘어갈 때, "그만두기"를 확인했을 때. 데이터 검사 실패(4.2절)는 해제 대상이 아니다. 검사가 실패하면 판이 시작되지 않으므로 등록 자체가 일어나지 않는다. 해제하지 않으면 정상적으로 끝낸 뒤에도 창을 닫을 때마다 경고가 뜬다. 정상 종료에까지 경고가 붙으면 사용자는 경고를 무시하는 법을 배우고, 정작 진행 중 실수를 막는 효과가 사라진다.
- **확인창 문구는 지정할 수 없다.** 모든 최신 브라우저가 커스텀 메시지를 무시하고 자체 기본 문구를 띄운다. 문구를 정하는 작업은 하지 않는다.
- **Safari에서는 이 경고가 동작하지 않는다.** 4.1절을 볼 것.

### 3.3 결과 화면

- 최종 점수를 표시한다 (예: `8 / 10 정답`).
- 정답률을 백분율로 표시한다. 소수점 첫째 자리에서 반올림한 정수로 적는다.
- 플레이어 이름과 플레이한 모드를 함께 표시한다.
- 해당 모드의 순위표를 함께 표시한다. 카테고리별 도전이면 그 카테고리의 5행, 전 범위 도전이면 전 범위 순위표 10행을 보여 준다.
- 순위 저장 결과에 따라 다음과 같이 표시한다. 저장 함수의 반환값으로 판단한다(3.4절).

| 반환 | 표시 |
|---|---|
| 정수 | "순위표 N위 진입"을 표시하고, 순위표에서 해당 인덱스의 행을 강조한다 |
| `null` | "순위표에 들지 못했습니다."를 표시하고, 강조 없이 순위표만 보여 준다 |
| `'unavailable'` | 진입 여부는 표시하지 않고 4.2절의 안내 문구만 표시한다. 순위표 영역도 함께 감춘다 |

세 번째 경우에 진입 여부를 표시하면 만점을 받은 사람에게도 "순위표에 들지 못했습니다."가 뜬다. 사실과 다른 메시지다.

- 버튼 두 개를 둔다.
  - "다시 도전": 같은 모드로 문제를 새로 뽑아 다시 시작한다. 이름은 직전 판의 이름을 그대로 쓴다.
  - "처음으로": 시작 화면으로 돌아간다. 입력해 둔 이름은 그대로 남는다.

### 3.4 순위 기록

순위표는 다섯 개를 독립으로 관리한다.

| 순위표 | 대상 | 보관 수 | 만점 |
|---|---|---|---|
| 카테고리별 (4개) | 카테고리별 도전 결과 | 카테고리마다 상위 5개 | 10점 |
| 전 범위 (1개) | 전 범위 도전 결과 | 상위 10개 | 10점 |

만점은 같지만 출제 범위가 다르므로 표를 나눈다. 전 범위 도전은 네 분야가 섞여 나오므로 한 분야를 깊게 아는 사람과 두루 아는 사람의 성적이 다르게 나온다. 같은 10점이어도 의미가 다르다.

- 같은 이름의 기록도 합치지 않고 판마다 별개로 쌓는다. 순위표는 사람 목록이 아니라 도전 기록이다.
- **정렬 키는 둘이다.** 점수 내림차순으로 정렬하고, 동점이면 마친 때가 늦은 것이 위에 온다.
- **키를 둘로 못박는 까닭은 안정 정렬에 기대지 않기 위해서다.** 1차에서는 새 기록을 맨 앞에 넣고 점수로만 정렬해 "동점이면 최근이 위"를 안정 정렬로 얻었다. 정렬이 DB로 옮겨 가면 그 전제가 서지 않는다.
- **보관 수를 넘어도 기록을 지우지 않는다.** 보관 수는 순위표에 보이는 행 수이며, 조회할 때 상위 N만 뽑는다. 지우면 성적 관리 화면과 대시보드가 위쪽 기록만 보게 된다.
- 순위표에 보이는 항목은 응시자의 이름, 점수, 총 문제 수, 마친 날짜다.

**순위는 서버 DB에 저장한다.** 1차에서는 브라우저의 `localStorage`에 두었으나 그 기기에서만 보이고 수강생끼리 견줄 수 없었다. 저장 위치가 서버로 옮겨지면서 다음이 달라진다.

- **순위표는 모든 수강생의 기록을 함께 담는다.** 기기나 브라우저가 달라도 같은 순위표를 본다.
- **기록을 쓰는 것은 서버 함수뿐이다.** 브라우저에서 직접 쓰지 못하게 막는다(3.8절). 점수를 브라우저가 정하면 값을 조작할 수 있기 때문이다.
- **순위표를 읽는 것도 서버 함수다.** 순위표는 남의 이름과 점수를 함께 보인다. 브라우저에 응시 기록 전체 조회를 열면 "학생은 자기 기록만 조회한다"(3.8절)가 깨지고, 열지 않으면 순위표가 나오지 않는다. 서버 함수가 상위 N만 뽑아 돌려주면 둘이 함께 선다.
- **자기 응시 기록 조회는 브라우저가 직접 한다.** 무엇을 읽을 수 있는지는 3.8절의 권한이 정한다.

#### 저장 함수의 계약

**판을 마치는 요청이 저장과 순위 판정을 함께 한다.** 서버 함수가 응시 기록을 마감하고, 그 기록이 상위 N에 드는지를 같은 요청 안에서 판정해 돌려준다.

- **자르기 단계가 없다.** 기록을 지우지 않으므로(위) 삽입한 뒤 상위 N을 뽑아 그 안에 있는지만 본다.
- **1차의 "읽기를 쓰기 직전에 한다"는 필요 없어진다.** 두 탭이 각각 플레이해도 서로의 목록을 덮어쓸 자리가 없다. 순위는 저장된 값이 아니라 조회할 때 계산되는 것이다.

반환값은 세 가지다.

| 반환 | 조건 |
|---|---|
| 정수 | 상위 N 안에 이번 기록이 있으면 그 인덱스 |
| `null` | 들지 못했으면 `null` |
| `'unavailable'` | 요청이 실패했으면 `'unavailable'` |

인덱스는 삽입한 행의 식별자로 찾는다. **이름과 점수로 행을 되찾으려 하면 같은 이름, 같은 점수의 기록과 구별되지 않는다.**

#### 날짜

로컬 시간대를 기준으로 `YYYY-MM-DD` 형식으로 만든다.

**`new Date().toISOString().slice(0, 10)`을 쓰지 않는다.** UTC 기준이라 한국 시간 오전 9시 이전에는 전날 날짜가 찍힌다. 화면으로는 알아채기 어려운 종류의 오류다.

#### 저장 구조

**순위표를 담는 테이블을 따로 두지 않는다.** 다섯 개 순위표는 응시 기록(3.10절)에서 모드와 카테고리로 걸러 뽑은 것이다. 담는 열은 3.10절이 정한다.

`total`은 현재 언제나 10이지만, 결과 화면의 `8 / 10 정답` 표기에 쓰이고 출제 수가 바뀔 때 기존 기록을 구별하는 근거가 되므로 그대로 둔다.

**연습 모드로 친 판은 저장하지 않는다**(3.1절). 채점은 서버가 그대로 하되 응시 기록을 남기지 않으므로 순위표에도 오르지 않는다.

**1차의 저장 구조는 `localStorage` 키 `quizGameRankings` 하나였다.** 그 서술은 [`archive/PRD-v5.md`](../archive/PRD-v5.md)에 있고 1차 계획서가 그것을 가리킨다.

**함수의 구체 계약과 실패 상태 구분은 `spec/IMPL-PLAN-2.md`에서 정한다.** 브라우저 저장이 실패하는 상황 대신 서버 요청이 실패하는 상황을 다룬다.

### 3.5 순위표 화면

- 시작 화면의 "순위표 보기" 버튼으로 진입한다.
- 카테고리별 순위표 네 개와 전 범위 순위표를 함께 보여 준다.
- 열은 순위, 이름, 점수, 날짜 네 가지다. 동점이어도 순위 번호는 행 순서대로 매긴다.
- 기록이 없는 순위표에는 "아직 기록이 없습니다."를 표시한다.
- **"기록 지우기" 버튼을 두지 않는다.** 1차에는 있었으나 기록이 서버에 모이므로 학생에게 주면 남의 기록까지 지운다. 시연 기록이 남는 문제는 연습 모드(3.1절)가 대신 덜어 낸다.
- 화면 아래에 기록이 어디에 저장되는지를 안내한다. **문구는 `spec/IMPL-PLAN-2.md`에서 정한다.** **저장이 막힌 상태에서는 감춘다.** 저장이 된다는 전제로 쓰인 문장이라 그대로 두면 사실과 반대되는 안심을 준다.
- **읽기와 쓰기를 따로 판정한다.** 아래 표의 세 상태는 서버 요청의 읽기와 쓰기가 각각 되는지로 가른다. 읽기는 되고 쓰기만 막히는 경우가 흔한데, 읽기 성공 여부만 보면 그 상태를 알 수 없다. 한 판도 하지 않은 사용자는 저장 함수를 지나지 않으므로 저장 불가가 전달될 다른 통로가 없다.

| 상태 | 4.2절 안내 | 하단 고정 안내 | 순위표 |
|---|---|---|---|
| 정상 | 감춤 | 보임 | 보임 |
| 읽기는 됨, 쓰기만 막힘 | 보임 | 감춤 | 보임 |
| 읽기까지 막힘 | 보임 | 감춤 | 감춤 |

**1차 표에 있던 "기록 지우기" 열은 뺐다.** 그 버튼을 두지 않기로 했기 때문이다.
- "닫기" 버튼으로 시작 화면으로 돌아간다.

### 3.6 문제 데이터

**1차에서는 `questions.js` 파일에, 2차에서는 DB 테이블에 둔다(1.5절).** 아래의 필드 규칙과 작성 규칙은 담는 곳이 바뀌어도 그대로 적용한다. 아래 코드는 1차의 파일 형식이며 필드의 이름과 뜻을 보이기 위해 남긴다.

카테고리 정의와 문제 데이터를 각각 전역 상수로 선언한다.

```javascript
const CATEGORIES = [
  { id: 'korean_history', name: '한국사' },
  { id: 'science',        name: '과학' },
  { id: 'geography',      name: '지리' },
  { id: 'art_culture',    name: '예술과 문화' }
];

const QUESTIONS = {
  korean_history: [
    {
      id: 'kh_01',
      question: '조선을 건국한 인물은 누구인가?',
      options: ['이성계', '이방원', '정도전', '왕건'],
      answer: 0,
      difficulty: 'easy',
      explanation: '이성계는 1392년 고려를 무너뜨리고 조선을 세워 태조가 되었다.'
    }
    // ... 카테고리마다 10문제
  ],
  science: [],
  geography: [],
  art_culture: []
};
```

필드 규칙은 다음과 같다.

| 필드 | 설명 |
|---|---|
| `id` | 문제 식별자. 카테고리 약어와 두 자리 번호를 잇는다 (`kh_01`, `sc_07`) |
| `question` | 문제 텍스트. 60자를 넘기지 않는다 |
| `options` | 선택지 네 개의 배열. 각 선택지는 20자를 넘기지 않는다 |
| `answer` | 정답의 인덱스. 0 이상 3 이하의 정수 |
| `difficulty` | `'easy'`, `'medium'`, `'hard'` 중 하나 |
| `explanation` | 해설. 한두 문장으로 정답의 근거를 설명한다 |

카테고리 약어는 `kh`(한국사), `sc`(과학), `ge`(지리), `ac`(예술과 문화)를 쓴다.

난이도 값을 영문 키로 두는 이유는 배지 색상을 CSS 클래스로 구분하기 위해서다. 화면에 보이는 "초급, 중급, 고급" 라벨은 `script.js`에서 매핑한다.

데이터를 작성할 때 다음을 지킨다.

- **카테고리마다 최소 10문제를 둔다.** 한 판이 10문제이므로 그보다 적으면 뽑을 수 없다.
- 난이도 배분은 카테고리마다 초급 4문제, 중급 4문제, 고급 2문제를 기준으로 한다. 합이 10이면 다른 조합도 된다.
- 정답 인덱스를 고루 흩는다. 카테고리마다 0부터 3까지가 각각 2~3회씩 나오게 배치한다. 선택지를 섞기는 하지만, 데이터 자체가 한쪽으로 쏠려 있으면 문제를 검토하기 어렵다.
- **한 문제 안에 같은 텍스트의 선택지를 두지 않는다.** 정답 강조가 두 곳에 걸리고 "정답은 ○○입니다"가 어느 쪽인지 가리키지 못한다.
- **같은 문제 텍스트를 다른 `id`로 두 번 쓰지 않는다.**
- 문제 텍스트와 해설에 선택지의 위치를 지칭하는 표현을 쓰지 않는다(2.1절).
- **정답이 하나로만 읽히게 쓴다.** 다른 해석이 가능하면 문제 텍스트에 조건을 밝힌다. 오답 셋이 모두 명백한 오답이어야 한다.
- **최상급 표현에는 재는 기준을 함께 적는다.** "가장 큰", "가장 높은"은 무엇으로 재느냐에 따라 답이 갈린다. 면적인지 인구인지, 해발인지 기저부터인지를 문제 텍스트에 넣는다. `ge_09`의 "국토 면적이 세계에서 가장 넓은 나라"가 본보기다.
- **시점과 범위를 한정한다.** 시점에 따라 달라지는 수치는 피하고, 피할 수 없으면 해설에 기준 시점을 적는다(역사적 상수는 해당하지 않는다). 지리적, 분류적 범위도 문제 텍스트에서 좁힌다. `ge_04`의 "남한에서 가장 긴 강"이 본보기다. 범위를 열어 두면 압록강, 두만강까지 후보가 된다.

### 규칙마다 무엇이 확인하는가

**작성 규칙을 더할 때는 확인 수단을 함께 정한다.** 쓰라고만 적고 확인하는 자리를 두지 않으면 그 규칙은 규격에만 있고 아무 데서도 지켜지지 않는다. 아래 표의 칸이 비면 그 자리가 그것이다.

| 규칙 | 확인 수단 |
|---|---|
| 카테고리마다 문제 10개 이상 | 데이터 검사(4.2절) |
| `options` 네 개, 빈 원소 없음, 같은 선택지 없음 | 데이터 검사(4.2절) |
| `answer`가 0 이상 3 이하의 정수 | 데이터 검사(4.2절) |
| `difficulty`가 세 값 중 하나 | 데이터 검사(4.2절) |
| `id`가 비어 있지 않고 중복되지 않음 | 데이터 검사(4.2절) |
| `question` 텍스트가 중복되지 않음 | 데이터 검사(4.2절) |
| `question` 60자 이내, 각 선택지 20자 이내 | 데이터 검사(4.2절) |
| `options[answer]`가 정말 정답인가 | 클로드가 판정 (계획서 1.8절) |
| 해설이 정답의 근거를 대는가 | 클로드가 판정 (계획서 1.8절) |
| 선택지 위치를 지칭하지 않는가 (2.1절) | 클로드가 판정 (계획서 1.8절) |
| 정답이 하나로만 읽히는가 | 클로드가 판정 (계획서 1.8절) |
| 최상급 표현에 재는 기준이 있는가 | 클로드가 판정 (계획서 1.8절) |
| 시점과 범위가 한정되어 있는가 | 클로드가 판정 (계획서 1.8절) |
| 해설의 연도, 수치, 인명을 출처 둘 이상으로 대조 | 클로드가 판정 (계획서 1.8절) |
| 문항끼리 같은 사실을 묻지 않는가 | 클로드가 판정 (계획서 1.8절) |
| 난이도 배분, 정답 인덱스 분포 | `/quiz-stats` 명령어가 센다 |

**자동 검사로 판정할 수 없는 규칙은 위 표에서 "클로드가 판정"으로 표시된 것들이다.** 세거나 목록으로 뽑을 수는 있어도 맞는지는 **클로드가 판정하고 사람이 채택 여부를 결정한다.** 검사 함수에 넣을 수 없으므로 8.1절이 정한 확인을 거친다. 판정을 누가 언제 하고 언제 닫는지는 계획서 1.8절이 정한다.

### 3.7 인증과 역할

**이름 입력만으로 시작하던 흐름을 로그인으로 바꾼다.** 1차에서는 같은 이름을 적으면 같은 사람으로 보였고 선생님과 학생을 구별할 수 없었다.

| 역할 | 무엇을 하는가 |
|---|---|
| 학생 | 응시하고 자기 기록을 조회한다 |
| 선생님 | 문항 생성을 요청하고 채택 여부를 정하며, 수강생 전체의 기록을 조회한다 |

- **역할은 둘뿐이다.** 반이나 학급 같은 단위를 두지 않는다. 수업용이라 수강생 전체를 하나로 본다.
- 역할은 사용자 테이블에 두고, 로그인한 사용자의 역할로 화면과 권한을 가른다.
- 인증은 Supabase Auth를 쓴다. **비밀번호를 우리 테이블에 저장하지 않는다.** 인증 서비스가 암호화해 자체 보관한다.
- **로그인은 깃허브 계정으로만 한다.** 비밀번호를 우리가 다루지 않으므로 가입 화면을 두지 않는다.

#### 로그인의 수명

- **로그인에는 수명이 있다.** 만료되면 다시 로그인해야 하고, 만료가 가까우면 미리 알린다.
- **판을 시작하기 전에 남은 시간이 모자라면 먼저 다시 로그인하도록 안내한다.**
- **판 도중에 만료되면 그 판을 버린다.** 이어 하기는 7장이 제외했다. 그래서 판을 시작하기 전에 안내한다.
- 알리는 시점과 문구는 `spec/IMPL-PLAN-2.md`에서 정한다.

**7장이 제외한 제한 시간과 다르다.** 저것은 문제를 푸는 데 걸리는 시간을 재는 것이고, 이것은 로그인이 남은 시간을 알리는 것이다. 화면에 시간이 보인다는 점만 같다.

#### 누가 선생님인가

- **사용자 테이블의 역할 열로 가른다.** 로그인한 사용자의 깃허브 아이디로 그 행을 찾고, 역할이 선생님이면 선생님 화면을 연다.
- **첫 선생님은 DB에 직접 넣는다.** 앱 안에서 만들 수 없다. 권한을 줄 사람이 아직 없기 때문이다. 테이블을 만들 때 한 줄을 함께 넣는다.
- **그다음부터는 선생님이 설정 화면에서 더하고 바꾸고 지운다**(5장). 배포 설정을 열거나 다시 배포할 일이 없다.
- **역할을 바꾸는 것은 서버 함수만 한다**(3.8절). 브라우저가 역할 열을 쓸 수 있으면 학생이 자기를 선생님으로 바꾼다.
- **마지막 선생님은 지우거나 강등할 수 없다.** 선생님이 0명이 되면 설정 화면에 들어갈 사람이 없어져, 되돌리는 길이 DB를 직접 여는 것뿐이 된다.
- **브라우저가 보낸 역할을 믿지 않는다.** 선생님 전용 링크나 가입 시 체크는 통제가 되지 않는다. 링크는 숨겨지지 않고 체크는 브라우저가 보내는 값이다. 3.8절이 점수 값을 두고 정한 것과 같은 자리다.
- **아이디로 가르고 이메일로 가르지 않는다.** 깃허브는 이메일을 비공개로 둘 수 있어 값이 비거나 `noreply` 주소가 온다.

### 3.8 권한

**권한은 두 자리에서 갈린다.** 브라우저가 직접 읽는 것은 DB의 행 수준 보안(RLS, row level security)이 거르고, 쓰는 것과 정답을 읽는 것은 서버 함수가 검사한다.

| 무엇 | 누가 | 어떻게 통제하나 |
|---|---|---|
| 자기 응시 기록 조회 | 학생 | 행 수준 보안(RLS) |
| 전체 응시 기록 조회 | 선생님 | 행 수준 보안(RLS) |
| 순위표 조회 | 학생, 선생님 | 서버 함수. 상위 N만 뽑아 돌려준다 |
| 문항 조회 | 학생, 선생님 | 서버 함수. 정답 열을 제외하고 전달한다 |
| 응시 기록 저장 | 서버 함수만 | 브라우저에 쓰기 정책을 두지 않는다 |
| 문항 생성과 저장 | 서버 함수만 | 선생님의 요청을 서버 함수가 확인한 뒤 수행한다 |
| 역할 바꾸기 | 서버 함수만 | 요청한 사람이 선생님인지 확인하고, 마지막 선생님을 내리는 요청은 거절한다(3.7절) |

**행 수준 보안(RLS, row level security)은 행을 걸러낼 뿐 열을 가리지 않는다.** 문항 행을 조회하도록 허용하면 정답 열도 함께 조회된다. 그래서 문항은 행 수준 보안이 아니라 서버 함수를 거쳐 전달한다.

**행 수준 보안(RLS, row level security)으로도 점수 값 자체는 보호하지 못한다.** 어느 행을 저장할 수 있는지는 정해도 무슨 값을 저장하는지는 정하지 못한다. 그래서 응시 기록은 서버 함수만 저장한다.

**순위표는 행 수준 보안(RLS, row level security)으로 낼 수 없다.** 순위표에는 남의 이름과 점수가 뜨는데, 그 행을 조회하도록 열면 위의 첫 행("자기 응시 기록 조회")이 함께 깨진다. 행을 열면 그 행 전부가 열리고, "순위표에서만 보이게" 하는 조건을 정책에 담을 자리가 없다. 그래서 순위표도 서버 함수를 거친다(3.4절).

**모든 테이블에 행 수준 보안(RLS, row level security)을 켠다.** 켜지 않은 테이블은 공개 키(`publishable key`)로 전부 조회된다.

### 3.9 문항 생성

**선생님이 문항을 직접 출제하거나 등록하는 화면은 두지 않는다.** 화면에서 요청하면 서버가 생성하고 검증한다.

1. 선생님이 화면에서 요청한다. 예 — 지리 5개 문항 추가
2. 서버 함수가 요청한 사람이 선생님인지 확인한다
3. 서버 함수가 Anthropic API를 호출해 문항을 생성한다
4. 생성된 문항을 3.6절의 작성 규칙과 4.2절의 데이터 검사에 건다
5. 검사를 통과한 것만 선생님에게 보인다
6. 선생님이 확인하고 채택 여부를 정한다
7. 채택한 것만 DB에 넣는다

- **6번을 생략하지 않는다.** 1차에서 클로드가 판정하고 사람이 채택 여부를 결정하던 방식을 그대로 잇는다.
- 4번에서 걸린 문항은 넣지 않고 무엇이 걸렸는지 함께 보인다.
- **4번의 판정은 생성과 다른 호출로 한다.** 판정에 생성 맥락을 주지 않고 문항만 넘긴다. 쓴 쪽이 판정하지 않는다는 규칙을 앱 안에서 지키는 방법이다.
- **앱 안에서는 판정을 한 번만 돌린다.** 계획서 1.8절은 서로 다른 세션 둘이 각각 한 번씩 돌라고 정했는데 앱 안에는 세션이 없다. 같은 모델을 같은 프롬프트로 두 번 부르는 것은 서로 다른 세션이 아니므로 두 번째 라운드는 6번의 사람이 맡는다. **규격을 한 칸 무른 것이며, 문제은행을 크게 늘릴 때는 세션 둘이 도는 경로를 그대로 쓴다.**

#### 고치기와 지우기

- 선생님은 문항, 선택지, 해설을 고치고 문항을 지울 수 있다.
- **고친 문항은 위의 4번부터 다시 지난다.** 고치면서 규격을 깰 수 있기 때문이다.
- **이미 응시 기록이 쌓인 문항을 고치면 과거 기록의 뜻이 달라진다.** 점수는 그대로이나 무엇을 틀렸는지가 바뀐다. 이 관계를 어떻게 둘지는 `spec/IMPL-PLAN-2.md`에서 정한다.
- **생성 요청과 결과를 어떻게 기록할지는 `spec/IMPL-PLAN-2.md`에서 정한다.** 3.10절의 "만든 때"만으로는 한 요청이 만든 여러 문항을 묶어 낼 수 없다. 요청을 담는 테이블을 둘지, 문항에 요청 식별자를 더할지가 정해지지 않았다.

### 3.10 데이터 모델

| 테이블 | 항목 |
|---|---|
| 사용자 | 아이디, 이름, 역할 |
| 문항 | `id`, 카테고리, 문제, 선택지, 정답, 난이도, 해설, 만든 이, 만든 때 |
| 응시 기록 | 응시자, 카테고리, 점수, 총 문제 수, 응시 때, 섞인 순서, 문항별 응답, 마감 여부 |

- **비밀번호는 담지 않는다.** 인증 서비스가 따로 보관한다(3.7절).
- **문항의 필드는 3.6절의 것을 그대로 옮긴다.** 만든 이와 만든 때만 더한다. 누가 넣은 문항인지 가리기 위해서다.
- **한 생성 요청이 만든 문항들을 묶어 내려면 자리가 더 필요하다.** 만든 때만으로는 못 가른다. 만든 때는 문항마다 찍히는 값이라 어디까지가 한 요청인지를 담지 못하기 때문이다. 그 자리를 어떻게 둘지는 3.9절에 따라 `spec/IMPL-PLAN-2.md`에서 정한다.
- **응시 기록 행은 판을 시작할 때 만들고 마칠 때 마감한다.** 판이 도는 동안 서버가 알아야 하는 것을 그 행이 담는다.
  - **섞인 순서** — 2.1절이 선택지를 섞으라고 했고 3.8절이 정답을 브라우저에 내려보내지 않기로 했다. 정답이 없으니 브라우저가 섞을 수 없고, 서버가 섞으면 브라우저가 보낸 "3번"이 무엇인지 서버만 안다. 그 대응을 담는 자리다.
  - **문항별 응답** — 점수만으로는 무엇을 틀렸는지 남지 않는다. 대시보드의 "많이 틀린 문항"이 이 열에서 나온다. 3.9절이 "고치면 무엇을 틀렸는지가 바뀐다"고 적은 것도 이 열을 전제한 것이다.
  - **마감 여부** — 진행 중인 판과 끝난 판을 가른다. 순위표와 성적 관리는 마감된 행만 본다.
- **판을 담는 테이블을 따로 두지 않는다.** 진행 중인 판과 끝난 판이 같은 행이므로 마칠 때 옮겨 담을 일이 없다.
- **연습 판과 "그만두기"로 끝난 판은 그 행을 지운다**(3.1절, 3.2절).
- **소속을 담는 자리가 없다.** 반 단위를 두지 않기 때문이다(3.7절).

### 4.1 알려진 제약

다음은 코드로 해결할 수 없어 알려진 동작으로 둔다. 구현 중에 다시 검토하지 않도록 여기에 모아 둔다.

1. **`index.html`을 직접 열면 동작하지 않는다.** 서버 함수가 있어야 문항을 받고 채점할 수 있다. 로컬 확인은 배포된 주소나 로컬 개발 서버로 한다.
2. **Safari는 `beforeunload`를 지원하지 않는다.** 진행 중 새로고침이나 이탈을 막는 확인창(3.2절)이 Safari, 특히 iOS Safari에서는 뜨지 않는다. Apple이 페이지 캐시 정책상 의도적으로 막은 것이라 우회 방법이 없다. 대체로 거론되는 `pagehide`는 정리 작업용이라 확인창을 띄울 수 없다. 결과적으로 이탈 보호는 Chrome과 Edge에서만 동작한다.
3. **무료 요금제의 프로젝트는 1주일 동안 사용하지 않으면 일시정지된다.** 수업이 주 1회면 매 시간 정지된 상태로 만나게 된다. 수업 전에 동작을 재개시키는 절차가 필요하다.
4. **1차 배포본 여섯은 그대로 둔다.** GitHub Pages의 `gh-pages` 브랜치에 남아 있고, 구현 단계별로 실행해 볼 수 있게 존치한다. 그 여섯은 여전히 `localStorage`를 쓰므로 기록이 서로 섞이는 동작도 그대로 남는다.
5. **무료 요금제로는 깃 조직이 소유한 저장소를 배포에 연결할 수 없다.** 저장소를 개인 계정에 두어야 한다. **배포 직전에 발견하면 되돌릴 시간이 없으므로 첫 구현 단계에서 확인한다.**

   조직 저장소를 개인 계정으로 복사하면 복사본은 연결된다. **이 우회는 55번에 없는 사실이고 2026년 8월 22일 배포처 문서에서 확인했다.** 문서가 조항을 바꾸면 함께 확인해야 한다.
6. **구현 단계별 배포본을 여럿 두면 같은 DB를 함께 쓴다.** 1차에서 여섯 배포본이 오리진을 공유해 기록이 섞이던 것과 같은 종류이나, DB는 한 곳이므로 다른 사람의 기록까지 영향을 받는다는 점에서 더 위험하다. 개발용과 수업용 저장을 어떻게 나눌지는 `spec/IMPL-PLAN-2.md`에서 정한다.

7. **배포 주소는 30일 뒤 사라질 수 있다.** 무료 요금제의 보존 기간이 30일이고 늘릴 수 없다. 최근 배포 열 개와 상태가 정상인 최근 프로덕션 배포 스무 개는 예외로 남으나, 깃에 밀어 넣을 때마다 배포가 생기므로 그냥 두면 앞 단계의 주소가 밀려난다. **2026년 8월 23일 배포처 문서에서 확인했다.**

   그래서 배포 횟수를 줄인다. **구현 단계 작업은 브랜치에서 하고 `main` 병합은 단계를 마칠 때 한 번만 하며, 소스가 바뀌지 않은 커밋은 배포하지 않는다.** 이 저장소는 소스와 문서가 같은 브랜치에 있어 문서만 고쳐도 배포가 생긴다.

   단계마다 그 시점 배포 주소를 README에 적되, 오래 남겨야 하는 것은 태그다.

**2차 앱에서는 1차의 제약 가운데 둘이 해소된다.** 기록이 브라우저에만 남던 것과, Safari가 7일 뒤 저장 데이터를 삭제하던 것이다. 저장 위치가 서버로 옮겨졌기 때문이다. **1차 배포본 여섯(4번)에서는 둘 다 그대로 남는다.**

### 4.2 에러 처리

**막을 것은 화면을 그리기 전에 막는다.** 시작 화면을 정상 표시했다가 버튼을 누른 뒤에야 막으면 사용자가 원인을 알기 어렵다.

**문제 데이터 검사(2번)는 문항을 넣는 시점에 서버에서 한다**(1.5절). 다만 카테고리 대응과 카테고리별 문제 수는 문항을 넣을 때가 아니라 지우거나 카테고리를 늘릴 때 어긋나므로 **넣는 시점에 판정할 수 없다.** 각 항목을 어느 시점에 둘지는 `spec/IMPL-PLAN-2.md`에서 정한다.

1. **문제 데이터를 받지 못함**: 서버에서 문항이나 카테고리를 받지 못했으면 시작 화면에 "문제 데이터를 불러오지 못했습니다."를 표시하고 게임 시작을 막는다.

2. **문제 데이터 검사**: 다음을 모두 확인하고 하나라도 어긋나면 그 문항을 넣지 않는다.

   | 검사 | 빠뜨릴 때 증상 |
   |---|---|
   | 카테고리 목록의 모든 `id`에 해당하는 문항이 있는가 | 카드는 그려지는데 시작하면 빈 배열에서 문제를 뽑는다 |
   | 카테고리마다 문제가 `QUIZ_LENGTH` **이상**인가 | 10문제를 뽑지 못한다 |
   | `options.length === 4`인가 | 선택지가 셋만 들어가도 에러 없이 채점만 틀린다 |
   | 선택지 원소가 **비어 있지 않은 문자열**인가 | 빈 버튼이 그려지고, 그 선택지가 정답이면 피드백이 "정답은 입니다."가 된다 |
   | `answer`가 0 이상 3 이하의 **정수**인가 | `'0'`(문자열)이나 `1.5`면 강조와 채점이 어긋난다 |
   | `difficulty`가 세 값 중 하나인가 | 오타면 배지 CSS 클래스가 없어 스타일만 빠진 채 표시된다 |
   | `question`, `explanation`이 비어 있지 않은가 | 빈 화면이 나오고 원인을 찾기 어렵다 |
   | 한 문제 안에 같은 선택지가 없는가 | 정답 강조가 두 곳에 걸린다 |
   | `id`가 **비어 있지 않은가** | 누락을 중복으로 잘못 보고하고, 3단계 R2 검증이 원본을 못 찾아 예외가 난다 |
   | `id`가 중복되지 않는가 | 문제를 추가하다 겹치면 추적이 어려워진다 |
   | `question` 텍스트가 중복되지 않는가 | 같은 문제를 다른 `id`로 두 번 쓰게 된다 |
   | `question`이 60자 이내인가 | 3.6절이 못박은 규칙인데 확인하는 자리가 없었다. 문제를 늘릴 때 조용히 어긋난다 |
   | 각 선택지가 20자 이내인가 | 같은 자리. 긴 선택지는 좁은 화면에서 줄바꿈이 늘어 버튼 높이가 들쭉날쭉해진다 |

   문제 수 검사는 **"10개인가"가 아니라 "10 이상인가"로 쓴다.** 전자로 쓰면 문제를 늘리는 순간 검사 자체가 걸림돌이 된다(8장).

   **넣는 사람에게 문제 `id`와 위반 항목을 알린다** (`kh_07: options 길이가 3`). 이 검사의 주 사용자는 플레이어가 아니라 데이터를 쓰는 사람이다. 어느 문제가 틀렸는지 알려주지 않으면 하나씩 뒤져야 한다.

3. **순위 저장 실패**: 서버 요청이 실패해도 게임은 정상 진행하고 순위 저장만 건너뛴다. 저장 함수는 `'unavailable'`을 돌려준다(3.4절). 결과 화면과 순위표 화면에 순위를 저장하지 못했다는 것을 표시한다. **구체적인 상태 구분과 문구는 `spec/IMPL-PLAN-2.md`에서 정한다.**

4. **순위표 응답이 예상한 형태가 아님**: 다섯 개 가운데 어느 하나가 예상한 형태가 아니면 **그 표만** 비워 표시하고 나머지는 그대로 그린다. 다섯 개를 한꺼번에 비우지 않는다. 하나가 깨졌다고 나머지 네 개까지 감출 이유가 없다.

   **1차의 `localStorage` 손상 전제는 사라졌다.** 저장 위치가 서버로 옮겨져 브라우저에 손상될 데이터가 없다. 남는 것은 서버가 돌려준 값이 형태에 어긋나는 경우이고, 처리는 같다.

5. **채점 요청 실패**: 답을 고른 뒤 응답이 오지 않으면 **재시도 버튼**을 낸다. 재시도해도 실패하면 **그 판을 버리고 시작 화면으로 돌아간다.**

   2차에서는 문항마다 서버를 지나므로(1.4절) 실패할 자리가 판마다 열 번 생긴다. 3번의 순위 저장 실패와 달리 **게임을 이어 갈 수 없다.** 정오와 해설이 오지 않으면 다음 문제로 넘어갈 근거가 없기 때문이다.

   **진행 상황을 남겨 두지 않는다.** 이어 하기는 7장이 제외했다. 한 판이 10문제로 짧아 다시 하면 되는 정도의 손실로 본다.

### 4.3 접근성

- 조작 가능한 모든 요소는 키보드로 도달하고 실행할 수 있다(3.0절).
- 선택지 버튼에 키보드 초점이 보이도록 한다.
- 선택지 버튼은 최소 높이 44px로 하고, 글이 길면 줄바꿈해 전부 보이게 한다. 잘라 내지 않는다.
- 정답과 오답을 색만으로 구분하지 않는다. ✓와 ✗를 함께 표시한다(3.2절).
- 정답 여부와 해설은 초점 이동으로 전달한다. `aria-live`를 쓰지 않는다(3.2절).
- 화면을 전환하면 제목으로, 문제를 새로 그리면 문제 텍스트로, 답을 고르면 피드백 영역으로 초점을 옮긴다. 퀴즈 진행 화면에 들어갈 때는 두 규칙이 겹치므로 제목을 건너뛰고 첫 문제 텍스트로 옮긴다.
- **글자와 배경의 대비를 4.5:1 이상으로 한다(WCAG AA).** 난이도 배지 세 가지와 정답 초록, 오답 빨강에 모두 적용한다. 주황 계열 배지가 흰 배경에서 대비가 잘 나오지 않으므로 특히 확인한다.

### 4.4 비밀값 관리

**키를 자리마다 하나씩 둔다.**

| 어디서 실행되나 | 무슨 키 | 어디에 두나 |
|---|---|---|
| 브라우저 (`script.js`) | 공개 키(`publishable key`) | 소스 코드에 그대로 적어도 된다 |
| 서버 함수 (`api/`) | 비밀 키(`secret key`) | 배포 환경 변수. 저장소에 넣지 않는다 |
| 서버 함수 (`api/`) | Anthropic API 키 | 배포 환경 변수. 저장소에 넣지 않는다 |

- **대시보드에 이름이 두 벌 있다.** 위의 둘은 API Keys 탭의 현행 이름이고 `sb_publishable_…`, `sb_secret_…` 형태다. Legacy API Keys 탭의 `anon`과 `service_role`이 예전 이름이며 하는 일은 같다. **2026년 말 폐기 예정이므로 현행 이름을 쓴다.**
- **공개 키는 그 자체로 아무 권한도 주지 않는다.** 무엇을 조회하고 저장할 수 있는지는 행 수준 보안 정책이 정한다(3.8절).
- **비밀 키는 행 수준 보안 정책의 범위를 벗어난다.** 정책이 적용되지 않아 모든 행과 열을 조회하고 저장할 수 있다.
- **두 키를 바꿔 쓰면 안 된다.** 서버 함수에 공개 키를 쓰면 채점을 수행하지 못하고, 브라우저에 비밀 키를 쓰면 학생이 DB 전체를 임의로 조회하고 수정할 수 있다.
- **비밀 키는 권한 검사도 함께 건너뛴다.** 서버 함수가 로그인 정보를 기반으로 누구의 요청인지 직접 확인해야 한다. 이 단계를 빠뜨리면 아무나 다른 학생의 이름으로 점수를 저장할 수 있다.
- 저장소에 키가 들어가지 않았는지 커밋 전에 확인한다.

## 5. 화면 흐름

```
[시작 화면]
  로그인한 사용자로 진입 → 카테고리 카드 선택 또는 전 범위 도전
        │                                    └─→ [순위표 화면] ─→ 시작 화면
        ▼
[퀴즈 진행 화면]  (10문제)
  문제 표시 → 선택지 클릭 → 즉시 피드백 + 해설 → "다음 문제"
        │                                              │
        │      └─ "그만두기" → 확인 → 시작 화면 (기록 없음)
        │                                              │
        └──────────── 남은 문제 있음 ←─────────────────┘
        │ 마지막 문제 완료
        ▼
[결과 화면]
  점수, 정답률, 순위표 진입 여부
        ├─ "다시 도전" → 퀴즈 진행 화면 (같은 모드, 새로 뽑음)
        └─ "처음으로"  → 시작 화면
```

**화면은 여덟이다.** 위 도해의 넷 앞에 로그인 화면이 붙고, 선생님에게 세 화면이 더 있다.

```
[로그인] → [시작 화면] → … → [결과 화면]
    └─(선생님) → [문항 관리]  목록과 분포, 생성 요청, 채택, 고치기, 지우기, 생성 이력
                 [성적 관리]  수강생 기록, 학생별 보기, 대시보드
                 [설정]       사용자 목록과 역할 바꾸기
```

## 6. 구현 단계

**2차 구현 단계는 다섯이다.** 준비와 배포 골격, 인증, 문항 이전, 서버 채점과 순위, 선생님 화면 셋이다. 계획서를 쓰기 전에 정했고 근거는 `history/impl_v2/65-plan2-design-decisions.md`에 있다. **각 단계의 작업 목록과 완료 기준은 `spec/IMPL-PLAN-2.md`가 정한다.**

각 단계에서 화면을 만들 때 그 화면의 스타일도 함께 쓴다. `style.css`를 마지막에 몰아 쓰지 않는다.

**로컬 확인을 완료 기준으로 삼지 않는다.** 파일명 대소문자와 상대 경로 문제는 로컬에서 재현되지 않고 배포해야만 드러난다. 배포 후 확인을 어느 단계에 둘지도 계획서에서 정한다.

**1차의 여섯 단계 표는 [`archive/PRD-v5.md`](../archive/PRD-v5.md) 6절에 있다.** 1차 계획서 `spec/IMPL-PLAN.md`가 그 판본을 직접 가리킨다.

## 7. 범위에서 제외한 것

다음은 이번 구현에 넣지 않는다. 각 항목에 제외한 이유를 함께 적는다.

- **제한 시간(타이머)과 시간 기반 점수 가중치** — 해설을 읽고 넘어가는 흐름(3.2절)과 맞지 않는다. 시간에 쫓기면 해설을 읽지 않게 된다.
- **난이도별 배점 차등, 난이도 필터 선택** — 배점을 난이도로 나누면 몇 문제를 맞혔는지가 점수에서 보이지 않는다. 난이도 데이터는 그대로 보관하므로 나중에 붙일 수 있다.
- **오답 노트, 틀린 문제만 다시 풀기** — 한 판이 끝난 뒤에도 어느 문제를 틀렸는지 남겨 두어야 하므로 저장 구조(3.4절)가 순위 기록보다 커진다.
- **진행 중 새로고침 시 이어 하기** — 진행 상황을 저장해야 하므로 저장 구조가 커진다. Chrome과 Edge에서는 확인창으로 실수를 막지만(3.2절), **Safari는 `beforeunload`를 지원하지 않아 확인창 없이 진행 상황이 사라진다**(4.1절). 한 판이 10문제로 짧아 다시 하면 되는 정도의 손실이라고 보고 이대로 둔다.
- **브라우저 뒤로 가기 처리** — 네 화면을 한 페이지에서 전환하므로 히스토리 항목이 하나뿐이다. 퀴즈 진행 중 뒤로 가기를 누르면 시작 화면으로 돌아가는 것이 아니라 사이트를 벗어난다. `history.pushState`로 화면마다 항목을 넣으면 해결되지만 화면 전환 전반을 다시 설계해야 한다. 모바일에서 흔한 제스처이므로 알려진 동작으로 적어 둔다.
- **사운드 효과, 화면 전환 애니메이션** — 이런 퀴즈 게임에서는 없어도 진행에 지장이 없다. 만드는 분량만 늘어난다.

## 8. 2차 구현

**1차 구현은 배포로 닫혔고 2차 구현이 진행 중이다.** 이 절은 예정이던 것과 지금 하는 것을 함께 담는다.

### 8.1 문제은행 확대 — 진행 중

- 카테고리마다 문제를 늘린다. 한 판의 출제 수는 10문제로 고정되어 있고 전 범위 도전의 카테고리 배분도 3+3+2+2로 고정이므로(2장), **순위표 구조와 만점은 그대로 유지되고** 반복 플레이 시 문제 구성만 달라진다. 1차에서 만점을 10점으로 정한 것이 이 확장을 위한 것이다.
- 문제 추가는 3.6절의 작성 규칙과 4.2절의 데이터 검사를 통과해야 한다. 더해 **`answer`가 실제 정답을 가리키는지, 해설이 그 정답의 근거를 설명하는지 클로드가 판정하고 사람이 채택 여부를 결정한다.**
- **이 판정을 검사 함수로 대신할 수 없다.** `answer`가 0~3 안에 있으면서 틀린 선택지를 가리키는 경우, 해설이 채워져 있으나 정답과 무관한 경우는 검사를 통과하고 화면도 정상이며 채점만 조용히 틀린다. 판정을 누가 언제 하고 언제 닫는지는 계획서 1.8절이 정한다.
- 추가 시 카테고리별 난이도 배분과 정답 인덱스 분포를 확대된 문제 수 기준으로 다시 맞춘다.
- 카테고리를 추가하거나 출제 수를 바꾸는 경우에는 2.1절의 `counts` 배열을 함께 고쳐야 한다. 3+3+2+2는 카테고리 네 개, 10문제 전제에 묶여 있다.
- **2026년 8월 22일 기준으로 네 카테고리가 15문항씩 60문항이다.**

### 8.2 인증과 저장, 배포의 전환 — 진행 중

- 인증과 저장을 Supabase로, 배포를 Vercel로 옮긴다(1.3절)
- 채점과 응시 기록 저장을 서버 함수로 옮긴다(3.8절)
- 문항을 파일에서 DB로 옮기고 선생님이 화면에서 생성을 요청하게 한다(3.9절)
- 결정의 근거는 `history/impl_v2/55-phase2-design-decisions.md`에 있다

### 8.3 뒤에 정해진 것

이 절은 2차 개정 때 넷을 미정으로 두었다. 구현계획서를 준비하며 넷이 모두 정해졌다. 근거는 `history/impl_v2/65-plan2-design-decisions.md`에 있다.

- **화면은 여덟이다**(5장). 로그인 하나, 학생 넷, 선생님 셋이다
- **대시보드는 표와 차트를 함께 낸다.** 항목은 카테고리별 정답률, 점수 추세, 많이 틀린 문항이다. **차트 라이브러리를 쓰지 않는다**(4장 외부 의존성). 막대는 요소 너비로, 추세는 인라인 SVG로 그린다
- **문제은행은 카테고리마다 30문항에서 멈춘다.** 상한에 닿으면 더 넣지 않고 알린다
- **2차 구현 단계는 다섯이다**(6장). 계획서가 정하도록 넘겼던 것을 계획서를 쓰기 전에 정했다

### 선택지가 몇 개인지 스크린리더에 알리기

**5단계에서 사람이 스크린리더로 확인하다 나온 것이다.** 문제 텍스트를 읽고 나면 아무 안내 없이 조용해지고, **선택지가 몇 개 있는지 알 방법이 없다.** `Tab`을 눌러 보아야 안다.

- 결함은 아니다. 스크린리더는 초점이 있는 것만 읽으므로 `Tab`으로 옮겨 가며 듣는 것이 정상 경로다
- 다만 시각 사용자는 보기 넷을 한눈에 보는데 스크린리더 사용자는 그렇지 못하다. 처음 쓰는 사람은 문제를 들은 뒤 무엇을 해야 할지 모른다
- 방법 후보 — `#options`에 `role="group"`과 `aria-label="선택지 4개"`를 주거나, 문제 텍스트에 안내를 덧붙이거나, 선택지 라벨 앞에 순번을 붙인다

1차에서 하지 않은 이유는 둘이다. **4.3절에 없는 새 요구**라 1차 5단계의 "새 기능을 넣지 않는다"와 부딪히고, **R5와 인접**해 접근성 속성을 덧붙이면 낭독 흐름을 다시 확인해야 하는데 그 확인 수단을 더 쓰지 않기로 했다.

확인 환경은 크롬과 VoiceOver였다. 사파리는 확인하지 않았다(`history/25-open-items.md` 2절).

## 부록: 문서를 고칠 때 점검할 것

**1차의 서술을 찾을 때는 [`archive/PRD-v5.md`](../archive/PRD-v5.md)를 본다.** 2차 개정에서 이 문서는 2차 기준으로 다시 쓰였고, 1차에서만 쓰이던 서술은 남기지 않았다.

이 문서는 두 차례 개정을 거쳤다. 개정 때마다 새 항목을 추가하면서 그 항목의 경계 조건을 빠뜨리는 일이 반복됐다. 항목을 늘린 뒤 다음 여섯 가지를 훑는다.

1. **언제 끝나는가** — 켜는 시점만 적고 끄는 시점을 빠뜨리지 않았는가 (`beforeunload` 해제)
2. **언제 시작하는가** — 무엇을 할지만 적고 언제 할지를 빠뜨리지 않았는가 (데이터 검사 시점)
3. **대상 브라우저가 지원하는가** — 기능을 도입하기 전에 확인했는가 (Safari의 `beforeunload`)
4. **기존 항목과 부딪히지 않는가** — 특히 접근성 항목은 서로 간섭한다 (`aria-live`와 초점 이동)
5. **다른 절과 어긋나지 않는가** — 새 항목이 기존 절의 서술이나 제외 항목과 모순되지 않는가 (구현 단계와 제외 항목)
6. **이 조건은 참과 거짓 둘로 갈리는가, 중간 상태가 있는가** — 앞의 다섯은 **항목을 추가할 때** 묻는 것이다. 이것은 **이미 있는 항목**에 대해 묻는다

여섯 번째는 4단계 구현에서 나왔다. 3.5절이 "`localStorage`를 쓸 수 없으면"을 한 상태로 뭉뚱그렸는데, 실제로는 셋이었다 — 정상, **읽기는 되고 쓰기만 막힘**, 읽기까지 막힘. **가장 흔한 것이 가운데인데 규격에 없었다.** 검토를 세 바퀴 돌고도 못 봤고, 앞의 다섯 질문으로도 걸리지 않았다. 항목을 새로 추가한 것이 아니라 있던 항목의 상태 구분이 모자랐기 때문이다.

같은 자리가 더 있다. 저장 데이터가 정상이다 손상이다(다섯 순위표 중 일부만 손상될 수 있다), 문제 데이터가 맞다 틀리다(검사로 잡히는 것과 육안으로만 잡히는 것이 다르다). **둘로 갈린다고 적기 전에 중간을 찾아본다.**
