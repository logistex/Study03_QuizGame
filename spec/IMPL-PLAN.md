# 상식 퀴즈 게임 구현 계획

`PRD.md`(최종본)를 구현 순서로 옮긴 문서다. 계획을 받아 구현하는 사람이 PRD를 다시 해석하지 않아도 되도록 파일명, 함수명, 요소 id, 화면 문구, 확인 절차를 모두 확정해 적었다.

## 이 계획의 전제

- 단계 구조는 `archive/PRD-v5.md` 6절의 6단계를 그대로 쓴다. **1차 착수 시점의 PRD 판본이다.** 2차 개정으로 `spec/PRD.md` 6절이 2차의 다섯 단계를 담게 되었으므로, 이 문서가 "6절 N단계"로 부르는 것은 모두 그 보존 판본을 가리킨다. 합치거나 나누거나 순서를 바꾸지 않는다. 무거운 단계만 하위 작업으로 쪼갰다.
- 빌드 도구, 외부 라이브러리, 테스트 프레임워크를 쓰지 않는다.
- 검증 수단은 두 가지뿐이다.
  1. **데이터 검사 함수** (PRD 4.2절). 페이지 로드 시점에 자동 실행되고 위반 내용을 콘솔에 출력한다.
  2. **브라우저 수동 체크리스트**. 각 단계 끝에 있다.
- 로컬 확인은 **Chrome 또는 Edge**로 한다. Safari는 `file://`에서 `localStorage`가 막히고 `beforeunload`도 지원하지 않아 6단계(배포 후)에서 확인한다(PRD 4.1절의 `beforeunload` 항목). `file://`의 `localStorage` 제약은 2차 개정으로 PRD 4.1절에서 빠졌다. 1차 구현에서는 그대로 유효하다.
- 각 단계에서 만든 화면의 스타일은 그 단계에서 함께 쓴다. `style.css`를 마지막에 몰아 쓰지 않는다(PRD 6절 머리말).

## 위험 구간 요약

다음 여섯 가지는 **화면상으로는 정상으로 보이면서 결과만 틀리거나, 배포해야만 드러난다.** 해당 단계 체크리스트에 확인 항목으로 넣어 두었다.

| # | 위험 | PRD 근거 | 확인 단계 |
|---|---|---|---|
| R1 | 전 범위 도전에서 카테고리별로 뽑은 뒤 합친 결과를 **다시 섞지 않음** | 2.1절 | 3단계 |
| R2 | 선택지를 섞은 뒤 `answer`를 **새 인덱스로 갱신하지 않음** | 2.1절 | 3단계 |
| R3 | 저장 함수가 인덱스를 **이름과 점수로 찾음** (객체 참조로 찾아야 함) | 3.4절 | 4단계 |
| R4 | 날짜에 **`toISOString()`을 씀** | 3.4절 | 4단계 |
| R5 | 피드백 영역에 **`aria-live`를 줌** (초점 이동으로만 전달해야 함) | 3.2절, 4.3절 | 3단계, 5단계 |

## 게임 상태 객체

`script.js`에 `state` 하나를 둔다. 3단계에서 만들고 이후 단계가 읽는다.

| 필드 | 값 | 설명 |
|---|---|---|
| `playerName` | 문자열 | 앞뒤 공백을 잘라 낸 이름 |
| `mode` | `'category'` \| `'all'` | 플레이 모드 |
| `categoryId` | 문자열 \| `null` | 카테고리별 도전일 때의 카테고리 id |
| `quiz` | 배열 | 이번 판의 문제 10개 (선택지를 이미 섞은 상태) |
| `index` | 정수 | 현재 문제 번호(0부터) |
| `score` | 정수 | 현재 점수 |

**"이미 답했는가"를 나타내는 플래그를 두지 않는다.** 재선택 방어는 선택지 버튼의 `disabled` 하나가 한다. 비활성 버튼은 자식 요소를 눌러도 클릭 이벤트가 발생하지 않고, `handleAnswer`가 동기 함수라 연타의 두 번째 클릭은 이미 비활성이 적용된 뒤에 도착한다. **이 근거는 선택지가 진짜 `<button>`일 때만 성립한다.** `<div>`에 `aria-disabled`나 클래스만 걸면 클릭이 그대로 발생한다(PRD 3.0절).

순위표 저장 키는 `state.mode === 'all' ? ALL_KEY : state.categoryId`로 정한다.

# 1단계 — 데이터 검사 함수와 `questions.js`

`archive/PRD-v5.md` 6절 1단계. 여섯 단계 중 가장 무거우므로 하위 작업 여덟 개로 쪼갠다. **검사 함수를 문제 데이터보다 먼저 만든다.** 그래야 40문제를 쓰는 동안 위반이 즉시 콘솔에 드러난다.

**선행 조건**: 없다. 여기가 시작점이다.

## 만들거나 고칠 파일

| 파일 | 이 단계에서 하는 일 |
|---|---|
| `index.html` | 신규. 검사를 실행할 **최소 골격만** 만든다. 화면 마크업은 2단계에서 채운다 |
| `questions.js` | 신규. `CATEGORIES`와 `QUESTIONS`를 선언하고 40문제를 채운다 |
| `script.js` | 신규. 전역 상수, 검사 함수, 로드 시점 초기화만 넣는다 |
| `style.css` | 신규. 에러 문구 스타일 한 가지만 넣는다 |

파일명은 모두 소문자로 만들고 `index.html`의 참조와 정확히 일치시킨다(PRD 4절).

## 이 단계에서 정의할 함수

`script.js`

| 함수 | 책임 |
|---|---|
| `validateData()` | `CATEGORIES`와 `QUESTIONS`를 PRD 4.2절 2번의 검사 항목으로 검사해 위반 문자열 배열을 반환한다. 위반이 없으면 빈 배열 |
| `showDataError()` | `data-error`의 `hidden`을 풀어 `문제 데이터를 불러오지 못했습니다.`를 보이게 하고, 게임 시작 경로를 막는다 |
| `init()` | 페이지 로드 시 한 번 실행한다. 데이터 존재 확인 → `validateData()` → 위반이 있으면 콘솔 출력과 `showDataError()`, 없으면 이후 단계의 초기화를 잇는다 |

`init()`은 `DOMContentLoaded`에 건다. `questions.js`가 `script.js`보다 먼저 로드되므로 전역 상수는 이미 준비된 상태다.

## 검사 항목과 콘솔 출력 형식

위반 한 건마다 `console.error(문자열)`로 출력한다. 형식은 `{문제 id}: {위반 내용}`으로 하고, 문제 단위가 아닌 위반은 `{카테고리 id}: {위반 내용}`으로 쓴다. 사용자 화면에는 일반 문구 하나만 띄운다(PRD 4.2절).

| # | 검사 | 출력 예 |
|---|---|---|
| V0 | `CATEGORIES`, `QUESTIONS`가 정의되어 있고 각각 배열, 객체인가 | `CATEGORIES가 정의되지 않았습니다` |
| V1 | `CATEGORIES`의 모든 `id`가 `QUESTIONS`에 배열로 있는가 | `geography: QUESTIONS에 항목이 없습니다` |
| V2 | 카테고리마다 문제 수가 `QUIZ_LENGTH` **이상**인가 | `science: 문제 수가 8입니다. 10 이상이어야 합니다` |
| V3 | `options`가 길이 4의 배열인가 | `kh_07: options 길이가 3` |
| V4 | `answer`가 0 이상 3 이하의 **정수**인가 (`Number.isInteger`로 판정) | `sc_02: answer가 정수가 아님 ('1')` |
| V5 | `difficulty`가 `DIFFICULTY_LABELS`의 키인가 | `ge_05: difficulty가 'hardd'` |
| V6 | `question`, `explanation`이 문자열이며 공백을 뺀 길이가 0이 아닌가 | `ac_09: explanation이 비어 있음` |
| V7 | 한 문제 안에 같은 텍스트의 선택지가 없는가 | `kh_03: options에 중복된 선택지 '세종'` |
| V8 | `id`가 전체에서 중복되지 않는가 | `sc_04: id 중복` |
| V9 | `question` 텍스트가 전체에서 중복되지 않는가 | `ge_08: question 텍스트 중복` |
| V10 | `question`이 60자 이내인가 | `kh_06: question이 63자` |
| V11 | 각 선택지가 20자 이내인가 | `ac_04: options[2]가 24자` |

V2는 **`>= QUIZ_LENGTH`로 쓴다.** `=== QUIZ_LENGTH`로 쓰면 2차 구현에서 문제를 늘리는 순간 검사 자체가 걸림돌이 된다(PRD 8절).

V8과 V9는 카테고리를 넘어 전체 범위에서 판정한다. 카테고리 안에서만 보면 다른 카테고리와 겹치는 id를 놓친다.

### 문제 데이터 작성 규칙 (1.6~1.7)

- 카테고리마다 초급 4, 중급 4, 고급 2를 기준으로 한다. 합이 10이면 다른 조합도 된다.
- 카테고리마다 `answer` 값 0, 1, 2, 3이 각각 2~3회씩 나오게 배치한다.
- `question`은 60자 이내, 각 선택지는 20자 이내로 쓴다.
- **문제 텍스트와 해설에 선택지의 위치를 지칭하는 표현을 쓰지 않는다.** "위의 두 번째 보기", "첫 번째 항목"은 선택지를 섞는 순간 사실과 어긋난다(PRD 2.1절). 이 규칙은 검사 함수가 잡을 수 없다.
- 해설은 한두 문장으로 **그 정답이 정답인 근거**를 쓴다. 문제를 되풀이하는 문장은 해설이 아니다.

### 저장소 밖에서 검사 함수를 부를 때

브라우저 콘솔 말고 **명령줄에서 검사 함수만 돌려야 할 때**가 있다. 커스텀 명령어가 그렇다.
그 경로를 여기 정해 둔다. **정해 두지 않으면 부르는 쪽마다 다른 방법을 새로 만든다.**

```bash
node -e "
const fs = require('fs'), vm = require('vm');
const ctx = vm.createContext({ console, document: { addEventListener() {} } });
vm.runInContext(fs.readFileSync('questions.js','utf8'), ctx);
vm.runInContext(fs.readFileSync('script.js','utf8'), ctx);
const errors = vm.runInContext('validateData()', ctx);
console.log(errors.length ? errors.join('\n') : '위반 0건');
"
```

- `script.js`는 브라우저용이다. 그냥 읽으면 마지막 줄의 `document.addEventListener`에서
  `ReferenceError: document is not defined`가 난다. `export`도 없다
- `vm.createContext`에 `document` 스텁을 주면 통과하고, 같은 컨텍스트에서 함수를 부를 수 있다
- **행 번호나 줄 범위로 파일을 잘라 쓰지 않는다.** 함수가 옮겨지면 같이 틀린다
- 이 줄은 저장소 뿌리에서 실행한다

`script.js`의 로드 방식이나 마지막 줄이 바뀌면 이 줄도 함께 고친다.

### 검사 함수 검증 절차 (1.5)

검사 함수가 실제로 위반을 잡는지 확인하지 않으면, 이후 40문제가 통과한 것이 "데이터가 맞다"는 뜻인지 "검사가 아무것도 안 한다"는 뜻인지 구별할 수 없다.

**파일을 고치지 않고 브라우저 콘솔에서 한다.** `validateData()`는 전역 `QUESTIONS`를 읽으므로, 그 객체의 내용을 바꾼 뒤 함수를 직접 부르면 파일을 고쳐 새로고침한 것과 같은 상태를 본다. 복구는 새로고침 한 번이면 되고, 임시 변경이 커밋에 섞일 수 없다.

1. `questions.js`에 `kh_01` 한 문제만 정상으로 넣고 페이지를 연다.
2. 콘솔에서 아래를 하나씩 적용하고 `validateData()`를 불러 기대한 메시지가 나오는지 본다. `QUESTIONS`는 `const`라 재할당은 안 되지만 **속성 변경은 된다.**

```javascript
const base = QUESTIONS.korean_history[0];
const broken = JSON.parse(JSON.stringify(base));
broken.options.pop();                    // 아래 표의 임시 변경
QUESTIONS.korean_history = [broken];     // 전역 객체의 속성을 바꾼다
validateData();                          // 기대 출력 확인
QUESTIONS.korean_history = [base];       // 복구
```

| 임시 변경 | 기대 출력 |
|---|---|
| `options`에서 하나 삭제 | V3 |
| `options`의 한 값을 `''`로 | V3-원소 |
| `options`의 두 값을 같게 | V7 |
| `answer: 0` → `answer: '0'` | V4 |
| `answer: 0` → `answer: 4` | V4 |
| `difficulty: 'easy'` → `'esay'` | V5 |
| `explanation: ''` | V6 |
| `question: '   '` | V6 |
| `id` 삭제 | V8-존재 |
| 같은 문제를 복사해 둘로 | V8, V9 |
| 복사본의 `id`만 `kh_02`로 변경 | V9 |
| `QUESTIONS`에서 카테고리 키 하나 삭제 | V1 |
| `question`을 60자 넘게 늘리기 | V10 |
| `options`의 한 값을 20자 넘게 늘리기 | V11 |

3. 마지막에 새로고침한 뒤 `validateData()`가 문제 수 부족만 보고하는지 확인하고 1.6으로 넘어간다. `git diff questions.js`도 비어 있어야 한다. 이 방식에서는 자동으로 충족되지만, 5단계 5.3절은 파일을 직접 고치므로 그때 다시 쓴다.

### 육안 검토 절차 (1.8)

검사 함수가 통과해도 잡히지 않는 종류가 있다. `answer`가 0~3 안에 있으면서 **틀린 선택지를 가리키는 경우**, 해설이 채워져 있으나 **정답과 무관한 경우**다. 둘 다 화면은 정상이고 채점만 조용히 틀린다(`archive/PRD-v5.md` 6절).

**누가 판정하고 언제 닫는가**

- **클로드가 판정하고 사람이 채택 여부를 결정한다.** 클로드는 어긋난 자리와 근거를 올리고, 고칠지는 사람이 정한다.
- **판정은 문항을 쓴 세션이 아닌 다른 세션이 한다.** 쓴 세션이 검토하면 쓸 때 한 판단을 그대로 되풀이한다.
- **판정을 두 번 받되 두 번을 서로 다른 세션이 한다.** 새로 걸리는 것이 없어야 닫는다.
  같은 세션이 두 번 도는 것은 한 번으로 친다. 두 세션 모두 문항을 쓴 세션이 아니어야 한다.
- **어디서 멈출지를 정해 둔다.** 매 라운드 한 칸 더 미세한 것을 찾으면 종료 조건에 닿지 못한다.
  **정답 판정을 바꾸지 않고 읽는 사람을 틀린 결론으로 이끌지 않으면 고치지 않는다.**
- **걸린 것을 사람이 반려하거나, 고친 뒤 다시 돌리지 않기로 정하면 그것도 닫는 결정이다.**
  판정은 클로드가 하고 채택은 사람이 한다. 반려나 조기 종료를 정했으면 그 판단을 문서에 남긴다.
- **라운드마다 문항별 판정을 `history/`에 남긴다.** 클로드의 판정은 재현되지 않아 같은 40문항에서도 걸리는 것이 라운드마다 다르다. 기록이 있어야 다음 라운드가 앞 라운드를 덮지 않고 더한다.
- **서로 다른 세션인지는 문서 앞머리의 이름이 아니라 커밋으로 판정한다.** 이름은 자기 것이 아닌 것을 적어도 아무도 못 거른다. 주 작업 폴더도 유일하지 않다. `git log`의 커밋 신원과 해시가 유일하다. 앞머리에 세션 이름을 적는 것은 그대로 두되 그것으로 세지 않는다.
- **대조 단위는 문항이 아니라 사실 하나다.** 해설 한 문장에 연도나 인명이 둘이면 둘 다 댄다. 하나만 대고 문항을 통과시키면 나머지가 대조를 안 거친 채 남는다.
- **고친 문장만 다시 대조하지 않는다. 그 문장이 놓인 자리도 함께 본다.** 해설을 고치면서 같은 낱말을 쓰는 문항이 어긋날 수 있다. 대조 범위가 한 칸씩 넓어져 온 자리다 — 새로 넣은 사실(38번), 한 문장 안의 둘째 사실(43번), 문장 밖의 어긋남(44번).

40문제를 하나씩 보며 다음 네 가지를 확인한다.

1. `options[answer]`가 정말 그 문제의 정답인가.
2. `explanation`이 그 정답의 근거를 설명하는가.
3. 문제 텍스트와 해설에 선택지 위치를 지칭하는 표현이 없는가.
4. 오답 선택지 세 개가 명백한 오답인가. 정답이 둘로 읽히는 문제가 없는가.

이어서 PRD 3.6절의 작성 규칙이 지켜졌는지 본다. **규칙은 쓸 때 지키고 여기서 확인한다.** 넷 다 클로드가 판정하는 것이라 검사 함수에 넣을 수 없으므로, 대신 **점검 목록을 뽑아 볼 곳을 좁힌다.** 40문제에서도 도움이 되고, 2차에서 문항이 늘면 이것 없이는 확인이 성립하지 않는다.

**5. 최상급 표현에 재는 기준과 범위가 있는가**

```javascript
Object.values(QUESTIONS).flat()
  .filter(q => /가장|최초|최대|최고|유일/.test(q.question + q.explanation))
  .map(q => q.id + '  ' + q.question + '  /  ' + q.explanation)
```

나온 목록을 한 줄씩 보며 **최상급 표현이 놓인 자리(문제 텍스트든 해설이든)에** "무엇으로 재는가"와 "어디 안에서인가"가 함께 있는지 판정한다. **해설도 함께 거는 이유는** 문제 텍스트에 최상급이 없고 해설에만 있는 문항이 있어서다. `question`만 걸면 후보에 들지 않는다. `ge_07`이 그런 경우다. 없으면 넣거나, 기준을 바꿔도 답이 갈리지 않는지 확인한다. 1차에서는 문제 텍스트만 걸어 9개가 나왔고 `ge_02` 하나를 고쳤다. 해설까지 걸도록 넓힌 뒤에는 10개가 나온다.

**6. 시점에 따라 달라지는 수치가 있는가**

```javascript
Object.values(QUESTIONS).flat()
  .filter(q => /\d{4}년|\d[\d,.]*\s*(만|억)?\s*(미터|제곱|%|배)/.test(q.explanation))
  .map(q => q.id + '  ' + q.explanation)
```

나온 해설을 보며 그 수치가 시간이 지나 달라질 것인지 판정한다. 역사적 상수는 넘어가고, 측정치나 최신 기록이면 해설에 기준 시점을 적는다.

**7. 해설의 연도, 수치, 인명을 출처 둘 이상으로 대조했는가**

이것만은 목록으로 뽑을 수 없다. 출처를 봤는지는 데이터에 흔적이 남지 않는다. 대신 **자료가 갈리는 문항에는 판단 근거를 주석으로 남긴다.** 근거가 비어 있으면 대조하지 않았다는 뜻이 된다.

```javascript
{
  id: 'kh_07',
  // 근거: 문항이 "지은 사람"을 물으므로 저술 완성(1610) 기준. 간행 1613년은 다른 사건.
  question: '조선의 의서 『동의보감』을 지은 사람은 누구인가?',
```

자료가 갈리면 주류 학설을 따른다. 작성자와 검토자가 같은 오해를 공유하면 기억에만 기대는 검토는 그대로 통과한다.

**주석이 서술하는 것과 `question`, `explanation`이 실제로 담은 것이 맞는지 함께 확인한다.** 어긋나면 다음 라운드가 주석을 믿고 그 자리를 안 본다. `ac_15`가 그 자리였다 — 주석은 소란의 원인을 쓰지 않았다고 적었는데 해설에는 적혀 있었다(54번 6절).

**8. 문항끼리 같은 사실을 묻고 있지 않은가**

검사 함수는 `question` 텍스트 중복만 잡으므로 "조선을 건국한 인물은?"과 "1392년 조선을 세운 사람은?"은 둘 다 통과한다. 카테고리별로 문제 목록을 훑어 같은 사실을 두 번 묻는지 본다.

```javascript
QUESTIONS.korean_history.map(q => q.id + '  ' + q.question)
```

**한 문항의 정답이 다른 문항의 오답 선택지로 쓰인 자리도 함께 뽑는다.** 위 목록으로는 안 보인다. 먼저 만난 문항이 다음 문항의 답을 알려 주는 자리이며, **위반이 아닌 것이 보통이므로 뽑아만 주고 판정하지 않는다.**

```javascript
Object.entries(QUESTIONS).forEach(([cat, qs]) => {
  const ans = new Map(qs.map(q => [q.options[q.answer], q.id]));
  qs.forEach(q => q.options.forEach((o, i) => {
    if (i !== q.answer && ans.has(o)) console.log(cat + ': ' + o + ' — 정답 ' + ans.get(o) + ' / 오답 ' + q.id);
  }));
});
```

**표기가 다르면 이 검사가 못 잡는다.** `ac_10`은 "스트라빈스키", `ac_15`는 "이고르 스트라빈스키"로 적어 문자열이 어긋난다. 인명은 성만 떼어 한 번 더 대조한다.

**카테고리별 분포 확인**

`answer` 분포와 난이도 배분은 콘솔에서 세는 편이 빠르다. 확인만 하고 코드에 남기지 않는다.
2차에서는 `/quiz-stats` 명령어가 이 자리를 가져갔다(PRD 3.6절 확인 수단 표). 아래 두 줄은 1단계 당시의 방법이다.

```javascript
QUESTIONS.korean_history.map(q => q.answer).sort()
QUESTIONS.korean_history.map(q => q.difficulty).sort()
```

| `clearNameError()` | `name-error`를 비운다. 입력란의 `input` 이벤트에 건다 |
| `startGame(mode, categoryId)` | **이 단계에서는 스텁.** 이름 검증을 통과하면 `state`에 이름과 모드를 넣고 `showScreen('screen-quiz')`만 한다. 3단계에서 채운다 |

`showScreen`은 `visibility`나 투명도를 쓰지 않는다. `hidden` 속성으로 감춰야 감춘 화면이 스크린리더와 탭 순서에서 빠진다(PRD 3.0절).

**이벤트 바인딩도 이 단계에서 한다.** 카드 네 개와 전 범위 버튼은 `startGame`에, `btn-open-ranking`과 `btn-close-ranking`은 `showScreen` 호출에 건다. 뒤 두 개는 별도 함수를 만들지 않지만 거는 작업은 2단계 몫이다. 순위표 내용을 그리는 것은 4단계이므로, 여기서는 빈 껍데기 화면이 열리고 닫히기만 하면 된다.

## 마크업 규칙

- 각 화면은 `<section class="screen" id="screen-...">`이고, 제목은 `<h2 id="...-title" tabindex="-1">`이다.
- **조작 가능한 요소는 전부 `<button>` 또는 표준 폼 요소다.** 카테고리 카드도 `<button>`이며 모양은 CSS로 낸다. `<div>`에 클릭 핸들러를 붙이면 키보드로 조작할 수 없다(PRD 3.0절).
- 이름 입력란에 `maxlength`를 **주지 않는다.** 자르기 전 길이를 세는 규칙과 어긋난다(PRD 3.1절).
- 카드 라벨은 `${cat.name}` + `${QUIZ_LENGTH}문제` 꼴로 조립한다. 마크업에 `10`을 직접 쓰지 않는다. 보유 문제 수는 표시하지 않는다.
- "전 범위 도전 (10문제)" 버튼의 숫자도 `QUIZ_LENGTH`에서 조립한다.

## 이름 검증 규칙

| 입력 | 결과 |

| `"  "` (공백만) | 시작 불가, `이름을 입력해 주세요.` |
| `"홍길동"` | 통과 |
| 13자 이상(공백 제거 후) | 시작 불가, `이름은 12자까지 입력할 수 있습니다.` |
| `"  홍길동  "` | 통과. `state.playerName`은 `"홍길동"` |

**조용히 잘라 내지 않는다.** 절단하면 순위표에 본인이 입력한 적 없는 이름이 남는다(PRD 3.1절).

## 이 단계에서 정의할 함수

| 함수 | 책임 |
|---|---|
| `shuffle(arr)` | Fisher-Yates로 섞은 **새 배열**을 반환한다. 원본을 건드리지 않는다 |
| `prepareQuestion(q, category)` | 선택지를 섞고 정답 텍스트의 새 인덱스로 `answer`를 갱신한 새 객체를 만든다. `categoryName`을 함께 붙인다 |
| `pickCategoryQuiz(categoryId)` | 해당 카테고리에서 `QUIZ_LENGTH`문제를 뽑아 `prepareQuestion`을 거친 배열을 반환한다 |
| `pickAllQuiz()` | 카테고리 순서를 섞어 3, 3, 2, 2문제를 뽑고 **합친 결과를 다시 섞은 뒤** `prepareQuestion`을 거친 배열을 반환한다 |
| `startGame(mode, categoryId)` | 2단계의 스텁을 채운다. `state` 초기화 → 문제 뽑기 → `showScreen('screen-quiz')` → `renderQuestion()` → 이탈 경고 켜기 순서로 진행한다 |
| `renderQuestion()` | 현재 문제로 상단 정보, 문제 텍스트, 선택지 버튼 네 개를 그리고 피드백 영역과 "다음 문제" 버튼을 감춘다. 문제 텍스트로 초점을 옮긴다 |
| `handleAnswer(choiceIndex)` | 채점하고 점수를 갱신한 뒤 버튼을 잠그고 강조와 피드백을 표시한다 |
| `goNext()` | 다음 문제를 그리거나, 마지막이면 결과 화면으로 넘어간다 |
| `quitGame()` | 확인창을 띄우고 확인하면 이탈 경고를 끄고 시작 화면으로 돌아간다 |
| `enableUnloadGuard()` / `disableUnloadGuard()` | `beforeunload` 핸들러를 등록, 해제한다. 등록과 해제에 같은 함수 참조를 쓴다 |
| `finishGame()` | **이 단계에서는 스텁.** 이탈 경고를 끄고 `showScreen('screen-result')`만 한다. 4단계에서 채운다 |

## 하위 작업

### 3.1 셔플과 문제 선정

`shuffle`은 PRD 2.1절의 Fisher-Yates 구현을 그대로 쓴다. **`sort(() => Math.random() - 0.5)`를 쓰지 않는다.** 섞이기는 하므로 화면으로는 이상을 알아챌 수 없지만 정답이 특정 자리에 더 자주 남는다.

`pickCategoryQuiz`는 뽑기가 한 줄이다.

```
shuffle(QUESTIONS[categoryId]).slice(0, QUIZ_LENGTH)
```

뽑은 각 문제를 `prepareQuestion(q, category)`에 넘긴다. `category`는 `CATEGORIES.find(c => c.id === categoryId)`로 얻는다. `pickAllQuiz`는 카테고리를 돌며 뽑으므로 그 객체를 그대로 넘기면 된다.

`pickAllQuiz`는 세 단계다. **셋을 모두 거쳐야 한다.**

1. `shuffle(CATEGORIES)`로 카테고리 순서를 섞는다 — 어느 카테고리가 3문제인지가 판마다 달라진다.
2. `ALL_COUNTS`의 `[3, 3, 2, 2]`만큼 각 카테고리에서 `shuffle` 후 `slice`한다.
3. **합친 결과를 다시 `shuffle`한다** — 이 단계를 빠뜨리면 한국사 세 문제가 연달아 나오고 그다음 과학 문제가 나오는 식으로 카테고리 순서대로 출제된다(R1).

뽑기와 최종 순서 섞기는 별개 단계다.

### 3.2 선택지 섞기와 `answer` 갱신

`prepareQuestion`은 다음 순서로 한다.

1. 원본 `q.options[q.answer]`의 **텍스트를 먼저 기억한다.**
2. `shuffle(q.options)`로 새 선택지 배열을 만든다.
3. 새 배열에서 기억해 둔 텍스트의 위치를 찾아 `answer`로 삼는다.
4. 원본을 수정하지 않고 새 객체를 반환한다. 반환 객체는 `id`, `question`, `options`(섞인 것), `answer`(갱신된 것), `difficulty`, `explanation`, `categoryName`을 갖는다.

**3번을 빠뜨려도 화면은 정상으로 보이고 채점만 조용히 틀린다(R2).** 원본 배열을 그 자리에서 섞으면 다음 판의 데이터까지 오염되므로 반드시 새 배열을 만든다.

`categoryName`은 화면 상단의 카테고리 표시(PRD 3.2절)에 쓰고, R1 확인에도 쓴다.

### 3.3 상단 정보와 문제 렌더링

| 요소 | 내용 |
|---|---|
| `quiz-progress` | `${state.index + 1} / ${QUIZ_LENGTH} 문제` |
| `quiz-score` | `점수 ${state.score} / ${QUIZ_LENGTH}` |
| `quiz-category` | `question.categoryName` |
| `quiz-difficulty` | `DIFFICULTY_LABELS[question.difficulty]`, 클래스는 `diff-${question.difficulty}` |

숫자는 모두 `QUIZ_LENGTH`에서 조립한다. `"/ 10 문제"`를 마크업에 직접 쓰지 않는다.

"점수" 라벨을 반드시 붙인다. 진행 상황과 표기가 같은 꼴이라 라벨이 없으면 어느 쪽이 점수인지 즉시 읽히지 않는다.

문제 텍스트와 선택지는 `textContent`로 넣는다. 렌더링 후 `question-text`로 초점을 옮긴다.

### 3.4 채점과 피드백

`handleAnswer(choiceIndex)`의 순서다. **맨 앞에 "이미 답했는가" 가드를 두지 않는다.** 재선택은 2번의 `disabled`가 막는다(상태 객체 절 참고).

1. `choiceIndex === question.answer`면 `state.score`를 1 올리고 상단 점수 표시를 갱신한다.
2. 선택지 버튼 네 개를 모두 `disabled`로 만든다.
3. 정답 버튼에 정답 클래스를 걸고 텍스트에 `✓`를 덧붙인다.
4. 틀렸으면 고른 버튼에 오답 클래스를 걸고 `✗`를 덧붙인다. **색만으로 구분하지 않는다.**
5. `feedback`에 판정 문구와 해설을 채운다. 오답이면 `오답입니다. 정답은 ${question.options[question.answer]}입니다.`
6. `feedback`으로 **초점을 옮긴다.**
7. `btn-next`를 노출한다. 마지막 문제(`state.index === QUIZ_LENGTH - 1`)면 라벨을 `결과 보기`로 바꾼다.
8. `btn-next`가 화면에 들어오도록 스크롤한다(`scrollIntoView`). 해설이 펼쳐지면 모바일에서 버튼이 화면 밖으로 밀리는데, 눌러야 넘어가는 구조라 그대로 두면 게임이 멈춘 것처럼 보인다.

**`feedback`에 `aria-live`, `role="status"`, `role="alert"`를 주지 않는다(R5).** 초점을 옮기면 스크린리더가 그 내용을 읽으므로 낭독은 보장되고, 라이브 영역과 초점 이동을 함께 쓰면 낭독이 도중에 끊긴다. `btn-next`는 마크업에서 `feedback` 바로 뒤에 두어 Tab 한 번으로 닿게 한다.

### 3.5 다음 문제

`goNext()`의 순서다.

1. `btn-next`를 **즉시 숨긴다.** 연타로 문제를 건너뛰는 것을 막는다.
2. `state.index`를 1 올린다. `QUIZ_LENGTH`에 도달했으면 `finishGame()`을 부르고 끝낸다.
3. `renderQuestion()`을 부른다.
4. 스크롤을 문제 영역 상단으로 되돌린다. 앞 문제에서 내려간 위치를 그대로 두면 다음 문제가 중간부터 보인다.

자동으로 넘어가는 타이머를 넣지 않는다. 해설을 읽을 시간이 필요하다.

### 3.6 그만두기와 이탈 경고

`quitGame()`은 `confirm(그만두기 확인창 문구)`를 띄우고, 확인하면 `disableUnloadGuard()` 후 `showScreen('screen-start')`로 간다. 기록은 남기지 않는다. 이름은 입력란에 그대로 둔다.

`beforeunload`는 다음 규칙을 지킨다(PRD 3.2절).

- **등록**: `startGame`에서 판을 시작할 때.
- **해제**: 결과 화면으로 넘어갈 때(`finishGame`), "그만두기"를 확인했을 때(`quitGame`). 이 두 곳뿐이다.
- 데이터 검사 실패는 해제 대상이 아니다. 검사는 페이지 로드 시점에 돌고 등록은 판 시작 시점이라, 검사가 실패하면 등록 자체가 일어나지 않는다. `showDataError()`에 해제 호출을 넣지 않는다.
- 해제하지 않으면 정상적으로 끝낸 뒤에도 창을 닫을 때마다 경고가 뜬다. 사용자는 경고를 무시하는 법을 배우고, 정작 진행 중 실수를 막는 효과가 사라진다.
- **확인창 문구는 지정할 수 없다.** 모든 최신 브라우저가 커스텀 메시지를 무시한다. 문구를 정하는 작업은 하지 않는다.
- Safari에서는 동작하지 않는다(PRD 4.1절의 `beforeunload` 항목). 우회 방법을 찾지 않는다.

## 완료 기준

Chrome에서 `index.html`을 열고 다음을 한다.

1. `홍길동`으로 한국사 도전을 시작한다 → 상단에 `1 / 10 문제`, `점수 0 / 10`, `한국사`, 난이도 배지가 보인다.
2. 오답을 하나 고른다 → 네 버튼이 모두 비활성이 되고, 정답 버튼이 초록 `✓`, 고른 버튼이 빨강 `✗`이며, 피드백에 `오답입니다. 정답은 ○○입니다.`와 해설이 나오고, 점수는 그대로다.
3. 정답을 고른 문제에서는 `점수 1 / 10`처럼 상단 점수가 즉시 오른다.
4. 10번째 문제에서 버튼 라벨이 `결과 보기`로 바뀐다. 누르면 결과 화면(빈 껍데기)으로 간다.
5. 판을 다시 시작해 "그만두기"를 누른다 → 확인창이 뜨고, 확인하면 시작 화면으로 돌아간다.
6. 진행 중 새로고침을 누른다 → 브라우저 확인창이 뜬다. 결과 화면까지 정상으로 끝낸 뒤 새로고침하면 **확인창이 뜨지 않는다.**

  ```javascript
  state.quiz.map(q => q.categoryName).filter((c, i, a) => i === 0 || c !== a[i - 1]).length
  ```

  최종 섞기가 빠지면 카테고리별로 뽑아 이어 붙인 그대로라 값이 **정확히 4**가 된다. 반대로 제대로 섞였는데 우연히 4가 나올 확률은 배열 25,200가지 중 24가지, 1050분의 1이다. 눈으로 "뭉쳐 보이는가"를 판정하거나 최대 연속 길이를 세면 안 된다. 최대 연속 3은 제대로 섞여도 12.6% 확률로 나와 여덟 판에 한 번꼴로 멀쩡한 코드를 버그로 부른다
- [ ] **(R1) 3+3+2+2 배분.** 같은 콘솔 출력에서 카테고리별 개수를 센다. 네 카테고리가 각각 3, 3, 2, 2개이고 합이 10이다. 판마다 어느 카테고리가 3개인지 달라진다
- [ ] **(R2) `answer` 갱신.** 판을 시작한 뒤 콘솔에 아래를 입력한다. **`true`여야 한다.** 섞은 뒤의 정답 텍스트가 원본의 정답 텍스트와 열 문제 모두 일치하는지 본다

  ```javascript
  state.quiz.every(q => {
    const orig = Object.values(QUESTIONS).flat().find(o => o.id === q.id);
    return q.options[q.answer] === orig.options[orig.answer];
  })
  ```

  `false`면 `every`를 `filter`로 바꿔 어느 문제인지 찾는다. **화면 조작으로는 R2를 잡을 수 없다.** 강조와 피드백이 둘 다 같은 `answer`를 참조하므로, 갱신을 빠뜨려도 화면 안에서는 앞뒤가 맞는다. 원본 데이터와 대조하는 것이 유일한 수단이다
- [ ] **(R2) 원본 오염.** 같은 카테고리로 판을 세 번 시작한 뒤 콘솔에서 `QUESTIONS.korean_history[0].options`가 `questions.js`에 적힌 원래 순서 그대로인지 확인한다. 순서가 바뀌어 있으면 `prepareQuestion`이 원본 배열을 제자리에서 섞은 것이다
- [ ] **(R5) `aria-live` 없음.** `grep -nE 'aria-live|role="status"|role="alert"' index.html script.js`가 아무것도 출력하지 않는다. 개발자 도구 Elements에서 `#feedback`에 해당 속성이 없다
- [ ] `sort(() => Math.random() - 0.5)`를 쓰지 않았다. `grep -n 'Math.random' script.js`로 나온 줄이 `shuffle` 안의 Fisher-Yates 한 줄뿐이다
- [ ] 선택지가 `<button>`이고, 답을 고르면 네 개가 모두 `disabled`가 된다. 개발자 도구 Elements에서 속성을 확인한다. **재선택 방어를 여기에만 맡기므로**(가드 플래그가 없다) `<div>`나 `aria-disabled`로 대신하면 안 된다
- [ ] 답을 고른 뒤 같은 문제의 다른 선택지를 눌러도 점수가 변하지 않는다. `✓`가 붙은 정답 버튼의 글자 부분을 정확히 눌러도 마찬가지다
- [ ] "다음 문제"를 빠르게 두 번 눌러도 문제가 한 개만 넘어간다
- [ ] 답을 고르면 초점이 `#feedback`에 있다(`document.activeElement`로 확인). 새 문제를 그리면 `#question-text`에 있다
- [ ] 퀴즈 화면에 처음 들어갈 때 초점이 제목을 **거치지 않고** 곧장 첫 문제 텍스트로 간다(PRD 4.3절). 판을 시작하기 전에 아래를 콘솔에 넣고, 판을 시작한 뒤 `seen`을 본다. **`['question-text']` 하나여야 한다.** `['quiz-title', 'question-text']`이면 초점이 두 번 움직인 것이다. 최종 상태만 보는 `document.activeElement`로는 이 결함이 잡히지 않는다

  ```javascript
  const seen = [];
  document.addEventListener('focusin', function (e) { seen.push(e.target.id); });
  ```
- [ ] 진행 상황과 점수의 `10`이 `QUIZ_LENGTH`에서 조립되었다. 마크업에 `10`이 박혀 있지 않다
- [ ] 정답, 오답이 `✓`, `✗` 기호로도 구분된다. 브라우저를 흑백으로 봐도(개발자 도구 Rendering의 색각 이상 에뮬레이션) 판정을 읽을 수 있다
- [ ] `beforeunload`가 정상 종료 후 해제된다(완료 기준 6번)

# 4단계 — 결과 화면과 순위 기록, 순위표 화면

`archive/PRD-v5.md` 6절 4단계. **R3과 R4가 이 단계에 있다.**

**선행 조건**: 3단계 완료. `finishGame()` 스텁이 호출되는 지점까지 도달하고, `state`에 이름, 모드, 점수가 들어 있어야 한다.

## 만들거나 고칠 파일

| 파일 | 이 단계에서 하는 일 |
|---|---|
| `script.js` | 저장소 읽기/쓰기, 날짜, 순위 저장, 결과 렌더링, 순위표 렌더링 |
| `style.css` | 결과 화면과 순위표 화면 스타일, 강조 줄 스타일 |
| `index.html` | 결과, 순위표 화면 마크업 보정만 |

## 이 단계에서 정의할 함수

| 함수 | 책임 |
|---|---|
| `formatDate(date)` | 로컬 시간대 기준 `YYYY-MM-DD` 문자열을 만든다. 인자를 생략하면 현재 시각을 쓴다 |
| `emptyRankings()` | 다섯 키가 모두 빈 배열인 객체를 만든다 |
| `sanitizeList(value)` | 값이 기대한 형태의 배열이면 그대로, 아니면 **빈 배열**을 반환한다 |
| `readRankings()` | `localStorage`에서 읽어 다섯 키를 가진 객체를 반환한다. 접근이나 파싱이 실패하면 `null` |
| `writeRankings(data)` | `localStorage`에 쓴다. 성공하면 `true`, 실패하면 `false` |
| `saveRanking(key, record)` | 읽기 → 삽입 → 정렬 → 자르기 → 쓰기. 정수 인덱스 / `null` / `'unavailable'`을 반환한다 |
| `clearAllRankings()` | 저장 키를 지운다. 성공 여부를 반환한다 |
| `renderRankingTable(container, list, highlightIndex)` | 순위, 이름, 점수, 날짜 네 열의 표를 그린다. 빈 배열이면 `아직 기록이 없습니다.`를 넣는다 |
| `finishGame()` | 3단계 스텁을 채운다. 이탈 경고를 끄고 순위를 저장한 뒤 결과 화면을 그린다 |
| `renderResult(saveResult)` | 점수, 정답률, 이름과 모드, 순위 진입 문구, 해당 모드 순위표를 그린다. 순위표 목록은 **`readRankings()`를 다시 불러** 얻는다 |
| `renderRankingScreen()` | 순위표 다섯 개를 그린다. 읽기와 쓰기를 따로 판정해 세 갈래로 나뉜다. 정상이면 하단 고정 안내를 보이고, **쓰기만 막히면** 저장 불가 안내로 바꾸되 표와 "기록 지우기"는 그대로 두며, **읽기까지 막히면** 표와 "기록 지우기"를 함께 감춘다 |
| `canWriteRankings()` | 저장소에 쓸 수 있는지 별도 키로 시험하고 곧바로 지운다. 읽기 성공만으로는 쓰기 가능 여부를 알 수 없다 |

## 하위 작업

### 4.1 저장소 읽기와 쓰기

`localStorage` 접근은 전부 `try/catch`로 감싼다. 실패해도 게임 진행은 막지 않는다.

`readRankings()`의 순서:

1. `localStorage.getItem(STORAGE_KEY)`를 `try` 안에서 읽는다. 예외가 나면 `null`을 반환한다.
2. 값이 없으면 `emptyRankings()`를 반환한다.
3. `JSON.parse`가 실패하면 `emptyRankings()`를 반환한다.
4. 다섯 키를 각각 `sanitizeList`에 통과시킨 객체를 만든다.

`sanitizeList(value)`는 **리스트 단위**로 판정한다. 배열이 아니거나, 항목 중 하나라도 `name`이 문자열이 아니거나 `score`, `total`이 숫자가 아니거나 `date`가 문자열이 아니면 빈 배열을 반환한다.

**다섯 개를 한꺼번에 비우지 않는다.** 하나가 깨졌다고 나머지 네 개의 기록까지 날릴 이유가 없다(PRD 4.2절 4번).

### 4.2 날짜

`formatDate(date = new Date())`는 `getFullYear()`, `getMonth() + 1`, `getDate()`를 두 자리로 채워 `YYYY-MM-DD`를 만든다.

**`toISOString().slice(0, 10)`을 쓰지 않는다(R4).** UTC 기준이라 한국 시간 오전 9시 이전에는 전날 날짜가 찍힌다. 화면으로는 알아채기 어려운 종류의 오류다.

인자를 받게 만드는 이유는 하나다. 시스템 시계를 바꾸지 않고도 콘솔에서 새벽 시각을 넣어 검증할 수 있어야 하기 때문이다(체크리스트 참고).

### 4.3 순위 저장

`saveRanking(key, record)`는 **읽기 → 삽입 → 정렬 → 자르기 → 쓰기** 순서다.

1. `readRankings()`를 **이 시점에** 부른다. 화면에 들어올 때 읽어 둔 값을 재사용하지 않는다. 두 탭에서 각각 플레이하면 나중에 저장하는 쪽이 앞선 저장을 덮어쓰는데, 읽기를 늦추면 대부분 해결된다. `null`이면 `'unavailable'`을 반환하고 끝낸다.
2. 해당 목록의 **맨 앞**에 `record`를 넣는다.
3. `score` 내림차순으로만 정렬한다. **비교 함수에 동점 처리를 넣지 않는다.** `Array.prototype.sort`는 ES2019부터 안정 정렬이 보장되므로, 맨 앞 삽입 + 안정 정렬이면 동점 시 최근 기록이 위에 온다.
4. `key === ALL_KEY ? ALL_LIMIT : CATEGORY_LIMIT`으로 자른다.
5. `writeRankings`가 실패하면 `'unavailable'`을 반환한다.
6. **자른 목록에서 `indexOf(record)`로 인덱스를 찾는다.** 있으면 그 정수를, `-1`이면 `null`을 반환한다.

**6번을 이름과 점수로 찾지 않는다(R3).** 같은 이름, 같은 점수의 기록과 구별되지 않는다. 순위표는 사람 목록이 아니라 도전 기록이라 같은 이름의 기록도 판마다 별개로 쌓인다.

`record`의 형태는 `{ name, score, total, date }`다. `total`은 `QUIZ_LENGTH`를 넣는다. 지금은 언제나 10이지만 결과 화면의 `8 / 10 정답` 표기에 쓰이고, 출제 수가 바뀔 때 기존 기록을 구별하는 근거가 된다.

### 4.4 결과 화면

`finishGame()`은 다음 순서다.

1. `disableUnloadGuard()`
2. `const key = state.mode === 'all' ? ALL_KEY : state.categoryId`
3. `const saveResult = saveRanking(key, { name: state.playerName, score: state.score, total: QUIZ_LENGTH, date: formatDate() })`
4. `renderResult(saveResult)`
5. `showScreen('screen-result')`

`renderResult`가 그리는 것:

| 요소 | 내용 |
|---|---|
| `result-score` | `${state.score} / ${QUIZ_LENGTH} 정답` |
| `result-rate` | `정답률 ${Math.round(state.score / QUIZ_LENGTH * 100)}%` |
| `result-player` | 이름과 모드. 모드 라벨은 카테고리별이면 `${카테고리 이름} 도전`, 전 범위면 `전 범위 도전`. 이름은 `textContent`로 넣는다 |

순위 진입 표시는 `saveResult`의 값으로만 판단한다.

| `saveResult` | 표시 |
|---|---|
| 정수 `N` | `result-rank-message`에 `순위표 ${N + 1}위 진입`. 순위표를 그리되 인덱스 `N`인 줄을 강조한다 |
| `null` | `순위표에 들지 못했습니다.` 강조 없이 순위표만 그린다 |
| `'unavailable'` | **진입 여부를 표시하지 않는다.** `result-rank-message`를 비우고, `result-ranking`을 감추고, `result-storage-notice`만 보인다 |

세 번째 경우에 진입 여부를 표시하면 만점을 받은 사람에게도 `순위표에 들지 못했습니다.`가 뜬다. 사실과 다른 메시지다.

결과 화면의 순위표는 **해당 모드 것 하나만** 보여 준다. 카테고리별 도전이면 그 카테고리의 표(최대 5줄), 전 범위 도전이면 전 범위 표(최대 10줄)다.

**순위표에 그릴 목록은 `renderResult`가 `readRankings()`를 다시 불러 얻는다.** `saveRanking`은 인덱스만 돌려주고 저장한 목록은 돌려주지 않기 때문이다. 저장 함수가 `{ index, list }`를 돌려주게 바꾸면 읽기 한 번을 아낄 수 있지만, PRD 3.4절이 반환값을 정수, `null`, `'unavailable'` 세 가지로 못박았으므로 계약을 바꾸지 않는다.

버튼 둘의 동작:

- **다시 도전**: 같은 모드, 같은 카테고리로 `startGame`을 다시 부른다. 문제는 새로 뽑는다. 이름은 직전 판의 이름을 그대로 쓴다(이름 입력을 다시 받지 않는다).
- **처음으로**: `showScreen('screen-start')`. 입력란의 이름은 그대로 남는다.

### 4.5 순위표 화면

`renderRankingScreen()`은 `readRankings()`를 부르고:

- `null`이면 `ranking-storage-notice`만 보이고 `ranking-tables`와 `btn-clear`를 **둘 다 감춘다.** 지울 것이 없는 상태에서 버튼만 남으면 눌러도 아무 일이 없어 고장으로 보인다.
- 정상이면 `CATEGORIES` 순서로 카테고리 표 네 개를 그리고, 마지막에 전 범위 표를 그린다. 각 표에 카테고리 이름(전 범위 표는 `전 범위`)을 제목으로 붙인다.

`renderRankingTable`은 순위, 이름, 점수, 날짜 네 열을 그린다. 점수는 `${score} / ${total}`로 쓴다. **순위 번호는 동점이어도 줄 순서대로 매긴다**(1, 2, 3, …). 이름은 `textContent`로 넣는다.

`ranking-persist-notice`는 마크업에 고정으로 두되, **저장소를 쓸 수 없을 때는 감춘다.** "브라우저 정책에 따라 사라질 수 있습니다"는 저장이 된다는 전제로 쓰인 문장이라, 저장이 아예 막힌 상태에서 이 문장만 남으면 사실과 반대되는 안심을 준다. 저장 불가 안내와 이 문장은 서로 배타적으로 보인다.

"기록 지우기"는 확인창을 한 번 띄우고, 확인하면 `clearAllRankings()` 후 `renderRankingScreen()`을 다시 부른다. "닫기"는 시작 화면으로 돌아간다.

## 완료 기준

Chrome에서 다음을 순서대로 한다.

1. `홍길동`으로 한국사 도전을 끝까지 푼다 → 결과 화면에 `N / 10 정답`, 정답률(정수 %), `홍길동`, `한국사 도전`이 보이고, 한국사 순위표에 방금 기록이 한 줄 있으며 그 줄이 강조되어 있고, `순위표 1위 진입`이 표시된다.
2. 콘솔에 `JSON.parse(localStorage.getItem('quizGameRankings'))`를 입력한다 → 다섯 키가 모두 있고 `korean_history`에 `{name, score, total, date}` 한 건이 있다. `date`가 **오늘 날짜**다.
3. "다시 도전"을 누른다 → 이름을 다시 묻지 않고 한국사로 새 판이 시작되며, 문제 구성이 1번과 다르다.
4. **기록이 쌓인 상태에서 낮은 점수로 한 판을 끝까지 푼다** → 순위표에서 그 줄이 아래에 오고, 강조된 줄이 정확히 **하나**이며 그 줄이다. 콘솔로 대신하지 않는다. 1번은 빈 순위표라 강조가 언제나 인덱스 0이고, **인덱스 0이 아닌 강조를 지나는 경로는 이 항목뿐이다.**
5. 페이지를 새로고침하고 "순위표 보기"를 누른다 → 다섯 개 표가 보이고 앞서 만든 기록이 그대로 있다. 기록이 없는 표에는 `아직 기록이 없습니다.`가 있다.
6. 카테고리 표에 6판을 쌓는다 → 5줄만 남고 가장 낮은 기록이 사라진다. 6번째 판이 5위 안에 못 들면 `순위표에 들지 못했습니다.`가 뜨고 강조된 줄이 없다.
7. "기록 지우기" → 확인창 → 확인 → 다섯 표가 모두 `아직 기록이 없습니다.`가 된다. 새로고침해도 비어 있다.

**6번의 기록 쌓기는 손으로 풀지 않아도 된다.** 정렬, 자르기, 미진입 판정은 저장 함수만 지나가므로 콘솔에서 직접 부르면 된다.

```javascript
saveRanking('korean_history', { name: '테스터A', score: 9, total: 10, date: formatDate() })
```

반환값이 인덱스인지 `null`인지도 콘솔에서 바로 읽힌다. 이 대체가 **건너뛰는 경로**는 `finishGame`의 뒷부분, 곧 `renderResult`와 화면 전환이다. 그래서 완료 기준 **1번과 4번은 실제로 한 판을 푼다.** 1번이 빈 순위표에서의 경로를, 4번이 기록이 쌓인 상태에서의 경로를 덮는다. 확인이 끝나면 7번의 "기록 지우기"로 테스트 데이터를 비운다.

> **콘솔 대체를 허용하는 자리에는 그 대체가 건너뛰는 경로를 함께 적는다.**
> 무엇을 콘솔로 대신할 수 있는지만 적으면, 대신하는 순간 무엇이 확인되지 않는지가 남지 않는다. 그 빈틈은 나중에 우연히 발견되거나 발견되지 않는다.

## 체크리스트

- [ ] **(R3) 인덱스를 객체 참조로 찾는다. — 실행 검증 없음, 코드 확인 필수.** `grep -nE 'findIndex|\.name ===' script.js`로 `saveRanking` 안에 이름 비교가 없는지 확인하고, 코드에서 `list.indexOf(record)`를 쓰는지 눈으로 본다. **R3를 잡는 수단은 이 코드 확인 하나뿐이다.** 맨 앞 삽입 + 안정 정렬 아래에서는 이름, 점수 검색과 참조 검색이 같은 값을 내므로 화면에 차이가 나타나지 않는다. 아래 두 항목은 R3 검증이 아니다
- [ ] **(PRD 3.4절) 같은 이름 기록을 합치지 않는다.** 같은 이름으로 같은 점수를 두 번 낸다. 순위표에 **두 줄이 각각 남는다.** 한 줄로 합쳐지거나 기존 줄이 갱신되면, 순위표를 사람 목록으로 다루는 구현이다
- [ ] **(렌더링 계약) 강조는 `highlightIndex`로만 건다.** 위와 같은 상황에서 두 번째 판의 결과 화면을 본다. 강조된 줄이 **하나뿐이고 두 줄 중 위쪽**이다. 두 줄이 모두 강조되면 `renderRankingTable`이 인덱스를 무시하고 이름 대조로 클래스를 걸고 있는 것이다
- [ ] **(R4) `toISOString`을 쓰지 않았다.** `grep -n 'toISOString' script.js`가 아무것도 출력하지 않는다
- [ ] **(R4) 새벽 시각 검증.** 콘솔에서 `formatDate(new Date('2026-08-12T01:30:00+09:00'))`를 실행하면 `'2026-08-12'`가 나온다. `'2026-08-11'`이 나오면 UTC 기준으로 만들고 있는 것이다
- [ ] 저장 함수가 `readRankings()`를 **쓰기 직전에** 부른다. 화면 진입 시 읽어 둔 변수를 재사용하지 않는다. 탭 두 개를 열어 A에서 판을 끝내고, 그다음 B에서 판을 끝낸 뒤 새로고침하면 **두 기록이 모두 남아 있다**
- [ ] 정렬 비교 함수가 `(a, b) => b.score - a.score` 한 줄이다. 동점 처리(날짜 비교 등)를 넣지 않았다
- [ ] 카테고리 표는 5개, 전 범위 표는 10개까지 쌓인다
- [ ] 결과 화면의 순위표가 **해당 모드 것 하나만** 나온다. 다섯 개를 모두 그리지 않았다
- [ ] 순위 번호가 동점이어도 1, 2, 3, …으로 줄 순서대로 매겨진다
- [ ] 이름이 `textContent`로 들어간다. 이름에 `<b>홍</b>`을 넣고 한 판을 끝내면 순위표에 **태그가 글자 그대로** 보인다(굵은 글씨가 되면 안 된다)
- [ ] `localStorage` 실패 경로. 개발자 도구 Application → Local Storage에서 `quizGameRankings` 값을 `{{{`처럼 깨뜨린 뒤 새로고침하면, 순위표가 빈 상태로 정상 표시되고 게임이 진행된다
- [ ] **쓰기만 막힌 경로.** 콘솔에서 `Storage.prototype.setItem`이 예외를 던지게 만든 뒤 **한 판도 하지 않고** "순위표 보기"를 연다. 저장 불가 안내가 보인다. 읽기가 되면 `readRankings()`는 성공하므로 **읽기 성공 여부만으로는 이 상태를 판정할 수 없다**
- [ ] **읽기까지 막힌 경로.** `Storage.prototype.getItem`도 던지게 만든 뒤 순위표를 연다. 표와 "기록 지우기"가 함께 감춰지고 안내만 남는다. `setItem`만 막아서는 이 분기가 한 번도 실행되지 않는다
- [ ] 한 순위표만 깨진 경우. 값을 `{"korean_history": "깨짐", "science": [{...정상 한 건...}]}`로 바꾸고 새로고침하면 **한국사만 비고 과학 기록은 남아 있다**

# 5단계 — 반응형 마무리와 에러 처리

`archive/PRD-v5.md` 6절 5단계. 새 기능을 넣지 않는다. 앞 단계에서 만든 것을 모바일 폭과 접근성, 에러 경로에서 점검하고 마무리한다.

**선행 조건**: 4단계 완료. 네 화면이 모두 동작하고 순위가 저장되어야 한다.

## 만들거나 고칠 파일

| 파일 | 이 단계에서 하는 일 |
|---|---|
| `style.css` | 반응형 보정, 대비 조정, 초점 표시, 최소 높이 |
| `script.js` | 에러 경로 보정만. 새 함수는 원칙적으로 없다 |
| `index.html` | 접근성 속성 보정만 |

## 점검 항목

### 5.1 반응형

- 모바일 세로(폭 375px)에서 가로 스크롤이 생기지 않는다.
- 선택지 버튼은 **최소 높이 44px**이고, 글이 길면 줄바꿈해 전부 보인다. **잘라 내지 않는다.**
- 순위표 네 열이 375px에서 겹치지 않는다.
- 카테고리 카드가 좁은 폭에서 세로로 쌓인다.

### 5.2 접근성 (PRD 4.3절)

- 조작 가능한 모든 요소에 키보드로 도달하고 실행할 수 있다.
- 초점 표시가 모든 버튼에서 보인다.
- 정답과 오답을 색만으로 구분하지 않는다(`✓`, `✗`).
- 정답 여부와 해설은 초점 이동으로 전달한다. **`aria-live`를 쓰지 않는다(R5).**
- 초점 이동 규칙 세 가지: 화면 전환 → 제목, 새 문제 → 문제 텍스트, 답 선택 → 피드백 영역. **퀴즈 화면 진입은 두 규칙이 겹치므로 제목을 건너뛰고 첫 문제 텍스트로 간다.**
- **글자와 배경 대비 4.5:1 이상.** 난이도 배지 세 가지와 정답 초록, 오답 빨강 모두. **주황 계열 배지가 흰 배경에서 대비가 잘 나오지 않으므로 특히 확인한다.**

### 5.3 에러 처리 네 가지 (PRD 4.2절)

| # | 상황 | 확인 방법 |
|---|---|---|
| 1 | `questions.js` 로드 실패 | `index.html`의 `<script src="questions.js">`를 `questions-x.js`로 잠시 바꾼다 |
| 2 | 문제 데이터 검사 실패 | `kh_01`의 `answer`를 `9`로 잠시 바꾼다 |
| 3 | `localStorage` 사용 불가 | 개발자 도구에서 사이트 데이터를 차단하거나, 콘솔에서 `Storage.prototype.setItem`을 예외를 던지도록 잠시 덮어쓴다 |
| 4 | 저장 데이터 손상 | 4단계 체크리스트의 마지막 두 항목과 같다 |

1번과 2번에서는 시작 화면에 `문제 데이터를 불러오지 못했습니다.`가 뜨고 **카드와 전 범위 버튼을 눌러도 게임이 시작되지 않아야** 한다. 시작 화면을 정상 표시했다가 버튼을 누른 뒤에야 막으면 사용자가 원인을 알기 어렵다. 콘솔에는 위반 문제의 `id`가 나온다.

3번에서는 게임이 끝까지 정상 진행되고, 결과 화면과 순위표 화면에 `이 브라우저에서는 순위 기록을 저장할 수 없습니다.`가 뜬다. 결과 화면은 진입 여부를 표시하지 않고 순위표 영역을 감춘다.

순위표 화면은 **막힌 곳이 어디냐에 따라 갈린다.** `setItem`만 덮어쓰면 읽기가 살아 있어 표와 "기록 지우기"가 그대로 보이고 안내만 바뀐다. `getItem`까지 덮어써야 표와 "기록 지우기"가 함께 감춰진다. **두 경우를 모두 확인한다.**

**확인이 끝나면 임시 변경을 전부 되돌린다.**

## 완료 기준

1. 개발자 도구 기기 툴바에서 폭 375px로 바꾸고 시작 → 퀴즈 → 결과 → 순위표를 한 바퀴 돈다. 가로 스크롤이 없고, 어느 화면에서도 글자가 잘리지 않는다.
2. 마우스를 쓰지 않고 Tab, Enter, Space만으로 한 판을 끝까지 끝낸다.
3. 5.3의 네 상황을 모두 재현하고 되돌린다.
4. 개발자 도구 Rendering의 색각 이상 에뮬레이션을 켜고 한 문제를 푼다. 정답과 오답을 구별할 수 있다.

## 체크리스트

- [ ] **(R5)** `grep -nE 'aria-live|role="status"|role="alert"' index.html script.js`가 아무것도 출력하지 않는다. 5단계에서 접근성을 손보다 뒤늦게 추가되기 쉬운 항목이다
- [ ] 폭 375px에서 가로 스크롤이 없다
- [ ] 선택지 버튼 높이가 44px 이상이고 긴 선택지가 줄바꿈된다. 개발자 도구에서 실제 높이를 잰다
- [ ] 난이도 배지 세 가지의 대비가 4.5:1 이상이다. 개발자 도구에서 색을 집어 대비값을 확인한다. **주황(`diff-hard`)을 반드시 확인한다**
- [ ] 정답 초록, 오답 빨강의 대비가 4.5:1 이상이다
- [ ] 퀴즈 화면 진입 시 초점이 제목을 거치지 않고 첫 문제 텍스트로 간다. 3단계 체크리스트의 `focusin` 절차로 확인한다
- [ ] 데이터 검사 실패 시 카드를 눌러도 게임이 시작되지 않는다
- [ ] `localStorage` 불가 상태에서 게임이 끝까지 진행되고, 결과 화면에 `순위표에 들지 못했습니다.`가 **뜨지 않는다**
- [ ] `setItem`만 막은 순위표 화면 — 저장 불가 안내가 뜨고, 하단 고정 안내는 감춰지며, 표와 "기록 지우기"는 **그대로 보인다**
- [ ] `getItem`까지 막은 순위표 화면 — 표와 "기록 지우기"가 **함께 감춰진다**
- [ ] 5.3에서 손댄 파일과 값이 전부 원상 복구되었다. `git status`와 `git diff`로 확인한다

# 6단계 — 배포와 배포 후 확인

`archive/PRD-v5.md` 6절 6단계. **로컬 확인을 완료 기준으로 삼지 않는다.** 파일명 대소문자와 상대 경로 문제는 로컬에서 재현되지 않고 배포해야만 드러난다(R6).

**선행 조건**: 5단계 완료. 로컬에서 다섯 단계의 체크리스트가 모두 통과해야 한다.

## 만들거나 고칠 파일

새 파일을 만들지 않는다. 배포 과정에서 문제가 드러나면 해당 파일을 고친다.

## 절차

1. 파일 네 개(`index.html`, `style.css`, `questions.js`, `script.js`)를 커밋하고 GitHub 저장소에 올린다. 빌드 과정은 없다.
2. 저장소 Settings → Pages에서 브랜치를 지정해 배포한다.
3. 배포 URL(`https://<사용자>.github.io/<저장소>/`)이 뜰 때까지 기다린 뒤 접속한다.
4. 아래 확인을 **배포 URL에서** 수행한다. 로컬 파일로 다시 확인하지 않는다.

## 완료 기준

**Chrome (배포 URL)**

1. 페이지가 스타일이 적용된 상태로 뜬다. 개발자 도구 Network 탭에 **404가 하나도 없다.**
   - 경로를 고쳐 다시 올렸는데도 404가 이어지면 GitHub Pages의 CDN 캐시를 의심한다. 강제 새로고침(Shift+새로고침)으로 확인하고, 그래도 같으면 몇 분 기다린 뒤 다시 본다. 코드를 더 고치기 전에 이것부터 배제한다.
2. 콘솔에 에러가 없다.
3. 시작 → 카테고리 도전 10문제 → 결과 → 순위표 → 시작으로 한 바퀴를 돈다.
4. 전 범위 도전으로도 한 바퀴를 돈다.
5. 순위가 저장되고, 새로고침 후 순위표에 그대로 있다.

**Safari (배포 URL)**

6. 네 화면이 모두 정상으로 보인다.
7. 한 판을 끝내고 순위가 저장되며, 새로고침 후에도 남아 있다. (`file://`이 아닌 `https://`이므로 `localStorage`가 동작한다.)
8. 진행 중 새로고침해도 확인창이 뜨지 않는다. **이는 알려진 제약이며 고치지 않는다**(PRD 4.1절의 `beforeunload` 항목).

**모바일**

9. 휴대폰 브라우저로 배포 URL에 접속해 한 판을 끝낸다. 선택지 버튼을 누를 수 있고 해설 뒤의 "다음 문제" 버튼이 화면 안에 들어온다.

## 체크리스트

- [ ] **(R6) 상대 경로.** 배포 URL에서 개발자 도구 Network 탭을 열고 새로고침한다. `style.css`, `questions.js`, `script.js`의 요청 URL이 모두 `https://<사용자>.github.io/<저장소>/` **아래**를 가리키고 상태가 200이다. 도메인 최상위(`https://<사용자>.github.io/style.css`)를 가리키며 404가 나면 절대 경로를 쓴 것이다
- [ ] **파일명 대소문자.** GitHub 저장소의 파일 목록과 `index.html`의 참조 문자열을 글자 단위로 대조한다. macOS는 대소문자를 구분하지 않아 로컬에서는 통과하지만 GitHub Pages는 구분한다
- [ ] 배포 URL에서 순위가 저장된다. 콘솔에서 `JSON.parse(localStorage.getItem('quizGameRankings'))`로 확인한다
- [ ] 저장 키가 `quizGameRankings` 그대로다. 같은 계정의 다른 프로젝트 페이지와 오리진을 공유하므로 이름을 바꾸지 않는다(PRD 3.4절)
- [ ] Safari에서 순위 저장이 동작한다(배포 URL 기준)
- [ ] Safari에서 이탈 경고가 뜨지 않는 것을 **확인만 하고 고치지 않는다.** 우회 방법을 찾지 않는다(PRD 4.1절)
- [ ] 모바일 실기기에서 한 판을 끝냈다

## 부록 — 이 계획이 다루지 않는 것

PRD 7절의 제외 항목과 4.1절의 알려진 제약은 구현하지 않고 우회도 시도하지 않는다. 구현 중 다음이 눈에 띄어도 손대지 않는다.

- 타이머, 난이도별 배점, 오답 노트, 이름 자동 입력, 이어 하기, 뒤로 가기 처리, 사운드, 애니메이션, 서버 연동
- Safari의 `beforeunload` 미지원, Safari의 7일 데이터 삭제, `file://`에서의 `localStorage` 차단, 기록이 브라우저에만 남는 점

문제은행 확대는 2차 구현이다(PRD 8절). 1차에서는 카테고리마다 10문제만 쓴다.
