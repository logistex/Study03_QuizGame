# 상식 퀴즈 게임 2차 구현 계획

`spec/PRD.md`를 2차 구현 순서로 옮긴 문서다. 1차 계획서 `spec/IMPL-PLAN.md`를 대신하지 않고 그 옆에 선다. 1차 계획서는 그대로 두며 이 문서가 그것을 가리킬 때는 절 번호가 아니라 항목 이름으로 가리킨다.

## 이 계획의 전제

- **개발 단계의 구분과 이름은 PRD 6장이 정했다.** 이 문서는 각 단계의 작업 목록, 완료 기준, 검증 절차를 채운다. 단계를 합치거나 나누거나 순서를 바꾸지 않는다.
- **선행 결정의 근거는 [`history/impl_v2/65-plan2-design-decisions.md`](../history/impl_v2/65-plan2-design-decisions.md)에 있다.** 65번과 PRD가 어긋나면 PRD가 맞다.
- 빌드 도구, 프레임워크, 테스트 프레임워크를 쓰지 않는다(PRD 1.3절, 4장).
- **로컬 확인을 완료 기준으로 삼지 않는다**(PRD 6장). 단계마다 배포 후 스모크를 밟는다.
- 각 단계에서 만든 화면의 스타일은 그 단계에서 함께 쓴다(PRD 6장 머리말).

### 절 번호를 소수점으로 매기지 않는다

PRD 3.6절과 8.1절, 그리고 커스텀 명령어 넷이 **"계획서 1.8절"**로 1차 계획서를 가리키고 있다. 이 문서에 `1.8절`이 생기면 그 참조가 어느 계획서를 가리키는지 갈리지 않는다.

- 공통 절은 이름으로 부른다.
- 계획서가 정한 것은 **결정 1**부터 **결정 10**까지 번호를 붙인다.
- 개발 단계는 **1단계**부터 **5단계**까지다.

**문항 판정의 정본은 여전히 1차 계획서다.** PRD 3.6절 확인 수단 표와 8.1절이 가리키는 "계획서 1.8절"은 `spec/IMPL-PLAN.md`의 "육안 검토 절차 (1.8)"이며, 이 문서가 그것을 옮겨 오지 않는다. 앱 안에서 도는 판정은 그것을 한 칸 무른 것이고 PRD 3.9절이 그 사실을 적어 두었다(결정 9).

### 검증 수단

1차의 셋(데이터 검사 함수, 클로드의 판정, 수동 체크리스트)에 하나가 붙는다.

| 수단 | 어디서 |
|---|---|
| 데이터 검사 | **서버 함수 안**으로 옮겨 간다. 문항을 넣는 시점에 돈다(PRD 1.5절, 결정 7) |
| 클로드의 판정 | 문제은행을 크게 늘릴 때는 세션 둘, 앱 안에서는 한 번(결정 9) |
| 수동 체크리스트 | 단계마다 있다 |
| **거절 확인** | 단계마다 새로 생기는 권한 경계가 실제로 막는지 본다. 2차에서 붙는 것이다 |

거절 확인이 붙는 까닭은 권한 경계가 단계마다 새로 생기고, **막히는지는 화면이 정상으로 보이는 것과 무관하기 때문이다.**

# 계획서가 정한 것

PRD가 이 문서를 가리킨 문장 열셋과 65번 9절이 넘긴 항목 아홉을 여기서 닫는다. 대조표는 부록에 있다.

## 결정 1 — 브라우저는 `fetch`로 DB를 조회한다. 라이브러리를 쓰지 않는다

**PRD가 가리킨 자리** — 1.3절 외부 라이브러리 행, 4장 외부 의존성 행.

| 무엇 | 어떻게 |
|---|---|
| 자기 응시 기록 조회, 사용자 목록 조회 | 브라우저가 DB의 REST 경로를 `fetch`로 부른다. 공개 키를 헤더에 담고, 무엇이 보이는지는 행 수준 보안이 정한다(PRD 3.8절) |
| 문항, 채점, **순위표 조회**, 문항 관리, 역할 바꾸기 | 서버 함수를 `fetch`로 부른다(결정 2) |

**순위표 조회가 아래 줄에 있다.** 순위표는 남의 이름과 점수를 함께 보이므로 행 수준 보안으로 낼 수 없다. PRD 3.4절과 3.8절이 그 까닭을 적어 두었다.

**까닭 셋.**

- PRD 4장이 **CDN을 쓰지 않기로** 했다. 라이브러리를 브라우저에 넣으려면 CDN이거나 저장소에 파일을 넣어야 한다.
- PRD 4장이 **빌드 과정 없이** 정적 파일을 그대로 올리기로 했다. 번들러가 없으므로 라이브러리를 묶어 넣을 자리가 없다.
- PRD 1.4절이 파일 구성을 넷으로 정했다. 라이브러리 파일을 저장소에 넣으면 그 구성이 깨지고, 학생이 읽어야 할 코드가 아닌 것이 저장소에서 가장 큰 파일이 된다.

**인증 클라이언트도 라이브러리를 쓰지 않는다.** 인증 서비스의 깃허브 인증 경로로 보내고, 돌아온 주소에서 토큰을 직접 꺼내 쓴다. 위의 까닭 셋이 그대로 적용되고, **로그인 흐름이 코드에 그대로 보여 수업에 쓰기 좋다.**

**대가는 토큰 만료를 직접 다뤄야 한다는 것이다.** 그 대가를 2단계의 만료 안내가 받는다(PRD 3.7절 "로그인의 수명").

## 결정 2 — 서버 함수는 네 파일이다

**PRD가 가리킨 자리** — 1.4절 "파일을 몇 개로 나눌지와 그 이름".

| 파일 | 책임 | 만드는 단계 |
|---|---|---|
| `api/questions.js` | 판을 시작할 때 문항을 정답 열 없이 전달한다 | 3단계 |
| `api/submit.js` | 채점하고 응시 기록을 저장하며 순위표를 돌려준다 | 4단계 |
| `api/authoring.js` | 문항을 생성하고 판정하고, 채택, 수정, 삭제를 수행한다 | 5단계 |
| `api/users.js` | 역할을 더하고 바꾸고 지운다 | 5단계 |

**책임 단위로 가른다.** PRD 1.4절이 책임 넷을 적었고 파일도 넷이다. 이렇게 가르면 **파일 경계가 단계 경계와 맞아** 한 단계가 한 파일을 만든다. 5단계만 둘을 만드는데, 문항 관리와 설정이 서로 다른 화면이고 서로 다른 것을 거절하기 때문이다.

**순위표 조회를 `api/submit.js`에 둔다.** 다섯째 파일을 만들지 않는다. 순위표는 응시 기록에서 뽑은 것이고(결정 3) 그 테이블을 다루는 함수가 이것이다. 쓰기 상태를 같은 응답에 실을 수 있는 것도 여기라서다(결정 4).

파일명은 모두 소문자로 쓴다(PRD 4장 파일명 행).

## 결정 3 — 순위는 응시 기록에서 뽑는다. 순위표 테이블을 두지 않는다

**PRD가 가리킨 자리** — 3.4절 "저장 구조와 함수 계약은 1차의 것이다".

1차 계약은 **읽기 → 삽입 → 정렬 → 자르기 → 쓰기**였고 보관 수를 넘으면 낮은 기록을 지웠다. 2차에서 이 계약을 그대로 옮기면 지워진 기록이 성적 관리 화면과 대시보드에서도 사라진다.

**그래서 이렇게 정한다.**

- **응시 기록은 지우지 않는다.** 모든 판이 남는다.
- **순위표는 조회 시점에 응시 기록을 점수 내림차순, 마친 때 내림차순으로 정렬해 상위 N을 뽑은 것이다.** 카테고리별은 5, 전 범위는 10(PRD 3.4절).
- **자르기가 사라지므로 "잘려 나갔으면 `null`"의 뜻이 바뀐다.** 상위 N 안에 들지 못했으면 `null`이다. 화면 표시는 PRD 3.3절의 표 그대로다.
- **뽑는 것은 브라우저가 아니라 서버 함수다.** 응시 기록에 전체 조회를 열면 "학생은 자기 기록만 조회한다"가 깨진다(PRD 3.8절).

**까닭** — PRD 3.10절이 응시 기록 테이블 하나를 두었고, 65번 7절의 대시보드가 점수 추세와 많이 틀린 문항을 그 기록에서 낸다. 낮은 기록을 지우면 추세가 위쪽만 남아 사실과 달라진다.

**인덱스는 삽입한 행의 식별자로 찾는다.** 이름과 점수로 되찾지 않는다는 PRD 3.4절의 근거가 서버에서도 그대로다.

### 저장 함수와 조회 함수의 계약

| 함수 | 어디서 도나 | 입력 | 반환 |
|---|---|---|---|
| `submitAnswer` | 브라우저 → `api/submit.js` | 응시 기록 식별자, 문항 `id`, 선택지 번호 | 정오, 정답 텍스트, 해설 |
| `finishQuiz` | 브라우저 → `api/submit.js` | 응시 기록 식별자 | 점수, 총 문제 수, 순위 결과 |
| `loadRankings` | 브라우저 → `api/submit.js` | 없음 | 순위표 다섯과 **쓰기 가능 여부**, 또는 실패 |

`finishQuiz`가 돌려주는 순위 결과는 PRD 3.3절과 3.4절이 정한 셋을 그대로 쓴다.

| 반환 | 조건 |
|---|---|
| 정수 | 상위 N 안에 이번 기록이 있으면 그 인덱스 |
| `null` | 들지 못했으면 |
| `'unavailable'` | 요청이 실패했으면 |

**`loadRankings`가 순위표만 돌려주지 않는다.** 쓰기 가능 여부를 같은 응답에 싣는다(결정 4). 호출을 하나 더 늘리지 않기 위해서다.

**읽기를 쓰기 직전에 한다는 1차 규칙은 필요 없어진다.** 순위가 조회 시점에 정렬로 나오므로 두 탭이 서로를 덮어쓸 자리가 없다. 대신 **점수는 언제나 서버가 센다**(PRD 3.8절).

## 결정 4 — 저장 실패의 세 상태와 문구

**PRD가 가리킨 자리** — 3.5절 하단 안내 문구, 4.2절 3번 상태 구분과 문구.

PRD 3.5절이 세 상태를 정해 두었다. **순위표 조회 응답 하나로 셋을 가른다.**

| 상태 | 무엇으로 판정하나 |
|---|---|
| 정상 | 순위표 조회가 성공하고 응답의 쓰기 가능 여부가 참 |
| 읽기는 됨, 쓰기만 막힘 | 순위표 조회는 성공, 응답의 쓰기 가능 여부가 거짓 |
| 읽기까지 막힘 | 순위표 조회가 실패 |

**`api/submit.js`가 순위표를 뽑으면서 쓰기 권한을 함께 확인해 같은 응답에 싣는다.** 별도 호출을 두지 않는다. 순위표 조회가 서버 함수로 옮겨 왔으므로(결정 3) 읽기와 쓰기를 한 함수가 함께 볼 수 있다.

**호출을 늘리지 않으면서 세 상태가 서는지를 적어 둔다.** 견줄 상대는 "직전 저장 시도의 결과로 판정한다"이다.

| 무엇 | 한 판도 안 친 사용자 | 호출 |
|---|---|---|
| 저장 시도 결과로 판정 | **판정할 수 없다.** 정상으로 보이거나 아무 표시도 못 낸다 | 늘지 않는다 |
| 순위표 응답에 싣기 | 판정된다 | **늘지 않는다.** 순위표 조회는 어차피 한다 |

**PRD 3.5절이 그 사용자를 명시해 두었다** — "한 판도 하지 않은 사용자는 저장 함수를 지나지 않으므로 저장 불가가 전달될 다른 통로가 없다." 저장 시도 결과로만 판정하면 PRD 3.5절 표의 가운데 상태(읽기는 됨, 쓰기만 막힘)를 그 사용자에게 낼 수 없다. **가장 흔한 것이 가운데라는 것이 1차 4단계에서 나온 것이고**(PRD 부록 6번), 그것을 못 내면 하단 안내가 저장이 된다는 전제로 남는다.

**쓰기 가능 여부를 무엇으로 판정하는가.** 서버 함수가 응시 기록 테이블에 쓸 수 있는지를 실제로 확인한다. 순위표를 뽑는 조회가 성공한 것만으로는 쓰기가 된다는 뜻이 아니다. 확인은 기록을 남기지 않는다.

### 화면 문구

완결된 문장은 마침표로 끝낸다.

| 상황 | 문구 |
|---|---|
| 순위표 하단 고정 안내 | `기록은 서버에 저장되며, 수강생 모두가 같은 순위표를 봅니다.` |
| 쓰기가 막힘 (PRD 4.2절 안내) | `순위를 저장하지 못했습니다. 게임 진행에는 영향이 없습니다.` |
| 읽기까지 막힘 | `순위표를 불러오지 못했습니다.` |
| 로그인 안내 | `게임을 시작하려면 로그인해 주세요.` |
| 로그인 실패 | `로그인하지 못했습니다. 다시 시도해 주세요.` |
| 로그인 만료 | `로그인이 만료되었습니다. 다시 로그인해 주세요.` |
| 만료가 가까움 (배너) | `로그인이 곧 만료됩니다. 다시 로그인해 주세요.` |
| 판 시작 전 안내 | `남은 로그인 시간이 한 판을 마치기에 모자랍니다. 먼저 다시 로그인해 주세요.` |
| 채점 요청 실패 | `채점 결과를 받지 못했습니다. 다시 시도해 주세요.` |
| 채점 재시도 실패 | `채점 결과를 받지 못해 이 판을 끝냅니다.` |
| 연습 응시 결과 | `연습 응시라 기록이 남지 않습니다.` |
| 카테고리 상한 | `이 카테고리는 30문항이 차서 더 넣을 수 없습니다.` |
| 문항 삭제 거절 | `이 카테고리의 문항이 10개 아래로 내려가 지울 수 없습니다.` |
| 마지막 선생님 | `마지막 선생님은 내리거나 지울 수 없습니다.` |
| 응시 기록이 있는 문항 고치기 | `이 문항에는 이미 응시 기록이 있습니다. 고치면 과거 기록의 정오 뜻이 달라집니다.` |
| 선생님 권한 없음 | `선생님만 할 수 있습니다.` |

1차에서 그대로 가져오는 문구는 `문제 데이터를 불러오지 못했습니다.`(PRD 4.2절 1번), `아직 기록이 없습니다.`, `순위표 {N}위 진입`, `순위표에 들지 못했습니다.`, `정답입니다.`, `오답입니다. 정답은 {정답 텍스트}입니다.` 여섯이다. 여기 다시 적지 않는다.

**`이름을 입력해 주세요.`와 `이름은 12자까지 입력할 수 있습니다.`는 사라진다.** 이름을 입력받지 않는다(PRD 3.1절).

## 결정 5 — 생성 요청은 테이블로 둔다

**PRD가 가리킨 자리** — 3.9절 "생성 요청과 결과를 어떻게 기록할지", 3.10절 "한 생성 요청이 만든 문항들을 묶어 내려면".

문항에 요청 식별자 열만 더하는 안을 쓰지 않는다. **채택한 것만 DB에 들어가므로**(PRD 3.9절 7번) 문항 쪽에만 자리를 두면 걸러진 문항과 반려된 문항이 이력에 남지 않는다. 65번 5절이 문항 관리 화면에 "생성 요청 단위로 되돌아보기"를 둔 것을 그러면 만들 수 없다.

| 테이블 | 담는 것 |
|---|---|
| 생성 요청 | 요청한 사람, 요청 때, 요청 문자열, 생성된 문항 전문, 검사에서 걸린 항목, 판정 결과, 채택 여부 |
| 문항 | PRD 3.10절의 열에 **요청 식별자**를 더한다 |

### "채택 전 문항이 DB에 안 들어간다"의 경계

**들어가지 않는 곳은 문항 테이블이다.** 생성된 문항은 채택 전에도 생성 요청 테이블에 담긴다. 담기지 않으면 이력이 성립하지 않고, 화면을 새로 고치면 판정 결과가 사라진다.

| 테이블 | 채택 전 | 채택 후 |
|---|---|---|
| 생성 요청 | **들어간다.** 생성된 문항 전문과 검사, 판정 결과를 담는다 | 채택 여부가 채워진다 |
| 문항 | **들어가지 않는다** | 들어간다 |

**판이 문항을 뽑는 곳은 문항 테이블뿐이다.** 그래서 이 경계가 PRD 3.9절 7번("채택한 것만 DB에 넣는다")이 막으려던 것을 그대로 막는다. 5단계 거절 확인과 체크리스트는 **문항 테이블의 행 수를 센다.**

**고치기도 요청 행을 만든다.** 고친 문항이 생성된 문항과 같은 관문을 지나므로(PRD 3.9절 "고치기와 지우기") 그 관문의 기록도 같은 자리에 남는다.

## 결정 6 — DB를 둘 둔다. 프리뷰는 개발용, 프로덕션은 수업용

**PRD가 가리킨 자리** — 4.1절 6번 "개발용과 수업용 저장을 어떻게 나눌지".

65번 8절이 배포를 이미 둘로 갈라 두었다. 개발 단계 작업은 브랜치에서 하고 프리뷰가 생기며, `main` 병합이 프로덕션을 만든다. **저장을 그 갈림에 얹는다.**

| 배포 | 어느 DB | 어떻게 |
|---|---|---|
| 프리뷰 (브랜치) | 개발용 | 배포 환경 변수의 Preview 값 |
| 프로덕션 (`main`) | 수업용 | 배포 환경 변수의 Production 값 |

- 키를 배포 환경 변수에 두는 것은 PRD 4.4절이 이미 정했다. **환경별로 값을 나누는 것뿐이라 코드가 갈리지 않는다.**
- 브라우저가 쓰는 공개 키도 환경별로 갈려야 한다. 소스에 적어 두면 프리뷰가 수업용 DB를 본다. **공개 키도 배포 환경 변수에서 읽어 서버 함수가 브라우저에 내려 준다.** PRD 4.4절이 "소스 코드에 그대로 적어도 된다"고 한 것은 노출이 문제가 아니라는 뜻이고, 적어야 한다는 뜻이 아니다.

### 공개 키는 `api/questions.js`가 내려 준다

넷 가운데 이것이다. **로그인을 시작하려면 프로젝트 주소와 공개 키가 먼저 있어야 하므로, 로그인한 요청만 받는 함수에 둘 수 없다.**

| 함수 | 왜 아닌가 |
|---|---|
| `api/submit.js` | 응시자의 요청만 받는다 |
| `api/authoring.js` | 선생님의 요청만 받는다 |
| `api/users.js` | 선생님의 요청만 받는다 |
| **`api/questions.js`** | **설정 요청 하나만 로그인을 요구하지 않게 둔다** |

- 문항을 내는 요청은 그대로 로그인을 요구한다. **설정 요청만 예외다.**
- **공개 키는 그 자체로 아무 권한도 주지 않는다**(PRD 4.4절). 로그인 전에 내려도 열리는 것이 없다.
- 함께 내려 주는 것은 프로젝트 주소와 깃허브 인증 경로다. 브라우저가 로그인을 시작하는 데 필요한 값이 그 둘이다.

### 둘이 한도의 전부다

**무료 요금제는 조직당 활성 프로젝트 둘까지다.** 결정 6이 그 둘을 다 쓴다. 여유가 없다는 것을 계획서에 적어 둔다.

- **셋째 프로젝트를 만들 수 없다.** 실습 도중 새 DB가 필요해지면 둘 중 하나를 지우거나 멈춰야 한다.
- **PRD 4.1절 3번의 일시정지가 둘 모두에 걸린다.** 1주일 쓰지 않으면 멈춘다.
- **개발용도 관리 대상이다.** 수업용만 깨우면 다음 개발 단계를 시작할 때 프리뷰가 멈춘 DB를 본다. 화면에는 데이터가 없는 것처럼 보이므로 원인을 찾기 어렵다.
- 수업 전에 **둘 다** 깨우는 절차를 둔다.

## 결정 7 — 데이터 검사 항목을 네 자리로 가른다

**PRD가 가리킨 자리** — 4.2절 머리말 "각 항목을 어느 시점에 둘지".

PRD 4.2절 2번의 검사 열셋을 시점으로 가른다.

| 시점 | 어디서 | 항목 |
|---|---|---|
| 문항을 넣거나 고치는 시점 | `api/authoring.js` | `options.length === 4`, 선택지가 비어 있지 않은 문자열, 한 문제 안에 같은 선택지 없음, `answer`가 0~3 정수, `difficulty`가 세 값 중 하나, `question`과 `explanation`이 비어 있지 않음, `id`가 비어 있지 않음, `question` 60자 이내, 각 선택지 20자 이내 |
| 넣는 시점 + DB 유일 제약 | `api/authoring.js`, DB | `id` 중복, `question` 텍스트 중복 |
| 문항을 지우는 시점 | `api/authoring.js` | 지운 뒤 그 카테고리 문항 수가 `QUIZ_LENGTH` 아래로 내려가면 거절한다 |
| 판을 시작하는 시점 | `api/questions.js` | 카테고리 목록의 모든 `id`에 문항이 있는가, 카테고리마다 `QUIZ_LENGTH` 이상인가 |

**셋째와 넷째를 넣는 시점에 둘 수 없다.** PRD 4.2절 머리말이 짚은 그대로다. 카테고리 대응과 카테고리별 문제 수는 문항을 넣을 때가 아니라 **지우거나 카테고리를 늘릴 때** 어긋난다.

- 넷째가 어긋나면 PRD 4.2절 1번의 `문제 데이터를 불러오지 못했습니다.`를 시작 화면에 내고 게임 시작을 막는다.
- **넣는 사람에게 문제 `id`와 위반 항목을 알린다**(PRD 4.2절). 화면의 생성 결과 자리에 그대로 적는다.
- `id` 중복과 `question` 중복은 넣는 시점에도 보지만 **최종 방벽은 DB의 유일 제약이다.** 검사와 삽입 사이에 다른 요청이 끼어들면 검사만으로는 못 막는다.

## 결정 8 — 고친 문항은 판본을 남기지 않는다. 대신 알린다

**PRD가 가리킨 자리** — 3.9절 "이미 응시 기록이 쌓인 문항을 고치면".

- **문항 행을 그대로 고친다.** 옛 판본을 새 행으로 남기지 않는다.
- **과거 응시 기록의 점수는 바뀌지 않는다.** PRD 3.9절이 이미 그렇게 적었다.
- **대시보드의 "많이 틀린 문항"은 현재 판본을 기준으로 센다.** 고친 뒤의 문항 텍스트로 보이며, 그 수치가 고치기 전 응시를 포함한다.
- **고치기 전에 알린다.** 그 문항에 응시 기록이 있으면 결정 4의 문구를 보이고 확인을 받는다.

**판본을 남기지 않는 까닭 둘.** PRD 3.10절의 문항 테이블에 판본 열이 없고, 판본을 두면 문항 조회가 언제나 "가장 최근 판본"을 골라야 해서 3단계의 문항 전달이 무거워진다. 수업용 앱에서 얻는 것보다 드는 것이 크다.

## 결정 9 — 앱 안의 판정은 한 번이다. 두 번째 라운드는 선생님이 맡는다

**PRD 3.9절이 이미 정했다.** 여기서는 그것이 규격을 한 칸 무른 것이라는 사실을 계획서에 적어 둔다(65번 6절이 그렇게 하도록 지정했다).

| 규칙의 핵심 | 앱에서 |
|---|---|
| 쓴 쪽이 판정하지 않는다 | **지킨다.** 생성 호출과 판정 호출을 나누고 판정에 생성 맥락을 주지 않는다 |
| 재현되지 않으니 두 번 돈다 | **형식만 남는다.** 같은 모델을 같은 프롬프트로 두 번 부르는 것은 서로 다른 세션이 아니다 |

- 앱 안에서는 판정을 한 번 돌린다.
- 두 번째 라운드는 사람이 맡는다. 선생님이 판정 결과를 보고 채택하는 자리가 그것이다(PRD 3.9절 6번).
- **문제은행을 크게 늘릴 때는 세션 둘이 도는 경로를 그대로 쓴다.** 그 경로의 정본은 1차 계획서의 "육안 검토 절차 (1.8)"이고 커스텀 명령어 넷이 그것을 부른다.

## 결정 10 — 응시 기록 행이 판의 진행도 담는다. 세션 테이블을 두지 않는다

**PRD 3.10절이 응시 기록에 열 셋을 담았다** — 섞인 순서, 문항별 응답, 마감 여부. 그 열을 어떻게 쓰는지를 여기서 정한다.

**왜 서버가 순서를 알아야 하는가.** PRD 2.1절이 판마다 선택지를 섞고, PRD 3.8절이 정답을 브라우저에 내려보내지 않으며, PRD 1.4절이 브라우저는 고른 번호만 보내기로 했다. 정답이 없으니 브라우저가 섞을 수 없고, 서버가 섞으면 그 "3번"이 무엇인지 서버만 안다. 요청 사이에 서버는 기억하지 않으므로 저장하거나, 서명해 돌려받거나, 다시 계산해야 한다. **저장을 고르되 테이블을 새로 만들지 않는다.**

- 판을 시작하면 `api/questions.js`가 **응시 기록 행을 미리 만든다.** 응시자, 카테고리, 총 문제 수, 섞인 순서, 연습 여부를 담고 마감 여부를 거짓으로 둔다.
- **섞인 순서에 문항 열 개의 `id`와 그 문항의 선택지 순서가 함께 들어간다.** 브라우저가 보낸 번호를 되돌리는 데 둘 다 필요하다.
- 문항은 그 섞인 순서로 브라우저에 간다. **정답 열은 가지 않는다**(PRD 3.8절).
- **선택지 섞기가 브라우저에서 서버로 옮겨 간다.** 1차의 위험 R2(섞은 뒤 `answer`를 갱신하지 않음)가 사라지는 대신, 서버가 저장한 순서와 채점이 어긋날 자리가 새로 생긴다.
- 답을 고를 때마다 `api/submit.js`가 그 행의 문항별 응답에 적고 정오와 해설을 돌려준다. **즉시 피드백**(PRD 3.2절)이 서버 채점과 함께 서려면 문항마다 한 번씩 지나야 한다.
- 판이 끝나면 `api/submit.js`가 쌓인 응답으로 **점수를 다시 세어** 같은 행을 마감한다. 브라우저가 보낸 점수를 쓰지 않는다(PRD 3.8절).
- **연습 판과 "그만두기"로 끝난 판은 그 행을 지운다.** PRD 3.4절이 연습 판을 저장하지 않기로 했다.
- 문항별 응답이 그 행에 남으므로 65번 7절의 **"많이 틀린 문항"이 여기서 나온다.**

**테이블을 새로 만들지 않는 까닭.** 진행 중인 판과 끝난 판이 같은 행이면 마칠 때 옮겨 담을 일이 없고, PRD 3.10절이 정한 테이블 셋이 그대로 선다.

**순위표와 성적 관리는 마감된 행만 본다.** 마감 여부를 보지 않으면 진행 중인 판이 0점으로 순위표에 뜬다.

# 함수 계약

**서버 함수 넷의 책임, 입력, 출력, 거절을 적는다.** 브라우저 쪽 함수는 1차 계획서의 것을 잇되 채점과 저장이 서버로 옮겨 간 만큼만 바뀐다.

## 공통

- **모든 함수가 요청한 사람이 누구인지 먼저 확인한다.** 비밀 키는 행 수준 보안을 지나가므로 서버 함수가 직접 확인하지 않으면 아무나 남의 이름으로 요청할 수 있다(PRD 4.4절).
- **역할은 사용자 테이블에서 읽는다.** 브라우저가 보낸 역할을 믿지 않는다(PRD 3.7절).
- 거절은 무엇이 거절되었는지를 함께 돌려준다.

## `api/questions.js`

| 무엇 | 내용 |
|---|---|
| 책임 | 판을 시작할 때 문항을 정답 열 없이 전달하고 **응시 기록 행을 만든다.** 설정값을 내려 준다 |
| 입력 (`start`) | 모드(`category` 또는 `all`), 카테고리 `id`(카테고리 모드일 때), 연습 여부 |
| 출력 (`start`) | 응시 기록 식별자, 문항 열 개(각각 `id`, 카테고리, 문제, 섞인 선택지 넷, 난이도) |
| 입력 (`config`) | 없음 |
| 출력 (`config`) | 공개 키, 프로젝트 주소, 깃허브 인증 경로(결정 6) |
| 검사 | 카테고리 대응과 카테고리별 문항 수(결정 7). 어긋나면 문항을 내지 않는다 |
| 거절 | 로그인하지 않은 `start` 요청. **`config`는 로그인을 요구하지 않는다** |

**출력에 `answer`와 `explanation`이 없다.** 해설은 답을 고른 뒤 `api/submit.js`가 그 문항 것만 돌려준다. 해설에 정답이 적혀 있으므로 미리 내려보내면 정답을 뺀 뜻이 없다.

전 범위 도전의 카테고리 배분 3+3+2+2와 뽑은 뒤 다시 섞기는 PRD 2.1절 그대로이며 서버에서 돈다.

## `api/submit.js`

| 무엇 | 내용 |
|---|---|
| 책임 | 문항 하나를 채점하고, 판이 끝나면 응시 기록 행을 마감한다. 순위표를 돌려준다 |
| 입력 (`answer`) | 응시 기록 식별자, 문항 `id`, 고른 선택지 번호 |
| 출력 (`answer`) | 정오, 정답 선택지 텍스트, 해설 |
| 입력 (`finish`) | 응시 기록 식별자 |
| 출력 (`finish`) | 점수, 총 문제 수, 순위 결과(정수 / `null` / `'unavailable'`) |
| 입력 (`rankings`) | 없음 |
| 출력 (`rankings`) | 순위표 다섯과 쓰기 가능 여부(결정 4) |
| 입력 (`abort`) | 응시 기록 식별자 |
| 출력 (`abort`) | 없음. 그 행을 지운다 |
| 거절 | 남의 행에 대한 요청, 이미 마감된 행, 같은 문항에 두 번째 응답 |

- **점수는 그 행에 쌓인 응답에서 다시 센다.** 브라우저가 보낸 점수를 받지 않는다.
- **연습 판은 마감할 때 행을 지우고 순위 결과로 `null`을 돌려준다.** 결과 화면은 결정 4의 연습 문구를 낸다.
- `abort`는 "그만두기"와 이탈, 그리고 **채점 재시도가 실패했을 때**(PRD 4.2절 5번) 쓴다.
- **`rankings`는 마감된 행만 센다.** 진행 중인 행이 0점으로 순위표에 뜨지 않게 한다.
- **`rankings`가 쓰기 권한을 함께 확인한다.** 별도 호출을 두지 않는다(결정 4).

## `api/authoring.js`

| 무엇 | 내용 |
|---|---|
| 책임 | 문항을 생성하고 판정하고, 채택, 수정, 삭제를 수행한다 |
| 입력 (`generate`) | 요청 문자열 또는 하루치 고정값 |
| 출력 (`generate`) | 요청 식별자, 생성된 문항, 검사 결과, 판정 결과 |
| 입력 (`adopt`) | 요청 식별자, 채택할 문항 |
| 출력 (`adopt`) | 넣은 수, 넣지 못한 것과 까닭 |
| 입력 (`update`) | 문항 `id`, 고친 값 |
| 출력 (`update`) | 검사 결과, 판정 결과, 응시 기록 유무 |
| 입력 (`delete`) | 문항 `id` |
| 출력 (`delete`) | 지웠는지, 거절이면 까닭 |
| 거절 | 선생님이 아닌 요청, 카테고리 상한 30 초과, 삭제 후 `QUIZ_LENGTH` 미만, 검사에 걸린 문항의 삽입 |

- **생성 호출과 판정 호출을 나눈다.** 판정에 생성 맥락을 주지 않는다(결정 9).
- **채택하지 않은 문항은 DB의 문항 테이블에 들어가지 않는다.** 요청 테이블에만 남는다(결정 5).
- **고친 문항은 생성된 문항과 같은 관문을 지난다** — 검사, 판정, 선생님 채택(PRD 3.9절).
- **자연어를 그대로 받으므로 역할 검사가 실질적인 방벽이다.** 임의 문자열이 생성 요청으로 들어간다(65번 5절).

## `api/users.js`

| 무엇 | 내용 |
|---|---|
| 책임 | 사용자를 더하고 역할을 바꾸고 지운다 |
| 입력 (`add`) | 깃허브 아이디, 이름, 역할 |
| 입력 (`role`) | 깃허브 아이디, 바꿀 역할 |
| 입력 (`remove`) | 깃허브 아이디 |
| 출력 | 바뀐 줄, 거절이면 까닭 |
| 거절 | 선생님이 아닌 요청, **마지막 선생님을 내리거나 지우는 요청** |

**사용자 목록 조회는 여기 없다.** 브라우저가 행 수준 보안 아래에서 직접 읽는다(결정 1, PRD 3.8절).

**그 정책이 역할에 따라 갈린다.**

| 누가 | 무엇이 보이나 |
|---|---|
| 학생 | 자기 줄 하나 |
| 선생님 | 전체 |

- 학생에게 전체를 열면 수강생 명단이 그대로 보인다.
- **선생님에게 전체가 보이지 않으면 설정 화면이 서지 않는다.** 역할을 바꿀 대상을 고를 수 없다.
- 정책 안에서 요청한 사람의 역할을 읽어 가른다. **브라우저가 보낸 역할을 쓰지 않는다**(PRD 3.7절).

## 사용자 테이블의 아이디 — 열 둘을 둔다

**키는 깃허브 아이디다. 인증 식별자를 담는 열을 함께 둔다.**

| 열 | 무엇 | 언제 채워지나 |
|---|---|---|
| 깃허브 아이디 | 사람이 넣고 사람이 읽는 키 | 사용자를 더할 때. 첫 선생님은 DB에 직접 |
| 인증 식별자 | 행 수준 보안 정책이 행을 거를 때 쓰는 값 | **그 사람의 첫 로그인 때** |

**깃허브 아이디를 키로 쓰는 까닭** — 첫 선생님은 DB에 직접 넣는데(PRD 3.7절), 그 사람이 아직 로그인한 적이 없어 인증 식별자를 알 수 없다. 깃허브 아이디는 저장소 주소에 이미 들어 있어 수업에서 알기도 쉽다(65번 3절).

**인증 식별자 열이 따로 필요한 까닭** — 행 수준 보안 정책은 요청에 실린 인증 정보로 행을 거른다. 깃허브 아이디는 그 정보 안에 없으므로 **정책이 깃허브 아이디만으로는 "이 줄이 요청한 사람의 줄인가"를 판정할 수 없다.** 열을 하나 더 두고 그것으로 정책을 쓴다.

**두 열을 잇는 것은 첫 로그인이다.** 로그인한 사람의 깃허브 아이디로 줄을 찾아 인증 식별자가 비어 있으면 채운다. 줄이 없으면 만들고 역할을 학생으로 둔다(2단계).

- **인증 식별자가 빈 줄은 정책이 아무에게도 열어 주지 않는다.** 첫 선생님이 로그인하기 전까지 그 줄은 브라우저에서 보이지 않는다. 서버 함수는 비밀 키로 지나가므로 영향받지 않는다(PRD 4.4절).
- **이미 채워진 인증 식별자를 다시 쓰지 않는다.** 값이 갈리면 그 줄의 주인이 바뀐다.

**이메일로 가르지 않는다.** 깃허브는 이메일을 비공개로 둘 수 있어 값이 비거나 `noreply` 주소가 온다(PRD 3.7절).

# 개발 단계

**단계 구분과 이름은 PRD 6장이 정했다.** 각 단계는 완료 기준 두 줄과 검증 셋을 밟는다.

## 검증 셋

단계마다 같은 셋을 밟는다(65번 2절).

1. **완료 기준 대조** — 두 줄이 모두 참인가
2. **배포 후 스모크** — 로컬에서 됐다는 것은 증거가 되지 못한다
3. **거절 확인** — 그 단계에서 새로 생긴 것을 서버가 실제로 막는가

**마지막 단계 뒤에 둘을 더 밟는다.** 아래 "마지막에 하는 둘"에 있다.

**문항 판정은 여기 들어가지 않는다.** 문항이 늘 때마다 도는 것이라 개발 단계와 주기가 다르다(65번 2절).

## 1단계 — 준비와 배포 골격

**끝나면 화면에서** — 1차와 같은 앱이 Vercel 주소에서 돈다.

### 만들거나 고칠 것

| 무엇 | 내용 |
|---|---|
| 저장소 | 개인 계정에 둔다. **조직 소유면 무료 요금제로 연결할 수 없다**(PRD 4.1절 5번) |
| 배포처 프로젝트 | 저장소를 연결한다. 빌드 없이 정적 파일과 `api/`를 올린다(PRD 4장) |
| DB 프로젝트 둘 | 개발용과 수업용(결정 6). **무료 한도가 활성 둘이라 여유가 없다** |
| `db/schema.sql` | 테이블과 정책. 저장소에 남긴다 |
| 배포 환경 변수 | 공개 키, 비밀 키, Anthropic API 키를 Preview와 Production으로 나눠 넣는다(PRD 4.4절, 결정 6) |
| 빌드 건너뛰기 조건 | 배포처 설정에 아래 한 줄 |

```bash
git diff --quiet HEAD^ HEAD -- index.html style.css script.js api/ vercel.json
```

- 종료 코드가 0이면 건너뛰고 1이면 배포한다. **조건을 반대로 두면 아무것도 배포되지 않는다**(65번 8절).
- 소스 넷과 `api/`가 안 바뀌면 배포하지 않는다. 나머지는 문서다.

### 테이블과 정책

이 단계에서 빈 테이블과 정책만 만든다. 열을 채우는 것은 뒤 단계다.

| 테이블 | 언제 쓰나 |
|---|---|
| 사용자 | 2단계 |
| 문항 | 3단계 |
| 응시 기록 | 3단계에 행이 생기고 4단계에 마감된다 |
| 생성 요청 | 5단계 |

**PRD 3.10절이 정한 셋에 생성 요청이 더해져 넷이다.** 판을 담는 테이블을 따로 두지 않는다(결정 10).

- **모든 테이블에 행 수준 보안을 켠다**(PRD 3.8절). 켜지 않은 테이블은 공개 키로 전부 조회된다.
- **첫 선생님 한 줄을 사용자 테이블에 직접 넣는다**(PRD 3.7절, 65번 3절). 학생이 자기 앱을 만들 때는 자기 아이디를 넣는다.

### 완료 기준

- **동작한다** — 1차 앱이 Vercel 프로덕션 주소에서 그대로 돌고, 문서만 고친 커밋은 배포를 만들지 않으며 소스를 고친 커밋은 만든다.
- **거절한다** — 정책 없는 테이블이 공개 키로 조회되지 않고, 비밀 키가 저장소가 아니라 배포 환경 변수에서만 읽힌다.

### 검증

| 무엇 | 어떻게 |
|---|---|
| 완료 기준 대조 | 위 두 줄 |
| 배포 후 스모크 | 프로덕션 주소로 접속해 1차 앱의 네 화면을 지난다 |
| 거절 확인 | 공개 키로 각 테이블을 조회해 빈 결과나 거절이 오는지 본다. 저장소 전체에서 비밀 키 문자열을 찾아 없는지 본다 |

### 체크리스트

- [ ] 문서만 고친 커밋을 하나 올려 배포가 생기지 않는 것을 보았다

## 2단계 — 인증

**끝나면 화면에서** — 로그인해야 게임이 시작된다.

### 로그인 흐름

**라이브러리를 쓰지 않는다**(결정 1).

| 순서 | 무엇 |
|---|---|
| 1 | `api/questions.js`의 `config`를 불러 프로젝트 주소, 공개 키, 깃허브 인증 경로를 받는다(결정 6) |
| 2 | `btn-login-github`를 누르면 그 인증 경로로 보낸다 |
| 3 | 돌아온 주소에서 토큰을 꺼내 `sessionStorage`에 넣고, 주소에서 그 값을 지운다 |
| 4 | 서버 함수와 DB 요청의 헤더에 토큰을 싣는다 |
| 5 | 로그아웃은 `sessionStorage`의 토큰을 지우고 로그인 화면으로 돌아간다 |

**토큰을 `sessionStorage`에 둔다.**

| 어디 | 새로고침 | 탭을 닫으면 |
|---|---|---|
| 변수 | 사라진다 | 사라진다 |
| **`sessionStorage`** | **남는다** | **사라진다** |
| `localStorage` | 남는다 | 남는다 |
| 쿠키 | 남는다 | 설정에 따른다 |

새로고침에 살아남아 실습이 끊기지 않고, 탭을 닫으면 지워져 실습실 공용 컴퓨터에 남지 않는다.

**3번에서 주소의 토큰을 지운다.** 지우지 않으면 주소창에 남고, 새로고침이나 주소 공유로 그대로 흘러 나간다.

### 로그인 만료를 알린다

**갱신을 만들지 않는다.** 토큰 안에 만료 시각이 있으므로 남은 시간은 알 수 있다(PRD 3.7절 "로그인의 수명").

| 무엇 | 값 |
|---|---|
| 배너를 띄우는 때 | 남은 시간 5분 아래 |
| 판 시작 전 안내 | 남은 시간 10분 미만이면 시작을 막고 다시 로그인하도록 안내 |
| 401이 왔을 때 | 로그인 화면으로 보내고 문구를 낸다 |
| 문구 | 결정 4의 문구 표에 있다 |

- **판 도중에 만료되면 그 판을 버린다.** 이어 하기는 PRD 7장이 제외했다. 그래서 판 시작 전 안내가 필요하다.
- **PRD 7장이 제외한 제한 시간과 다르다.** 저것은 문제를 푸는 시간을 재는 것이고 이것은 로그인이 남은 시간을 알리는 것이다. 화면에 시간이 보인다는 점만 같아 헷갈리기 쉬우므로 여기 적어 둔다.

### 만들거나 고칠 것

| 파일 | 무엇 |
|---|---|
| `index.html` | 로그인 화면 마크업. 시작 화면에서 `player-name`과 `name-error`를 뺀다 |
| `style.css` | 로그인 화면 스타일 |
| `script.js` | 로그인, 역할 판정, 화면 가르기, **만료 안내**. 이름 검증 함수를 뺀다 |
| `index.html` | 만료 배너 `session-expiry`를 둔다 |
| DB | 사용자 테이블의 열을 채운다 — 깃허브 아이디, 이름, 역할, **인증 식별자**. 그 열로 행 수준 보안 정책을 쓴다 |

- **역할은 사용자 테이블의 역할 열로 가른다**(PRD 3.7절). 로그인한 사람의 깃허브 아이디로 그 줄을 찾는다.
- **첫 로그인에 인증 식별자를 채운다.** 깃허브 아이디로 줄을 찾아 비어 있으면 채운다(함수 계약의 "사용자 테이블의 아이디").
- 사용자 테이블에 줄이 없는 사람은 **학생으로 본다.** 첫 로그인에 줄을 만들고 역할을 학생으로 둔다.
- 선생님이면 `btn-open-teacher`의 `hidden`을 벗긴다. **버튼을 감추는 것은 안내이지 통제가 아니다.** 통제는 서버 함수가 한다(PRD 3.7절).
- **사용자 테이블 정책이 역할에 따라 갈린다** — 학생은 자기 줄 하나, 선생님은 전체(함수 계약의 `api/users.js`). 이 단계에서 그 정책을 쓴다.

### 완료 기준

- **동작한다** — 깃허브로 로그인하면 시작 화면에 `user-name`이 뜨고 게임을 시작할 수 있으며, 선생님 계정에만 `btn-open-teacher`가 보인다.
- **거절한다** — 로그인하지 않으면 게임 시작이 막히고, **학생 계정으로 사용자 테이블을 조회하면 남의 줄이 보이지 않는다.**

**둘째 줄을 2단계에서 확인할 수 있는 것으로 좁혔다.** 처음에는 "학생 계정으로 선생님 화면을 열어도 그 요청이 거절된다"였는데, 그 요청(`api/authoring.js`, `api/users.js`)과 화면이 5단계에 생겨 2단계에는 확인할 대상이 없었다. **선생님 요청 거절은 5단계 거절 확인에 이미 있다.**

2단계에서 새로 생기는 권한 경계는 인증 식별자 열로 건 정책이므로 성격도 맞는다.

### 검증

| 무엇 | 어떻게 |
|---|---|
| 완료 기준 대조 | 위 두 줄 |
| 배포 후 스모크 | 프리뷰 주소에서 로그인, 게임 한 판, 로그아웃. 새로고침해도 로그인이 살아 있는지 |
| 거절 확인 | 로그인 없이 시작 버튼을 눌러 막히는지. 학생 계정으로 사용자 테이블을 조회해 자기 줄만 오는지 |

### 체크리스트

- [ ] 시작 화면에 이름 입력란이 없다. `grep -n "player-name\|name-error" index.html script.js`가 비어 있다
- [ ] 순위표에 남는 이름이 로그인한 사용자의 이름이다(PRD 3.1절)
- [ ] 사용자 이름을 `textContent`로 넣는다(PRD 3.0절)
- [ ] 화면을 전환한 직후 그 화면의 제목으로 초점을 옮긴다. `login-title`에 `tabindex="-1"`이 있다(PRD 3.0절)
- [ ] 첫 선생님이 처음 로그인한 뒤 그 줄의 인증 식별자가 채워졌다. **채워지기 전에는 그 줄이 브라우저에서 보이지 않는다**
- [ ] 학생 계정에서 `btn-open-teacher`가 `hidden`이다
- [ ] 학생 계정으로 사용자 테이블을 조회하면 자기 줄 하나만 온다. 선생님 계정으로는 전체가 온다
- [ ] 토큰이 `sessionStorage`에 있다. 새로고침하면 로그인이 살아 있고, 탭을 닫았다 열면 로그인 화면이 뜬다
- [ ] 로그인 뒤 주소창에 토큰이 남아 있지 않다
- [ ] 만료가 가까울 때 `session-expiry`가 뜬다. **시각을 앞당겨 확인한다**
- [ ] 남은 시간이 10분 미만이면 판 시작이 막힌다

## 3단계 — 문항 이전

**끝나면 화면에서** — 문제가 서버에서 오고 정답이 브라우저에 없다.

**순서 셋이 이 단계 안에 함께 들어간다**(65번 1절). DB 적재 → 명령어 넷 수정 → `questions.js` 삭제. 그 사이에 문항 관리가 멈추지 않게 하기 위한 순서다.

### 만들거나 고칠 것

| 파일 | 무엇 |
|---|---|
| `api/questions.js` | 새로 만든다(함수 계약) |
| `script.js` | 문항을 서버에서 받는다. `QUESTIONS` 전역과 `validateData()`를 뺀다 |
| `index.html` | `questions.js`를 읽는 `<script>` 태그를 뺀다(PRD 1.4절) |
| `questions.js` | **지운다.** 1차의 파일은 태그 안에 그대로 남는다 |
| `.claude/commands/` 넷 | 대상이 `questions.js`에서 DB로 바뀐다 |
| DB | 60문항을 문항 테이블에 넣는다 |

- **선택지 섞기가 서버로 옮겨 간다**(결정 10). `script.js`에서 섞기와 `answer` 갱신이 빠진다.
- **판을 시작할 때 응시 기록 행을 만든다**(결정 10). 그 행이 섞인 순서를 담는다. 채우고 마감하는 것은 4단계다.
- **데이터 검사가 서버로 옮겨 간다**(PRD 1.5절, 결정 7). 페이지 로드 시점의 검사가 사라진다.

| `quiz-validate` | 읽는 대상이 DB로. 볼 곳을 좁히는 목록도 DB에서 뽑는다 |
| `quiz-stats` | 세는 대상이 DB로 |
| `quiz-daily` | 위 셋을 부르는 것은 그대로 |

### 완료 기준

- **동작한다** — 판을 시작하면 문항 열 개가 서버에서 오고, 저장소에 `questions.js`가 없으며, 명령어 넷이 DB를 보고 돈다.

| 거절 확인 | 네트워크 응답 본문에 정답 열이 없는지. 검사 열셋을 하나씩 깨뜨린 문항을 넣어 거절되는지 |

## 4단계 — 서버 채점과 순위

**끝나면 화면에서** — 점수가 서버에서 나오고 수강생 순위가 함께 보인다.

### 만들거나 고칠 것

| 파일 | 무엇 |
|---|---|
| `api/submit.js` | 새로 만든다(함수 계약) |
| `script.js` | 채점 로직을 뺀다. 답을 고르면 서버에 보내고 응답으로 피드백을 그린다 |
| `script.js` | 순위표를 `api/submit.js`의 `rankings`로 받는다. `localStorage` 코드를 뺀다 |
| `script.js` | **채점 실패 경로**(PRD 4.2절 5번) |
| `index.html` | 시작 화면에 `practice-mode`, 퀴즈 진행 화면에 `btn-answer-retry`를 넣는다. 순위표 화면에서 `btn-clear`를 뺀다 |
| DB | 응시 기록 테이블의 열을 채운다 — 점수, 문항별 응답, 마감 여부 |

- **`btn-clear`를 두지 않는다**(PRD 3.5절). 기록이 서버에 모이므로 학생에게 주면 남의 기록까지 지운다.
- `result-storage-notice`와 `ranking-storage-notice`는 남되 문구가 결정 4의 것으로 바뀐다.
- `ranking-persist-notice`의 문구도 결정 4의 것으로 바뀐다.

### 응시 기록 행의 시작과 마감

행을 만드는 것은 3단계의 `api/questions.js`이고, **이 단계가 그 행을 채우고 마감한다**(결정 10).

| 언제 | 무엇 |
|---|---|
| 판 시작 | 행을 만든다. 마감 여부는 거짓 (3단계) |
| 답을 고를 때마다 | 문항별 응답에 적는다 |
| 판 마감 | 점수를 다시 세어 적고 마감 여부를 참으로 |
| 연습, 그만두기, 채점 재시도 실패 | 행을 지운다 |

**마감되지 않은 행은 순위표와 성적 관리에 뜨지 않는다.** 보지 않으면 진행 중인 판이 0점으로 순위표에 오른다.

### 채점이 실패하면

PRD 4.2절 5번이 정한 것을 화면으로 옮긴다.

- 답을 고른 뒤 응답이 오지 않으면 `btn-answer-retry`를 낸다. `btn-next`는 내지 않는다.
- 재시도해도 실패하면 결정 4의 문구를 내고 **그 판을 버린다.** `abort`를 보내 행을 지우고 시작 화면으로 돌아간다.
- **진행 상황을 남기지 않는다.** 이어 하기는 PRD 7장이 제외했다.

### 완료 기준

- **동작한다** — 답을 고르면 서버가 정오와 해설을 돌려주고, 판을 마치면 서버가 센 점수와 순위 진입 결과가 나오며, 순위표에 다른 수강생의 기록이 함께 보인다.
- **거절한다** — 브라우저에서 응시 기록을 직접 저장하려 하면 막히고, 점수를 고쳐 보내도 서버가 다시 센 값이 이긴다.

### 검증

| 무엇 | 어떻게 |
|---|---|
| 완료 기준 대조 | 위 두 줄 |
| 배포 후 스모크 | 서로 다른 계정 둘로 한 판씩 치고 두 기록이 같은 순위표에 오르는지 |
| 거절 확인 | 공개 키로 응시 기록 테이블에 직접 삽입해 거절되는지. 남의 기록을 직접 조회해 거절되는지. `finish` 요청에 점수를 실어 보내 무시되는지 |

### 체크리스트

- [ ] 공개 키로 응시 기록 테이블에 `insert`를 보내 거절된다(PRD 3.8절)
- [ ] 공개 키로 남의 응시 기록을 조회하면 오지 않는다. **순위표에는 남의 이름이 뜨는데 직접 조회로는 안 온다** — 이 둘이 함께 서는 것이 순위표를 서버 함수로 돌린 까닭이다(PRD 3.8절)
- [ ] `finish` 요청 본문에 점수를 넣어 보내도 결과 화면의 점수가 서버가 센 값이다
- [ ] 남의 응시 기록 식별자로 `answer`를 보내면 거절된다
- [ ] 연습 모드로 친 판이 순위표에 오르지 않고, 행도 남지 않는다
- [ ] "그만두기"로 끝낸 판의 행이 남지 않는다
- [ ] 판을 마치지 않고 탭을 닫으면 그 행이 마감되지 않은 채 남는다. **순위표와 성적 관리에 뜨지 않는지 본다**
- [ ] 순위 인덱스가 삽입한 행의 식별자로 찾아진다. **같은 이름, 같은 점수의 기록이 둘 있을 때 강조가 옳은 줄에 걸리는지를 코드로 확인한다**(PRD 3.4절)
- [ ] 날짜가 로컬 시간대 기준이다. `toISOString()`을 쓰지 않았다(PRD 3.4절)
- [ ] 순위표 응답에 쓰기 가능 여부가 실려 온다. 세 상태를 각각 만들어 표시가 PRD 3.5절의 표와 맞는다
- [ ] **한 판도 치지 않은 계정으로 순위표 화면에 들어가도 가운데 상태가 표시된다**(결정 4)
- [ ] 채점 요청을 막아 `btn-answer-retry`가 뜬다. 그때 `btn-next`는 보이지 않는다
- [ ] 재시도도 막으면 판을 버리고 시작 화면으로 돌아가며 행이 남지 않는다(PRD 4.2절 5번)
- [ ] 답을 고른 뒤 초점이 `feedback`으로 간다. **서버 응답을 기다리는 사이에 초점이 흩어지지 않는지 `focusin` 기록으로 본다**(PRD 3.2절)
- [ ] `feedback`에 `aria-live`가 없다(PRD 3.2절, 4.3절)

## 5단계 — 선생님 화면 셋

**끝나면 화면에서** — 선생님이 화면에서 문항을 늘리고 성적을 보며 역할을 바꾼다.

### 만들거나 고칠 것

| 파일 | 무엇 |
|---|---|
| `api/authoring.js` | 새로 만든다(함수 계약) |
| `api/users.js` | 새로 만든다(함수 계약) |
| `index.html` | 선생님 화면 셋의 마크업 |
| `style.css` | 선생님 화면 셋의 스타일. 막대 차트도 여기서 |
| `script.js` | 선생님 화면 셋의 렌더링과 요청 |
| DB | 생성 요청 테이블의 열을 채운다. 문항 테이블에 요청 식별자를 더한다 |

- **명령어 넷의 규격을 화면이 다시 적지 않는다.** 규격이 이미 명령어 안에 있으므로 화면은 인수를 받는 자리만 만든다(65번 5절).
- **설정 화면이 전체 사용자 목록을 보는 근거는 정책이다.** 사용자 테이블 조회 정책이 선생님에게 전체를 열어 둔다(함수 계약의 `api/users.js`). 정책은 2단계에서 쓰고 이 화면이 그것을 쓴다. **서버 함수가 목록을 내려 주는 것이 아니다.**
- **대시보드에 차트 라이브러리를 쓰지 않는다.** 막대는 요소 너비로, 추세는 인라인 SVG로 그린다(PRD 8.3절).

### 완료 기준

- **동작한다** — 선생님이 화면에서 문항 생성을 요청해 판정 결과를 보고 채택하며, 문항을 고치고 지우고, 수강생 성적과 대시보드 셋을 보고, 사용자의 역할을 바꾼다.
- **거절한다** — 학생 계정의 문항 생성과 역할 변경 요청이 막히고, 채택하지 않은 문항이 **문항 테이블에** 들어가지 않으며, 마지막 선생님을 내리는 요청이 거절된다.

**"문항 테이블에"를 빼고 읽지 않는다.** 채택 전 문항은 생성 요청 테이블에 담긴다(결정 5). 세는 대상은 문항 테이블이다.

### 검증

| 무엇 | 어떻게 |
|---|---|
| 완료 기준 대조 | 위 두 줄 |
| 배포 후 스모크 | 프리뷰에서 하루치 버튼을 한 번 돌려 다섯 문항이 생성, 판정, 표시까지 가는지 |
| 거절 확인 | 학생 계정으로 `api/authoring.js`와 `api/users.js`를 직접 부른다. 채택 전 문항이 **문항 테이블에** 있는지 센다. 선생님을 하나만 남기고 그를 내려 본다 |

### 체크리스트

- [ ] 학생 계정으로 `api/authoring.js`의 `generate`를 부르면 거절된다. **자연어가 그대로 생성 요청으로 들어가므로 이 자리가 실질적인 방벽이다**(65번 5절)
- [ ] 학생 계정으로 `api/users.js`의 `role`을 부르면 거절된다
- [ ] 생성 결과를 화면에 띄운 채로 **문항 테이블**의 행 수를 세면 늘지 않았다. 채택 버튼을 누른 뒤에 는다
- [ ] 같은 시점에 **생성 요청 테이블**에는 그 문항들이 들어 있다. 둘을 함께 세어야 경계가 확인된다(결정 5)
- [ ] 검사에 걸린 문항은 채택 버튼이 없고 위반 항목이 함께 보인다(PRD 3.9절 4번)
- [ ] 판정 호출에 생성 맥락이 들어가지 않는다. 요청 본문을 열어 확인한다(PRD 3.9절, 결정 9)
- [ ] 카테고리 문항이 30개일 때 하루치 버튼이 멈추고 결정 4의 문구를 낸다
- [ ] 카테고리 문항이 10개일 때 삭제가 거절된다(결정 7)
- [ ] 응시 기록이 있는 문항을 고치려 하면 결정 4의 문구가 먼저 나온다
- [ ] 고친 문항이 검사와 판정을 다시 지난다(PRD 3.9절)
- [ ] 선생님이 하나일 때 그를 학생으로 바꾸는 요청과 지우는 요청이 둘 다 거절된다
- [ ] 선생님 계정으로 설정 화면에 들어가면 전체 사용자가 보인다. **정책이 여는 것이지 서버 함수가 내려 주는 것이 아니다**
- [ ] 대시보드 셋에 외부 스크립트가 없다. `grep -n "cdn\|https://" index.html`이 라이브러리를 보이지 않는다
- [ ] 생성 이력이 요청 단위로 보이고, 채택하지 않은 문항도 그 안에 남는다(결정 5)

# 마지막에 하는 둘

5단계를 마친 뒤 둘을 더 밟는다(65번 2절).

## A. 알려진 제약을 하나씩 대조한다

PRD 4.1절의 일곱과 노트 5.3.1의 한계를 하나씩 짚어 **해소되었는지, 그대로인지, 새로 생겼는지**를 적는다.

| PRD 4.1절 | 2차에서 |
|---|---|
| 1. 직접 열면 동작하지 않는다 | 그대로다. 서버 함수가 있어야 한다 |
| 2. Safari의 `beforeunload` | 그대로다 |
| 3. 무료 요금제 일시정지 | **프로젝트 둘 모두에 걸린다**(결정 6) |
| 4. 1차 배포본 여섯 | 그대로 둔다 |
| 5. 조직 저장소 | 1단계에서 확인했다 |
| 6. 배포본이 같은 DB를 쓴다 | **결정 6이 프리뷰와 프로덕션으로 갈랐다** |
| 7. 배포 주소가 30일 뒤 사라질 수 있다 | 65번 8절의 둘로 줄였다. 실제 배포 수를 세어 예외 안에 있는지 본다 |

**노트 5.3.1의 항목은 여기 옮겨 적지 않는다.** 노트가 정본이고, 대조할 때 그것을 연다.

**해소되었다고 적기 전에 확인한다.** PRD 4.1절이 "1차 배포본 여섯에서는 둘 다 그대로 남는다"고 범위를 좁혀 둔 것이 이 자리다.

## B. 전체 스모크

화면 여덟을 전부 지난다(PRD 5장).

| 순서 | 무엇 |
|---|---|
| 1 | 로그아웃 상태에서 시작이 막히는지 |
| 2 | 로그인 → 시작 → 카테고리별 도전 한 판 → 결과 → 순위표 |
| 3 | 로그인 → 전 범위 도전 한 판 → 결과 |
| 4 | 연습 모드로 한 판 → 기록이 안 남는지 |
| 5 | 진행 중 "그만두기" → 기록이 안 남는지 |
| 6 | 선생님 계정 → 문항 관리 → 하루치 한 번 → 채택 |
| 7 | 선생님 계정 → 성적 관리 → 대시보드 셋 → 학생 하나 짚어 들어가기 |

| 9 | 모바일 세로 화면에서 2번과 6번을 다시(PRD 4장 반응형) |

**둘 다 프로덕션 주소에서 한다.** 프리뷰가 아니다.
